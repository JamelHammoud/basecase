# Security

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 0h. Security (mandatory)

The agent reads untrusted pages and files and drives an app that can spawn processes, so treat every input from the renderer, the HTTP bridge, the agent and downloaded assets as hostile. The full checklist, attack surface and accepted risks are in the `security-audit` skill; these rules hold for every change:

- **HTTP bridge:** every `/api/*` middleware is wrapped in `guardBridge` (`electron/bridgeGuard.mjs`: loopback `Host`, same-origin `Origin` and `Sec-Fetch-Site`). Vite plugin middlewares run before Vite's own host check and CORS, so nothing else protects them. A website could otherwise POST `/api/bridge/acp-connect` and run a command.
- **IPC** registers through `trustedIpc` (`electron/appOrigin.mjs`, main frame of the app origin only). Compare origins with `isAppUrl`, never `startsWith`; open only `isExternalWebUrl` links.
- **Ids that become paths** go through `checkedFileId` / `isSafeFileId` (or `safeFileId`) in `electron/backend/constants.mjs`. `library/agent.json` holds the command the app spawns.
- **Outbound fetches the agent controls** use `publicFetch` and `readCapped` (`electron/publicFetch.mjs`): public addresses only, every redirect re-checked, bodies capped. The renderer fetches agent URLs over https only.
- **Hugging Face** (`electron/hub/`, §8h): the token lives only in the main process, sealed with `safeStorage` (`hub-keys.json`, memory only without encryption); the page gets a signed-in flag and the account name. Every Hub URL is built from the fixed origin (`https://huggingface.co`, or `BASECASE_HUB_URL` for tests) and checked to stay on it; repo names and the account name must match the Hub's name rule (letters, digits, `.`, `_`, `-`, no `--` or `..`, at most 96) and file paths are plain segments, all checked before any request. Requests to the Hub refuse redirects. LFS upload addresses on another origin must be https and go through `publicFetch`, and never get the token; only verify calls on the Hub itself carry it. Error text from the Hub has the token cut out. `electron/hub/hub.test.mjs` holds the exploit tests.
- **Agent CLI downloads** (§0i) fetch only `https://registry.npmjs.org/` tarballs named in the build's manifest, refuse redirects, and install only when the sha512 matches the lockfile's `integrity`.
- **CAD files the agent downloads or a person drops** (`electron/cadImport/`) are hostile: fetched by `publicFetch` with a 200 MB cap and parsed only in the CAD kernel's Chromium sandbox (below), never in Node; archives are capped at 600 MB unpacked and their entry names are never used as paths. Library ids go through `checkedFileId`. Links must be https. Page text from a link check is only searched for the part number, never shown to the agent as instructions.
  - The main process reads the downloaded file and sends its bytes as a kernel pool job (`SandboxKernel.convert`, checked by `checkedConvertJob` in `cadImport/convertPolicy.mjs`); the kernel page starts a fresh module Worker (`/convert.js`, built from `cadImport/convertWorker.mjs`) for each file and ends it after, so no file inherits another's state. It runs under the worker CSP (`connect-src 'none'`, `worker-src 'none'`; occt-import-js's embind needs `'unsafe-eval'`), gets the compiled OpenCascade module from the page, and answers with a JSON header, a newline and the GLB (`cadImport/reply.mjs`).
  - A dropped STEP or IGES (`openCadFile.mjs`, IPC `cad:open`) is checked only for its extension before its bytes go to the same pool job with `bodies: true`; the Worker answers with one header entry per body and their packed positions and indices (`bodiesCore.mjs`). `checkedBodies` (`bodiesPolicy.mjs`) refuses the answer unless the byte length matches the counts exactly, every position is finite, every index is in range, colours are `#rrggbb` and names short, and there are at most 1,000 bodies. Nothing is written to disk.
  - The main process trusts nothing in the answer: `checkedConversion` keeps only the size, origin, triangle count, holes (at most 500) and member names it knows, refuses anything malformed or a GLB without its magic, and is the only code that writes `mesh.glb`. A hung parse hits the 150 s limit, and a file that eats memory hits the pool's 4 GB limit; either kills the window, answers with the converter's own error and the next file gets a fresh one.
  - Converter and kernel jobs share the pool's windows. A file that broke out of its Worker would reach only what agent code in the kernel already can: the kernel page's four host calls.
  - Without the sandbox (the Vite middleware, tools) `import_maker_cad` refuses before downloading anything; nothing falls back to Node. `cadImport/nodeHost/` runs the same Worker in a Node `worker_threads` thread for unit tests and the gate's canary only, and isn't packaged (nor is `occt-import-js` in `node_modules`).
  - `e2e/app/cadImportSandbox.app.test.ts` runs the packaged app's converter self-test (`BASECASE_CADIMPORT_SELFTEST=<spec.json>`, `cadImport/selfTest.mjs`): fixed probes in the converter's Worker (`cadImport/probes.mjs`, no eval channel) try to read and write files under home, fetch, import, open sockets, spawn processes and read the environment, against a local server that must see nothing; a parse that never returns and one that eats memory must be stopped and the next file convert; a truncated STEP must fail to open while a two-body one opens. `verify/fixtures/cadimport/` holds a STEP, a zip of it and an STL with the bytes they converted to before the move, and the conversions must match, plus `two-bodies-inch.step` (two named, coloured bodies drawn in inches) for the bodies mode. With `BASECASE_CADIMPORT_UNSANDBOXED=1` the same self-test runs on the Node host, and the canary must catch the probes getting through (gate `s0-cadimport-sandbox`).
- **The CAD kernel** (agent-written OpenSCAD, and replicad run through `new Function`) runs only in a Chromium sandbox: a module Worker in a hidden `BrowserWindow` (`electron/cad-kernel/sandbox/`) with `sandbox: true`, no Node, context isolation, its own in-memory session (`basecase-kernel-sandbox`) and its own scheme (`basecase-kernel://kernel`).
  - The session cancels every request that isn't to that scheme (`webRequest`), denies every permission, download and device, and the protocol serves only `dist/kernel/` (bundle files by extension, no traversal, `bundleFile`) plus `/library.json`, BOSL2 and the robotics library read by the main process from `vendor/`.
  - CSP is default-deny: the page gets `'self'` scripts, `'wasm-unsafe-eval'` and `connect-src 'self'`; the worker, where agent code runs, gets `'unsafe-eval'` and `'wasm-unsafe-eval'` with `connect-src 'none'` and `worker-src 'none'`. The worker fetches nothing: the page compiles the WASM modules and hands them over with the libraries. Navigation, new windows and webviews are refused.
  - A Worker that ran replicad code is replaced before the next job, so no job inherits another's globals. Results come back as JSON bytes the main process never parses, matched to the job id, at most 64 MB.
  - The page talks to the main process only through its preload's four calls, on its own `webContents.ipc` behind `trustedIpc(…, KERNEL_ORIGIN)`; the app's IPC refuses it, and it refuses the app.
  - The MCP server (a separate Node process) never compiles: `cad-kernel/client.mjs` sends `kernel_render` / `kernel_audit` / `kernel_warm` over the token bridge, which is behind `guardBridge` too.
  - A sandbox that can't start answers every job with an error; nothing in the app falls back to Node. The Node host (`cad-kernel/nodeHost/`) is for tests, the bench and `tools/` only: the Vite middleware uses it only with `BASECASE_NODE_KERNEL=1`, and the packaged app doesn't ship it (`package.json` `build.files`).
  - `e2e/app/kernelSandbox.app.test.ts` runs agent-code probes (files, fetch, XHR, WebSocket, EventSource, beacons, `import()` from `file:` and `http:`, `process`, `require`, service workers, windows, other origins, the bridge) in the worker and the page against a local server that must see nothing; the canary runs the same probes on the Node host and must catch them.
- **Generated HTML** escapes every value (coerce numbers); the guide viewer strips scripts, handlers, links and non-image URLs. No `dangerouslySetInnerHTML`.
- **The robot daemon** (`electron/robot/`, §8k) is spawned only from the bundled `<resources>/hw/robot-daemon` (or `hw/dist` from source; `BASECASE_ROBOT_DAEMON` overrides it for tests), with no shell and a fixed argv that always has `--emulated` and never `--port`. `robot:connect` takes exactly the four spec keys of a plain object (`checkedRobotSpec`): a port, `emulated` not `true`, an extra or inherited key, an id outside 1–253 or a string smuggling a flag is refused before anything starts. `robot:command` rebuilds each documented command from its known fields (`checkedCommand`) and drops everything else, so the page can't write registers. Real serial isn't in the binary at all; `verify/hw/motorLock.mjs` checks the staged file. The exploit inputs are in `security.test.mjs` (“robot daemon”).
- **No `shell: true`**, no string `exec` with interpolated input, no TLS verification off outside the Bambu LAN connector.
- Every security fix gets a test that feeds it the exploit input (`electron/security.test.mjs`).
