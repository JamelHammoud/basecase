# Robot runtime

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8k. Robot runtime

The daemon that owns motor writes, the servo emulators, the emulated Unitree G1, the emulated ros2_control robot and the fault tests, in `hw/` (a Cargo workspace). Nothing here has moved a real motor. Everything is proven against emulated servos, an emulated G1 and an emulated ros2_control robot, which are models, not hardware.

- **One write handle.** Only the safety layer can write to a motor.
- **Motors stay locked.** Real serial transport and the real network are compiled out of default builds until the Stage 8 session (§0k), because this code has never moved a motor.
- **`hw/emu/ledger.yaml` records where each emulated behaviour came from:** datasheet, client-derived, community or assumed.

### Motor lock

- Default builds can't open a serial port. `robot-daemon --port <path>` exits with "Real motors are locked in this build" unless it was built with the `unlock-real-motors` feature, which is the only path to `transport-real`.
- The daemon never opens a device path itself. Its only default transport is the in-process emulator (`--emulated`).
- Default builds open no network interface either. `robot-daemon --family unitree-g1 --interface <name>` and `robot-daemon --family ros2 … --interface <name>` exit with the same words; only `--emulated` works, and it binds a pair of UDP sockets to 127.0.0.1 and nothing else.
- The gate fails if `serialport` or `rustdds` appears in `cargo tree -e normal`, if `serialport::` appears in any `.rs` file outside `transport-real`, if `rustdds::`, `::bind(`, `0.0.0.0` or `UNSPECIFIED` appears outside `transport-real` and the emulators' loopback module (`servo-emu/src/loopback.rs`), or if that module binds anything but `LOOPBACK`. `verify/hw/motorLock.mjs` asks the built binary for a port, a G1 on an interface and a ROS 2 robot on an interface, and checks it carries neither `serialport` nor `rustdds`. Turning the feature on is a Stage 8 decision, made by a maintainer with a power cut in reach.

### Control interface

The app spawns `robot-daemon --family feetech|dynamixel --ids 1,2,3 --emulated [--factory] [--units <file>] [--latency-ms 16] [--class arm|legged] [--artefacts <dir>]`, or `robot-daemon --family unitree-g1 --emulated [--latency-ms 16] [--artefacts <dir>]` (no ids or class: the G1 has its own 29 motors), or `robot-daemon --family ros2 --controller forward_position|joint_trajectory|diff_drive --topic <topic> --joints a,b,c --emulated [--latency-ms 16] [--artefacts <dir>]` (ROS 2, below), and talks JSON lines over stdin and stdout. There's no network port. The artefacts folder holds `calibration.json` and `policy.onnx`; the app writes both (The daemon in the app, below). Every `enter` and `recheck` reads them again, so a policy written after the daemon started counts. Only builds with the `onnx` feature run the policy, loaded once at start; the app's build doesn't, so on Rehearse and up the robot follows the app's intents. Its observation is each joint's position and velocity, not the 12 + 3n terms a trained policy reads (§8d), so the two must meet before an `onnx` build can run one.

In, one object per line:

| `cmd` | Fields | Effect |
|---|---|---|
| `enter` | `mode`: `look`, `set_up`, `test`, `rehearse`, `first_run`, `policy`, `longer_runs` | Climb one rung, or drop to Look. The daemon checks the artefacts itself; the UI can't skip a rung |
| `intent` | `joints`: radians, one per calibrated joint; `null` becomes not-a-number and stops the robot | Latest wins. Also counts as a heartbeat |
| `heartbeat` | | Must arrive at least every 100 ms while motors run |
| `stop` | | Arm: hold. Legged: walk to the stand pose, then hold |
| `fall` | | Lower torque to 10% and hold |
| `release` | | Switch every motor off and return to Look. The only write a stopped robot accepts |
| `clear_fault` | | Only in Look |
| `recheck` | | Re-read the artefacts now |
| `assign_id` | `id`: a servo id in `--ids`; `model`: the model it must report | Number the one new servo on the bus (Servo IDs, below). Only in Set up, motors off |
| `plug_in` | | `--factory` only: put the next new servo on the emulated bus |

Out: `{"event":"hello",...}` first (below), then `{"event":"status",...}` every 100 ms (mode, run state, sealed, fault latched, and per joint id, position, temperature, volts, torque, reply), plus `fault` (with `code`, a plain `message`, and `id` when the fault is about one motor: overheat, servo protection, stall and wrong direction, `Fault::motor_id`), `mode`, `stopped`, `completed`, `refused` and `assigned` (`id`) events. When stdin closes, the robot stops within 100 ms and the daemon exits once nothing moves. If the daemon itself dies, show `daemon_lost_message`: Dynamixel servos stop on their bus watchdog within 100 ms; Feetech servos have none and hold their last goal.

### Runtime tiers and intent slots

- The loop runs every 20 ms. It reads each slot once a tick and never waits on a client. A slot is a seqlock of atomics (`intent.rs`): a writer that stalls mid-write only makes the reader skip that tick.
- A coordinator gets an `IntentWriter`, which can only publish intents and heartbeats. Policy actions use their own slot from `First run` up; Test and Rehearse read the coordinator slot.
- No new intent for 100 ms stops the robot (`intent_stale` or `policy_stale`), and so does no heartbeat for 100 ms (`client_lost`).
- The policy runs on its own thread. A hung or slow policy can't stretch a tick, and a policy that outputs a value that isn't a number stops the robot.

### Safety layer

- `safety::ReadBus` can only ping and read. Write encoding (`safety/encode.rs`) and `ReadBus::send` are private to the safety module. A `SafetyLayer` needs an `ArmGrant`, which only the ladder issues. `compile_fail.md` holds doctests that fail to compile if any of this leaks.
- Every write is a broadcast sync write, so it never gets a reply that could be mistaken for telemetry.
- Goals are integer counts. `guard::next_goal` clamps to the calibrated range, moves at most one step per tick (`min(0.02 rad, speed cap × 20 ms)`), and won't lead the measured position by more than 0.25 rad. Not-a-number never reaches a goal.
- **Soft start:** read positions, write the torque limit at 5%, the goal at the present position, the speed cap, and the Dynamixel bus watchdog (100 ms); then enable torque and ramp it over 1 s. A joint outside its calibrated range refuses to start.
- **Stale replies:** each tick's telemetry read asks for a length that cycles through four values, so a late reply to an earlier request is rejected and counted as late, never used as present. Without this, 40 ms of latency fed 40 ms-old positions to the controller.
- **Seal:** after a stop finishes, the layer is sealed and every write returns `Sealed`. Leaving a sealed layer means dropping it (`release` or Look), and climbing again builds a new one.
- **Hold only what's powered.** Some Feetech firmware switches torque on when a goal is written (the emulator models this), so a hold never writes a goal to a motor that reports torque off.

### Caps (hard-coded in `caps.rs`)

| | Test, Rehearse, First run | Policy | Longer runs |
|---|---|---|---|
| Torque | 30% | 60% | 60% |
| Speed | 0.5 rad/s | 2 rad/s | 2 rad/s |
| Step per tick | 0.02 rad | 0.05 rad | 0.05 rad |
| Run length | 30 s | 5 min | none |

All tiers stop a motor at 50 °C, keep the supply inside 6.0 to 8.4 V (Feetech) or 3.7 to 6.0 V (Dynamixel), and stop on a 100 ms watchdog.

### Mode ladder

Look (read-only bus), Set up (servos checked: each that answers has the right model and no ID is shared, and servos still missing are allowed so they can be numbered; motors off), Test (needs calibration and known firmware, which is read only once every servo answers, so from Set up the daemon recounts the bus and refuses Test until each id answers; earns `tested` after 5 s with every joint moved), Rehearse (needs a policy; motors off, intents run through the guard without writing; earns `rehearsed` after 10 s), First run, Policy, Longer runs.

- Each `enter` re-reads the calibration and policy files, hashes them with the servos' firmware versions, and checks the target's requirements. Evidence is earned only by finishing a stage; it can't be set.
- A calibration, policy or firmware change clears the evidence it invalidates, drops anything above First run back to First run, and holds.
- A fault latches. Nothing climbs until the robot is back in Look and `clear_fault` is sent.
- `hw/spec/ladder.tla` is the TLA+ spec. TLC isn't installed here, so `tests/ladder_model.rs` reads the spec's `Requires`, `Clears`, `Earns`, `Observed` and `Earned` tables, checks the Rust table matches, and walks every reachable state (about 1,300 states and 46,000 transitions) checking the spec's invariants. That search found a real bug: evidence could once be set directly.

### Faults and stops

| Fault | Stop |
|---|---|
| No reply, garbled replies, wrong ID, late replies, duplicate ID, adapter unplugged | Seal at once: no more writes on an unreliable bus |
| Overheat, stall, wrong direction, servo overload flag | Switch that motor off (confirmed by reading it back, up to 5 tries), hold the rest |
| Supply voltage, servo restarted, bus watchdog tripped, joint out of range | Switch every motor off |
| Lost app, stale or not-a-number intents or policy | Arm holds; legged robot stands still |
| Reported fall | Torque down to 10%, hold |
| ROS 2: any of the above that applies, `/joint_states` lost or damaged for 60 ms | Publish a hold at the last measured positions (a base: zero twist) at once, then seal (ROS 2, below) |
| G1: any of the above that applies, lost or damaged lowstate, a motor error | Ramp the arm_sdk weight to 0 (at most 80 ms), then seal (Unitree G1, below) |

Each fault has a beginner-readable message in `fault.rs`. The fourteen gate tests (`fault_*` in `crates/robot-daemon/tests/faults_*.rs`) check the safe state, its time limit, no writes after it, and the message. Comm faults seal in 58 ms (three ticks), and a lost app or policy in about 100 ms.

Known limits: a calibration with the wrong sign moves the joint the wrong way while its encoder agrees, so only a person or a camera can catch it (Stage 8 step 4). Two servos sharing an ID and sitting at exactly the same position answer identically and go unnoticed until they differ. Gravity-loaded joints that sag during the 5% soft start trip `wrong_direction`.

### Unitree G1

The G1 talks DDS over Ethernet through unitree_sdk2. The daemon drives its arms and waist through `rt/arm_sdk`, which the G1 blends with its own locomotion controller by a weight from 0 to 1, so the robot keeps balancing. Handing the weight back to 0 is the G1's stop.

- **Messages** (`servo-wire/src/unitree/`): `LowState` from `rt/lowstate` and `LowCmd` on `rt/arm_sdk`, in unitree_hg's layout as CDR (little endian, 4-byte encapsulation header). There are 35 motor slots with the 29 joints first in unitree_sdk2's order (legs 0–11, waist 12–14, left arm 15–21, right arm 22–28); slot 29's `q` is the arm_sdk weight. Each message carries unitree's `crc32_core` over the C struct image (padding as zeros, every word but the last), and a test pins it to that function compiled from C (1004 and 2092 bytes). A `LowState` whose CRC doesn't match is refused and counted.
- **Ids:** a daemon joint id is the motor index + 1, so 1–29, and only ids 13–29 (waist and arms) can be written. Status lists all 29 with positions in the servo counts convention (`2048 + rad × 4096 / 2π`), plus `weight`.
- **Transport:** `TopicTransport` (`servo-wire/src/topics.rs`) publishes and receives whole CDR samples. Default builds have one kind: the emulated G1 on a thread in the daemon's process, reached through two UDP sockets on 127.0.0.1 (`LoopbackLink`, one datagram per sample, a topic byte first). That isn't RTPS. The real network is `transport_real::DdsTransport` on rustdds, built only with `unlock-real-motors` (`--interface en0`). rustdds is pure Rust, so it builds on Mac and Windows with no C toolchain, and it speaks RTPS, which CycloneDDS matches by topic and type name (rustdds sends XCDR1 and no XTypes type information). It binds its unicast sockets to the wildcard address even when told which interface to use, which is why it can't be in a default build. Its writers are reliable, keep last 1; its readers are best-effort, so they match either kind of writer. Nothing in it has met a real G1 or CycloneDDS.
- **Safety layer:** `safety::ArmSdkLayer` is the G1's one write handle. Like `SafetyLayer` it needs an `ArmGrant` from the ladder, and `G1Bus` (the read side: lowstate, and the loco service's GetFsmId) can't publish (`compile_fail.md`). Every arm command goes through the same guard (`next_goal`): the calibrated range intersected with the G1's URDF limits (`g1.rs`), one step per tick at the caps' speed, and no more than 0.25 rad ahead of the measured joint. Gains are kp 60 and kd 1.5 with no feed-forward, as in unitree_sdk2's arm example. The encoder only fills writable motors, so leg slots and slots past 29 are never written. The weight rises 0.02 per tick (the 1 s soft start) and falls 0.25 per tick, so it reaches 0 at most 80 ms after a stop begins; then the layer seals. Dropping a layer (`release`) publishes weight 0 only when that is one tick's fall or less, and `enter` is refused (“Go back to Look first.”) while the arms are held (soft start, running or handing back), so a new layer never replaces a weighted one in a single message.
- **Stops:** Stop, Fall, a stale intent, a lost app, an intent that isn't a number, a joint out of range, a motor error, and lowstate that's lost or damaged for 60 ms all hand the arms back: the weight ramps to 0, the layer seals and the daemon says so, in words that say the arms went back to the G1's own controller (`Fault::g1_message`). The torque cap and voltage window don't apply; the G1's own PD and limits set its torque.
- **Ladder:** Look reads lowstate and publishes nothing. Set up waits up to 60 ms for fresh lowstate, that all 29 motors answer (mode 1, no motorstate error), and that the loco service's GetFsmId (api 7001 on `rt/api/loco/request`) answers 200, its locomotion mode; no answer within 50 ms is `loco_silent`, a wrong mode `not_balancing`. It records the robot type and version as the firmware. Test needs `calibration.json` listing ids 13–29 exactly, streams arm intents, earns `tested` after 5 s with every joint moved, and runs until stopped. Rehearse and the policy rungs above it are refused for the G1.
- **Emulator** (`servo-emu/src/g1/`): publishes lowstate every 2 ms. Each joint is a PD-driven inertia with friction and torque limits, stepped at 1 kHz, following the weighted blend of arm_sdk and its own standing pose; hidden per-unit inertia, friction and gain come from the seed. `InProcessG1` (virtual clock, latency each way, a sample filter) carries the tests and `serve_loopback` the binary. Faults: `BadCrc`, `Silent`, `MotorDown`, `NotBalancing`. Every behaviour has a `unitree-g1` entry in the ledger.
- **Tests:** `tests/g1.rs` (the round trip, the weight ramp both ways, `enter` refused while the arms are held, a stale intent released within 100 ms, a bad CRC refused, legs never written, policy rungs refused, Set up's checks including a silent loco service, Look and Set up never publishing), `tests/faults_g1.rs` (`fault_g1_lowstate_lost` and `fault_g1_app_lost` in the gate's fault matrix, and a motor error), `tests/binary_g1.rs` (the release binary over JSON lines and the loopback sockets, and `--interface` refused), and `tests/no_unsafe_write_g1.rs`, a 128-case proptest whose checker decodes every `LowCmd` and fails on a leg or spare slot written, a goal outside calibration and the URDF limits, a jump larger than one step other than a hold at the measured position, a weight rising or falling faster than the ramp, changed gains, or anything published after the layer sealed. Its canaries check that it sees real motion and catches a planted jump and a planted weight drop.

### ROS 2

Most robots people already own run ROS 2 through `ros2_control`: UR and Franka arms, TurtleBot bases, SO-101 drivers. The `ros2` family drives any of them the same way: it reads `sensor_msgs/JointState` from `/joint_states` and writes one controller's topic. Only an emulated one connects in this build.

- **Messages** (`servo-wire/src/ros2/`): `JointState`, `std_msgs/Float64MultiArray`, `trajectory_msgs/JointTrajectory` and `geometry_msgs/Twist` in CDR (XCDR1, little endian), as rmw lays them out; golden byte arrays pin each. A ROS topic `/a/b` is DDS topic `rt/a/b`. Decoding checks every length against the bytes left before allocating: at most 64 names or values, 256 bytes a string, 64 trajectory points. A `JointState` with mismatched counts, a duplicate name or a position that isn't a number doesn't decode.
- **Spec:** a controller kind and its topic, and the joints in the scene's order (ids 1…n). The topic follows ROS 2 name rules (absolute, one to four segments of `[A-Za-z_][A-Za-z0-9_]*`, no `__`, at most 128 characters) and must end in its kind's fixed segment: `commands` (`forward_position`), `joint_trajectory` (`joint_trajectory`), `cmd_vel` or `cmd_vel_unstamped` (`diff_drive`). Joint names are 1 to 64 of `[A-Za-z0-9_]`, not starting with a digit, 1 to 32 distinct, exactly two (left wheel, right wheel) for `diff_drive`. `checked_topic` and `checked_joints` (`names.rs`) refuse anything else before a socket opens, and the app checks the same rules first (`electron/robot/ros2.mjs`).
- **Joint map:** `map_joints` (`ros2/joint_map.rs`, pure) matches the spec's names to `JointState.name`, so a robot that publishes in another order works. Status reads each joint by name; one missing from the newest fresh state replies `missing`.
- **Transport:** the G1's seam. `Endpoints::ros2` reads `rt/joint_states` and writes the controller topic; the emulated robot runs behind the shared loopback sockets (`serve_ros2_loopback`), and `DdsTransport` takes the same endpoints in an unlocked build. Nothing in it has met a real ros2_control robot or a ROS 2 DDS.
- **Safety layer:** `safety::Ros2Layer` is the one write handle and needs an `ArmGrant`; `Ros2Bus` reads and can't publish (`compile_fail.md`). Arm goals go through `next_goal` like every servo: the calibrated range, one step per tick at the caps' speed, at most 0.25 rad ahead of the measured joint. `forward_position` publishes the goals as a `Float64MultiArray` in the spec's order, so the controller's `joints` must list them in that order; `joint_trajectory` publishes one point at the goals, 20 ms from start, with `joint_names`. `diff_drive` intents are `[m/s, rad/s]`, capped at 0.2 m/s and 1.0 rad/s in Test (0.5 and 2.0 from Policy), changing at most 0.01 m/s and 0.04 rad/s a tick.
- **Stops:** ros2_control controllers hold their last command, so the daemon's stop is a hold: Stop, Fall, a stale intent, a lost app, an intent that isn't a number, a joint out of range, and `/joint_states` lost or damaged for 60 ms publish the last measured positions (each within its range, else its last goal) or a zero twist at once, then the layer seals and the daemon says the robot is holding still (`Fault::ros2_message`). Torque and voltage caps don't apply; the robot's own controller sets its torque.
- **Ladder:** Look reads `/joint_states` and publishes nothing. Set up waits up to 100 ms for a fresh `JointState` and refuses (`joints_unmatched`) if the robot leaves out a scene joint or publishes one the scene lacks, naming up to three of each in one sentence; it records the published names as the firmware. Test needs `calibration.json` listing ids 1…n, soft-starts with one hold at the measured pose, streams intents, earns `tested` after 5 s with every joint (or both wheels) moved, and runs until stopped. Rehearse and the policy rungs are refused until the app can send a policy (issue #286).
- **Emulator** (`servo-emu/src/ros2/`): `Ros2Emulator` takes `Ros2Options` (joints in controller order, a `ControllerKind`, the controller's topic, a seed, a fault) and refuses joints and topics the name rules refuse. It publishes `sensor_msgs/JointState` (name, position, velocity, effort) every 10 ms, its joints in a seeded permutation of the controller order. `forward_position` and `joint_trajectory` drive an arm: one PD-driven joint each (kp 50, kd 3, 10 Nm), stepped at 1 kHz, starting within ±0.2 rad, with hidden per-unit inertia, friction and gain from the seed. `forward_position` holds the last `Float64MultiArray` of the right length; `joint_trajectory` matches `joint_names` to its joints, refuses a message naming an unknown joint or leaving one out, interpolates linearly from the current setpoint over each point's `time_from_start` and holds the last point. `diff_drive` takes `Twist` (linear x, angular z) with acceleration limits of 1 m/s² and 4 rad/s², turns its two wheels (left, then right) at `(v ∓ ω·0.160/2)/0.033` rad/s times a hidden per-wheel gain within 10%, and zeroes the command 0.5 s after the last one. Messages it can't decode are ignored and counted (`Ros2Counters`). Faults: `Silent`, `MissingJoint`, `ExtraJoint`, `Malformed` (a NaN position). `in_process_ros2` (virtual clock) carries the tests and `serve_ros2_loopback` runs it behind the loopback sockets. Every behaviour has a `ros2-control` entry in the ledger.
- **Tests:** `tests/ros2.rs` (a 6-joint arm on a forward position controller and on a joint trajectory controller, a diff-drive base inside its caps, a robot publishing in another order, Set up naming a missing and an extra joint, a stale app held within 100 ms then nothing more, hostile `JointState`s with a NaN or 10,000 entries dropped and counted, Look and Set up never publishing, Stop holding at the measured position, policy rungs refused), `tests/faults_ros2.rs` (`fault_ros2_joint_states_lost` and `fault_ros2_app_lost` in the gate's fault matrix), `tests/binary_ros2.rs` (the release binary over JSON lines and loopback, `--interface` refused, crafted topics and joint names refused before hello) and `tests/no_unsafe_write_ros2.rs`, a 128-case proptest over both arm controllers and the base whose checker decodes every command and fails on a goal outside calibration, a jump larger than one step other than a hold at the measured position, a twist over the cap or ramp, a wrong-length or unnamed command, or anything after the seal; its canaries check it sees real motion and catches a planted jump and an over-cap twist.

### Emulator

- `servo-emu --family feetech|dynamixel --ids 1,2,3 --pty [--seed N] [--fault bad-checksum|wrong-model|silent|wrong-id|truncated]` prints `{"pty":"/dev/ttysNNN"}` and serves until killed or its parent exits. The PTY is put in raw mode before the path is printed.
- Windows has no PTY: the PTY module is behind `cfg(unix)` and the binary says so. The Windows path is the in-process transport with 16 ms of injected latency (`InProcessBus`, `WINDOWS_LATENCY_US`), which the fault and end-to-end tests cover.
- **macOS PTYs reject 1 Mbaud.** macOS has no `B1000000`, so pyserial sets custom rates with the `IOSSIOSPEED` ioctl, which only real serial drivers accept, so `setBaudRate(1000000)` fails on a PTY. On macOS the gate runs `verify/hw/conformance.py` through `verify/hw/pty_baud.py`, which turns only that ioctl into a no-op on PTYs and leaves the SDKs untouched. On Linux, PTYs accept it and the gate runs the script directly; `sh hw/emu/linux-gate.sh` runs Gatekeeper's `s5-emu-daemon` in a Linux container (Docker), with Linux build output kept in a volume so it never mixes with `hw/target`.
- **Build output and `npm run check`:** Prettier reads only the root `.gitignore`, so `hw/target/` (which the gate builds) needs `hw/target` in the root `.prettierignore`, or `npm run check` fails on cargo's fingerprint JSON.
- **Factory bus:** `--factory` (with `--emulated`) starts the bus empty, the bag of new servos a first robot arrives as. Each `plug_in` adds one new servo at the factory ID 1 (`ServoBus::plug_in_new_servo`, through `add_servo`), up to one per id in `--ids`; another answers “Every new servo is already plugged in.” as a `refused` line.
- **Part models:** `--units <file>` (with `--emulated`, Feetech or Dynamixel only) makes each servo stand in for the catalog part on its joint. The file is a JSON array with one entry per `--ids` entry: `null` keeps the protocol's own unit (STS3215 C001 on Feetech, XL330 on Dynamixel), and an object gives the part's BAM M6 fit (`ServoUnit` in `robot-daemon/src/units.rs`: `volts`, `kt`, `resistance`, `armature`, `friction` with its eleven terms, `firmwareKp`, `errorGain`, `errorGainRatio`, `maxDuty`, `maxVelocity`, `delayS`). A wrong count, an unknown or missing key, friction below 0, any other number not above 0, volts over 60 or anything over 10⁴ stops the daemon before its hello (“The servo models file must give one entry per servo ID.”, “The model for servo 3 has a number out of range.”). The hidden per-unit spread (`UnitParams::from_seed`) is drawn around the part's fit with the same seed rule, so a seed repeats exactly; with no `--units`, or all `null`, every unit is what it was without it.
  - **P gain:** the firmware's P-gain register keeps the protocol's factory value (32 on Feetech, 400 on Dynamixel), so a part's error gain becomes `firmwareKp × errorGain ÷ that value`, which matches the part's model at factory settings.
  - **Supply:** the bus keeps one supply at the protocol's volts (7.4 or 5.0) and its sag; a part's motor is driven at the sagged supply times `volts ÷ the protocol's volts` (`UnitParams::supply_scale`), so an XL430 rated at 11.1 V runs at 11.1 V. Present voltage, the firmware's voltage limits and the daemon's voltage window all read the bus's own supply.
  - **Factory bus:** a servo takes the part of the id it holds (`ServoBus::with_parts`, `factory_with_parts`). A new servo starts as ID 1's part and becomes the part of the id it's given (`refit_renumbered`, after every instruction), so the order of the Set Up walk doesn't matter.
- **Broadcast ping** replies from servos that share an ID collide like addressed replies (bytes AND together), so identical replies read as one servo, as on a real half-duplex bus.
- **Ledger:** `datasheet` is the maker's manual, `client-derived` is read from client library source (scservo_sdk, DynamixelSDK, rustypot, LeRobot), `community` is published third-party measurement (BAM), and `assumed` was chosen here and is unchecked. Stage 8 step 2 dumps real registers and resolves every `assumed` entry. A new emulated behaviour gets a ledger entry in the same change.

### Proof

- `cargo test --release --manifest-path hw/Cargo.toml` runs unit tests, the emulator firmware tests, the fault matrix, the binary end-to-end tests, the ladder model, `no_unsafe_write`, the G1's tests (Unitree G1, above) and the ROS 2 robot's (ROS 2, above). CI doesn't run it; the gate does. That last one is a 256-case proptest whose checker decodes every frame on the wire and fails on a goal outside calibration, a jump larger than one step (other than a hold at the measured position), a torque or speed limit above the cap, torque switched on without a soft start, an ID written to a powered servo or outside the robot, or any write after a seal. Its steps include `assign_id`, and a separate case numbers three factory servos and then drives them. It carries two canaries: the checker must see real motion and must catch a planted jump.
- Loom: `RUSTFLAGS="--cfg loom" cargo test --release --manifest-path hw/Cargo.toml -p robot-daemon --test loom_intent --target-dir hw/target/loom`.
- Kani (`cargo install --locked kani-verifier && cargo kani setup`): `cargo kani --manifest-path hw/Cargo.toml -p servo-wire` proves both frame scanners never panic and never consume past their input, and that a single flipped byte never passes the Feetech checksum. `-p robot-daemon` proves the goal guard stays in bounds and moves at most one step, malformed rules never move a goal, torque requests never exceed their cap, and holds stay in bounds.
- Mutation testing: `cargo mutants --dir hw -p robot-daemon -f crates/robot-daemon/src/safety/guard.rs` (repeat `-f` for `layer.rs`, `encode.rs` and `bus.rs`). Every viable mutant in the safety module must be caught; `hw/.cargo/mutants.toml` skips the `cfg(kani)` proofs, which `cargo test` never compiles.
- Tests that mix the virtual clock with real threads (the policy worker) wait for the worker to act, within limits that hold under heavy load, and never assert a tight wall-clock bound. The end-to-end binary test accepts `intent_stale` as well as `client_lost`: a test thread starved past 100 ms stops the robot before the app closes, which is the same safe stop.
- The daemon's write encoder is checked against bytes captured from scservo_sdk and DynamixelSDK. The Python DynamixelSDK 4.1.0 never byte-stuffs what it sends (see the ledger).

### Servo IDs

A first robot's servos all answer at the factory ID 1. `assign_id` (`control/assign.rs`) writes one layout id onto the one new servo on the bus:

- Only in Set up with run Idle, and only for an id in `--ids`. The write goes through the safety layer (`SafetyLayer::renumber`), which refuses once that layer has switched torque on: Feetech clears Lock (55), writes ID (5) and sets Lock again on the new id; Dynamixel writes ID (7), which its firmware accepts only with torque off. Each is a broadcast sync write, like every other write.
- A broadcast ping (`ReadBus::census`, a 780 ms window, since the emulator spaces replies 3 ms per id) lists who answers. A servo is new when it's at ID 1 or at an id outside the robot. Then: the target id held by another servo refuses (“Another servo already has ID 2…”); none new or more than one refuse; the new servo must report `model`, pass the duplicate probe (two new servos at ID 1 answer a ping as one, but not a position read) and have torque off. The id is read back before `assigned` goes out; a servo that didn't keep it refuses.
- The census blocks the loop for under a second. That's safe because Set up never powers a motor and no watchdog runs below Test.
- Because new servos come at ID 1, which is also the first joint's id, the walk numbers from the highest id down and ID 1 last: every numbered servo stays plugged in, never collides with the next new one, and the finished bus holds every id, so Set up → Test climbs at once (LeRobot's motor setup walks in reverse for the same reason).
- Tests: `tests/assign_id.rs` (writes and reads back on one factory servo and survives a power cycle; refuses two new servos, none, outside Set up, a powered servo, a taken id; Test waits for every id) and `fault_numbering_interrupted` (adapter unplugged, or a second new servo appearing mid-walk: refused, nothing written).

### The daemon in the app (interface)

Stage 5b is judged by `s5b-daemon-app` (§0k); its tests in `verify/hw/` are the contract. The main-process side is `electron/robot/`, the page side `src/robot/` and `src/components/operate/`.

- **Bundling:** `npm run build:daemon` builds the release `robot-daemon` (`robot-daemon.exe` on Windows) and `tools/hw/stage.mjs` copies it into `hw/dist/` (build output, not committed), ad-hoc signed on macOS like Forge. electron-builder's `extraResources` copies `hw/dist` to `<resources>/hw` on Mac and Windows, and `npm run dist` / `dist:win` stage it first. The packaged app spawns only that file; from source it uses `hw/dist`. `BASECASE_ROBOT_DAEMON=<path>` overrides the binary, for tests (`daemonBinary` in `robotLink.mjs`).
- **Hello:** the daemon's first stdout line, printed once the transport opens (`hello_line` in `protocol.rs`), is `{"event":"hello","version","family","emulated":true,"real_transport":false,"lost_message"}`. `real_transport` is `real_motors_unlocked()`, so an unlocked build says so; `lost_message` is `daemon_lost_message(family)` (the G1's is `g1_lost_message`: an emulated G1 runs in the daemon's process and stops with it; a real one keeps its last arm command), so the app has the words before it needs them. A refused `--port` exits before any hello.
- **IPC** (all `handle` channels through `trustedIpc`, `electron/robot/robotRoutes.mjs`; preload names in brackets): `robot:connect` (`robotConnect(spec)`) takes exactly `{ family: 'feetech' | 'dynamixel', ids: number[] (1–253, distinct, at most 32), class: 'arm' | 'legged', emulated: true }`, optionally with `factory: true` (spawns with `--factory`) and `units` (one servo model or null per id, `electron/robot/servoUnits.mjs`: exactly the numeric fields of a `ServoFit` plus `volts`, finite and bounded; written to `units.json` and passed as `--units`), or exactly `{ family: 'unitree-g1', emulated: true }`, or exactly `{ family: 'ros2', emulated: true, controller: { kind, topic }, joints }` (ROS 2, above; `electron/robot/ros2.mjs`) as plain objects (`checkedRobotSpec`) → `{ ok: true }` or `{ ok: false, message }`. The G1 form becomes `{ family: 'unitree-g1', ids: [13…29], class: 'legged', emulated: true }` for everything after it, so intents carry its 17 writable joints, and the ROS 2 form becomes `{ family: 'ros2', ids: [1…n], class: 'arm', emulated: true, controller, joints }`; anything else (a `port`, `emulated` not exactly `true`, extra or inherited keys, bad ids, a second robot) is refused in plain words and starts nothing. `robot:command` (`robotCommand(cmd)`) forwards only the documented commands, rebuilt from their known fields (`checkedCommand`); an `intent` must carry one finite number or `null` per servo, and `assign_id` an integer id 1–253 and model 0–65535. `robot:policy` (`robotPolicy(refs)`) takes an array of at most 16 references, each exactly `{ kind: 'policy', id }` or exactly `{ kind: 'skill', hash }` as a plain object (`checkedPolicyRefs`, Policy below). `robot:disconnect` (`robotDisconnect()`) closes stdin; the daemon stops the robot and exits, and is killed if it hasn't after 3 s. `robot:state` (`robotState()`) returns the connection, hello and latest status, so a reloaded page picks up where the main process is. Events reach the page on `robot:event` (`onRobotEvent`): every daemon line, plus `{event:'link', state:'connected'|'closed'|'lost'}`.
- **Spawn:** `spawn` with no shell, argv `--family <f> --ids <ids> --class <c> --emulated --artefacts <dir>`, then `--factory` for a factory bus and `--units <dir>/units.json` when the spec carries `units` (for the G1, `--family unitree-g1 --emulated --artefacts <dir>`; for ROS 2, `--family ros2 --controller <kind> --topic <topic> --joints <names> --emulated --artefacts <dir>`), never `--port` or `--interface`. The artefacts folder is a fresh temp folder per connection, removed when the daemon exits. For an emulated robot the app writes `calibration.json` itself (`emulatedCalibration`: every id zeroed at 2048 counts, direction 1, ±2.8 rad; the G1's joints named by their URDF names, a ROS 2 robot's by its joint names), so Set up → Test climbs with no hardware steps. A Feetech or Dynamixel spec, with or without `factory`, may also carry `units`, one entry per id: `null` (the protocol's own unit) or exactly the part's fit numbers (Part models, above; checked in `electron/robot/servoUnits.mjs` with the daemon's bounds and refused as “Give one servo model, or null, per servo ID.”, “A servo model takes only the numbers of its fit, nothing else.” or “A servo model has a number out of range.”). The checked spec keeps its own copy, and the app writes it to `units.json` beside `calibration.json` for that connection.
- **Policy** (`src/robot/robotPolicy.ts`, `electron/robot/robotPolicy.mjs`): the scene in front sends the robot its candidates, and sends again when they change: its policies that aren't stale (`Training.isStale`, §8d) and its ready skills (`skillRows`, §8i), newest first, at most 16 (`readyRobotPolicies`). The renderer sends only references; the main process takes the first that yields ONNX, so a ready skill that replays an animation or follows IK doesn't hide an older policy. A policy is `library/policies/<id>/policy.onnx`, the trainer's own copy (`Trainer.policyOnnx`, ids matching `policy-[a-z0-9-]+`). A skill whose controller is a policy is encoded from its `skill.json` (`getSkill`) by `policyOnnx` (`electron/robot/policyOnnx.mjs`), which builds the graph Forge's `onnx.rs` builds: input `obs`, the normalizer, MatMul and Add per layer with Elu (or Tanh) between, an optional Tanh squash, output `action` clipped to ±1. It refuses layers that don't line up or numbers that aren't finite. When no candidate yields ONNX (none trained, a policy trained before ONNX export, only skills that aren't policies), it writes none and the daemon keeps refusing with “Load a policy first.” `RobotLink` keeps the references, writes `policy.onnx` before the daemon starts, and while connected rewrites it (a `.part` file renamed into place, or removed) and sends `recheck`, so `PolicyPresent` turns on with no click and a new policy clears the evidence it voids (§8k, Mode ladder). Tests: `policyOnnx.test.mjs` decodes the graph and runs the Motor Kit's Walk through it against `act()`; the same file in ONNX Runtime matched `act()` within 3e-6. `robotLink.test.mjs` checks the bytes for a stored skill and a trained policy, skipping candidates with none, the swap and `recheck`, and ids that try to leave the library. `tests/policy_folder.rs` writes the file after connect and climbs.
- **Heartbeat:** the main process keeps it, not the page, so a busy renderer can't starve the daemon (`IntentPacer`, every 30 ms). Below Test it sends `heartbeat`; from a `test` mode on it sends `intent` with the held targets: at first the measured pose (status counts back to radians through the same calibration), then whatever the page sent last. Measured through the gate's relay on the packaged app (three 10 s runs in Test, load average about 25): gaps median 31.1 ms, 99th percentile 32 ms, largest 32.8 ms, never a stale fault. Starving it stops the robot with `client_lost` 114 to 144 ms later. The gate checks the largest gap stays under 100 ms and the median at 60 ms or less while the robot runs.
- **Driving:** each sim frame carries `joints` (`SimEngine.jointStates`: per joint its target, the actuator's control for position joints or the joint position otherwise, its simulated position and its force); `noteSimAngles` takes the positions, and `offerSimTargets` (`src/robot/intentMirror.ts`) turns the targets into an `intent` at most every 25 ms, in joint order with ids 1…n over the scene's movable (non-fixed) joints recorded at Connect (kept in `sessionStorage`, so a reloaded page that adopts the main process's connection keeps following). A joint the sim doesn't have holds its measured position. So a Case try, a Routine run or Drive streams at the pacer's rate; when nothing drives, the main process repeats the last targets, so intents hold still. A connection made without a scene (`robotConnect` from a test) gets held intents only.
- **Operate** tab in the Play view (§5; `OperateIcon`, a joystick, in ⌘K; hidden in the web demo): Connect Emulated Robot (`sceneRobot`: Feetech, ids and `class` from `servoLayout`, which numbers the movable joints 1…n and calls the robot legged when a joint's limb is a leg; the robot package's `joint_map.json` uses the same helper, §8d). A scene with no catalog servos sends no `units`. A family control above it (`[data-testid="robot-family"]`, labels from `FAMILY_NAMES` in `src/robot/robotFamilies.ts`) offers the scene's own family first, then ROS 2 (`sceneRobotChoices`); the first is chosen, and ⌘K connects it. A Basecase design exported as a robot package names its URDF joints by their MJCF names (`j0_…`), so its `/joint_states` won't match these names. ### Calibration (Stage 6)

`src/reality/` fits a servo's model from logs and feeds it to the sim. It's judged by `s6-hidden-twin` against a hidden twin (§0k). No real servo has been logged with it.

- **Bench and logs:** a servo turning a pendulum (`benchInput`: the catalog servo and a 20 mm bob of the payload's mass at its arm), logged at 100 Hz with the servo's part id and variant, goal, position, load, volts, temperature and payload (`ServoLog` in `types.ts`).
- **Which servo:** each joint is fitted against its own catalog servo and variant (`jointServo` in `servoPart.ts`: the first actuator part with a catalog actuator spec), never a family. Its starting model is `presetServo` (`servoEstimate.ts`): the variant's `fit` when the catalog has one (STS3215 C001, XL330), else `estimatedFit`, the measured fit of the same bus's servo (XL330 for Dynamixel, STS3215 C001 for the rest) scaled to the part's stall torque, rpm and volts, so its force limit, stiffness and no-load speed match the catalog (an STS3215 C046 gets 1.412/1.912 of the C001's force). The preset the verdict and the grey replay compare against is the sim's own model of the joint, the MJCF built with no `servoFits`, the path `mjcfServo.ts` takes: the catalog fit where there is one, else the MJCF writer's estimated actuator. Old records name a `family` (`sts3215`, `xl330`) instead of a `servo`; `servoPartOf` reads them as that family's servo (`FAMILY_SERVOS`), so they still apply and roll back, and `calibrateServo` takes a request named by family the same way (the hidden twin sends one).
- **Forward model:** the MJCF and `SimEngine` the sim runs. `replayLog` holds the log's first position, then plays its goals. `MjcfInput.servoFits` gives a joint a fitted `ServoFit` and volts in place of the catalog's (`mjcfServo.ts`).
- **What it fits:** multipliers on the BAM M6 terms the MuJoCo model carries (`servoParams.ts`): position gain (`errorGain`), delay, damping (back-EMF and viscous together), armature, base friction, load friction (`loadExternal`, times the bench's holding torque) and torque limit (kt / R). Each stays within 0.25x to 4x, delay up to 8x. `scaledFit` writes them back into a `ServoFit`, so a calibration has the catalog's shape. Backlash, series compliance, stick-slip, supply sag, thermal drift and encoder bias aren't in the model; the fit absorbs what it can of them into these terms.
- **How it fits:** Levenberg–Marquardt with forward-difference Jacobians on MuJoCo replays (`leastSquares.ts`), a weak prior toward the preset, and a coarse delay grid first, because the cost has local minima in delay. It's TypeScript rather than `forge-id`: forge-id has no delay or torque-limit parameter, and the gate calls the calibrator in-process.
- **Held-out honesty:** the first 0.3 s of each log is skipped, because the servo may still be moving from the log before and the log doesn't record its speed. The rest is split in time: the first half fits, the second half checks.
- **Update ladder** (`ladder.ts`): `response` (gain, delay, damping, armature), then `friction-force` (adds base friction, load friction and torque limit). Each rung is fit on the first halves and scored on the second. Climbing stops at the first rung that predicts the second halves at least 25% better than the preset with no log worse; if none does, the best rung that's at least 5% better is kept. The chosen rung is then refit on whole logs.
- **Verdicts** (`calibrateServo`). Only `measured` changes the model; the other two return the preset fit.
  - `cant-tell`: fewer than two logs, a log from another servo or with missing samples, logs where the preset explains under half the motion (positions that don't follow the goals, as in shuffled logs), or an update that still leaves over 20% of the checked motion unexplained.
  - `consistent`: the preset predicts every log within one encoder count, or no rung is 5% better while the preset explains at least 80% of the motion.
  - `measured`: a rung passed or helped.
- **Versions and rollback** (`history.ts`): `project.servoCalibrations` keeps a `CalibrationHistory` per joint. Every calibration is recorded with the next version number, only a `measured` one becomes active, so a failed update keeps the last good one, and `rollBack` steps back to the previous measured version, then to the preset.
- **Into the sim:** `calibratedInput` applies each joint's active calibration when its servo and variant are the joint's own (`calibrationApplies` in `measuredJoints.ts`, kept apart from `bench.ts` so Checks don't load the bench fixtures). `useSimulation`'s `buildModel` uses it, so the Simulate tab, Cases, Skills and training run on calibrated servos. A new active calibration changes the robot's model fingerprint, so every policy trained before it shows Out of date in its row in the Simulate tab's Train section until it's retrained (right-click ▸ Retrain), and rolling back to the calibration it trained on makes it fresh again (§8d, Stale models).
- **Calibrate in Operate** (`RobotCalibration`, Calibrate Servos, also in ⌘K): offered only for Feetech and Dynamixel servos (`servoFamily`), only in Test with motors running, because Test is the one rung where the app's intents move motors (Rehearse writes nothing, First run and up follow the policy slot), and only in the scene the robot was connected from (`connectedFrom`: its movable joint ids match the ones recorded at Connect), so fits never land in another scene's project. `playBench` (`src/robot/benchRun.ts`) streams intents every 25 ms through the normal path (pacer, guard, motor lock, fault matrix all apply) and owns them while it runs, so `offerSimTargets` stays out. Every joint moves at once, offset from where it stood (a row's Calibrate, or Checks' Servo models Fix, passes `playBench` those joints' indexes, so only they move, the rest hold their start, and only their samples are logged): `benchOffset` (`benchSequence.ts`) is 9 s of ramps at 0.12 rad/s to ±0.25 rad with 0.6 s holds, then 9 s of a 0.15 rad, 0.12 Hz sine. It's that slow because the guard and the servo's speed cap clip anything faster, and a log whose goals aren't what the servo was given reads Can't tell. Status events (every 100 ms) are timed by `at_us`, put on the page's clock through the one heard soonest after its stamp, so a status that arrives late (a stalled page, a busy relay) keeps its place; the bench records until a status passes its 18 s (or 1 s after, if none does). They become two logs per joint (`benchLogs`), positions relative to the start so the bench's gravity doesn't bend them, with `EMULATED_LOAD` (0.2 kg at 0.1 m, the emulator's 0.002 kg·m²) as the payload and each joint's servo from the scene (`benchServo`: its catalog servo, or for a joint with none the protocol's stand-in, STS3215 C001 on Feetech and XL330 on Dynamixel). A joint whose catalog servo is on a bus the daemon can't speak (a PWM servo like the DS3218, a Hiwonder bus servo, a DC gearmotor, a CAN or RS485 actuator) is skipped: it holds its start, records nothing, and its row reads No reply in place of the emulator's reading (`offTheBus`, applied in `jointRows`). Fits run in `calibrate.worker.ts` one joint at a time and each is recorded through `history.ts` (`withCalibration`) as it lands. If the robot leaves Test or faults, nothing is recorded and the daemon's message says why.
- **Rows:** calibration lives in the joint's row under Emulated servos (`JointRow`; `[data-calibration-joint]` beside `[data-robot-joint]` on the same element, `data-verdict` from the newest version, `data-version` the active one or 0): under the name, the newest verdict when it isn't Measured (Consistent with preset, Can’t tell) and the active version (`v2`), or Preset when none is active and the newest isn't Consistent. Calibrate Servos sits above the rows. The row's More menu (`JointRowMenu`, in `RowActions`, so it floats over the row on hover) lists the measured versions (`v1`, `v2`…, the drawn one ticked) and Roll Back, after a confirmation (`rollBack`).
- **Which joints the sim measures** (`measuredJoints`, `src/reality/measuredJoints.ts`): a joint is Measured when its active calibration is `measured` and `calibrationApplies` to its servo, the same rule `calibratedInput` follows, so it says exactly which joints the sim runs on a fit. A preset servo with a catalog fit (STS3215 C001, XL330) isn't Measured: its model came from another unit. It's never read from the model's `dynamics`, which marks every catalog fit as measured. One state, shown wherever joints appear: a `Badge` reading Measured (the verdict word, accent; `MeasuredBadge` in `components/verdicts.tsx`, which Pose and Operate share) beside the joint's name in the Pose tab's rows (`pose/JointRow.tsx`) and in Operate's rows (`data-measured` on the row; the row drops its Measured verdict word only where the badge shows, so a measured fit for another servo still reads Measured beside its version), and the Servo models row in Checks (§8b). Every reader derives it from `project.servoCalibrations` in render, so a calibration or a rollback flips all three at once; the readiness fingerprint carries each joint's active version (`activeVersions`), so Checks run again.
- **Replay** (`JointReplayPlot`, `src/reality/jointReplay.ts`): clicking a joint's row opens its replay under it, one `TracePlot` (§14) on one time axis: the logged position (`trace-logged`, light), the preset's replay (`trace-preset`, grey) and the calibration's replay (`trace-calibration`, the accent), then the median absolute error of the two replays in degrees, grey and accent, with no other text. Choosing a version from the menu redraws the accent trace against it, so a person sees what a rollback would change before doing it; with no measured version there are two traces and one figure. Replays go through `predictLog`, the path the fitter scores, over the newest bench run's logs, skipping the settle window. They run in `calibrate.worker.ts` (`replay`) and are cached by log and version (`replayClient.ts`; version 0 is the preset). The logs live in memory only (`benchLogStore.ts`, `logId` on each recorded calibration): after a reload the rows stay, and replays come back with the next Calibrate Servos. The agent's `operate` reply ends with the same errors per joint (`calibrationErrorsText`), and `__studio.calibrationReplay(jointId)` returns them for tests.
- **Measured through the daemon** (3 emulated STS3215 on the release daemon, 90 samples per log at 97.6 ms): all three Measured at the `friction-force` rung, 7 to 10% better than the preset on the check halves, about 2 s of fitting each. Slow motion only shows what slow motion shows; delay and torque limit stay near the preset.
- **e2e** (`e2e/operate.e2e.test.ts`): the browser e2e has no daemon, so `__studio.attachRobot` (dev only) gives the robot store a stand-in link (`e2e/fakeDaemon.ts`: the ladder, refusing Rehearse and up with “Load a policy first.” until `robotPolicy` names one, a 0.5 rad/s goal limit and a 0.3 s lag, status every 100 ms). It keeps its own clock in 20 ms ticks and stamps each intent when it arrives. While intents stream in (one within its last five timer calls), it advances no further than 40 ms past the newest one, extrapolating from the last two, and moves through a gap between two intents along the line joining them. So a stalled page delays the emulator instead of changing what it records. The test connects a two-joint arm, calibrates, checks the rows, opens a measured joint's replay (three traces, the calibrated error below the preset's through `__studio.calibrationReplay`) and rolls it back, after which the accent trace goes, on every platform. `src/robot/benchRun.test.ts` runs the bench through the same script on a simulated event loop with page stalls of up to 420 ms, and checks the logs match a steady run within 2 encoder counts and still fit. The stand-in has a G1 mode too: `e2e/operateG1.e2e.test.ts` loads a 29-joint humanoid named like the G1 (`e2e/g1Fixture.ts`), connects it from Operate, climbs to Test, poses the right shoulder with `__studio.setPose` and plays Simulate (Hold pose sets each actuator to the pose), then checks the fake G1's right shoulder follows while its leg ids 1–12 count no writes. It has a ROS 2 mode too: `e2e/operateRos2.e2e.test.ts` loads the two-joint arm (`e2e/armFixture.ts`), clicks ROS 2 in the family control, connects, checks the fake was asked for a forward position controller on the arm's joint names, climbs to Test, poses the shoulder and plays Simulate, then checks through `__studio.robotGhost()` that the measured shoulder follows the sim.
- **e2e** (`e2e/operate.e2e.test.ts`): the browser e2e has no daemon, so `__studio.attachRobot` (dev only) gives the robot store a stand-in link (`e2e/fakeDaemon.ts`: the ladder, a 0.5 rad/s goal limit and a 0.3 s lag, status every 100 ms). It connects a two-joint arm, checks the Ladder carries the mode, calibrates, checks each row joins its bus ID, reading and verdict, checks the Pose rows mark the Measured joints and Checks' Servo models row passes when both are, opens a measured joint's replay (three traces, the calibrated error below the preset's through `__studio.calibrationReplay`) and rolls it back, after which the accent trace goes, the joint loses its mark and the Servo models row warns naming it. Its Fix selects the joint's servo and calibrates that joint alone, and the row follows the new verdict. A second test drives the arm with W in Simulate and reads `__studio.robotGhost()` (dev only: the layer's `ghostState`, plus measured, sim and gap degrees per joint): the ghost is posed at the measured angles while they differ from the sim's, the largest gap is over 1° while moving and under 1.5° at hold (the fake has no gravity, so what's left is the sim's sag, about 0.5°), and the ghost is gone after Disconnect. `src/robot/robotTwin.test.ts` checks the ghost against `poseDeltas`, the gap's timing and wrap, the 2 s rule, and a one-joint bench. A third loads `MIXED_ARM` (`e2e/armFixture.ts`: an STS3215 C046 shoulder and an XL430 elbow), runs Calibrate Servos, and checks through `__studio.calibrations()` (dev only: the project's calibration histories) that each joint's newest record names its own servo and carries the verdict its row shows. Operate policy loads the arm with a fresh trained policy, checks the stand-in was sent its reference and climbs to Rehearse, then loads the arm without one and gets “Load a policy first.”
- **Tests:** `npx vitest run src/reality` takes about a second: the fitter recovers a known gain and delay from synthetic logs, preset logs read consistent and shuffled logs can't tell. `calibrate.test.ts` also checks an STS3215 C046 starts from its own estimate, an XL430 unit with planted gain, damping and friction reads Measured against its estimated model while its shuffled logs can't tell, and a request named by family still works; `measuredJoints.test.ts` loads an old family-named record and rolls it back. `benchCalibration.test.ts` also replays a hidden unit's bench log: the calibrated median error is at least the gate's 25% (`LADDER.passGain`) below the preset's, and a shuffled log stays Can't tell with no gain.
- **Measured at the gate** (24 hidden units per family, held-out replay and other load): median error down 52% for the STS3215 (bootstrap lower bound 41%) and 65% for the XL330 (55%), below the 90% alarm. Most units stop at the `response` rung, in about 4 s each; shuffled logs read Can't tell and preset logs Consistent. The second-half check overstates the held-out gain (often 80–90%), because held-out logs start mid-motion and the replay starts at rest.

### Real tries (next)

A real try (§8h) tracks only a ground robot's base, from a tag on its root link. The next steps:

- **Arms:** an end-effector tag on the gripper or tool, solved the same way at its tracked height, so a reach or touch Case can judge a real arm.
- **Calibration from the path:** the tracked base path against the sim try with the same commands fits wheel slip and effective wheel radius, the way the bench fits servos here, and feeds them to the sim.
