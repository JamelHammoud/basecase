# Forge

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8g. Forge

Forge is Basecase's native trainer and batched physics, in `forge/`. It replaces Python for training, so nobody needs a terminal, uv or PyTorch to teach a robot.

- **C MuJoCo stays the compiler and oracle.** Forge links stock `libmujoco` to compile the generated MJCF and to check its own results. We never fork MuJoCo's C code. Forge's own engine is a reimplementation of MuJoCo's formulation for the subset Basecase generates.
- **Same events as the Python trainer.** Forge prints the same JSON lines on stdout, so `electron/trainer.mjs` barely changes.
- **Anything outside the subset routes to C MuJoCo, never silently.** The feature matrix refuses what it can't simulate exactly.
- **Speed claims use one number:** time-to-skill from `verify/`, not steps per second.

### Crates

| Crate | What it is |
|---|---|
| `forge-mujoco` | Our minimal FFI to stock `libmujoco`: `Model`, `Data` and the `mjb_*` batch API (`Batch`). A small C shim (`src/shim.c`) reads struct fields, so Rust never mirrors MuJoCo's struct layouts; the one struct Rust does declare, `mjBatchConfig`, is checked against the header's size and offsets in a test, as is the linked library's version against the headers'; `src/fields.c` reads any compiled model or data array by name through `mjxmacro.h` (`Model::array`, `Data::array`) |
| `forge-ir` | Lowers a compiled MuJoCo model to `Kernel`, plain data for Forge's own engines, or refuses it with every reason in readable words; `task::Task` describes a training task (observations, reward, falls, resets, pushes) for the GPU loop |
| `forge-sim` | Forge's SIMD and Metal engines and the `forge-sim` CLI: parity runs, batch identity and the bench. `RowBatch` (SIMD) and `MetalBatch` (Metal) step MuJoCo-layout state rows, so `forge-train` can swap either in for `Batch` |
| `forge-metal` | The only `unsafe` Metal code: a small safe wrapper over `objc2-metal` (device, shared buffers by id and offset, runtime compilation, one command buffer per run). Off macOS every call says the backend needs a Mac |
| `forge-wgpu` | A small safe wrapper over `wgpu` for the WGSL engine: device with the adapter's buffer and workgroup limits, one bind group layout for every entry point, upload, dispatch and read back. Metal on macOS, D3D12 and Vulkan on Windows, Vulkan on Linux |
| `forge-web` | The WASM build of Forge for a browser tab (`src/forge/forge.wasm`): `forge-ir`, the WGSL generator and `forge-train`'s PPO without MuJoCo, driving WebGPU through JavaScript imports |
| `forge-train` | The `forge-train` binary: PPO (default), FastSAC and FlashSAC on C MuJoCo batch (or Forge's SIMD engine with `backend: "simd"`; with `backend: "metal"`, PPO trains entirely on the GPU, the GPU loop), the drop-in for `electron/trainer/train.py` |
| `forge-id` | System identification: finite-difference Gauss-Newton (Levenberg-Marquardt) on C MuJoCo batch, and the batched fit on Forge's gradients (F7) |
| `forge-reward` | RewardLang parser, CPU interpreter and lowering to `code::Code` for the GPU, plus `handwritten::{stand, walk}`, the rewards `train.py` uses |

### Building

- `cargo build --release --manifest-path forge/Cargo.toml` from the repo root; `npm run check` never runs cargo, so it stays seconds-fast. The gates run `cargo test --release`.
- **MuJoCo comes from DeepMind's release.** `forge-mujoco/build/` downloads the pinned release (`VERSION` in `fetch.rs`, 4.0.0, the same version as the Python env and `@mujoco/mujoco`; `node tools/sim/update-mujoco.mjs` bumps all three, §8d) into the gitignored `forge/vendor/` on first build: the macOS `.dmg` framework, the Windows `.zip` or the Linux `.tar.gz`, with `curl`, `hdiutil` and `tar` (all built into macOS and Windows 10+). `FORGE_MUJOCO_DIR` points at an unpacked copy instead, for offline builds or a shared copy between worktrees. `FORGE_CHECK_ONLY=1` skips the download and the C shim, for `cargo check --target` on another OS.
- **Every crate that links MuJoCo carries a two-line `build.rs`** that adds the vendored folder to the binary's rpath (`DEP_MUJOCO_LIB_DIR`); on Windows `forge-train`'s copies `mujoco.dll` beside the binary. Packaging will ship `mujoco.framework` beside `forge-train` (`@executable_path` is already on the rpath).
- **Rust style matches §0 in spirit:** no comments, files under 400 lines, functions under about 120, `cargo fmt` (`forge/rustfmt.toml`, 120 columns) and `cargo clippy --all-targets -- -D warnings` clean. `forge-ir` and `forge-sim` make clippy enforce it (`[lints.clippy]` in their `Cargo.toml` and a `clippy.toml`: `too_many_lines` at 120, `too_many_arguments` at 5, `cognitive_complexity` at 15, no `unsafe`); `forge-sim` allows `needless_range_loop`, because index loops over lane arrays read better than zipped iterators in numeric kernels. Metal shader sources (`forge-sim/src/metal/shaders/*.metal`) follow the same rules, and `tests/style.rs` checks them with the Rust files.
- **`unsafe` lives only in `forge-metal` and `forge-web`.** `forge-web`'s is the WASM boundary: its JavaScript imports (`host.rs`) and the pointers its exports take (`exports.rs`). `forge-metal`'s is in `src/mac.rs`: slices over a shared buffer's contents and the encoder's `setBuffer`/`setBytes`. Slices borrow the `Gpu` and `run` borrows it mutably and waits for the command buffer, so no slice overlaps GPU work. `Gpu` and `Kernel` are `Send` because Metal's device, queue, buffers and pipeline states are thread-safe; command buffers and encoders never outlive `run`. Elsewhere `forge-metal` compiles to stubs, and `FORGE_CHECK_ONLY=1 cargo clippy --target x86_64-pc-windows-msvc` (or `x86_64-unknown-linux-gnu`) keeps both paths compiling.
- Benches: `cargo run --release -p forge-mujoco --example physics_bench -- <model.xml>` (batch stepping by thread count) and `cargo run --release -p forge-train --example learner_bench` (one PPO minibatch, per layer; add any argument for the portable kernels).

### forge-train

- **CLI:** `forge-train --job <dir>` reads `<dir>/model.xml` and `<dir>/job.json` with the same fields as `train.py` (`task`, `minutes`, `command`, `root`, `joints`, `defaultPose`, `ctrlDefault`, `initialJoints`, `rootOffset`, `actionScale`, `controlDt`, and optional `seed`, `maxIterations`, `gateEvery`, `evalSeeds`, `gateSpeed`, `envs`, and `gpuEnvs`, the robot count when the job trains on the GPU loop (otherwise `envs` applies); `threads` caps the physics threads; `algo` is `ppo` (the default), `fastsac`, `flashsac` or `shac` (F7, below); `warmStart` starts from a trained policy, below; `logStdMin` floors PPO's `log_std`; `squash` is `clip`, the default, or `tanh`, below). `forge-train --check` prints the MuJoCo version and CPU count. `forge-train --adam-vector <file>` writes the learner's Adam test vector (below).
- **Training conditions** (all optional; without them a job is `train.py`'s environment, line for line, and draws nothing extra from the random streams; `options.rs`, `conditions.rs`):
  - `reward`: a RewardLang program (`def reward(state):`) used instead of the hand-written Stand or Walk reward. It's compiled once per job and evaluated per robot per tick; a program that doesn't compile fails the job with its line number. The Motor Kit and the solver race send theirs (§8i).
  - `commands`: `{ ranges: [[lo, hi] × 3], resampleS: [lo, hi], stillShare }`. Each robot draws `[forward, left, turn]` at reset and again every `resampleS` seconds, all zero with probability `stillShare`; the observation and `state.command` read the robot's own command. `command` stays the one `policy.json` carries and the clean evaluation runs.
  - `delaySteps: [lo, hi]`: each robot's servo targets lag its actions by a whole number of control steps, drawn per episode (a ring buffer of past actions; `last_action` stays the policy's own). With `delayRamp: share` (above 0, at most 1) the delay ceiling `m` rises linearly from `lo` to `hi` over that share of the budget, or of `maxIterations` when that comes first, then holds. Each episode draws `lo + min(hi − lo, ⌊u·(m − lo + 1)⌋)`, so the distribution moves continuously from always `lo` to uniform over `[lo, hi]` (`conditions::delay_ceiling`, the same on the GPU loop). The trainer passes its progress to the learner before every iteration (`Algorithm::follow_progress`). Without `delayRamp` the draw is unchanged.
  - `encoderBias` (rad) and `imuBias` (rad): per-episode joint zero offsets added to the observed joint positions, and a roll and pitch mount bias that tilts the observed gravity. Rewards read the true state.
  - `actorLinvel: false`: linear velocity (observations 6–8) never reaches the actor. The actor's `Mlp` carries an input mask (`mask.rs`, `Mlp::mask_inputs`): its forward pass reads a copy of the observation with those columns zeroed, so their first-layer weights get no gradient, and its backward pass uses the same copy. The critic reads the full observation. `Deployed` zeroes the masked weights, so `policy.json` and the ONNX graph give the same action for any value in those inputs (the app's normalizer clips them to ±5 first). PPO and both SACs mask from the job's options when they're built; nothing projects weights after an iteration.
  - `resetNoise` (rad, default 0.05), `standHeight` (the `z0` rewards and falls compare against, for starts that aren't standing), `fallResets: false` (a fall neither ends the episode nor counts as terminal), `pushes: false`, `episodeS`.
  - Clean evaluations, gates and `policy-check.json` run without any of these, on the job's `command`.
- **Events:** the same `status`, `progress` (with `phases`: physics, observe, reward, inference, gradient), `gate` and one `done` (`policy`, `steps`, `stopped`, `eval`, `gate`). The budget counts active time only (a gap over 30 s between iterations counts as 30 s). It stops on SIGTERM or SIGINT, or on a `stop` file in the job folder (Windows has no signals), then still saves and evaluates; `stopped` is true for either.
- **Outputs:** `policy.json` in the `src/sim/policy.ts` format (weights rounded to 7 decimals like `train.py`), `policy.onnx` written by our own protobuf encoder (`src/onnx.rs`: input `obs`, output `action`, the normalizer baked in, opset 17), and `policy-check.json` with 16 raw observations and the clipped mean actions, which `verify/` replays through the app's `act()` and ONNX. Beside them, `resume.json` (`warm.rs`, format `basecase-resume`) holds what `policy.json` leaves out: the algorithm, the actor and critic as raw f32 parameters with their layer sizes (SAC: both twins and their targets, and `logAlpha`), PPO's `logStd` and adaptive learning rate, and the normalizer's exact mean, variance and count. It's written at every save, so `policy.json` keeps its format for every reader.
- **Warm start** (`warmStart`, relative to the job folder or absolute): a folder starts from its `resume.json` (or its `policy.json` when there's none); a file is read as a `policy.json`, giving the actor and a normalizer from `obsMean`, `obsStd` and `trainedSteps`. The actor must have the job's layer sizes (a SAC actor also takes a `policy.json`'s mean head); otherwise the job fails before training with both shapes ("its network is 48-256-128-64-12 and this job's is 51-256-128-64-13"). The critic, `logStd` and learning rate come along only from a `resume.json` of the same algorithm and shape, else the status says the value estimate starts fresh. Masked inputs stay masked. A warm start onto new conditions also wants `logStdMin`: biped-servo's walking policy ended with four joints at a `log_std` near −6 (a standard deviation of 0.0025), where a 0.01 shift in the mean moves the log-probability by about 8, and two 12-minute continuations onto 0–40 ms servo delays held a reward of 3 for 7,500–10,000 iterations, then collapsed to −2 within 100 and never came back. With `logStdMin: -2.5` (the Motor Kit sends it with every warm start, §8i) the same continuation held for all 16,742 iterations; a floor applied only when loading collapsed nothing in one run but lost the top speed, and −1.5 stopped it walking at speed. `tests/warm_start.rs` resumes a 60-iteration run whose reward rose from 1.14 to 1.61: the resumed run's first iteration reads 1.61.
- **Same environment as `train.py`:** observation, action, reward (`forge_reward::handwritten`), termination, resets, shoves and domain randomization match it line for line. A clean run with the same actions gives bit-identical observations and rewards to `train.py`'s `Envs`. Random streams differ (per-environment xoshiro streams), so runs are comparable, not identical; a seed replays exactly.
- **PPO as `train.py` runs it, with more reuse and one rollout of overlap:** orthogonal init, ELU 256-128-64 actor and critic, `log_std` starting at −0.7, GAE (γ 0.99, λ 0.95), clipped surrogate (0.2), value loss 0.5, entropy 0.004, 4 minibatches of a 24-step rollout, gradient norm clipped to 1, Adam with the rsl_rl adaptive learning rate (KL target 0.01). `log_std` is capped at 0 after every step (`LOG_STD_MAX`, a standard deviation of one full action range): where a joint's mean action sits past ±1 the clip hides its noise, so the entropy bonus grew that joint's `log_std` without limit (to 2.6 on biped-servo, a standard deviation of 13) until the noise flipped the clipped action and the run collapsed from a reward of 3 to −1.6 in a few hundred iterations. Gradients are hand-derived (`mlp.rs`, `heads.rs`) and checked against finite differences in tests. Two things differ from `train.py`, both for time-to-skill:
  - **30 epochs instead of 5 at 64 robots** (`Hyper::for_envs`: 30 × 64 / robots, at least 5, so 1024 robots keep 5). The walk task has a slow tail: many seeds creep from 0.15 to 0.2 m/s over millions of steps. Steps to the walk gate over 8 seeds (load average 30–60, steps are the same at any load): 5 epochs needed a median of 2.4M (quad-servo, 2 seeds past 4.1M) and 2.8M (hexapod, 3 past); 10 epochs 1.0M and 1.0M; 20 epochs 350K and 540K; 30 epochs 232K, 309K and 155K (biped-servo), with every seed under 850K; 50 epochs 190K and 230K but at 5/3 the learner time. `train.py` needed 0.7–1.1M on quad-servo with 2 of 5 seeds past 8M.
  - **Learning overlaps collecting** (`ppo/mod.rs`): while the learner thread trains on rollout k, the main thread collects rollout k+1 with a copy of the weights from before that update (`Collector` in `ppo/collector.rs` holds the copy, its own inference scratch and the environments). Before learning, the rollout's log-probabilities and values are recomputed with the current weights, so the PPO ratio starts at 1 and the KL-adaptive step size isn't fooled by the one-update lag. The first iteration only collects. Over 8 seeds the lag cost no samples (quad-servo 3.0M against 2.4M, hexapod 1.0M against 2.8M at 5 epochs, within the spread).
  - **Squashed actions** (`squash: "tanh"`, `ppo/collector.rs`, `heads.rs`): the robots act on `tanh(u)`, where `u` is the Gaussian sample, and the rollout keeps `u`, so the ratio and the KL are the Gaussian's (the squash's Jacobian is the same in both log-probabilities and cancels). The entropy bonus adds the squash's term, `−ent_coef × Σ log(1 − tanh² u)` per sample with `u = μ + σε` held at the sample: its gradient is `2·ent_coef·tanh u` on the mean and `2·ent_coef·tanh u·(u − μ)` on `log_std`, in every row block. Without it a mean past saturation gets no gradient at all. `policy.json` carries `"squash": "tanh"` as the SAC learners' do, and `tests/policy_loss.rs` checks the term against finite differences. Why: with the clip, mean actions drifted past ±1 (70% of samples past ±1.5 by iteration 1,500 on hexapod Velocity tracking; 90–96% of joints in finished policies, mean |μ| 6–10, with either learner). Past the clip a joint's noise changes nothing, so the entropy bonus walked its `log_std` up to the cap of 0. On the same hexapod job and seed, `tanh` kept 0.2–3% of samples past |u| = 2.65 (tanh 0.99), and `log_std` fell instead of rising. At 9.2M steps the clean evaluation covered 1.58 m of 1.6 m, where the clip covered 1.22.
  - **Squashing wants a floor on `log_std`.** On that seed, `tanh` alone reached a reward of 1.6 by 10,000 iterations. One joint's `log_std` then fell to −6.5, minibatch KL jumped to 3–30, and the run fell to −0.58: the collapse §8i records for biped warm starts. A minibatch's KL is set by its smallest σ: an Adam step moves every weight by about the learning rate, so a change of 0.1 in a mean costs a KL of 0.01 at σ = 0.7 but 1,000 at σ = 0.0015. That's also why the adaptive rate sits at 1e-5 most of the time. With `logStdMin: -2.5` the same seed climbed to 1.75 over all 20,600 iterations and passed the Kit's Arena at top speed, half speed and standing still (96/96, 95/96, 96/96). The rate came off its floor (1e-4 to 1.7e-4) for stretches. On a second seed it passed 96/96 at all three, as did quad-servo on its 12-minute stage (clean evaluation 1.52 m of 1.6). The Motor Kit sends both with every Velocity tracking stage on four or more feet (§8i). Without `squash` nothing changes: the default clip path is bit for bit the same as before (the same rewards over 30 iterations).
  - **`tanh` slowed the biped.** biped-servo's first stage (0 to 20 ms, 42,500 iterations) walked 0.52 m in the clean evaluation's 8 s at a floor of −2.5, and 0.73 m at a floor of −4, where 0.15 m/s asks for about 1.05 m. Both failed the Kit's Arena at top and half speed: 9/13/15 and 13/22/23 at −2.5, 13/11/14 and 14/16/10 at −4. Both steered through the gate's timeline and passed standing still. The clip's first stage scored 29/30/27, 31/30/29 and 31/31/31: it reaches the ends of the 0.5 rad action range on 55% of its joints, and the squash keeps the mean short of them. So the biped stays on the clip (§8i). Scaling each joint to its margin from neutral to the nearer limit (0.7, 1.57 and 2.27 rad for abduct, swing and bend; 0.52, 1.57, 2.09 and 0.87 for the biped's roll, pitch, bend and tilt) didn't fix it. At a floor of −2.5 the biped's first stage plateaued at a reward of 1.6 with every joint on the floor, because σ = e^−2.5 in u is 0.16 rad on a 2 rad joint. At −4 it walked 1.06 m but scored 6/9/7, 0/6/4 and 32/32/22 in the Arena. Its 0 to 40 ms continuation circled: 0.20 m forward, 1/0/1, 11/13/7 and 22/25/19. The hexapod at that scale and floor never walked (0.01 m; 0/0/0, 3/5/10, 0/0/0).
  - **Any other PPO learner must do the same** (the GPU loop behind `backend: "metal"` included): read `squash` and `logStdMin` from the job, act on `tanh(u)` and keep `u`, add the squash term above to the entropy gradient in every block of rows, export through `Deployed` with `Squash::Tanh`, and pass `tests/policy_loss.rs`'s finite-difference check for both terms. The Kit's Velocity tracking jobs send both options, so a learner that ignores them trains the saturating policy this section describes.
  - **What didn't help the saturation:** a soft bound on the mean in clip space (0.1 × the squared excess past ±1). `log_std` went to 0 within 1,000 iterations and the hexapod fell, because the policy reached the range's ends through noise instead. Stopping an iteration's epochs once a minibatch's KL passed 2× the target, with `tanh`, let the rate rise to about 5e-4. The means then ran away (mean |u| 100–370), so every iteration stopped after 2 minibatches. A bound on |u| past 2.5 held the means, but reward stayed near −0.4 at 4,000 iterations, against 1.1 without early stopping. At 30 epochs, early stopping cuts the reuse that buys the samples-to-skill above.
  - **What didn't help:** 256 robots per iteration (more samples to the gate on quad-servo: 1.8–3.7M) and 256 robots with a 6-step horizon (3 of 3 seeds past 4.1M); no entropy bonus (no better than 0.004).
- **Physics is MuJoCo's own batch API** (`mjb_makeBatch` with one `mjData` per thread, not per robot), with friction, link masses and servo gains expanded per robot (`mjb_expand`). Each robot's state row keeps its warm-start, and results are bit-identical at any thread count. This answers the memory-contention finding (32 concurrent 0.9 MB `mjData` cost 3× their work): there are only as many `mjData` as threads, so `<size memory>` doesn't need trimming.
- **`backend: "simd"` opts a job into Forge's SIMD engine** (`physics.rs`). The model is lowered once by `forge-ir`; when it's in the subset, every environment (training, gates and the final checks) steps on `forge_sim::RowBatch`, which reads and writes the same state rows, takes the same `expand` tables and rethreads like `Batch`, and the run says "Stepping physics on Forge's SIMD engine". When it isn't, the job steps on C MuJoCo and the status line carries every refusal reason. Without the option nothing changes: the C batch path is untouched. `tests/simd_backend.rs` steps randomized robots on both engines with the same actions and finds the same observations and rewards (within 1e-4 in f32).
- **`backend: "metal"` opts a job into Forge's Metal engine** the same way: every environment steps on `forge_sim::MetalBatch` (same rows, same `expand` tables; `rethread` does nothing) and the run says "Stepping physics on Forge's Metal engine (Apple M5 Pro)". The engine must first pass its on-device qualification vectors (below). When the model is outside the subset, the Metal engine refuses it, the GPU fails qualification, or there is no Metal device (any OS but macOS), the job steps on C MuJoCo and the status line says why ("Forge's Metal engine can't step this job: …"). A PPO job the engine admits trains in the GPU loop (below); other jobs learn on the CPU with physics on Metal. `tests/simd_backend.rs` checks the Metal engine against C MuJoCo the same way (within 1e-3 in f32 over 80 control steps of a randomized walk).
- **`backend: "wgpu"`** opts a job into Forge's WGSL engine the same way (`WgslBatch`, "Stepping physics on Forge's WGSL engine (Apple M5 Pro via Metal)"), and falls back to C MuJoCo with the reason when the model is refused or the GPU fails qualification. At 64 robots it's slower than C MuJoCo (latency-bound, below); it exists so Windows and Linux GPUs can step jobs, and it's the path a browser tab takes.
- **Model-free core:** `forge-train` builds without MuJoCo (`default-features = false`) for the browser: `Robot` holds a `ModelRef` (MuJoCo's `Model` natively, `host::HostModel` in WASM), its layout is `forge_sim::Offsets` from `RowMap`, `robot_load.rs` is the native loader and settle, and `physics_host.rs` replaces `physics.rs` with the WGSL engine on a JavaScript backend. `RowMap`, `WorldParams` and `forge_ir::lower` read any `forge_ir::Source`.
- **The learner:** on macOS, matrix products go to Accelerate's `cblas_sgemm`, which runs on the M-series matrix unit and measured 20× a NEON core (640 vs 30 GMAC/s on the 384 × 256 × 128 layer). Elsewhere `kernels/rows.rs` is portable, cache-friendly row kernels (FMA on aarch64, AVX2 + FMA detected at runtime on x86-64) split across a spin-then-park thread pool (`pool.rs`). `FORGE_PORTABLE_MATH=1` forces the portable path on a Mac. ELU uses a vectorizable polynomial `exp`; exported actions use the exact `expm1`.
- **Row blocks** (`blocks.rs`): a minibatch step splits its rows into blocks of about 96 (at most 8, fixed by the batch size, never by the thread count) and runs every block of both heads at once on the learner's own pool (half the cores, at most one thread per block). Each block does its whole forward and backward pass with serial matrix products and writes its own partial gradients; a second pass sums the partials in block order and takes the squared norm per 1024-value chunk, and a third applies the clip and Adam span by span (`AdamStep`). Refreshing the rollout's log-probabilities and values before learning runs on the same blocks. Results are bit-identical between runs and at any learner thread count. `update_tests.rs` checks every step against the whole-batch learner it replaced (one `policy_gradient` and `value_gradient` over all rows, `clip_gradient`, `Adam::step`, the log-std clamp) from the same parameters and Adam state, with an input mask and log-std at the floor and the cap: KL the same to 1e-6, the same learning rate, gradients within 1e-5 of their largest and parameters within 1% of the step size, on Accelerate and the portable kernels. Run free, two learners part after about a dozen steps, as any rounding does in this chaotic update, so compare learners step by step or over many seeds, never one free run. Why it pays: the matrix unit is shared, so one thread got 490–700 GMAC/s on 96-row products and eight threads together 1.0–1.3 TMAC/s, while everything around the products (bias and ELU, slope and bias-gradient passes, the norm, Adam) scales with cores. The squared norm keeps 16 running sums per chunk, because a single f32 sum is a serial chain of adds.
- **Measured on the M5 Pro** (quad-servo, 64 robots, 60 iterations, `train.py` was about 21–25K steps/s): 84K steps/s on a quiet machine, 44–48K under heavy load from other sessions (the F1 gate measured 43.7K at a load average of 23). The portable learner, forced on a Mac, ran at 24–26K under that load. Per iteration: physics about 10 ms, gradient about 7 ms, inference about 1.3 ms. These are F1's numbers, at 5 epochs in turn.
- **Measured for F2** (every number names its load average; other sessions kept the machine busy): at 1024 robots (5 epochs, overlapped) 140.7K steps/s at load 7.7, 63.7K at load 32 and 25.9K at load 46, against 14.4K for F1's in-turn PPO at load 48. At 64 robots the 30-epoch learner is the bottleneck: 30.5K steps/s at load 9.6 (per iteration about 50 ms learning, 120 minibatch steps of 384 rows, against 12 ms collecting), 14–16K at load 34–48. Time-to-skill on quad-servo seed 0 at load 34: 32 s (460K steps), against `train.py`'s 70.6 s (1.08M steps) at load 15. `train.py`'s time-to-skill on quad-servo over 5 seeds at load 11–17: 34.5, 50.3, 70.6, 452.8 s and one seed past 20 minutes.
- **Measured after row blocks** (quad-servo, the F1 job: 64 robots, 60 iterations): 54.8K steps/s at load 4.5–5.4, against 35.0K for the two-thread learner on the same machine minutes apart; one minibatch step 0.18–0.20 ms against 0.32 ms (`learner_bench`); learning about 28 ms per iteration against 44 ms, while collecting takes about 12 ms. Refreshing the rollout fell from 1.1 to 0.35 ms. At 1024 robots, 157K steps/s at load 4.8. The portable learner forced on a Mac: 16.6K against 11.2K at load 6.6–6.9. The F1 gate then measured 52.2K at load 4.9–5.3 (it had measured 34.7K at load 6.2 before), with Forge needing 154K–461K samples to the walk gate on all 10 seeds; the F2 gate measured 152.4K at 1024 robots at load 6.3 and time-to-skill 9.83× faster than `train.py`.
- **Off-policy learners** (`sac/`, `algo: "fastsac"` or `"flashsac"`, 256 robots unless `envs` is set): one iteration is one control step of every robot, then 2 updates on a batch of 1024 from a replay buffer of 262,144 transitions (raw observations, normalized when sampled; a timeout stores the observation before the reset and keeps bootstrapping, a fall cuts it). Both are SAC with twin categorical critics (101 atoms, cross-entropy against the projected target), a tanh-squashed Gaussian actor with a bounded `log_std`, and an automatically tuned temperature; they differ as their papers do:
  - **FastSAC** (Seo et al. 2025): critics 256-256 with LayerNorm and ReLU, the target averages the two critics, γ 0.97, τ 0.1, support −5…20, Adam β₂ 0.95 with weight decay 0.001, temperature from 0.001 toward a target entropy of 0, σ at most 1.
  - **FlashSAC** (Kim et al. 2026): critics 256-256 with RMSNorm whose weight vectors are projected back to unit norm after every step, the lower of the two critics in the target, rewards divided by the running return scale onto a −5…5 support, τ 0.01, actor every second update, learning rate cosine-decayed 3e-4 → 1.5e-4 over 100K updates, temperature from 0.01 toward the entropy of σ = 0.15, and exploration noise held for a Zeta(2)-distributed number of steps (at most 16). Its residual blocks and batch norm are left out: a plain normalized stack on the CPU.
  - The actor stays an ELU MLP so it exports like PPO's; its second head (`log_std`) is dropped on export. Gradients for LayerNorm, RMSNorm, the categorical critic and the squashed actor are hand-derived and checked against finite differences (`sac/dense_tests.rs`, `sac/actor_tests.rs`).
  - **They lose to PPO on time-to-skill here**, so PPO stays the default: an update costs about 5 ms on the matrix unit with these sizes, and a CPU learner can't afford the update counts the papers run on a GPU, while Forge's PPO reaches the walk gate in a few hundred thousand to a few million samples.
- **The Adam test vector** (`adam_vector.rs`): a 12-64-32-4 ELU MLP with random biases, 50 Adam steps (lr 1e-3) on the mean squared error of 64 random targets, using the same `Mlp` forward and backward and `Adam` as training. `verify/forge/adam_check.py` replays it in torch: worst difference 1.2e-7.
- **Delayed servos start primed.** Catalog servos carry MuJoCo's native actuator `delay` (§8d); an empty control history makes every reset kick the robot. `settle()` fills each delayed actuator's history with `ctrlDefault` (`Data::hold_delayed_controls`, `mj_initCtrlHistory` with `nsample` samples one timestep apart ending now) once before the settling second and again after the clock is reset to 0, as `train.py`'s `hold_delayed_controls` does. Batch rows hold `mjSTATE_INTEGRATION`, which includes the history, so every episode reset restores it. `forge-id` primes its start row with the experiment's first control. `tests/delayed_servo.rs` checks that a robot reset from the start row moves exactly like one without delay, and that an unprimed history would kick it.
- **Gate checks run beside training.** When `gateEvery` is due, the policy and normalizer are copied and checked on 32 clean robots on a scoped thread with at most 6 physics threads (every core when the job learns on the GPU loop, which leaves the CPU idle: 0.09 s against 0.14 s for biped-servo), while training goes on. The copy is the exported policy: its weights rounded to 7 decimals as `policy.json` stores them, so any replay of `policy.json` sees exactly what the gate saw. The `gate` event carries the iteration and steps of the copy it checked; training stops once a passing result comes back, and the run saves that checked copy (`policy.json`, `resume.json`, and the `done` event's `gate` and `steps`), not the weights a few iterations later. Before, the saved policy had trained on past the check, and on the biped a policy the gate passed at 29 or more of 32 replayed at 24 of 32; rounding alone moved another from 29 to 26, because seeds near the speed bar flip on a change of 1e-7. Gatekeeper's time-to-skill doesn't read these: it times the whole run on its own clock and replays the saved policy in C MuJoCo (§0k). `train.py` checks in line, so its gate time counts against it.
- **Physics threads tune themselves** (`threads.rs`) unless `threads` is set: every 240 control steps one trial of 24 steps runs on a neighbouring thread count (all cores, ¾, ½, ⅓, ¼), and the count moves when the trial is 3% faster. `Batch::rethread` rebuilds the MuJoCo batch with the state rows and per-robot model fields, so a run is identical at any thread count (tested). On a loaded machine fewer threads win by 2× (quad-servo, 64 robots, load 47: 1.9 ms per control step on 10 threads, 4.1 ms on 18).
- **The policy view** (`deployed.rs`): export, ONNX, gates and the final checks take a `Deployed` actor (an ELU MLP, its weights and a `squash`), so every learner exports the same `policy.json`. Off-policy actors are tanh-squashed: `policy.json` then carries `"squash": "tanh"`, which the app's `act()` applies before clipping, and the ONNX graph gains a `Tanh` node.
- **Platform code is isolated** in `platform.rs` (signals, macOS thread QoS), `kernels/accelerate.rs` and the MuJoCo fetch.

### forge-train: the GPU loop (F5)

- **Physics, policy and learner in one GPU buffer** (`gpu_loop/`). A PPO job with `backend: "metal"` that the Metal engine admits trains without leaving the GPU: the state rows stay in the Metal engine's `io` buffer for the whole run, and per control step the GPU normalizes the observations, runs the actor and critic, samples the actions, writes the controls, steps the physics, computes the reward, falls and timeouts, resets finished robots, observes and updates the normalizer; then it computes GAE, standardizes the advantages and runs every PPO minibatch (gather, forward, clipped surrogate and value heads, backward, the gradient norm, Adam, the `log_std` cap and the KL-adaptive learning rate). The CPU encodes two command buffers per iteration (the rollout, then the update) and commits them back to back, waiting once (`Gpu::run_chain`), shuffles each epoch's row order with the same random stream as the CPU learner, and reads back the rewards, episode ends, normalizer and weights for progress, gates and exports. Domain randomization is drawn once on the CPU (`randomize.rs`, as `Envs` does) and uploaded with the rows; resets, pushes and action noise draw from per-robot xoshiro128** streams on the GPU, so a GPU run is comparable to a CPU run, not identical; a seed replays exactly. In `progress`, `physics` is the rollout's GPU time (physics, observations, rewards, the policy and sampling) and `gradient` the update's; `observe`, `reward` and `inference` stay 0.
- **The task is IR, not a hand-written shader.** `forge_ir::task::Task` is plain data: the actuated joints (qpos and dof addresses, actuator, default pose, control range), the control defaults, the root, the action scale, the command, `z0`, the episode length, reset noise, falls and pushes, the observation layout, and the reward and fall test as `forge_reward::code::Code`, a straight-line program of scalar ops. `forge-reward` lowers any RewardLang program to `Code` (`Program::lower`, which inlines functions, unrolls vectors and keeps every term's NaN guard; `state.bodies` is refused), and the stand and walk rewards and the fall test are RewardLang programs (`programs.rs`), so the GPU computes exactly what the interpreter does (`tests/lowering.rs` checks 400 states to 1e-12 in f64). `forge-sim/src/metal/task.rs` emits the task's MSL (constants, `task_reward`, `task_fell`, the observation) after the physics source, and `shaders/task.metal` holds the fixed kernels (`task_reset`, `task_act`, `task_after`, `task_observe`). Observations and rewards are f32 read from the double-float state; resets and controls write double-float.
- **The learner** (`shaders/gemm.metal`, `rollout.metal`, `update.metal`) is f32 and uses the CPU learner's layout and formulas: the same parameter vector (actor, critic, `log_std`), the same orthogonal initialization from the same seed, the same loss, clip, entropy and value terms, Adam, gradient clipping and learning-rate rule. Matrix products are tiled `simdgroup_float8x8` GEMMs (32 × 32 tiles of 4 SIMD groups); a layer's bias rides along as an extra row of ones, because the bias follows the weights in the parameter vector; weight gradients split the rows into slices of 128 and sum the slices in a second kernel, so every reduction has a fixed order and a run is deterministic. The actor and critic share each dispatch. Tiles of 64 were 3.5× slower and tiles of 16 or a K step of 32 slower too; running the update on a second queue beside the next rollout (the CPU learner's one-rollout overlap) didn't shorten an iteration, because the physics already keeps the GPU busy.
- **Qualification before training:** the Metal engine's admission (`forge_sim::metal::admission`, used by every `backend: "metal"` job) runs double-float vectors (add, subtract, multiply, divide, square root, sine against f64 to 1e-12) and 12 control steps of 8 robots against C MuJoCo's batch (qpos and qvel to 1e-5 relative); a mismatch refuses the GPU with the reason ("Apple M5 Pro failed its qualification vectors: qvel[4] of robot 4 is off from C MuJoCo by 2.0e0 after 12 control steps…") and the job steps on C MuJoCo. `tests/qualification.rs` plants a 2% damping table and a 0.1% gravity error in the kernel and checks both fall back. The GPU loop then runs one PPO minibatch of 256 random rows on the device against the CPU learner's `policy_gradient` and `value_gradient`: the gradients must agree to 1e-3 of their largest value and the Adam step to 1e-2 of its largest move, or the job learns on the CPU with the reason.
- **Acceptance replay in C MuJoCo:** every gate and the final checks of a GPU-loop job evaluate in C MuJoCo (the trainer loads a second `Robot` on the C engine), so time-to-skill is measured to a passing C replay. `tests/acceptance_replay.rs` (run with the `acceptance_replay` filter; it trains, so plain `cargo test` skips its work) holds L4 and L5: L4 runs a trained walking policy's stochastic rollouts on the GPU and on C MuJoCo's `Envs` (4096 robots, 160 control steps, same randomization) and compares six per-robot statistics (reward, falls, forward speed, upright, joint speed, action size) within four combined standard errors plus 1% of the C value; L5 trains quad-servo here and replays the exported `policy.json` in C (32 seeds, 8 s, at least 0.2 m/s without falling, 29 of 32) and in MuJoCo's WASM build through the app's `observe` and `act` (`tools/forge/wasm-replay.mjs`, which loads `src/forge/walkReplay.ts` through Vite: the start is `forgeStart.ts`'s settle, 32 yaws, the same pass rule). The canary `canary_bad_physics_replay_fails` trains on a kernel whose knee axes are reversed (past qualification, as a bad GPU that slipped through would be), checks the policy passes on that physics, and must fail the C replay.
- **PPO from 2048 robots up takes its horizon from the robot's action count: enough control steps that every iteration holds at least 640 samples per actuated joint, from 2 to 4 steps, with 5 epochs of 16 minibatches and a KL target of 0.1** (`setup.rs`, `large_horizon`; below 2048 robots, the CPU learner's `Hyper::for_envs`). At 4096 robots that's 2 steps for biped-servo (8 joints) and quad-servo (12), 3 for hexapod (18). The policy gradient sums one score term per action dimension, so its noise grows with the joint count and a robot with more joints needs more samples per update; a fixed 640 per joint is the line between the fixture robots that learn at 2 steps and the one that doesn't. Time-to-skill is iterations to a passing gate times seconds per iteration, and an iteration is bound by physics (about 27 ms per control step for 4096 quad-servos at load 17), so the batch has to shrink and each update has to move further. Iterations to the walk gate (gates every 50, C replay, load 15–20):
  - The CPU learner's settings at 4096 robots (24 steps, 5 epochs of 4, KL 0.01): quad-servo seed 0 passed at 100 iterations (9.8M samples, 73 s) on the GPU loop and at 200 (19.7M, 167 s) with the CPU learner's one-rollout overlap.
  - At KL 0.01 shorter horizons never walked: 2 and 8 steps stood still for 300–400 iterations. 8 steps at KL 0.03 passed at 50 (1.6M, 12.2 s); 4 steps at KL 0.1 passed at 50 (0.8M, 6.5 s) on 4 of 5 seeds; KL 0.2 stood still.
  - hexapod needs more updates per sample: at 4 steps and KL 0.1, 5 epochs of 4 minibatches hadn't passed after 400 iterations, 10 epochs of 8 passed at 100 on 4 of 5 seeds, 5 epochs of 16 at 100–250. Its 2-step runs walked and then collapsed (any KL from 0.05 to 0.1), so the horizon stays at 4 although quad-servo and biped-servo pass faster at 2 (quad-servo 4.3–8.7 s on all 5 seeds, biped-servo 3.2–3.3 s on 4 of 5).
  - These settings suit the plain walk task, not command-conditioned walking. With the Kit's Velocity tracking job (resampled commands, delays, biases), biped-servo at 4096 robots and 4 steps never learned commanded speed in 6–8 minutes, while 1024 robots on the small-batch settings above passed every Kit Arena run in 8 (§8i). The Kit sends `gpuEnvs: 1024`.
  - With 4 steps on every robot, the iteration the walk gate passed at, seeds 0–4: quad-servo collapsed after 50 (still standing at 150), 100, 50, 50, 50; hexapod 200, 250, 100, 150, 150; biped-servo 50, 100, 50, 50, 100. The F5 gate then measured 3.51× on quad-servo, 12.10× on hexapod and 2.93× on biped-servo, below its 5× on two robots, while the CPU learner (F2) reached 9.52×, 44.06× and 5.51×. The CPU learner wasn't learning better per sample: the gate checks every 50 iterations, so a run costs at least 50 iterations, and at 4 steps a biped iteration took 95 ms (68 ms of physics, 27 ms of update) against the CPU learner's 30–60 ms.
  - At 2 steps a biped iteration takes 51 ms (34 ms of physics, 16–17 ms of update) and a quad-servo one about 70 ms. Over seeds 0–9 at 4096 robots and KL 0.1 (wall clock from launch to exit, replayed in C, load 4–6): biped-servo's own gate passed at 50 iterations on 8 of 10 seeds (2.8–3.2 s), and the C replay of the saved policy agreed on 6 (the other two are the misses the gate copy now fixes, above); quad-servo passed at 50 on 4 of 10 (4.2–4.8 s), at 100 on 5 (7.3–8.4 s) and never on one. hexapod at 2 steps walked and then collapsed (seed 0 still hadn't passed after 6 minutes); at 3 steps it passed at 150 and 200 iterations on 3 of 5 seeds (seed 1 passed its own gate at 300 and replayed at 27 of 32, seed 4 needed 550), a median of 31 s, against 28.6 s at 4.
  - What didn't help at 2 steps: 3 epochs (seeds 0–4: biped-servo passed at 50 on 1 of 5, quad-servo never passed on 2), 8 minibatches of 1024 rows (seeds 0–4: biped-servo 1 of 5 at 50), KL 0.15 (seeds 5–9: quad-servo passed on 1 of 5), KL 0.07 (seeds 5–9: quad-servo 2 of 5, biped-servo 2 of 5 at 50). 8 epochs was the most reliable (seeds 5–9: biped-servo 5 of 5 at 50, quad-servo 5 of 5 by 100), but its 26 ms update made the biped's 50 iterations 3.3 s. 1 step (seeds 0–4): biped-servo passed at 50 on 1 seed and at 100 on 3 (3.7 s), quad-servo never.
  - Fewer, larger dispatches in the update don't shorten it: deferring every layer's slice sums into one dispatch with the head sums, and running each layer's weight and input gradients in one dispatch (21 dispatches per minibatch down to 14), left the update at 16–17 ms. It's bound by the matrix products, about 1.5 TFLOPS on 512-row minibatches, so its cost follows epochs times rows.
- **Squashed actions** (`squash: "tanh"`, the CPU learner's option, §8g above): the task kernel acts on `tanh(u)` and the rollout keeps `u`, so the ratio and KL stay Gaussian; the policy head adds the squash's entropy term (`2·ent_coef·tanh u` per row on the mean, times `u − μ` on `log_std`, scaled by 1/rows as every term is); `logStdMin` floors `log_std` at the start and after every Adam step; exports carry `"squash": "tanh"`. `task.rs` sets the task's squash from the job. The learner's qualification minibatch runs at an entropy coefficient of 0.5 on both sides, so the entropy and squash terms stand well above its 1e-3 tolerance: a CPU reference without the squash term is off by 0.66 and the job falls back. `tests/gpu_loop.rs` trains on the GPU with and without the squash. The clip path is unchanged bit for bit (quad-servo seed 2 passes the gate at the same iteration with the same 29 of 32).
- **Measured on the M5 Pro** (quad-servo, 4096 robots): the F5 gate measured 122.3K steps/s over 10 iterations (load 5.9) and time-to-skill 7.16× `train.py` (quad-servo 7.16×, hexapod 12.0×, biped-servo 3.72×; load 6.3 before, 4.8 after); at load 17 a 10-iteration run gave 110K. An iteration at a 4-step horizon is about 105–130 ms of rollout (the physics is about 27 ms per control step; the policy, rewards and resets add about 1 ms) and 33 ms of update. For comparison, the CPU learner with Metal physics at 4096 robots and its own settings ran at 120K steps/s at load 14: at this batch size the physics bounds throughput either way, and what the GPU loop buys is an update short enough to run every 4 control steps.
- **Training conditions on the GPU** (`forge_ir::task::Conditions`, the CPU's `conditions.rs` line for line): `commands`, `delaySteps`, `encoderBias` and `imuBias` run in the task kernels. Each robot's `env` block (`Task::env_width`) holds its action, last action, command, encoder offsets, IMU roll and pitch, and a ring of its last `delaySteps[1] + 1` actions. Its four counters are the steps taken, the next push, the next command draw and its delay. A reset draws the command (still with probability `stillShare`, else uniform in the ranges, next draw after `resampleS / controlDt` steps), then the delay, the encoder offsets and the mount bias, from the robot's own stream after the reset noise and yaw, as `Conditions::reset` does. `task_act` pushes the policy's action into the ring and drives the servos from the delayed one, while `last_action` and the reward keep the policy's own. Only `task_observe` sees the offsets and the tilted gravity; rewards and falls read the true state. `gpu_loop/task_tests.rs` checks a two-step delay against the CPU's `a_delay_replays_older_actions` sequence, commands drawn in their ranges and redrawn, and biases that reach only the observation.
- **What the GPU loop doesn't take** (the job learns on the CPU with the reason, still stepping on Metal): algorithms other than PPO, and rewards that read `state.bodies`. `actorLinvel: false`, `warmStart`, `logStdMin`, `squash`, custom rewards, `fallResets`, `pushes`, `resetNoise`, `standHeight` and `episodeS` run on the GPU, with the training conditions above.

### Gradients, batched sysid and design sweeps (F7)

- **Exact forward, smoothed backward** (`forge-sim/src/grad/`). The forward is always the exact engine: `step_with_jacobian` and `Tracer::advance` run the SIMD engine's own `forward_block` and `implicit_step` in the same order as `step`, so a run with gradients is bit-identical to one without (`forward_stays_exact_with_gradients`). Tangents come from a surrogate of one physics step written once, generic over a `Real` scalar (`f64` or `Dual<16>`, forward-mode duals of 16 directions; more directions take more passes): kinematics, `comPos`, the dense mass matrix, RNE, damping, actuation with its clips, frictionloss, limit and contact rows, the implicitfast step and the free joint's quaternion integration, with `spatial.rs`'s algebra shared with the engine through the `Num` trait.
- **The constraint solve isn't differentiated through Newton's iterations.** At each physics step the surrogate takes the exact engine's contacts (each contact becomes a material point on its body, so its distance and Jacobian move with the joints) and its solution, polishes it with a dense Newton solve, then takes one Newton step in dual numbers: the tangent is the implicit-function derivative of the solution, `−H⁻¹ ∂g`. Off contact and with smoothing 0 that's the derivative of MuJoCo's own piecewise-quadratic problem; `Smooth { force }` replaces each contact row's one-sided quadratic with `½ D (w·softplus(−x/w))²` (`w` is `force` newtons in the row's units), so the active set blends over about that force. Frictionloss and limit rows stay exact, which keeps gradients off contact exact. The tangents are carried along the exact trajectory: after each physics step the real parts are reset to the engine's state.
- **Inputs** (`Wrt`): `qpos`, `qvel` and `ctrl` of a lane, and per-world parameters: body mass, servo stiffness (`gainprm[0]` with `biasprm[1] = −kp`), damping gain (`kv`), gear, joint damping, armature and frictionloss. Refused with the reason: actuators with `delay` (the control history isn't carried) and a `solimp` power other than 1 or 2.
- **Per-world tables** now carry gear (`actuator_gear` is expandable on the SIMD, Metal and WGSL engines; Metal and WGSL read `TGEAR` instead of a constant) and, on the SIMD engine only, damping, armature and frictionloss (`Tables::set_dofs`), which sysid varies. `Batch`-style `expand` still refuses the SIMD-only fields.
- **Tests** (all on the fixture robots quad-servo, hexapod and biped-servo, in f64, on states drawn at random): `gradient_matches_fd_off_contact` compares the Jacobian of a whole control step (10 physics steps) against central differences of the exact engine with the solver tolerance tightened to 1e-12, for every state, control and parameter input (146 inputs on quad-servo), on 16 airborne states per robot (random orientation, joints up to 0.05 rad past their limits, so limit rows fire), each column within 1%. `gradient_matches_fd_on_contact` takes 16 contact states per robot from random walks and checks the smoothed gradient of one physics step against differences of the smoothed step and the unsmoothed gradient against differences of the exact step, each column within 10%. A column whose forward and backward differences disagree straddles a kink (a force clip, a frictionloss zone, a limit switching on) and is judged against the nearer one-sided difference; the report counts them. `gradient_matches_fd_along_a_trajectory` checks parameter sensitivities of hoisted robots over 200 control steps. The canary `canary_wrong_gradient_fails` scales the velocity columns by 1.02 and must fail the off-contact check.
- **Measured** (worst column error per state; median, p90, max over 16 states): off contact, a control step: quad-servo 5.0e-5, 1.7e-4, 2.0e-4; hexapod 1.7e-4, 3.1e-4, 4.8e-4; biped-servo 1.5e-5, 7.9e-5, 8.3e-3 (5 of 1696 columns judged one-sided). On contact, one physics step, smoothed (0.05 N) against the smoothed step: quad-servo 1.5e-4, 5.7e-4, 1.4e-2; hexapod 1.4e-4, 2.5e-4, 3.2e-4; biped-servo 7.0e-5, 2.3e-4, 3.1e-4. Unsmoothed against the exact step: quad-servo 9.0e-5, 5.3e-4, 6.0e-2; hexapod 1.2e-4, 1.7e-4, 2.0e-4; biped-servo 4.9e-5, 7.6e-5, 1.0e-4. Sensitivities over 200 control steps: worst 4.3e-6, 3.5e-6 and 2.9e-7. Parameter differences use a step of 1e-5 of the value: at 1e-6 the f64 rounding of the state is 1e-3 of the column.
- **Cost:** a full control-step Jacobian (`cargo run --release -p forge-sim --example grad_bench -- <model.xml>`) takes 2.6–2.8 ms per robot on one core for quad-servo (49 directions) and about 5 ms for hexapod (67). Before the Newton polish stopped on the step size it took 36 ms: the gradient-norm test never fired in f64 and every solve ran to its iteration cap.
- **Batched Jacobian sysid** (`forge_id::identify_worlds`): Levenberg-Marquardt in log space on many worlds at once, each with its own parameters, where every residual column comes from `Tracer` sensitivities instead of finite differences: one forward pass per 16 parameters gives the whole trajectory's derivative. Worlds run four to a SIMD block and blocks and parameter chunks in parallel. The fit grows its window (1/32, 1/16, … of the recording, then all of it), because the full 24 s residual has local minima where a fit from 15–25% off stops. `batched_recovers_planted` plants stiffness, damping gain and frictionloss on all 12 servos of a hoisted quad-servo, 15–25% off and different on each of 16 worlds (576 parameters), records 24 s of multisine through a 4096-count encoder at 500 Hz in C MuJoCo, and recovers every one: stiffness and damping gain within 0.19%, frictionloss within 2.37% (166 s at load 6–10). Armature with stiffness and damping gain together isn't identifiable on this robot (the servo's reflected inertia dominates the leg's, so scaling all three together barely changes the motion; the fit stopped 6–10% off), and link masses aren't either; the test identifies what the robot can show.
- **SHAC** (`algo: "shac"`, `forge-train/src/shac/`): Xu et al.'s short-horizon actor-critic. Physics runs on the job's engine (`backend: "metal"` steps on the Metal engine) while, for the same control step, CPU threads replay it on the SIMD engine from the same rows and per-world tables and take the Jacobian of the control step (`qpos`, `qvel` and the actuated controls, `Smooth { force: 0.05 }`). The observation and the reward (the job's RewardLang program lowered to `Code`, the same the GPU loop runs) are differentiated with duals, the actor and critic are the PPO learner's ELU MLPs (`Mlp::input_gradient` gives the observation gradient), and the backward sweep runs through every step of the horizon with the reparameterized Gaussian noise held fixed, cutting at falls and bootstrapping the target critic at timeouts and at the horizon. Settings are the paper's Ant settings: 64 robots, 32 steps, γ 0.99, TD(λ 0.95) targets, actor and critic at 2e-3, Adam β₂ 0.95, 16 critic epochs of 4 batches, target critic kept at 0.2, gradients clipped to 1, `log_std` from −1 within [−2.5, 0]. Every gate and the final checks replay in C MuJoCo, as the GPU loop's do. Jobs with servo delays, `commands`, encoder or IMU bias are refused with the reason.
- **SHAC's gradient is checked** by `shac_actor_gradient_matches_fd` (forge-train): on the three fixture robots, the analytic derivative of the horizon's objective (rewards, the bootstrap value and the policy's dependence on the state through the observations) along a random direction in all actor parameters matches central differences of whole rollouts within 1% (0.0–0.8% at 1, 3 steps, on contact, with and without the critic). With steps of 1e-3 the same differences are off by 100× from the local slope: the exact return is rough at that scale (contacts making and breaking), which is what smoothing is for.
- **SHAC doesn't learn the walk skill here.** At 64 robots an iteration takes about 1 s (2.0–2.3K steps/s): the Metal engine's control step at 64 worlds is latency-bound at about 29 ms, and the Jacobians (about 11 ms per block of four robots per control step) run beside it. Quad-servo learned to stand (reward 1.41 → 1.56) but never walked: 0 of 32 seeds and a mean C-replay speed under 0.03 m/s at every gate over 4–10 minutes (650 iterations, 1.3M steps), with contact smoothing of 0.05, 1 and 8 N; 256 robots at a 16-step horizon and 8 N reached 0.13 m/s at iteration 25 and fell back to 0.01. The time-to-skill job (walk at 0.25 m/s, gates every 50 iterations, seed 0) on the defaults passed no gate on any robot: quad-servo in 10 minutes (650 iterations), biped-servo in 10 and hexapod in 20 (900 iterations), the best gate 0.11 m/s; a run that never passes counts as the 60-minute budget, so the F7 gate's speedup would come out at about 0.013× `train.py` (quad-servo 0.013×, hexapod 0.096×, biped-servo 0.005×). Even a SHAC that walked at its first gate couldn't reach 15×: 50 iterations of 32 control steps at 29 ms is 46 s, about 1× on quad-servo, and at a 4-step horizon 6 s, the same bound the GPU loop's PPO already meets (about 8× on quad-servo, 3× on biped-servo). The limits are the gate's cadence in iterations, the Metal engine's latency per control step at small batches, and first-order gradients that don't find a gait through stiff contact; the plan turns F7's learner on by default only at 3× after C replay, so PPO stays the default.
- **Design sweeps:** `design_sweep_varies_mass_and_gear_per_world` gives 12 worlds their own link masses (0.7–1.4×) and gears (0.6–1.5×) in one batch on the SIMD, Metal and WGSL engines and checks each world against a single-world C MuJoCo run with the same fields (SIMD within 1e-8, GPUs within 1e-5 relative) and against a single-world SIMD run bit for bit.

### forge-ir: the subset Forge's own engines simulate

- `forge_ir::lower(&Model)` reads the compiled model (after `mj_setConst`, so `dampratio`, `invweight0` and mesh hulls are MuJoCo's own) and returns a `Kernel` or a `Refusal` listing every reason ("joint hip is a ball joint; it uses the PGS solver, and Forge runs Newton only"). Nothing outside the subset is approximated.
- **In the subset:** free, hinge and slide joints; position, velocity and motor actuators on hinge and slide joints, with `delay` (zero-order hold or linear history); armature, damping, frictionloss and limits (with margins); plane contacts against convex mesh hulls, spheres, capsules, cylinders and boxes, condim 1 or 3, pyramidal cones, any solref, solimp, margin, gap, priority and solmix; the Newton solver; the implicitfast integrator; warmstart, refsafe and clampctrl on or off.
- **Refused:** other integrators, solvers and elliptic cones; noslip; fluid forces; ball joints; joint springs and polynomial damping; actuator activations, affine, muscle, DC-motor and PID gains, cubic delays, actuator damping and armature, joint-level force limits; tendons, equalities, flexes, sensors, plugins, mocap bodies, explicit pairs and exclusions, gravity compensation, height fields; disabled constraints, contacts, limits, frictionloss, damping, gravity or actuation; enable flags other than energy (4.0's speculative contacts included, and any flag newer than `forge-ir`); condim 4 and 6; surface velocity and adhesion; contacts between two moving bodies (no hull-hull yet); ellipsoid and SDF contacts; free bodies with no jointed children (MuJoCo integrates those with a gyroscopic 6×6 solve); simple bodies.
- Its tests build their models in code (`tests/common/mod.rs`) and are part of the F3 gate.

### forge-sim: the SIMD engine

- **Layout:** structure of arrays across worlds. Every quantity is a `V`, four `f64` lanes (`lanes.rs`), so one lane is one robot and the four lanes run the same instructions; LLVM lowers the lane loops to NEON on aarch64 and to SSE2 on x86-64, which `cargo check --target x86_64-pc-windows-msvc` with `FORGE_CHECK_ONLY=1` keeps compiling. AVX2 needs every stage compiled a second time under `#[target_feature]` and picked at run time; that isn't done. f64 throughout, because MuJoCo's Newton tolerance of 1e-8 needs it. The engine is bound by moving data rather than by arithmetic: 8 lanes ran slower than 4, and 2 lanes about the same.
- **Pipeline, in MuJoCo's order and with its formulas:** kinematics, `comPos`, CRB, the tree LDL factorisation (`sparse.rs`, a precompiled update list), collision, constraint assembly (frictionloss rows, limit rows, pyramidal contact rows with MuJoCo's `diagApprox`, impedance and regularisation), `comVel`, passive damping, RNE, actuation with delay history, `qacc_smooth`, MuJoCo's warmstart choice, the Newton solve and implicitfast.
- **Fixed slots, live rows:** each contact pair owns `max_contacts` slots and each slot its constraint rows, so every lane has the same structure; a row is live when any lane uses it, and every solver loop walks only live rows (that halved the solver's time). An inactive lane in a live row gets a zero Jacobian and a reference of −1, so it is always satisfied and adds exactly nothing.
- **Lockstep Newton:** the lanes iterate together; a finished lane is frozen with selects, never stepped again, so a world's result doesn't depend on its neighbours (`--batch-identity` checks this bit for bit at 1, 3 and 8 threads). The line search is MuJoCo's own (`search.rs`, `bracket.rs`) run with per-lane masks. The cost: a block iterates as often as its slowest lane (2.6 iterations against MuJoCo's 1.6 per world on the bench). `RowBatch` therefore regroups robots before every control step, sorting them by their last contact count so that robots in the same block need similar work; a robot computes the same result in any lane, so this changes nothing but speed (single-threaded on the bench, 265K to 332K robot-steps per second), and `--batch-identity` compares the regrouped batch with each robot stepped alone.
- **Per-thread scratch:** `State` holds what persists per block (qpos, qvel, ctrl, warmstart, time, delay history, the per-world tables) and is swapped into one `Workspace` per thread for each step, like MuJoCo's one `mjData` per thread. Kinematics, Jacobians and solver scratch for one block of quad-servo take about 200 KB, so keeping them per block put tens of megabytes in play at 1024 robots.
- **Per-world tables** (`tables.rs`): body masses, geom sliding friction, servo gains (`gainprm[0]`, `biasprm[0..3]`) and gears, with C MuJoCo's semantics (masses change, inertias and `subtree_mass` don't; nothing reruns `mj_setConst`), plus joint damping, armature and frictionloss for sysid (F7).
- **What differs from MuJoCo, and why it doesn't matter:** the Newton Hessian is rebuilt and refactored every iteration instead of updated by rank-1 steps; sin and cos are a vector port of musl's kernels (within 5e-16 of libm). Both change results only at rounding level.
- **Parity, measured against C MuJoCo 4.0 on the 200 fuzzed robots of the F3 gate:** worst L0 (xpos, cinert, qfrc_bias) 4.2e-16, L1 (qacc) 8.0e-14, L3 qpos 2.2e-15 and qvel 1.5e-12 after 60 steps; contact counts identical (against 3.17: 4.2e-16, 8.0e-14, 1.3e-15 and 1.7e-12). C MuJoCo 3.17 and 4.0 themselves differ by rounding on the same robots (L0 0, L1 1.4e-14, qpos 1.9e-15, qvel 1.3e-12, the same contacts): 4.0 changed nothing in the subset's formulas, so the engine didn't change with it. The fixture robots stay within 1.3e-9 (qvel) over 2000 steps, where 3.17 and 4.0 already differ by 1.1e-9. `tests/row_batch.rs` checks rows against C MuJoCo's batch with randomized tables, linear and held delays, and every primitive foot.
- **CLI:** `forge-sim --xml <model> --steps N --backend simd|mujoco|metal|wgpu` prints the gate's parity JSON (`single` after `mj_forward`, then qpos and qvel every 25 steps under `ctrl = 0.2 sin(0.01 i)`); `--batch-identity`; `--bench --envs N --seconds S [--threads N]` runs the bench below on any backend (the GPU benches also report `gpuShare`, the fraction of wall time the GPU was busy). `cargo run --release -p forge-sim --example stages -- <model.xml>` times each stage per world-step.
- **The bench workload** is the training path: state rows stepped by `RowBatch` (or C MuJoCo's `Batch` with `--backend mujoco`, same rows, same controls), ten substeps per control step, on a rayon pool with one `Workspace` per thread. Robots reset every 2 s to their start pose plus up to 0.02 rad per joint; controls are sines around the middle of each control range, with amplitude 0, 5, 10 or 15% of the range by robot, so a quarter stand still on all feet and the rest shuffle in place. The sines advance by rotation so writing controls costs almost nothing beside the physics. `contactsPerWorld` reports the average contact count (about 2 on quad-servo).
- **Measured on the M5 Pro** (quad-servo, other sessions kept the load at 8–20): one thread, best of five 2 s runs, 355K robot-steps per second against C MuJoCo's 135K (2.6×); 18 threads and 1024 robots for 30 s, a mean of 2.99M and a slowest second of 2.78M against C MuJoCo's 1.59M and 1.47M (1.9×). The F3 gate measured a mean of 3.35M and a slowest second of 3.21M at load 6–12. Per robot-step on one thread, about 55% is the Newton solve (factorisations, Hessians and line-search evaluations in about equal parts), 12% kinematics, 11% constraint assembly and 6% collision.

### forge-sim: the Metal engine

- **One GPU thread per world, kernels generated per model** (`src/metal/`). `forge-ir`'s `Kernel` becomes MSL source: the model's tables as `constant` arrays and sizes as `#define`s (`tables.rs`, `actuators.rs`, `layout.rs`), followed by the fixed stages in `shaders/` (kinematics, CRB, collision, constraint rows, RNE and actuation, Newton with MuJoCo's line search, implicitfast). Metal compiles it at run time in safe math mode; the first compile of a model takes about 3 s and Metal caches it after that. Per-world state and scratch live in one buffer, blocked by 16 worlds so each scalar of a block is 128 contiguous bytes; threadgroups are 16 threads. `MetalBatch` packs the f64 state rows into the GPU's buffer (rayon), runs every substep of a control step in one dispatch, and unpacks them.
- **Double-float arithmetic** (`shaders/df.metal`): Metal has no f64, and f32 can't meet L0. The gate's floor of 1e-4 at 5e-5 relative allows 5e-9 absolute near zero, and a free robot's gravity torques about its own centre of mass cancel to about 1e-16 in f64 but to about 1e-7 in f32. Every real is a pair of f32 (about 48 bits): additions are Knuth's two-sum without renormalising the low part between terms, products use `fma` for the exact error. Sums run through lazy accumulators that keep only one f32 add on the dependent chain, and long expressions are summed as trees, because the GPU is latency-bound and these chains set the time. Fast math would delete the error terms, so the library is always compiled with `MTLMathMode::Safe`; `tests/metal_df.rs` checks add, subtract, multiply, divide and square root against f64 to 1e-13.
- **Where f32 is enough:** the Newton Hessian, the factorisation of M and the implicitfast matrix are factored in f32 in threadgroup memory (`factor_h`, `solve_h`; the triangular solves also keep their vector there). The Hessian only shapes the search direction: the gradient, costs and line search stay double-float, so Newton still stops on MuJoCo's tolerances (same iteration counts, 1.62 per world-substep on the bench). `qacc_smooth` and the implicit step take one step of iterative refinement against M in double-float. This was 12–15% faster than double-float factorisations; it moves qacc from within 1e-9 of C MuJoCo's to within 7e-5 on the fuzzed robots (1e-6 on the fixtures), still 15 times inside L1, because Newton now stops a little further from the exact optimum. `HESSIAN_DF` in `layout.rs` switches it back. When 16 × (nm + nv) floats don't fit the 32 KB of threadgroup memory (56-DoF robots), the matrix lives in device memory instead.
- **Rows:** contact pairs keep F3's fixed slots, but each world compacts its own live rows (frictionloss, active limits, active contact rows), so it never walks another world's rows. Collision first lists each world's contacts, then the rows are built for every world's first contact together, then its second, so a SIMD group pays for its busiest world's contacts rather than for every pair any of its worlds touches. Jacobian rows are stored densely over all dofs for `J x` (every lane reads the same index, so loads coalesce) and as chain-compact rows for `Jᵀ f` and the Hessian. Data-dependent indices that differ across a SIMD group were the most expensive accesses measured: moving chain dof lists to device memory, a dense `Jᵀ f` and a dense Hessian were all slower.
- **What the time goes to** (`cargo run --release -p forge-sim --example metal_stages -- <model.xml> [envs]`, quad-servo at 4096 worlds, GPU time per substep at load 9): kinematics 0.15 ms, CRB and factor 0.20, collision and rows 0.28, RNE, actuation and `qacc_smooth` 0.29, warmstart 0.14, start 0.12, first Hessian 0.24, the remaining Newton iterations 1.06, implicit about 0, 2.5 ms in all. The engine is bound by latency, not arithmetic: making every df operation a plain f32 operation saved only 15%, and 1024 worlds take 70% as long as 4096. Newton dominates through divergence: a world needs 1.62 iterations per substep on average, but a SIMD group waits for its slowest world (3.8 iterations in groups of 32, which is why blocks are 16). Regrouping worlds by their last contact count and solver work (as `RowBatch` does) doesn't change that, because the iteration count varies from substep to substep.
- **Refused** (on top of `forge-ir`'s refusals, so `backend: "metal"` falls back with the reason): a `solimp` power other than 1 or 2, which would need `pow` in double-float.
- **Parity, measured against C MuJoCo 4.0 on the 200 fuzzed robots of the F4 gate:** worst L0 (xpos, cinert, qfrc_bias) 4.4e-11, L1 (qacc) 6.7e-5, L3 qpos 4.6e-9 and qvel 1.5e-6 after 60 steps, the same as against 3.17 to two digits; contact counts identical. Before the Hessian moved to f32, L1 was 8.0e-10 and L3 qvel 9.2e-12, so L1 is the field the f32 factorisation spends. The 12 fixture robots: L0 8.7e-11, L1 1.1e-6, L3 qpos 1.8e-9 and qvel 5.1e-7. `tests/metal.rs` steps randomized rows (masses, friction, gains), linear and held delays, every primitive foot and robots of 38, 46 and 56 DoF (past the 32 DoF where another Metal port's factorisation broke) for 60 steps against C MuJoCo's batch, within 1e-5 relative (worst about 5e-7).
- **Batch identity:** a world's result never depends on its neighbours. `forge-sim --batch-identity --backend metal` steps 37 worlds alone, together, and scattered through a crowd of 300 in a shuffled order, 400 steps each, and compares qpos, qvel and the warmstart bit for bit.
- **Measured on the M5 Pro** (quad-servo, 4096 worlds, every number with its load average): the F4 gate measured a mean of 1.57M substeps per second and a slowest second of 1.50M over 60 s (load 3.5 before, 3.1 after), against the 1M it asks for. At load 10 a 20 s run gave a mean of 1.45M and a slowest second of 1.33M. The GPU is busy 97% of the wall time; the rest is packing and unpacking rows and regrouping worlds on the CPU. C MuJoCo needed 18 threads for 1.59M at 1024 worlds and Forge's SIMD engine reaches about 3M there, so on this Mac the CPU engine is still the faster one; the Metal engine leaves the CPU free for the learner.

### forge-sim: the WGSL engine

- **The Metal engine's design in WGSL** (`src/wgsl/`): one GPU thread per world, kernels generated per model, worlds in blocks of 16, double-float reals, an f32 Hessian and factorisation in workgroup memory with one double-float refinement step, per-world compacted rows. The model's tables, the layout and the packing of state rows are shared with Metal in `src/gpu/` (`Sink` is the one trait both dialects emit through: `#define` and `constant` arrays for MSL, `const` declarations and two table buffers for WGSL), so a change to the formulation lands in one place and two shader sets. The shaders (`src/wgsl/shaders/*.wgsl`) mirror `metal/shaders/*.metal` file by file, with df arithmetic as calls (`ad`, `sb`, `ml`, `dv`, `mf`) because WGSL has no operator overloading; sums keep the Metal engine's association, term for term.
- **Tables live in storage buffers,** not `const` arrays: indexing a `const` array with a runtime index makes Tint copy it into every thread. Reals are one `array<vec2<f32>>` (`TR`), integers one `array<i32>` (`TI`); the generator emits each table's offset as a `const`. Workgroup memory holds the Hessian when 16 × (nm + 2 nv) floats fit the device's `maxComputeWorkgroupStorageSize` (requested at the adapter's limit), otherwise it lives in the scratch buffer.
- **Fast math is on everywhere WGSL runs,** and it deletes the error terms df arithmetic depends on: wgpu compiles MSL with Metal's default (fast) math mode, and Chrome showed `(a + b) − a` folded to `b` and a two-sum's error coming back 0. Every operation in an error-free transform goes through `pn(x)` (`bitcast<f32>(bitcast<u32>(x) | PIN)`, with `PIN` read from the uniform buffer and always 0), which the compiler can't see through, so it can't reassociate or fold. `fma` is used for exact products; finiteness and NaN tests are bit tests, since fast math assumes both away.
- **Qualification before any step:** `Engine::new` runs the `qualify` kernel on 16 df add, subtract, multiply, divide, square-root and sine cases and refuses the GPU when any is off by more than 1e-12 (`wgsl/qualify.rs`), with the operation in the reason. A backend whose `fma` isn't fused (naga lowers WGSL `fma` to HLSL `mad` on D3D12, which may be split) or whose compiler gets past the pins is refused this way instead of drifting. This check is the only evidence for D3D12 and Vulkan so far: the gate runs on a Mac.
- **One `Backend` trait, two hosts:** `WgslBatch` packs rows exactly as `MetalBatch` does and hands an `Engine` call to a `Backend` (`load` a program, `run` an entry point on io, order and stats, read `scratch` for parity). `Native` (`wgsl/native.rs`, `forge-wgpu`) is the desktop one; `forge-web`'s `HostBackend` calls JavaScript, which drives WebGPU (`src/forge/forgeGpu.ts`).
- **Refused** (as Metal): a `solimp` power other than 1 or 2.
- **Parity, measured against C MuJoCo 4.0 on the 200 fuzzed robots** (wgpu on the M5 Pro's Metal): worst L0 3.6e-11, L1 6.9e-5, L3 qpos 4.5e-9 and qvel 1.4e-6 after 60 steps; contact counts identical, and the same to two digits as against 3.17. The 12 fixture robots: L0 1.2e-10, L1 1.1e-6, L3 qpos 1.8e-9 and qvel 3.8e-7. These match the Metal engine's to the digit, because the arithmetic is the same.
- **Batch identity:** `forge-sim --batch-identity --backend wgpu` passes the Metal engine's check (37 worlds alone, together and scattered through a crowd of 300).
- **Measured on the M5 Pro** (quad-servo, 4096 worlds, through wgpu's Metal backend): the F6 gate on MuJoCo 4.0 measured a mean of 780K substeps per second and a slowest second of 693K over 60 s (load 5.7 before, 4.4 after; on 3.17, 771K and 649K at load 6.1); a 20 s run at load 12 gave a mean of 700K and a slowest second of 611K, against the 400K F6 asks for and the hand-written MSL's 1.45M at load 10. The difference is naga's MSL, bounds checks wgpu inserts on every storage access, the pins and the tables in device memory instead of `constant` arrays. At 64 worlds a control step (10 substeps) takes about 40 ms: one world's substep is a long serial chain, so small batches are latency-bound.
- `cargo run --release -p forge-sim --example wgsl_source -- <model.xml> [workgroup bytes]` prints the generated WGSL, for checking a model's shader in Chrome or naga.

### Forge in a browser tab

- **`forge-web`** compiles `forge-ir`, the WGSL generator and `forge-train` without their native features (`forge-ir/mujoco`, `forge-sim/native`, `forge-train/native`) to `wasm32-unknown-unknown` with SIMD128. `npm run build:forge-web` (`tools/forge/build-web.mjs`) writes `src/forge/forge.wasm` (about 780 KB) and `forge.build.json` (source and wasm hashes; `--check` compares with a fresh build). It loads only in the Forge worker.
- **C MuJoCo stays the compiler.** The worker (`src/forge/forgeTab.worker.ts`) compiles the MJCF with `@mujoco/mujoco`, settles the start pose exactly as `robot_load.rs` does (`forgeStart.ts`: start joints, primed control history, a second of settling, the standing check) and reads the state row with `mj_getState`. `forge-ir` reads the model through its `Source` trait; in the tab that's `Fields`, filled lazily: `forge_prepare` lowers the model, the missing fields come back as `array:`, `size:`, `option:` and `state:` keys, and `forgeFields.ts` answers each from the compiled model until nothing is missing (134 rounds for quad-servo, all in-memory).
- **Physics stays synchronous in Rust.** `forge-train`'s environments, PPO and exports run unchanged; the GPU calls are JavaScript imports wrapped in JSPI (`WebAssembly.Suspending`, `WebAssembly.promising`), so a physics step suspends the WASM stack while WebGPU maps its results back. Without JSPI (anything but Chrome today) the worker refuses with that reason. On wasm the learner runs in turn instead of overlapping collection, the row-block learner runs its blocks on one thread (`pool_threads` in `blocks.rs`; results don't depend on the thread count), and `clock::Instant` reads no clock (phase times are 0).
- **`tabForge()`** (`src/forge/tabForge.ts`) is a `ForgeRunner`: one worker per job, the same events, `policy.json`'s spec, and a run id whose `resume.json` text it keeps for the next job's `warmStart`. Anything that takes a `ForgeRunner` trains in the tab: `trainKitInTab` (`tabTraining.ts`) runs the Motor Kit's `trainKitEntry` in the skills worker with it, so the Kit's own Arena judges the result.
- **Measured** (Chrome 157, headless, Metal, quad-servo Stand from the Kit's job at 64 robots): about 1,100 steps per second, physics-bound (a 64-world control step is latency-bound, above). The Kit's Stand needed 57K steps on C MuJoCo to pass Arena 32 of 32, so its first 2-minute try is enough in a tab: in the F6 gate on MuJoCo 4.0 (load 4.4 before, 3.3 after) the tab passed in 135 s; on 3.17 it trained 130,560 steps in one Forge run and passed Arena 32 of 32 in every variant, 134 s from the call to the verdict.
- **What's left for the product:** a button on the gallery card (and in the web studio's Skills) instead of the `__forge` hook, with progress and the result in the card; saving the trained skill to the web app's IndexedDB; a faster learner (the WASM learner is single-threaded: WASM threads, or the matrix products on WebGPU), and larger batches once the PPO settings are tuned for them (at 256 and 1024 robots the Kit's Stand needs far more samples than at 64); Firefox and Safari once they ship JSPI; checking qualification on real D3D12 and Vulkan GPUs, where `fma` may not be fused (a Dekker split would replace it); `scratch` read-back in the tab, for parity runs in a browser.

### forge-id

- `identify(model, specs, data, options)` fits `ParamSpec`s (armature, damping, frictionloss per DOF, position-servo stiffness per actuator, body mass) to recorded joint positions. Parameters move in log space within `[low, high]`; each iteration runs the nominal and ± steps of every parameter as one MuJoCo batch with per-simulation model fields and `mj_setConst`.
- **It flags what it can't identify.** The relative standard deviation of each parameter comes from the Gauss-Newton normal matrix (residuals scaled by the sensor noise, inflated when the fit is worse than the noise). Above `max_relative_std` (2%), or tied to a null direction, the parameter is flagged and keeps its preset value; it is never reported as measured.
- The test plants servo parameters 15–25% off on a hoisted two-joint arm, records 12 s of multisine excitation through a 4096-count encoder, and recovers all eight within 1.3%. An idle joint's damping and armature are flagged.

### forge-reward and RewardLang

- **RewardLang is a Python subset that is parsed, never executed.** A program is `def` functions only; `reward(state)` is the entry and returns a number. Statements are assignments to plain names and one final `return`.
- **Pure and bounded:** the state is read-only (`state.gravity`, `angvel`, `linvel`, `command`, `z`, `z0`, `control_dt`, `joint_pos`, `joint_vel`, `action`, `last_action`, `bodies` with `pos`, `vel`, `z`); the only iteration is `sum`/`mean`/`min`/`max` over `state.bodies`; a function may call only functions defined above it, so there is no recursion. Imports, loops, `if` blocks, lambdas, lists, `__` names and unknown names are refused with a line number.
- **Total operators:** `/` only by a nonzero number or a provably positive value (`max(x, 0.05)`, `exp(...)`), otherwise `safe_div(a, b)` (0 when `b` is 0); powers are whole numbers 0–8; `exp` caps its argument at 80, `log` and `sqrt` clamp at their domain. Also `abs`, `tanh`, `sin`, `cos`, `square`, `min`, `max`, `clamp`, `dot`, `norm`, conditionals (`a if c else b`), `and`, `or`, `not`.
- **Per-term logs:** `term("name", x)` records each term. A term that comes out NaN or infinite is set to 0 and blamed by name, so one broken term never poisons the total.
- `forge_reward::programs::{stand, walk}` are `train.py`'s rewards in RewardLang; tests check them against the hand-written ones on 500 states, including falls.

### Canaries in cargo tests

A canary test (`canary_*`) runs a planted fault through the same check as the real test and must fail. It does its work only when its full name is the test filter, so plain `cargo test` passes and `cargo test -p <crate> canary_<name>` exits non-zero, which is what the gate wants.

### In the app

- `electron/trainer.mjs` runs Forge when it finds `forge-train` (the packaged `Resources/forge/`, or `forge/target/release/` in a checkout), and falls back to `train.py` otherwise. `BASECASE_TRAINER=python` forces Python. With Forge, `status()` reports ready with no `trainer-env`, so nobody installs Python.
- `npm run build:forge` builds the trainer and stages it in the gitignored `forge/dist/` (`tools/forge/stage.mjs`). On macOS it copies `libmujoco.<version>.dylib` (the version `fetch.rs` pins) beside the binary and points the binary at it with `install_name_tool`, because DeepMind's `mujoco.framework` has no root binary and codesign refuses it as a bundle. electron-builder ships `forge/dist/` as `Resources/forge/` and signs both files; Windows ships `forge-train.exe` and `mujoco.dll`, signed through `signExts`. CI builds Forge before packaging (`check.yml`, `release.yml`).
