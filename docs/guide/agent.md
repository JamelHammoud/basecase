# Agent and agent panel

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.


## Priorities

What matters most in the CAD agent's output, and so in its prompt, tools, checks and the bench, in order:

1. **Designs that can be assembled and serviced.** Every part can actually be put together, and a battery or board in the torso can be replaced without taking the whole robot apart (split shells and clamshells where an expert would split them, not one-piece parts).
2. **Cost-aware part choices.** No part more expensive than the job needs.
3. **Parts that look expertly designed**, not simple blocks.

Silhouette and proportion scores (what the bench measures today) matter less than these; the bench should grow to measure them.

## 9. Agent (Claude Code over ACP) and Agent Panel

### Architecture
- The app is an ACP client (`electron/backend-service.mjs`). It runs one agent at a time, picked in Settings → Agent and saved in `library/agent.json`: **Claude Code** (`@agentclientprotocol/claude-agent-acp`, the default), **Codex** (`@agentclientprotocol/codex-acp`, which bundles its own Codex binary) or **Gemini CLI** (`@google/gemini-cli`, `gemini.js --acp`), each pinned in `package.json` and run with the user's own login. The offline tracer `electron/acp-3d-agent.mjs` remains selectable. Relative script paths in a command resolve against the repo root (`anchorArgs`).
- **Agent profiles** (`electron/backend/agentProfiles.mjs`, `codexProfile.mjs`, `geminiProfile.mjs`) hold everything that differs per agent, so each runs as the same CAD agent: the CAD instructions, only the CAD MCP server plus todos and web lookups, thinking that streams, and no shell or file tools.
  - **Claude Code:** session `_meta` (below).
  - **Codex** runs from its own home, `library/agent-config/codex-home` (`CODEX_HOME`): `auth.json` is a symlink to the user's, so the ChatGPT login and its token refreshes are shared; `config.toml` is written at every launch with the user's default model and effort copied over, `sandbox_mode = "read-only"`, the shell, unified exec, plugins, apps, browser and computer use, image generation and memories features off, `project_doc_max_bytes = 0` (no AGENTS.md) and detailed reasoning summaries. Overriding the user's own `~/.codex` instead didn't hold: the adapter replaces `mcp_servers` with the client's, plugins add MCP servers (computer use, Gmail, Drive…) and code mode exposed hundreds of tools. CAD instructions go in `_meta.jetbrains.air.customInstructions`; the agent starts in the `read-only` mode (`INITIAL_AGENT_MODE`), and `apply_patch` asks for permission, which is declined. Codex has no plan tool in this release, so its runs show no plan card.
  - **Gemini CLI** reads a generated system settings file (`GEMINI_CLI_SYSTEM_SETTINGS_PATH` → `library/agent-config/gemini-settings.json`, highest precedence: `tools.core` = write_todos and the two web tools, `mcp.allowed` = robotics_cad, folder trust off) and the CAD instructions as its whole system prompt (`GEMINI_SYSTEM_MD`). It runs with `--approval-mode yolo --allowed-mcp-server-names robotics_cad`: its permission requests and tool calls carry no input or server name, so the allowlists are the boundary. Google no longer signs in personal accounts to Gemini CLI (“no longer supported for Gemini Code Assist for individuals”, since Antigravity replaced it on 2026-06-18; Antigravity's `agy` has no ACP mode), so a personal account needs a Gemini API key: the sign-in banner's **Add API Key** stores it encrypted with Electron `safeStorage` (`library/agent-config/agent-keys.json`, memory only where there's no encryption) and the profile passes it as `GEMINI_API_KEY` with `security.auth.selectedType = gemini-api-key`, leaving `~/.gemini` untouched. Gemini has no effort control over ACP, so the slider is hidden.
  - Codex and Gemini sessions use `library/agent-workspace` as their working folder, so the repo's AGENTS.md and file tree never reach them. Claude Code keeps the repo root, where its saved sessions live, but loads nothing from it: `settingSources: []` (no project or user CLAUDE.md, AGENTS.md, settings, hooks or permission rules), plus `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` and `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1` (no git status). Before that, every CAD session carried this whole file and the repo's git status as context, so it read “Add support for end effectors” as a change to Basecase's code instead of the robot.
- **Signing in:** a first session that fails with an auth error (`isAuthError`) puts `signIn` (the agent's browser methods, and `apiKey` when it takes a key) in the status instead of an error. The Agent tab shows “Sign in to use ⟨agent⟩” with the agent's own method (`authenticate`) and Add API Key, plus the agent's message when sign-in failed. While the browser sign-in runs, the line reads “Finish signing in in your browser” and the method's button goes, so the wait is said once. The banner's buttons (the method, Add API Key, Save, Reconnect) are the design system's `Button`.
- **Steering** works wherever the agent advertises it (`_meta.steering.supported`: Claude Code and Codex); Gemini's messages queue for after the run.
- **Session settings:**
  - Claude Code's built-in tools are limited to TodoWrite, Agent (subagents, below), WebSearch and WebFetch. File, shell and edit tools are off.
  - CAD instructions are appended to the system prompt (`electron/cad-agent-prompt.mjs`), once: the MCP server's own `instructions` are a one-line pointer (they were a second copy of the whole prompt). The prompt is a short core (role, frame, check integrity, workflow, part rules, kernel choice, assembly and service, cost, an index of guides, about 170 lines). The rest lives in guides (`electron/cad-agent-guides/`: photos, shells, replicad, servos, fasteners, electronics, build, joints, motion, simulation, new_design, priors, simready), which a tool result attaches the first time it applies (`cad-mcp/guideTools.mjs`: the first `look` brings photos, the first block named head or shell brings shells, the first servo brings servos…), once per lane; `get_guide` fetches any of them. Codex and Gemini get the core without the Claude-only subagent section. Part designers get a cut-down prompt with the shell, replicad, servo and fastener guides inline.
  - **A change to the prompt, a guide, a tool description or a check is judged by the micro-evals**, not by reading it: `node bench/compare.mjs --against main --tune`, then `--heldout`, runs the agent on both harnesses ([Benchmark](bench.md)). The harness lane keeps its own changes only on a held-out win, and `bench/experiments.md` lists every change measured so far. Every other pull request that changes what the agent reads or calls (`AGENT_PATHS`) is measured on the tune set by the review lane before it merges, and fails review when it measures worse ([The loop](loop.md), §0l).
  - **Check integrity** is a core rule: never narrow a range, change a role, hide, offset or delete a part to pass a check; report a check that seems wrong instead. The prompt never says "make every check pass" (a test enforces it).
  - Thinking is `adaptive` with `display: "summarized"`, so reasoning streams to the UI. `forwardSubagentText` sends subagents' thinking and text too (Claude Code sends only their tool calls by default), one whole block at a time, since subagents don't stream deltas.
  - Host-session env vars (`CLAUDE_CODE_*`, `CLAUDECODE`, and the desktop host's `ANTHROPIC_BASE_URL`) are stripped, so the agent uses the user's login. `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` is set, so subagents always run in the foreground and the lead's turn waits for them. `ENABLE_CLAUDEAI_MCP_SERVERS=false` keeps the user's claude.ai connectors (Drive, Docs…) out of CAD sessions.
- **Permissions:** anything other than the CAD tools, TodoWrite, Agent (part designers) and web lookups is declined and shown as a toast.
- **One session per chat lane:** one agent process; each scene tab runs up to 4 chats at once (**lanes**, `src/workspace/agentLanes.ts`), each with its own ACP session (`sessions`: lane key → session id in `acpAgent.mjs`). A lane key is the tab id for the tab's first lane (`main` lane) and `<tab>__<lane>` for the others.
  - Each session's MCP server gets its own bridge URL (`…/<token>/w/<lane key>`), so CAD requests land in that tab's scene and are attributed to that chat. `agent-request`, `agent-status`, `agent-blocked`, `acp-session` and `acp-session-update` events carry the lane key as `workspaceId`; `useTabs.routeEvent` routes them to the tab (`splitLaneKey`), and answers requests for a closed tab with “This scene was closed.”
  - Prompt, steer, cancel, resume and new-conversation calls take the lane key. Sessions start lazily on a lane's first message (the first tab's `main` lane gets one at launch). A reopened chat resumes its session on the next message. Closing a tab cancels and closes every lane's session (`closeWorkspace` with a tab id); dropping one lane closes only its key.
  - Callers without a workspace id (bench, `tools/parts/generate.mjs`) use `main`, the first tab's first lane.
  - A conversation lives in one lane: opening it from History shows its lane, or the tab that has it.
- **Surviving reloads:** the agent runs in the main process, so a renderer reload (Vite full reload, ⌘R) never stops it. Tabs keep their ids across reloads (`open-scenes` stores `tabIds`), so lane keys still match. While a prompt runs, the backend journals it per lane key (`electron/backend/liveRuns.mjs`: the messages the renderer sent with the prompt or a steer, `run`, then every session update). Each tab asks for its runs on mount (`useAdoptedRuns`): the chat is rebuilt from the saved conversation plus the journal (`restoreRunMessages`), the lane shows as running, and `acp-run-end` finishes it. The bridge re-sends unanswered `agent-request`s for that tab (`AgentBridge.replay`); the renderer handles each request id once. Journals are dropped once the renderer has the result (`forgetAcpRun`). Queued messages and Revert Changes don't survive a reload.
- **Concurrent chats (lanes):** New Chat or opening a chat while the current one runs puts it in another lane; the running chat keeps going in the background. A lane is reused when idle; past 4 lanes the oldest idle one (never `main`) is saved and closed. With 4 running: “Up to 4 chats run at once. Stop one to start another.” When a background lane finishes: “Agent finished “⟨chat⟩” · Show”. Scene-wide state (busy spinner, Stop on tab close) covers every lane; the scene record and tab snapshot keep the current lane's chat.
- **Subagents (part designers):** `options.agents` defines `part-designer` (`electron/backend/subagents.mjs`: a role preamble + the CAD instructions; no Agent, TodoWrite or web tools). Built-in types that aren't CAD work are denied (`disallowedTools: Agent(general-purpose)`, `Agent(statusline-setup)`; `CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1` drops Explore and Plan). Claude Code never asks permission for Agent calls, so the ACP permission handler can't gate them, and `Agent(<type>)` in `tools` removes the tool instead of narrowing it. Any subagent inherits the session's tools, so none can touch files. A subagent's report arrives as its last `SubagentHandback` call (`rawInput.message`), which the designer's row shows as its report instead of a step.
- **Scope:** every request is about the model in the scene (prompt “Scope”: “add support for end effectors” means design them into the robot). The prompt's “Parallel part designers” section has the lead launch one per subassembly in one message after the block-out, each briefed with its part ids, reference rows, photos, interfaces and sizes, then review and mirror. The adapter stamps a subagent's updates with `_meta.claudeCode.parentToolUseId`; `acpTranscript` nests its tool calls (`children`), report (`childText`) and thinking (`childThought`) under the Agent call, shown in the Subagents card (§9 Panel).
- **Who made an edit:** Claude Code sends `_meta["claudecode/toolUseId"]` with every MCP call; the MCP server (`withToolCall` in `cad-mcp/shared.mjs`, AsyncLocalStorage) forwards it to the bridge as the `x-tool-use-id` header, and `agent-request` carries it as `toolUseId`. `ActorIndex` (`src/workspace/agentActors.ts`) maps it to an actor: the lane (`<lane>`) or a subagent (`<lane>/<Agent call id>`).
- **Part ownership:** every agent write claims the part for its actor. A write to a part claimed by another *active* actor is skipped with a problem the agent reads (“left_knee not changed: the “Left leg” part designer is working on it…”). A lead and its own subagents never block each other; sibling subagents and other chats do. Claims lapse when the subagent's Agent call completes or the lane's run ends. The user's own edits are never blocked.
- **CAD tools** come from an MCP server (`electron/cad-mcp-server.mjs`): `get_scene` (one compact line per part, `cad-mcp/sceneText.mjs`; `group` / `ids` read part of it; Claude Code saves any text result over 50,000 characters to a file the CAD agent can't read, so a big scene drops its notes, then lists only groups), `model_part`, `get_part_code`, `add_parts` (block-out), `update_parts`, `delete_parts`, `mirror_parts`, `look` (multi-view renders, optionally isolated by ids), `check_scene`, `robot_skeleton` and `set_status`.
  - Evidence: `list_evidence` / `read_evidence` open the files the user attached (images come back as images, text as text). `find_images` lists the photos on a web page (WebFetch drops them) and `view_image` downloads up to 4 for Claude to look at, downscaled to 1568px by the renderer (`downscale_image` request). Both refuse local and private addresses.
  - `robot_skeleton` (`electron/robot-skeleton.mjs`) reads a published URDF or MJCF and returns the exact zero-pose joint positions, axes and offsets in the studio frame. It reads no meshes, so shapes still come from the photos.
  - `find_robot_description` searches GitHub (at most 2 searches and 4 tree reads, to stay inside the unauthenticated rate limit) for a named robot's URDF/MJCF files, and returns raw URLs for `robot_skeleton`. Without it, whether the agent found the description was luck, and scores swung 10+ points between runs. Repositories are ranked by exact-name match before stars, because a top-starred variant (Berkeley Humanoid **Lite**) once led the agent to build a different robot (r25: 62 vs 84).
  - `check_skeleton` checks the model against the same published description: every moving joint must sit inside some part. It fits the floor offset but not X or Y, so it says when the joints' centre falls outside the model along either (centre the model on the origin), and lists joints outside the model with their distance and the nearest part. A joint whose left and right frames disagree along its axis (an artefact of the CAD export) is checked as an axis line, not a point.
  - `compare` puts a reference image (`ref-N`, an evidence path or an image URL) beside renders of the model from a matching viewpoint, followed by a checklist: silhouette fractions, shell shapes, feature ownership, and shadows that aren't geometry. The agent uses it after the block-out, per subassembly and at the end.
  - `look` and `compare` take `az:<deg>,el:<deg>` views as well as the named ones (az 0 = front, +90 = the robot's left side).
  - For a straight-on view (front, side or back) and a reference photo on a plain background, `compare` also measures both silhouettes (`src/utils/silhouette.ts`). The photo is segmented by flood-filling the border colour; the model comes from a white-on-black render. It prints span width per tenth of height and flags bands off by more than 15%, since perspective photos distort widths 5–10%. Chasing every band of a perspective photo (r23) cost Memo's drawing match 0.87 → 0.73. On Memo it reproduces the held-out drawing's errors (hands ×0.85 too narrow).
  - `compare` also prints the model's silhouette profile: width and depth for each tenth of the height, as fractions of total height, with the widest parts per band (from part bounds). The agent checks its proportion table against these numbers instead of eyeballing.
  - **Photo masks:** `compare`, `fit_view`, `trace_outline`, `photo_scale` and `score_fit` mask photos with Apple Vision's `VNGenerateForegroundInstanceMaskRequest` (`electron/native/vision/`, Objective-C++ on Node-API, built by `tools/native/build.mjs`, run in the MCP server process where the photo bytes are, about 20–35 ms a photo). Without the addon or before macOS 14 they flood-fill plain backgrounds as before. Every mask goes through `checkMask` (`src/utils/photoMask.ts`): refused over 60% of the photo or 50% of its edge, and refused when the subject is cut off at the top or bottom unless `ids` is passed. All 13 chat references mask (the flood fill refused 8, and counted 74% of a G1 photo as robot).
  - **Automatic compare** (`cad-mcp/autoCompare.mjs`): `check_scene`, and the first whole-model `look` after `add_parts`, append a width-band verdict for up to 4 of the chat's photos (`ReferenceImages.ofLane`), skipping an unchanged scene.
  - **Sketch targets:** `compare` treats SVG references (an evidence file or pasted code) or `target: true` as outlines to match (`utils/targetFit.ts`): overlap, outline gap in mm, top and bottom corner radii, widths per tenth, a red/blue overlay. SVGs in mm compare at true scale.
  - `fit_view` fits azimuth, elevation and field of view to a photo's silhouette (silhouette renders one per frame, scoring in the image worker), seeded from EXIF focal length for image URLs; `trace_outline` turns a photo outline into 12–32 `profileBody` points in mm; `photo_scale` sets mm per pixel from a part of known size; `score_fit` is one 0–100 number over the photos for choosing between alternative block-outs. `look` takes `labels` (flat colour per part, the same number in every view, a legend), `grid` and `detail` (2,000 px for Claude).
  - **Image caps** (`cad-mcp/imageCaps.mjs`, `CAD_AGENT_KIND`): Claude's reference photos, `view_image` and detail renders go to 2,000 px, not the 2,576 it reads: the API rejects any image over 2,000 px once a request holds more than 20 images, history included. Default renders stay 1,024 px. Other agents keep today's sizes.
  - `set_world` and `start_drive` (`cad-mcp/worldTools.mjs`, renderer side `src/agent/agentDrive.ts`, §8h): `set_world` replaces the simulated world with static, dynamic and marker objects in the agent frame (never parts; ids and numbers checked by the Case reader); `start_drive` drives the robot with timed commands (`grip` closes an arm's gripper), headless by default (a legged robot passes the fall check first) and reports travel, turn, falls or the end effector, or with `live` drives the canvas and returns at once. Both are `SIM_TOOL_KINDS`; an unknown simulation kind now fails instead of answering with training status.
  - `operate` (`cad-mcp/worldTools.mjs`, renderer side `src/agent/agentOperate.ts`, §8l) runs the live sim one held action at a time and returns the scene view and the robot's camera views after each step; `/operate` asks for a task done this way. `simulate`'s `cameras` option returns what named cameras saw at each frame.
  - `create_case` (`cad-mcp/caseTools.mjs`, renderer side `src/workspace/agentCaseRequests.ts`, §8h): adds a Case built by the Case builder from a goal (reach, push, path, walk, touch, pick), a world (floor, corridor, block, shelf, the terrain worlds rough, steps and slope with `rise_mm` or `incline_deg`, or room, the scanned room open in New Case), a `target` (a name, or a list for path, matched by `targetNamed`, §8h Rooms: “under the kitchen table” is Under Table; a target picks the room world, and an unknown name replies with the room's names), numbers in mm, a dot count for touch, optional extra world objects in the agent frame (one marked `movable` is one the Case's code can move, recolor or hide with `basecase.world.set`), optional `logic` (a Routine the Case runs, compiled with the Case's `drive` skill; a refusal replies with the compiler's message) an optional `score` rule and an optional `console` (§8h, Running a Case: input sources, the Case's own signals, panels and their layout), and opens it; it never changes the design. The console goes through the same `parseCase`, so a refused input or panel replies with its path (`console.panels[2].kind …`) and adds nothing; with a console, the reply carries `running: true` and the app opens the new Case running (`useCaseRun.enterCase`), laid out by it. The tool's description lists the input ids, panel kinds, canvas overlays, signal names and a code panel's `window.basecase` calls and `--bc-*` variables, so the agent writes a console, code panels included, without reading the code. The prompt's `/case` line tells the agent to describe behaviours as Case logic: a base `do drive`, `case-fact` watchers (score, timer, `<spot>-count`, `<object>-over`) and `live-input` ones (a voice word). A message starting with `/case` (Ask the Agent in the Cases view prefills it, `tool.requestCompose`) asks for one, per the prompt's Slash commands.
  - `write_case_code`, `read_case_code` and `delete_case_code` (`cad-mcp/caseCodeTools.mjs`, renderer side `src/workspace/agentCaseCodeRequests.ts`, §8h, The agent writing a Case's code): write or replace one code panel (`panel`, `source`, `title`, `height`, `place`: a column `side` and `size`, or an `overlay` anchor with `width`, `height` and `pointer`), read a panel's source or list the Case's code panels, or take one out. Each write and delete is one undo step and goes through `parseCase`, so a source over 256 KB replies with its path. A write opens the Case running when it isn't; a running one reloads only that panel. About 2 s after the panel loads, the renderer replies `{ ok, case, panel, running, loaded, errors, logs, refused }`: the first 10 uncaught errors with their source lines, the first 20 console lines and the refused bridge calls with why. The tool then asks the main process for `capture_window` (a local handler on the token bridge, `electron/main.mjs`: `webContents.capturePage()`, at most 1,568 px wide, JPEG), which shows the whole window with the code panels' out-of-process frames, and returns it as an image after the JSON. Viewport captures (`captureViews`) can't, since they render only the 3D scene. Without the desktop app (the web demo, the e2e harness) the reply comes without the image.
  - `run_case` (same files, renderer side `src/workspace/agentCaseRun.ts`, §8h): runs a Case by id or name (the open Case when left out) over 20 seeded randomized runs, or `runs`, the same runs and cache as its Checks row, and returns the passes, the median margin, the failure labels most runs share, the refusal when the robot can't enter, and a three-frame filmstrip of the worst run. Check integrity says a design in a scene with Cases isn't done until `run_case` passes them, and never to edit a Case to make it pass. The renderer timeout is 300 s.
  - `read_try` (same files, renderer side `src/workspace/agentReadTry.ts`, pure part `src/cases/console/tryReading.ts`, §8h) answers questions about one recorded try: it takes a try `id` (the open Case's newest simulated try when left out), a window `from`/`to` in seconds, `signals` (names or `*` patterns as console panels take them; `robot.*` and `goal.*` when left out), `every` (seconds between rows; about 50 rows when left out) and `at` (when to capture; the first failure, else the window's end). It opens the try's Case when another is open (waiting for it to open), shows the try on the timeline (`timeline.show`, which scrubs the sim and finds the failure frames), builds the try's signals with `consoleTrack` (the same names and values the running Case's console shows), samples them (at most 200 rows, 32 signals, values to 3 decimals), seeks the timeline to `at`, waits for the sim's `sought` frame and captures the canvas (`captureViews`, `view`, iso when left out). The reply is one JSON object `{ ok, try: { id, case, passed, margin, seconds }, window: { from, to, every }, samples: { time, <signal>… }, failures: [{ label, time }], capture, unknown?, left_out? }` (`unknown`: patterns that matched nothing; `left_out`: signals past 32) with the picture after it; a missing try lists the open Case's tries, and a real try, a missing recording or one that no longer fits the robot returns `ok: false` with why. The handler reads the cases, sim and rig after each await through `RequestContext.live` (`useLatestRef`), since the context's own `cases` is the snapshot from when the request arrived. The prompt's Case apps section says to answer questions about a run from its recording with `read_try`, citing times and values. `tryReading.test.ts` checks the payload (window, wildcards, rounding, the row and signal caps, unknown patterns); `tryReadingFall.test.ts` plants a fall in a standing `quad-servo` recording on Walk (the root tipped 180°/s from 2 s) and finds `fell` at its time with `robot.tilt` crossing 45° just before; `agentReadTry.test.ts` checks the handler's try choice, Case opening, seek and capture, and its refusals. The renderer timeout is 120 s.
  - `compare_case` (same files, §8h) answers which of two designs is better: it runs a Case (the open one, or one named by id or name) on this scene's robot and on another open tab's (named, or the first that fits) with the same 20 seeds, and returns each scene's passes, median margin, cost in USD and mass, and `better`, the scene with the higher pass rate (null on a tie). When the Case is the open one, the rows also show in Results. A Case with more than one slot, or no fitting tab, returns `ok: false` with the scenes that fit.
  - `explore_case` (same files, §8h) answers which servo to buy: it runs Explore on a Case (the open one, or one named by id or name) through `useCaseExplore.explore`, the same sweep and rows as the Simulate tab's, and returns `current` (each joint's servo MPN and the supply volts) and every design sorted by passes then cost, each with its label, volts, passes of 8, worst margin, cost in USD, mass, the swapped MPNs and its refusal. It never edits the scene. The renderer timeout is 600 s. A Case with more than one slot, or a robot with no catalog servo that comes in versions, returns `ok: false` with why. The simulation guide tells the agent to recommend the cheapest design that passes every run.
  - **Skills** (`cad-mcp/skillTools.mjs`, renderer side `src/workspace/agentSkillRequests.ts`, §8i), replacing the stand/walk `train_policy`: `draft_skill` takes a name, the user's words, a goal (`reach` with waypoints in the agent frame, `velocity` in m/s and rad/s, or `open`), a try length, a contract over named signals in SI units, extra signals, optional RewardLang candidates and routing hints, and answers with the draft id, the contract in plain words, the router's first method and why, nominal rollouts (holding still, and the planned poses for a reach) and any design limit with its relaxation; `train_skill` runs the solver race on an approved draft, or one Motor Kit entry (`kit`: stand, walk, get-up, settle), or one move (`move`: a Pose-tab animation's name, matched without case), in the background and returns at once; `list_skills` lists the Kit, the moves and the taught skills with their state and the last race (the winning method, or each method tried and why it failed, plus the relaxation to offer). `coach_skill` changes how a ready Kit skill moves (§8i): called with `skill` and `words` it returns the skill's reward and five signals measured on one clean run with each one's minimum move; called again with the revised `reward`, a `signal` and a `direction` (`up` or `down`) it trains from the ready skill in the background, and `list_skills` adds the last coaching (kept, dropped or refused, with the signal's two numbers). The prompt's `/coach ⟨skill⟩: ⟨words⟩` line, which the Teach field sends when it's scoped to a row, asks for it. Handlers are tested with an in-process runner and a stub Forge (`agentSkillRequests.test.ts`).
  - **Case apps** (prompt section “Case apps”): when the user describes something to do with a robot rather than a change to it (teleop, a puppet, a game, a demo, a station, a behaviour), the agent builds it as a Case app: `create_case` with a console. It uses the scene's robot, or `import_robot` the one named when the scene has none; picks the input named, and when the console reader refuses it as missing in this version, says so in one sentence and uses keys; shows a camera panel for each camera mentioned; writes each control or view no panel kind has (a joystick, a piano, a HUD, a drawing pad) as a code panel with `write_case_code`, in the studio's `--bc-*` tokens, driving only through `window.basecase`; reads every write's reply and fixes each error and refused call, and looks at the capture, before it answers; and keeps the world to the closest goal on a plain floor with only the objects described. Hardware the app can't connect to yet gets one sentence, and the sim side is built anyway. A body movement the user names is a gesture event (§8h): `create_case` takes `gestures`, the names the Case reacts to, keeps the ones that aren't built in as gestures to teach, and returns them as `teach`; the agent then says in one sentence that the person teaches them with Teach Gesture. A message sent while a Case runs arrives with a note naming that Case (`runningCaseNote`), and the prompt says it's about that Case, so the agent changes its app in place. ### CAD kernel (fidelity)
- Parts are code:
  - **OpenSCAD** (`openscad-wasm`, `--backend=manifold`) with **BOSL2** (`vendor/BOSL2`, pinned commit in `.commit`) and the COTS library `vendor/robotics/robotics.scad`. The library has STS3215, MG996R, SG90, Dynamixel XL430 and XL330 servos and pockets, `qdd_actuator` / `qdd_pocket` pancake actuators (QDD_S/M/L) for humanoid-scale joints, mechanism modules (`servo_u_bracket`, `linear_lift`, `parallel_gripper`), wheels, casters, horns, screws, heat-set holes, a 608 bearing, a Pi Zero, a Pi 5 and an 18650 cell.
  - **replicad** (OpenCascade B-rep) for true fillets, shells and lofts.
- **Sandbox** (§0h): the kernel logic is pure (`kernelCore.mjs`, `openscadEngine.mjs`, `replicadEngine.mjs`: no Node, files come in through `libraryFiles`) and runs as a Worker in a hidden sandboxed window (`cad-kernel/sandbox/`). The main process keeps one pool for every lane (`SandboxKernel`, `pool.mjs`): up to 4 windows (half the CPU cores), each its own renderer process, opened on the first job (or 2 s after an MCP server starts, `kernel_warm`) and closed after 10 idle minutes. A part over its time limit (90 s by default) or a window over 4 GB kills that window; the next job gets a fresh one. The MCP server's `renderPart` / `auditPart` go over the bridge (`cad-kernel/client.mjs`). replicad works on every OS. The bundle (`dist/kernel/`: `host.js`, `worker.js`, the OpenSCAD, replicad and Manifold chunks and WASM) is built by `vite build` (`tools/kernelBundle.mjs`, skipped for `--mode web`); `npm run electron` / `electron:dev` rebuild it when the kernel sources changed. Tests and `tools/` compile through the Node host (`cad-kernel/nodeHost/client.mjs`), the same kernel logic in a forked Node process.
- **STEP export** (Export ▸ STEP, §7–8): the same pool runs it as one job (`SandboxKernel.exportStep`, marked `replicad` so the window starts fresh after it, 300 s limit, with its own timeout and stopped wording, `STEP_MESSAGES`, in place of the render's). The renderer sends a list of bodies (`workspace/stepExport.ts`: name, colour, group name, a rigid placement and a solid); the main process checks the list (`stepPolicy.mjs`: at most 2,000 bodies, 400 KB of code each, 40 M mesh numbers, finite sizes, rigid placements, `#rrggbb` colours, nesting 12 deep) and the kernel worker builds it (`stepAssembly.mjs`, `stepSolids.mjs`, `stepFacets.mjs`). A replicad part re-runs its code; a basic shape and a boolean whose operands are basic shapes or replicad parts are built as exact solids; anything else becomes a faceted solid from its mesh: welded, simplified toward 6,000 triangles a body and 40,000 a file (meshoptimizer stops at 0.2% of the body's size, and at 2% only if the first pass leaves it more than half again over its share), read through `StlAPI_Reader`, sewn, coplanar triangles merged (`ShapeUpgrade_UnifySameDomain`) and closed into solids. A body that has two or more solids becomes a sub-assembly of them, all named after the part, since readers drop the name of a body's extra solids. Names pass through `stepName` (apostrophes become ’, backslashes /, control and format characters spaces), because OpenCascade's own reader loses a body named `B'); X` even though the writer escapes it. Its STL reader also takes a binary file whose bytes all happen to be ASCII for text, so the 80-byte header is filled with `0xff`. The writer uses AP214, millimetres and no pcurves (`write.surfacecurve.mode` 0 halves the file). The reply is JSON `{ ok, step, skipped }`; `checkedStepReply` refuses one that isn't a whole `ISO-10303-21;` … `END-ISO-10303-21;` file or counts more skipped bodies than it was sent. A faceted catalog servo is about 5 MB.
- **OpenSCAD defaults:** `$fa = 6; $fs = 0.5` on the same line, so error line numbers stay correct.
- **Named dimensions** (`cad-kernel/dimensions.mjs`): a top-level numeric assignment made once (`wall = 2; // [1.2:0.4:4]`) is a dimension the Inspector edits (§7). The prompt asks the agent to name the dimensions a person would tune that way. `rewriteDimensions` replaces only that literal, clamped to the Customizer range and written as plain digits, and leaves every other byte alone, including the `// basecase: holes` and `// basecase: mirror` blocks. Those blocks keep definitions at the top level, and a statement keeps the comment that ends its line (`scadStatements.mjs`, shared with the renderer's `cadCode.ts`), so a part stays tunable after `fasten` or `mirror_parts`. `backend/cadTune.mjs` reads the code from the renderer (`part_source`), rewrites it and compiles it with the part's frozen `cad.expect`.
- **Hulls that crash CGAL** (`cad-kernel/hullFallback.mjs`): the wasm build's CGAL `convex_hull_3` asserts on some exact float inputs (a stack of thin slices, the same code every time; a tiny rotation fixes some cases and breaks others, so its predicates aren't reliable there). On that crash the kernel exports the evaluated tree (`-o part.csg`: loops, modules and `$fn` resolved), renders each innermost 3D `hull()` body alone, takes Manifold's hull of its vertices (`manifold-3d/manifold.js`), puts it back as a `polyhedron` and renders the result. Volumes match OpenSCAD's own hull exactly; 2D hulls are left to OpenSCAD; ports and warnings come from the export run. It costs about 2–12 s, only on a crash. A part that comes out 2D says so (“The part is 2D. Extrude it…”) instead of a bare “OpenSCAD failed.”
- **BOSL2 patches** (marked `basecase` in `vendor/BOSL2/shapes3d.scad`; re-apply them when you update BOSL2):
  - `cuboid` shrinks a rounding or chamfer that would meet itself (2r = size) to just under the limit.
  - `cuboid` roundings on one edge axis (e.g. `edges="Z"`) extrude a 2D hull instead of a 3D CGAL `hull()` of corners. The 3D hull crashed on everyday enclosures.
- The kernel runs one job at a time per worker, so an OpenSCAD instance and its logs are never shared. A worker prewarms the next OpenSCAD instance (and replicad, after a replicad job) while it waits.
- **Errors teach the fix:** OpenSCAD errors keep BOSL2's message and the user's line and module ("Must give two of spacing, n and size — at line 3, in grid_copies()"), without the raw assert source. Common replicad errors get a one-line hint. OpenCascade exceptions are decoded (`replicadSupport.mjs`: `getExceptionMessage`, `getStandard_FailureData`), so a failed fillet reads "StdFail_NotDone: BRep_API: command not done" instead of "[object WebAssembly.Exception]". The agent's replicad code runs inside an inner function, so its own `const` names never clash with the injected helpers.
- **Audit on every compile** (`cad-kernel/audit.mjs`, in the kernel worker): non-manifold edges located, with the fix "fuse with at least 0.2 mm overlap"; bodies and sealed voids (a hollow shell is one body with a void, by signed volume per surface); genus; open edges; an explicit error for an empty part; craft metrics (`craftMetrics.mjs`). `model_part` compares the convex-hull volume and body count with the last revision (`cad.audit`) and warns when the hull drops below 50% or the body count rises; raw volume isn't the signal, since deliberate hollowing cuts it.
- **replicad edge helpers** (`replicadEdges.mjs`): `edgeKeys`, `newEdges` (edges a boolean created), `convexEdges`, `edgesOnPlane`, `filletEdges` / `chamferEdges`, which retry edge by edge and at half size and report "fillet … hit N of M intended edges".
- Every compile returns errors (unknown names count as errors), the local bbox, volume and triangle count. The agent must self-check against these.
- **Rendering:** CAD parts are `kind: 'cad_part'` with `cad.{language, code, positions, indices, edges, originOffset, baseSize}`. They render with creased normals and crisp edges, and their code is appended to `DESIGN_BRIEF.md` (§3b).
- **Pending CAD parts:** a part with `cad.pending` shows its placeholder mesh until the desktop app's kernel compiles its code; every scene workspace compiles them itself (`useCadCompile`, two at a time, no undo step, a failed code isn't retried that session). The web demo keeps the placeholder.
- **Agent workflow** (the prompt's core; details in the guides): read every attachment and evidence file → find its own evidence (web; `find_images` + `view_image` for views the user didn't provide; `robot_skeleton` for published robot descriptions) → measure photo proportions and anchor scale → post a reference sheet (sources, key dimensions with confidence, structure, gaps) → plan the architecture (part tree, budget split, each enclosing shell's split plane and what must stay serviceable) → block out → `compare` and fix proportions → `define_joints` + `size_actuators` → `model_part` each part (recipes from `find_recipes`, parts placed with `mate`, joined with `fasten`) → inspect with `look(ids)` → mirror → detail pass, `check_scene`, `check_assembly` and `craft_review` → verify each reference with `compare`, ticking off the feature inventory. Up to 3 rounds. An import with no joints (STEP, meshes) is rigged from `find_joint_axes`, then each range is swept with `animate` before the report.
- **Guide examples** (`electron/cad-agent-guides/examples.mjs`): a silhouette-intersection shell, a tapered limb and an egg head (OpenSCAD), a fillet-after-boolean with a smaller-radius fallback and a loft (replicad). `examples.test.mjs` compiles each through the kernel and requires one clean body. Sizes are ratios of one dimension so they don't leak into designs.
- **Recipes** (`vendor/robotics/recipes.scad`, `modules.scad`, included by `robotics.scad`; `mechanisms.scad` on request, since it pulls in BOSL2's gears, joiners and hinges): proven modules that echo `PORT` lines (name, position, outward axis, kind, diameter): seam_shell, split_shell + silhouette_body, printed_block, heatset_boss, counterbore_cut, rib, vent_slots, joint_disc, servo_cradle, servo_u_link, servo_link, servo_base, battery_bay and hatch, pi5_tray, gear_pair, gt2_pulley_pair, four_bar, snap pins, pip_hinge, plus `arm_template` and `biped_template`. Place them with `placed(pos, r, prefix)` so ports follow (a plain `translate` moves geometry, not reported ports); the kernel drops duplicate echoes from `diff()`. `find_recipes(query)` (`electron/cad-mcp/recipes/`) returns use, parameters, ports and a snippet that compiles; snippets stay on neutral objects and are never pasted into the prompt. `synthesize_linkage(points, plane?, origin?, insert?)` (`electron/cad-mcp/recipeTools.mjs` → `src/linkage/agentLinkage.ts`) runs the Sketch's four-bar path solver in its worker on 5–12 points in a CAD plane and lists up to 3 crank-rocker four-bars (max and RMS path error, minimum transmission angle, crank sweep, links, coupler point); `insert` places one as `four_bar` bars with an STS3215 on the crank joint (one undo removes it all), so the agent sizes a leg, finger or nodding head from the path its tip traces instead of guessing lengths. `recipes.test.mjs` compiles every recipe in the kernel and checks ports and fits (servo in cradle, ±110° sweeps, hatch, gear mesh); `templates.test.mjs` checks the templates against the catalog STS3215's horn face. Not proven by printing yet: the GT2 groove, the 0.3 mm hinge gap. Avoid BOSL2 names in recipe code (`screw_head` collided; ours is `socket_head`). `npm run recipes:harvest <scene.json> <part>` turns a saved part into a candidate recipe in `scratch/recipes/` for review.

### Live presence
- **Cursor:** each scene op moves its agent's blue cursor (`AgentCursor`, `AGENT_COLOR`, the Figma blue `#0d99ff`) to the part before the change lands: one cursor per active actor (`useAgentCursors`), labelled “Agent” for a chat whichever agent runs it, and with its description for a part designer (“Left leg”). A designer's cursor goes when its Agent call completes; a lane's when its run ends. New parts pop in (`animateSpawn`).
- **Subagent colours:** the lead is blue; each subagent gets its own colour from `DESIGNER_COLORS` (`theme.ts`: amber, teal, violet, rose, green, cyan; never the selection blue or cutout red). A designer's colour is its place among the chat's Agent calls (`designerSlots` in `utils/designers.ts`), so the feed, the cursor, the canvas frame and a chat reopened from History always agree, with nothing stored. `colorCursors` (`workspace/designerFrames.ts`) colours each cursor.
- **Subagent frames:** while a subagent works, the parts it has claimed get corner brackets in its colour around their shared bounds (`three/viewport/agentFrames.ts`, `ViewportProps.agentFrames`). They're drawn in `stage.overlays`, so they never rebuild parts and never show in captures; bounds refresh after each render, so moves, poses and spawns follow. Hovering a subagent in the feed focuses its frame (thicker, plus a faint box outline, adding the parts it wrote) and dims the others; a finished subagent's parts frame on hover too. Claims reach the cursor state through `useAgentCursors.claim`.
- **Status:** `model_part` emits a `focus` event while compiling ("Designing ⟨part⟩").
- **Camera follow:** the camera frames the model while the agent builds (`frameAll`), and stops following once the user orbits or zooms.
- **Undo:** one undo step per tool call. **Revert Changes** restores only the parts that chat's last run changed (their state before the run; parts it added are removed), so other chats' and the user's edits stay (`runEdits.ts`, `AgentLane.edits`).

### Panel
- **No header row.** History opens from the Agent tab: while it's the open tab, hovering its pill widens it as a chevron fades in from the left beside the label, and clicking anywhere on the pill opens the chat list (`ChatHistory`). Until the scene has a saved or running chat the pill has no chevron and no list, so nothing opens onto an empty menu. New chat sits in the composer next to +, and ⌘K's New Chat does the same (§11).
- **History list:** as wide as the inspector's header content (the card less its 8px header padding; the menu anchors to the tab row, not the pill), grouped by last use (Today, Yesterday, Previous 7 days, then by month) under quiet group labels. Rows are one line: the title, and the time on the right, which Delete (a danger `IconButton`, confirmed first with “Delete ⟨title⟩?”, Cancel and Delete) replaces on hover or keyboard focus; hidden, it takes no clicks. Running chats in this scene sit in a **Running** group at the top, each with the agent spinner and no time. The current chat sits on a soft fill. Any chat can be opened while others run (§9 Concurrent chats).
- **History:**
  - Conversations are saved to `library/conversations/` after each run, and when their tab closes.
  - Opening one restores the transcript and resumes the ACP session (`resumeSession`), so Claude keeps its context.
- **Transcript (`segments`):** thoughts, markdown text (`Markdown`, GFM) and tool steps appear in the order they streamed.
  - **Follow:** the feed sticks to the bottom while the agent streams. Scrolling up (wheel, scrollbar, keys) stops the follow until you scroll back to the very bottom; a round “Scroll to bottom” button shows meanwhile. Sending a message re-sticks it.
  - **Edge fades:** a 28px mask fades the top and/or bottom of the feed only while there's more to scroll to past that edge (`feedMask`).
  - **User messages** taller than about 9 lines collapse with a fade and Show More / Show Less. Attached images open in `ImageViewer`; folders show as chips with their file count.
  - **No horizontal overflow:** the feed is `overflow-x-hidden`, and text uses `overflow-wrap: anywhere` (code blocks and tables scroll inside themselves). Tables keep their natural width (`MarkdownTable`: columns size to their content, a cell wraps past 240px) and scroll sideways, fading 24px at an edge only while columns are hidden past it.
  - Only content updates (thoughts, text, tool calls, plan) create a reply; session metadata from the adapter is ignored.
  - **Thoughts:** a light-bulb row (`ThoughtIcon`) styled like tool steps, with no rule or border. While streaming it reads “Thinking” and shows the whole text growing, with no height cap, while the feed follows the bottom (`useFeedFollow`). Once done it folds to “Thought ›”, which expands to the full text inline. Thoughts never scroll on their own, so the wheel always scrolls the conversation.
  - **Tool steps** (`ToolStep`, labels in `toolRules.ts`): one quiet row like Thought: a 16px glyph from `toolIcons.tsx`, a plain-language label (“Designing Left Coxa Bracket”, “Inspected …”, “Studied 4 attached files”, “Looked at 2 photos”) that shimmers while running, and a › when there's more. No status icons and no green checks: done is the past tense, failed turns the whole row red. Details (the parts touched, the search, the file) open under the label at the same 13px, with the code (`CodeBlock`) or photos. A failed step always opens: its reason comes first (`AcpToolCallEvent.error`, the text the agent saw, without code fences or `MCP error` codes, `workspace/toolFailure.ts`), then its code. A group with some failures says “2 failed” in red after its label; a failed subagent ends its feed with “Couldn’t finish. ⟨reason⟩”. Only details a person can use: no camera angles, no engine names. Every Basecase tool has a label; an unknown one is humanized (`some_tool` → “Some tool”), never shown as `mcp__…`.
  - **Disclosures** (Thought, tool details): a plain click anywhere in the open text folds it; a drag that selects text, or a click on a link, button or code, doesn't (`Disclosure.tsx`).
  - **Part links:** part names and ids in replies (prose and inline code) and in step details link to the part: clicking selects it on the canvas (`PartLinksProvider.tsx`, matching in `partIndex.ts`: whole words, case-sensitive, longest first, names under 3 characters skipped; a name several parts share selects them all). Code blocks and existing links are left alone.
  - **Groups:** 3 or more consecutive calls of one tool fold into one row with a count (“Designed 4 parts ›”, “Ran 3 checks ›”, `toolGroupLabels.ts`) that expands to the steps. Hidden steps (status, todos) don't break a run; text, thoughts and other tools do (`toolGroups.ts`).
  - **Subagents card** (`DesignersCard`): consecutive Agent calls, even a lone one, gather into one card (`PlanCard`'s soft fill). The UI calls them subagents, never part designers. Its header reads just “Subagents”, with no count or progress bar. Each row (`DesignerRow`) is the designer's arrow glyph in its colour (`DesignerGlyph`, the canvas cursor's shape, with no pulse), its name and, after it, the running step (or “Thinking” between steps) shimmering with the time since its last update (from 3 s, `useElapsed`), then “3 parts” when done or “Couldn’t finish” in red. Hovering a row frames its parts on the canvas. Clicking a row (its chevron nudges right on hover) opens the subagent over the whole Agent panel (`SubagentView`, sliding in with `animate-push-in`): a header with Back (Esc), its glyph and name, and Select 3 Parts once done (no status in the header); then its own feed (`SubagentFeed`) following the bottom like the chat: the lead's brief as the user message, then its thoughts, text and steps in the order they arrived (`childSegments`; steps grouped like the chat's), a “Thinking…” or “Working…” line at the bottom while it runs with the time since its last update (`WorkingStatus`), and its report. The composer stays mounted underneath, so a draft survives. While open, its parts stay framed on the canvas (`openedFocus`); the open subagent is per scene (`useAgentSession.openedDesigner`) and closes on its own when its chat isn't shown. While designers run, the lead's status reads “Waiting on ⟨name⟩” or “Waiting on subagents”.
  - **Plan card:** shows the agent's TodoWrite list with live status.
  - **Reply actions** (`ReplyActions`, under the last reply while the chat is idle): a run that was stopped (Stop, or the agent's turn or token limit) ends in “Stopped” + [Continue], which sends “Continue” as a message; a run that failed ends in “Couldn’t finish. ⟨reason⟩” (`AcpChatMessage.failed`, the error without IPC prefixes; the toast still shows) + [Retry], which resends the last user message with its images and folders (`resendPayload`, so it works on chats reopened from History) and replaces the failed reply, or keeps it when it streamed work. Revert Changes sits in the same row.
