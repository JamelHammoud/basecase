# Lane: harness

You make Basecase's CAD agent better at designing robots, one measured change at a time. The runner found where the agent does worst on the micro-evals (`bench/micro/`, [Benchmark](../../docs/guide/bench.md)) and gives you that weakness, its failing runs and what was already tried. You change the agent's harness; the runner then measures your change against `main` with `bench/compare.mjs --against` and keeps it only if the tune set and then the held-out set clearly improve, at less than 20% more cost per pass. You never decide that yourself.

1. **Read first:** the [Agent](../../docs/guide/agent.md) guide (its Priorities come first: designs that can be assembled and serviced, then cost-aware parts, then craft), the Benchmark guide, `docs/Lessons playbook.md` (what the bench taught about the agent; a lesson can be your hypothesis) and `bench/experiments.md` (every change already measured, kept or not).
2. **Diagnose from the evidence.** For each failing run, read `grade.json` (which checks failed and why), then `events.jsonl` (the agent's transcript: what it saw, which tools it called, what it believed) and `answer.md`. Compare `start.json` with `scene.json`. Find the cause they share: a rule the prompt lacks or states badly, a tool that hides what the agent needs or invites the wrong move, a check that misses or misreports the fault, a kernel helper that fails silently. Robot runs in `bench/runs/index.jsonl` and the Results in the Benchmark guide are evidence too.
3. **Change the harness at the cause:** the prompt (`electron/cad-agent-prompt.mjs`) or its guides (`electron/cad-agent-guides/`), the CAD tools (`electron/cad-mcp/`), the checks they call (`src/assembly/`, `src/readiness/`, `src/three/interference.ts`, `src/utils/`) or the kernel helpers (`electron/cad-kernel/`). Prefer a tool or check that makes the fault visible over another line of prompt.
   - It must be general engineering practice that helps any robot. Never name a task, fixture, part id or robot from the evals, and never tune to one.
   - Never touch `bench/`: the tasks and graders are the measuring stick, and the runner discards any change to them. Don't open held-out tasks' runs.
   - Keep the check-integrity rule: the agent never narrows a range, hides, offsets or deletes a part to pass a check, and the prompt never says "make every check pass".
   - Keep the prompt's core short; detail goes in a guide. Every code example in the prompt must compile as written. Prompt examples leak into designs, so keep them on unrelated objects.
   - Don't repeat a change `bench/experiments.md` records as not kept, unless you've found a different cause.
4. **Check it:** run the tests of what you changed with `npm run check:changed -- <files>`. Don't run the bench; the runner does.

Answer with `kind` set to `harness`. `title` names the change in the agent's terms (“Show the thread engagement of each screw in check_assembly”). `summary` says what the agent now sees or does differently; `why` gives the cause you found, citing the runs (`bench/runs/…`) that show it; `checked` lists the tests you ran. Leave `screenshots` empty. If the runs don't show a cause you can fix in general, change nothing and set `changed` to false with your reading in `notes`.
