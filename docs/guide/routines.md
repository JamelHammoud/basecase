# Routines

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8j. Routines

A Routine is an inspectable flowchart that runs as one background skill plus prioritised reactions. It lives in `src/routines/`, and its coordinator in `hw/coordinator/`.

- **The graph is the truth.** Sentences are an entry point, and plain English is generated back from the graph.
- **The motor loop never depends on a Routine.** Control reads one atomic slot, so a hung model or LLM can't stall motors.
- **Sim runs the code the robot runs.** One coordinator crate builds natively and to WASM.
- **A Routine is data, never code.** `Routine` (`schema.ts`) is plain JSON: it survives `structuredClone`, a file and a hash. No callbacks, no scripts.

### Shape

- **Base:** one `do` step that loops for the life of the Routine. Its `timeoutMs` is how long the Routine runs (the greeting walks for 5 min). When it runs out or fails, its path runs, then the robot stops with `safeStop`. Reactions only fire while the base runs, never on its path.
- **A Routine made by hand** (`newRoutine` in `edit.ts`) has a base `do settle` with id `start` and a 500 ms `timeoutMs`; its `onTimeout` path is the person's steps, in order. The flow labels the base Start and draws its timeout edge solid, as the main path.
- **Watchers** run perception models at 1–30 Hz and publish one fact each. A fact is fresh for `maxAgeMs`; a stale fact is unknown, and an unknown condition is never true (Kleene logic, so `not` of stale is still unknown).
- **Reactions** fire on the rising edge of `when`, in array order of priority: a higher one preempts a lower one; a lower one is dropped (or queued with `onRetrigger: 'queue'`) while a higher one runs. `cooldownMs` drops edges that come too soon after the last start. One reaction runs at a time, so coverage stays enumerable.
- **`keepGoing`** runs the steps while the base keeps its resources (say while walking). **`stopFirst`** stops the base through its `stopVia` skill first (at the next phase for an `atPhase` skill), then runs the steps, then resumes the base.
- **Steps:** `do`, `say`, `infer`, `ask`, `if`, `wait`, `together`. A `do` may carry `move`: `{ distance, speed, heading }` (metres, m/s, degrees with 0 ahead and 90 left) drives that far with `walk`, `{ turn }` (degrees, + left) turns that far with `turn-away`. The skill ends when the odometry says it has gone that far, the way a real drive controller reports done; the coordinator never sees the numbers, they ride on the plan op (`PlanOp.move`, which the Rust reader ignores). A move needs a distance or a non-zero turn (`schemaValidate.ts`). Every step except `if` and `together` has `timeoutMs`, `onTimeout` and `onFail`. An empty path means: end the reaction. There are no gotos; a path always ends the reaction.
- **Facts and names.** An `infer` or `ask` step publishes a fact named by its `id` (`recognize`, `ask`). Optional step `id`s name nodes for mocks, faults, traces and the flow UI; without one a node is named after its skill, its model's fact name (`factNameOf` in `nodes.ts`: Check Face publishes `recognize`, See Person `person`) or its kind (`say`, `say2`), so a Routine whose infer steps carry no ids still reads the facts it means.
- **Templates:** `{name}` is the name of the only identity fact checked so far; `{fact}`, `{fact.score}` and `{fact.name}` read any fact.

### Compiler refusals

`compileRoutine(routine, { skills, provenTransitions?, capabilities?, modelHash? })` never throws; it returns `{ ok, plan }` or `{ ok: false, errors: [{ code, message, path }] }`. Messages are user-facing copy (§3).

| Code | Refused when |
|---|---|
| `not-a-routine`, `schema-version`, `invalid-field`, `too-large`, `duplicate-id` | the input isn't a Routine of this schema, or is malformed, too deep or too big |
| `missing-timeout` | a guarded step has no positive `timeoutMs`, `onTimeout` or `onFail` |
| `resource-conflict` | two `together` branches hold the same resource, or a `keepGoing` reaction holds what the base holds |
| `holds-mismatch`, `unknown-skill`, `needs-training`, `unsafe-safe-stop` | a step's `holds` differ from its contract, the skill doesn't exist or isn't trained, or `safeStop` hands off to another skill |
| `unproven-transition` | a skill pair has no proof (at least 8 seeds, no falls, matching `modelHash`) and isn't the skill's own `stopVia` |
| `unbounded-ask`, `ask-holds-resource`, `timeout-out-of-range` | an Ask retries from its own failure path, its reaction's cooldown is under 5 s, a reaction asks more than 4 times, Ask holds anything, or Ask isn't given 0.2–60 s |
| `unguarded-name`, `use-before-set`, `unknown-slot` | a `{name}` isn't under an `if` on its identity fact, a model's answer is read before the model runs, or a slot names nothing |
| `unknown-fact`, `type-mismatch`, `unknown-answer`, `unknown-model` | a condition reads a missing fact, compares it the wrong way, names an answer Ask can't give, or uses a model the catalogue lacks |
| `rate-out-of-range`, `stale-by-design`, `wait-never-ends`, `uninterruptible`, `empty-reaction`, `missing-capability` | other graphs that can't run as written |

Transitions are tracked per resource. A `stopFirst` reaction starts from the hubs (the `stopVia` of every body skill in the Routine) and ends back at the base skill; a timed-out `do` hands off to its `stopVia`. Never blend skills linearly.

The plan is flat: ops only jump forward (the compiler emits in reverse and renumbers), so the coordinator can't loop, and `plan.hash` is the SHA-256 of its canonical JSON (`planHash`).

### Runtime tiers

| Tier | Rate | Rule |
|---|---|---|
| Control | 50 Hz | reads one 64-bit atomic slot and never waits; trips to `safeStop` when the slot's sequence stops changing for `controlDeadlineMs` (500 ms) |
| Coordinator | 20 Hz | `tick(now)` runs the plan; no allocation on the tick path |
| Perception | 1–30 Hz | publishes into a latest-wins mailbox of one per fact (seqlock; older stamps are dropped) |
| Remote LLM | 0.2–60 s | `ask` only: never holds a resource; an answer outside its list fails the step |

### Coordinator crate (`hw/coordinator/`)

A standalone Cargo workspace with no dependencies, so it builds offline and the same way everywhere. Rust follows §0 in spirit: no comments, `clippy -D warnings` with complexity 15, 120-line functions and 4 arguments (`clippy.toml`), and no `unwrap`, `expect`, `panic` or indexing outside tests, so a hostile plan can't panic it. `cargo fmt` formats.

- **Frozen slot layout:** `IntentSlot` is one `AtomicU64`: bits 0–15 body skill, 16–31 head skill, 32–63 sequence (bumped every tick). `0xffff` means no skill. `ControlReader` is the control tier's side.
- **Facts:** `FactBoard` (an `Arc` from `Coordinator::board()`) takes publishes from other threads; the coordinator copies them in at the start of each tick.
- **Host calls between ticks:** `complete(token, ok, (num, sym))`, `answer(token, index)`, `phase(token)`, `stop()`. Tokens come from `run` and `opStart` trace events; late or unknown tokens are ignored.
- **Trace events** are fixed records (`t`, kind, `a`, `b`, `c`, `v`) in a 256-slot buffer, written as JSON into a preallocated buffer by `drain_json`. Overflow adds one `lost` event.
- **WASM exports** (`ffi.rs`): `coord_alloc`, `coord_free`, `coord_load`, `coord_tick`, `coord_drain`, `coord_drain_ptr`, `coord_publish`, `coord_complete`, `coord_answer`, `coord_phase`, `coord_stop`, `coord_watchers`, `coord_control`, `coord_control_tripped`. The plan goes in as JSON in linear memory: `coord_load` takes a pointer and length from `coord_alloc`, and the caller frees that pair with `coord_free`. There is one coordinator per WASM instance (`coordinator.ts` makes a fresh instance per run).
- **Build:** `npm run build:routines` builds `src/routines/coordinator.wasm` and records the source and WASM hashes in `coordinator.build.json`; a unit test fails when the Rust changed and the WASM wasn't rebuilt. `npm run check:routines` rebuilds in a temporary folder and checks the bytes match. Built from inside the crate, Cargo's target folder is `node_modules/.cache/basecase-coordinator` (`.cargo/config.toml`). Cargo reads that config from the working folder, so `--manifest-path` from the repo root (the gate) still writes `hw/coordinator/target/`, which Prettier reads until the root `.prettierignore` lists `target`.
- **Parity:** `tests/parity.rs` records inputs and the native trace in `tests/fixtures/`; `coordinator.test.ts` replays the same inputs through the WASM and must match byte for byte. Regenerate with `UPDATE_FIXTURES=1 cargo test --test parity`.

### Scenario tests (L0)

`runScenario(plan, scenario)` runs the real WASM coordinator on virtual time with mocks. A scenario is `{ covers, world: [{ at, fact, value }], mocks, faults: [{ node, at, kind }], seconds, expect }`; times are in seconds.

- **Mocks:** watchers read `world` (default false); `mocks[node]` overrides. An identity mock is `'known'` (Maya, 0.83), `'unknown'` (0.31) or `{ name, score }`; an Ask mock is one of its answers (default the first). Latencies: infer 200 ms, Ask 1.5 s, a skill 1 s, speech 300 ms + 40 ms a character; the base skill never ends and reports a phase every 500 ms.
- **Faults:** `hang`, `fail`, `garbage` (an answer off the list, NaN from a watcher) and `slow` (10×), on any op node, skill, watcher, or `coordinator`. A fault on a node the plan doesn't have fails the scenario.
- **Expectations:** `always`/`never` (skill or said text in a window), `said`, `saidExactly`, `skills` (the body skills control ran, in order), `visits`, `elapsed`, and event counts (`{ event, reaction, node, fact, why, count, from, until }`).
- **Invariants checked in every run:** no gallery name is said unless the face check returned that name, nothing fires or speaks after a safe stop, two things never speak at once, and control never waits more than 20 ms.
- **Generated scenarios** (`generateScenarios`): the idle scenario stops 0.1 s before the base runs out; a base failure is only generated when the base runs over 2.5 s (a 500 ms Start ends before a phase could report the failure); the coordinator hangs at 5 s or half the base, whichever is sooner. Every op outcome and branch of every reaction (found by a forward route and a condition solver), thresholds hit exactly and just missed, preemption both ways, cooldowns, retriggers, stale watchers, base timeout and failure with their paths, a stop that never ends, a base that never reaches a phase, and a coordinator that hangs. Expectations come from an abstract run of the plan (`generateModel.ts`). Each has a unique `covers`.
- **Later tiers plug in here:** L1 (MuJoCo with real policies) replaces the skill mocks in `scenarioHost.ts`; L2 (rendered frames through real detectors) replaces the watcher and infer mocks. Scenario shape and expectations stay the same.
- The 1,000 reruns, 200 mutants (`mutate.ts`) and the canary live in `verify/routines/`, not `npm test`.

### Explanations

`explain.ts` builds sentences from trace events only, never from an LLM: "Said Hello Maya at 1.2 s because Check Face matched 0.83 (needs 0.60)". The cause is the nearest timeout, failure or branch that leads to the event, read with its condition leaves; otherwise the reaction's trigger. `describeRoutine` writes the graph as plain English.

### ML nodes

`nodes.ts` is the catalogue: id, label, inputs, outputs, tier, where it runs, model, licence and a `measuredMs` slot that stays empty until a node is measured on that device. Face recognition is a normal node: `gallery.ts` holds enrolments locally (normalised embeddings, newest 16 per person) and Forget removes a person and every embedding. The gallery file belongs in `library/` and never in git. This stage runs on mocks; real inference comes later.

### Flow, L1 and the app (interface)

Stage 4b is judged by `s4b-routines-flow` (§0k); its tests in `verify/routines/` are the contract, and type stubs are in `verify/routines/interfaces.ts`.

- **Flow** (`flow.ts`, with `flowTypes.ts`, `flowRead.ts`, `flowLight.ts`, `flowLabels.ts`): `routineToFlow(routine) → { routine, nodes, edges }`, `flowToRoutine(flow) → unknown` and `lightFlow(flow, events) → { states, rejected }`, all pure.
  - `flow.routine` is the Routine's own fields (everything but `base`, `watchers`, `reactions`). A node is `{ id, kind, data }`, kind `base`, `watcher`, `reaction`, `end` or a step kind; `data` is that object minus its child sequences (`then`, `else`, `branches`, `onTimeout`, `onFail`, `steps`), so a step without an id stays without one. Step node ids are the compiler's names (`CompileContext.names`), the base is `plan.base.node`, watchers and reactions keep their ids and order.
  - Edges: `next` chains a sequence (and a reaction to its first step); `then`/`else` go to a branch's first step and are absent for an empty branch; `branch` goes to each `together` branch in order; every guarded node (base, `do`, `say`, `infer`, `ask`, `wait`) has exactly one `timeout` and one `fail` edge, to the path's first step or to an `end` node (`end:<node>:<kind>`, an id no step can have) for an empty path; `trigger` joins each fact a reaction's `when` reads (a watcher, or an infer or ask node) to the reaction.
  - `flowToRoutine` walks the edges back. A missing `timeout` or `fail` edge leaves that key out, so the compiler refuses it (`missing-timeout` on `…onTimeout`); a missing base, a loop or a dangling node returns `null`, which the compiler refuses as `not-a-routine`. It never throws.
  - `lightFlow` starts every non-end node `idle`; `opStart` → `active`, `opDone` → `done`, `opFail` → `failed`, `opTimeout` → `timedOut`, `opCancel` → `cancelled`, `branch` → `then`/`else`, `fired` → `active` and `ended` → `done` on a reaction. Any event naming a node or reaction the flow lacks goes to `rejected` and changes nothing; other events (`said`, `watcher`, `result`) name nodes the flow has and leave their state alone.
- **Capabilities** (`capabilities.ts`): `sceneCapabilities({ parts, joints })`. Cameras give `camera`; Depth Cameras give `depth` and `camera`; a Displays & Audio part is a `speaker` when its name says speaker or amplifier and a `microphone` when it says mic. Movers come from `classifyRobot` (§8d): legged → `legs`, wheeled → `wheels`, both for wheel-legged; a joint with `limb: 'arm'`, or a fixed robot with movable joints other than a neck, gives `arms`; a movable neck joint (`limb: 'neck'`, or `neck`/`head` in its name) gives `head`.
- **Kit for Routines** (`physicsKit.ts`, `physicsBody.ts`): `routineKit(mj, robot, { skills?, model? })` returns `{ skills: SkillContract[], modelHash, problems, policies }` for `walk`, `settle`, `turn-away` and `look-at`. `modelHash` is `modelHashes(model).physics` (§8i). The policies are Motor Kit skills (§8i) found by name: Velocity tracking drives `walk` (command 0.2 m/s forward) and `turn-away` (0.6 rad/s counter-clockwise); Settle to neutral (or Stand) drives `settle`; `look-at` turns the neck servo to 25° while the body policy keeps running (the policy controller's `hold`). A policy fits when every joint it drives exists by id, so a Kit policy for the quad drives the greeter's legs.
  - A skill is `ready` only when it runs in MuJoCo on this model: every transition pair (walk → settle, settle → walk, settle → turn-away, turn-away → walk, turn-away → settle) runs 8 seeds from starts 2° off the pose, 1.5 s in the first skill and 2 s in the second, and the second must do its job each time (walk travels 8 cm, turn-away turns 0.3 rad, settle moves under 2 cm in its last 0.5 s, look-at holds the neck within 6°). Falls go into each `TransitionProof`, which the compiler checks. No policy, no neck, or a policy that doesn't do the job → `needsTraining` with the reason in `problems`.
  - Where the policies come from: `skills` when passed (the app may pass the scene's own), else `loadKitLibrary()` (`kitLibrary.ts`), which reads `src/routines/kit/*.skill.json`, so L1 and the app run on a clean clone.
  - **The committed Kit policies** (`src/routines/kit/`, a deliberate output, §0g, Prettier-ignored): quad-servo Velocity tracking and Settle to neutral, the `Skill` files the `s3a-motor-kit` gate's Kit run wrote (`verify/out/kit/quad-servo/<entry>/skill.json`), weights unchanged. They drive the greeter quad's legs; its head joint isn't in the policy, so `look-at` holds it. `manifest.json` lists each file with its robot, skill, Forge version and commit, MuJoCo version, training steps and wall time, and its Arena line; `kitLibrary.test.ts` checks the manifest against the files. The loader types its glob with `as`, not `import.meta.glob<Skill>(…)`: under Vitest the generic form came back empty while the folder held two skills. To refresh them, run the gate, then `node tools/routines/kitLibrary.mjs quad-servo:velocity-tracking quad-servo:settle-to-neutral` (it copies the skills and writes the manifest; it names the commit at HEAD, so fix the manifest's `forge` line if you commit in between) and rerun `s4b-routines-flow`. Passing the Kit's Arena isn't enough on its own: for MuJoCo 4.0 two quad Velocity tracking policies passed it, and the one from the second run turned the greeter only 0.20 rad in `s4b-routines-flow` (0.3 needed), so the committed one is the first run's (34M steps, first try, 30 of 32 Arena runs with servo delays), which passes both.
  - **Scripted drive.** Without a Kit policy, `walk`, `turn-away` and `settle` run on the scripted drive the Drive panel uses (`physicsDrive.ts` → `driveAccess`: four or more legs, or wheels; never a biped, a wheel-legged robot or an arm), and are proven the same way, 8 seeds a pair. Commands scale to the gait's full stride at 0.2 m/s and 0.6 rad/s (`SCRIPTED_FULL`), and the drive loop stays alive across skill switches so the gait never restarts mid-stride (`applyControl`). `look-at` still needs a Velocity tracking policy. The fixture quad, hexapod and rover prove all three in 0.6–4 s. A Kit policy always wins over the scripted drive.
  - **Other skills.** Library skills that aren't the Kit's run by their own controller, matched by `skillId(name)` (`Jump` → `jump`); anything else runs the settle controller.
- **L1 runner** (`physicsRun.ts`, `physics.ts`): `runPhysicsScenario(plan, scenario, { mj, robot, kit })` builds the fixture model (`modelOf`) and runs `PhysicsRun`: the L0 schedule (`startScenario` in `scenario.ts`: watchers, coordinator at 20 Hz, control at 50 Hz on the virtual clock), with each control change switching the MuJoCo controller (`controllerFor`) and physics stepped 20 ms per control tick. Perception, speech and Ask stay the L0 mocks; a `do` with a `move` ends when the body has gone that far from where the step started (straight-line distance in the ground plane, or accumulated yaw), through the host's `motion` hook (`ScenarioHost.motion`, `PhysicsRun.startMove`), and runs `walk` or `turn-away` with the move's command; other skills end on their own clock (`SKILL_SECONDS`: settle 1.5 s, turn-away 2.5 s, look-at 1 s; the base reports a phase every 500 ms). Samples every 50 ms: `{ t, base, yaw, tilt, joints }` in MuJoCo's world (metres, z up, radians). A fall adds a failure and sets `fellAt`. Same inputs give the same trace and samples.
- **In the app** (`src/workspace/useRoutines.ts`, on `SimTraining.routines`): a scene holds several Routines in `project.routines`, saved with the scene (`useRoutineStore.ts`); the view shows one, the first unless another is picked. `make` validates, stores the Routine (replacing one with the same id), builds the scene's `SimModel`, gets the Kit from `routines.worker.ts` (MuJoCo off the main thread, cached by physics hash in `routineCheck.ts`) and compiles with the scene's capabilities; any change to parts or joints recompiles. `test` runs `generateScenarios` through L0 in the worker. `runLive` loads the live sim and sends it the plan (`Simulation.runRoutine`, `routineLive.ts`): the sim worker steps `PhysicsRun` in real time on the live engine, so the canvas, `sim.stats` and anything that follows the live sim see the Routine move, and each frame brings the new trace events. `runHeadless` runs L1 in the worker and returns `{ passed, said, failures, fellAt }`.
- **Agent tools** (`electron/cad-mcp/routineTools.mjs` → bridge kinds → `agentRoutineRequests.ts`; replies are one JSON object as text): `make_routine { sentence, routine }` → `{ ok, errors?, nodes: [{ id, kind }] }` (the sentence fills `routine.sentence` when it's missing; a Routine with the id of one in the scene replaces it); `read_routine {}` → `{ routine, routines: [{ id, name, active }], nodes, compiled }`, hand edits included; `edit_routine { id?, edits }` → `{ ok, changed, errors?, nodes }` runs the same `RoutineEdit`s as the view through the same `editInSet`, so neither side loses the other's edits; `test_routine {}` → `{ passed, scenarios: [{ covers, passed }], errors? }`, `passed: false` when it doesn't compile; `run_routine { scenario, live? }`, where missing scenario fields default (20 s, at most 60), → `{ started: true }` at once with `live`, else the headless result. A Routine that doesn't compile never starts (`{ started: false, message, errors }`).
- **UI** (§5): the Routines tab in the Play view. `[data-testid="routine-flow"]` holds the header, the status, the Add buttons, the canvas and the step's fields (`[data-testid="routine-step"]`); each node is `[data-flow-node="<id>"]` with `data-state` from `lightFlow` over the latest run's trace, each edge a `<g data-flow-edge data-from data-to data-kind>`. Nodes carry their size and handles, so edges draw in the same frame as nodes. Add Camera (`routineMount.ts`) places the catalog part on the head (added to the neck joint's children) or on top of the body (added to the parents of the joints that hold it), so it moves with the robot; the recompile follows from the parts change.
- **Dev hook:** `__studio.routineState() → { routine, compiled: { ok, errors? , plan? }, tests, run: { live, done, trace, said } }`.
- **Soak** (`hw/crates/routine-soak`, §8k): `routine-soak --plan <plan.json> --seconds <n> --workers <n> --hang <node> --hang-seconds <n>`. Threads: `workers` spinning at the lowest priority; perception publishing every watcher fact at 10 Hz (person seen from 2 s); the native coordinator at 20 Hz with mocked completions (infer 200 ms at 0.83, say 900 ms, skills 1 s, base phases every 500 ms, Ask answered after 1.5 s except the hung node, whose answer comes `hang-seconds` late and is ignored once the step timed out); and the control loop at 50 Hz at the highest priority, reading the coordinator's slot through `ControlReader`, turning `walk` into a gait and writing it to the daemon's intent slot, then ticking the daemon (Look mode) on the emulated Feetech bus. It sleeps to 1.5 ms before each tick and spins the rest. Its last stdout line is the JSON report: lateness against the 20 ms schedule (`p50_us`, `p99_us`, `p999_us`, `max_us`), `tripped`, ticks per body skill, coordinator ticks, and `hung: { node, started_ms, answered }` (`answered` is true only if the coordinator accepted the late answer).

### Building by hand

The view edits the Routine itself; the graph stays the truth and a hand edit is a `RoutineEdit` on it (`edit.ts`, pure, never throws): `insert` a step at a path index, `remove` a step, watcher or reaction (never the base), `move` a step to another path index (never into itself), `update` fields on a step, watcher or reaction (never its paths, `kind` or `id`), `addWatcher`, `rename`. A path is `{ parent, key, branch? }` (`editLocate.ts`): the base's or a step's `onTimeout` / `onFail`, an If's `then` / `else`, a Together's `branches[i]`, a reaction's `steps`. Node ids are the compiler's names (`RoutineIndex`), so edits address the nodes the flow draws.

- **Adding.** `insertPoints(routine)` gives every place a step can go: one per edge (drawn as a “+” at the edge's middle) and one after the last step of each path and in each empty If branch (drawn as a “+” node under the step, labelled Yes or No for a branch; these are not flow nodes and carry no `data-flow-node`). The step menu (`stepMenu.ts`, `AddStepMenu.tsx`) groups Move (Drive 1 m ahead at 0.2 m/s, Turn 90° left, Stop: `settle`), Skills (every Kit or library skill the robot has besides walk, turn-away and settle, then Any Skill, which names one by hand), Talk (Say, Ask), Logic (Wait 1 s, If sees a person, Repeat, Together) and Senses (each perception model in `nodes.ts` as a Check step). It's keyboard navigable (↑ ↓ Home End, Enter) and focuses its first item.
- **Defaults keep the compiler's rules.** Every new step has an id of its own (`uniqueStepId`: `drive`, `drive2`…), a time limit and empty timeout and failure paths, which end the Routine safely. A move's time limit is twice its expected time plus 5 s (`moveTimeoutMs`), and grows when the distance, speed or angle does. If adds a `person` watcher when the Routine has none. Repeat copies the step above with fresh ids: the plan has no loops, so a repeat is a copy. Each edit adds what the Routine now needs to `requires` (`withNeeds`: a mover from the scene, a speaker for Say, a camera or microphone for a sense) and is refused whole when the result wouldn't validate (`editInSet`).
- **Editing.** Selecting a node shows its fields under the flow (`StepPanel.tsx`): Distance, Speed, Heading or Angle for a move, Skill and Time limit for a skill, the text for Say and Ask, Wait, the fact and Yes or No for If, All or First for Together, the model for a Check, the rate for a watcher, the cooldown and Keep Going or Stop First for a reaction. Numbers commit on Enter or blur, one history step each. Dragging a step onto a “+” moves it there; dragging from a step's handle to another step moves that step after it (from an If's side handles, into Yes or No).
- **Deleting.** ⌫ or right-click Delete removes a step at once with “Deleted ⟨step⟩” and Undo, like a part. Deleting a whole Routine asks first.
- **History.** ⌘Z / ⇧⌘Z step back and forward through the scene's Routines (`editHistory.ts`, 100 steps, kept per scene tab and not saved), including new, renamed, deleted and agent-made ones. The view owns its edits (`data-own-edits`), so the Edit menu's Undo, Redo and Delete reach it as an `own-edit` event while it has focus, and never touch the scene.
- **Fixes on the node.** A step whose skill isn't ready or doesn't exist shows Needs Training with Train ⟨skill⟩ (`onTrain(skill)`); a step whose transition isn't proven shows Stop First, which puts a Stop before it. Other compiler messages sit on their node.
- **Running.** Run (⌘↩) runs the open Routine live in the sim (`runLive`) for its worst case: the base, then each step's time limit, plus 3 s, at most 60 s (`runSeconds`). The trace lights the nodes as it runs.
- **Proof.** `edit.test.ts` covers each edit, history and a hand-built Routine passing every generated scenario; `routineSet.test.ts` covers hand and agent edits keeping each other; `handBuilt.test.ts` builds Drive 1 m, Jump, Stop through the menu's own edits on the fixture rover, compiles it against the rover's proven Kit plus a fixture Jump, and runs it in L1: the drive ends at 1 m or more, and the robot finishes within 0.1 m of 1 m (completion is seen within one 50 ms coordinator tick at 0.2 m/s, about 1 cm, plus the stop's coasting); `e2e/routines.e2e.test.ts` does it in the app.

### Interfaces for the next stages

- **Flow UI:** render `Routine` directly; node ids are `plan.ops[].node`; live trace lighting maps `opStart`, `branch`, `fired` and `said` events to those nodes; error `path`s name nodes; `describeRoutine` and `explainTrace` give the words.
