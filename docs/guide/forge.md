# Forge

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8g. Forge

Forge is Basecase's native trainer and batched physics, in `forge/`. It replaces Python for training, so nobody needs a terminal, uv or PyTorch to teach a robot.

- **C MuJoCo stays the compiler and oracle.** Forge links stock `libmujoco` to compile the generated MJCF and to check its own results. We never fork MuJoCo's C code. Forge's own engine is a reimplementation of MuJoCo's formulation for the subset Basecase generates.
- **Same events as the Python trainer.** Forge prints the same JSON lines on stdout, so `electron/trainer.mjs` barely changes.
- **Anything outside the subset routes to C MuJoCo, never silently.** The feature matrix refuses what it can't simulate exactly.
- **Speed claims use one number:** time-to-skill from `verify/`, not steps per second.

### Crates

| Crate | What it is |
|---|---|
| `forge-mujoco` | Our minimal FFI to stock `libmujoco`: `Model`, `Data` and the `mjb_*` batch API (`Batch`). A small C shim (`src/shim.c`) reads struct fields, so Rust never mirrors MuJoCo's struct layouts; `src/fields.c` reads any compiled model or data array by name through `mjxmacro.h` (`Model::array`, `Data::array`) |
| `forge-ir` | Lowers a compiled MuJoCo model to `Kernel`, plain data for Forge's own engines, or refuses it with every reason in readable words |
| `forge-sim` | Forge's SIMD and Metal engines and the `forge-sim` CLI: parity runs, batch identity and the bench. `RowBatch` (SIMD) and `MetalBatch` (Metal) step MuJoCo-layout state rows, so `forge-train` can swap either in for `Batch` |
| `forge-metal` | The only `unsafe` Metal code: a small safe wrapper over `objc2-metal` (device, shared buffers by id, runtime compilation, one command buffer per run). Off macOS every call says the backend needs a Mac |
| `forge-train` | The `forge-train` binary: PPO (default), FastSAC and FlashSAC on C MuJoCo batch (or Forge's SIMD engine with `backend: "simd"`, its Metal engine with `backend: "metal"`), the drop-in for `electron/trainer/train.py` |
| `forge-id` | System identification: finite-difference Gauss-Newton (Levenberg-Marquardt) on C MuJoCo batch |
| `forge-reward` | RewardLang parser and CPU interpreter, plus `handwritten::{stand, walk}`, the rewards `train.py` uses |

### Building

- `cargo build --release --manifest-path forge/Cargo.toml` from the repo root; `npm run check` never runs cargo, so it stays seconds-fast. The gates run `cargo test --release`.
- **MuJoCo comes from DeepMind's release.** `forge-mujoco/build/` downloads the pinned release (3.17.0, the same version as the Python env and `@mujoco/mujoco`) into the gitignored `forge/vendor/` on first build: the macOS `.dmg` framework, the Windows `.zip` or the Linux `.tar.gz`, with `curl`, `hdiutil` and `tar` (all built into macOS and Windows 10+). `FORGE_MUJOCO_DIR` points at an unpacked copy instead, for offline builds or a shared copy between worktrees. `FORGE_CHECK_ONLY=1` skips the download and the C shim, for `cargo check --target` on another OS.
- **Every crate that links MuJoCo carries a two-line `build.rs`** that adds the vendored folder to the binary's rpath (`DEP_MUJOCO_LIB_DIR`); on Windows `forge-train`'s copies `mujoco.dll` beside the binary. Packaging will ship `mujoco.framework` beside `forge-train` (`@executable_path` is already on the rpath).
- **Rust style matches §0 in spirit:** no comments, files under 400 lines, functions under about 120, `cargo fmt` (`forge/rustfmt.toml`, 120 columns) and `cargo clippy --all-targets -- -D warnings` clean. `forge-ir` and `forge-sim` make clippy enforce it (`[lints.clippy]` in their `Cargo.toml` and a `clippy.toml`: `too_many_lines` at 120, `too_many_arguments` at 5, `cognitive_complexity` at 15, no `unsafe`); `forge-sim` allows `needless_range_loop`, because index loops over lane arrays read better than zipped iterators in numeric kernels. Metal shader sources (`forge-sim/src/metal/shaders/*.metal`) follow the same rules, and `tests/style.rs` checks them with the Rust files.
- **`unsafe` lives only in `forge-metal`** (`src/mac.rs`): slices over a shared buffer's contents and the encoder's `setBuffer`/`setBytes`. Slices borrow the `Gpu` and `run` borrows it mutably and waits for the command buffer, so no slice overlaps GPU work. `Gpu` and `Kernel` are `Send` because Metal's device, queue, buffers and pipeline states are thread-safe; command buffers and encoders never outlive `run`. Elsewhere `forge-metal` compiles to stubs, and `FORGE_CHECK_ONLY=1 cargo clippy --target x86_64-pc-windows-msvc` (or `x86_64-unknown-linux-gnu`) keeps both paths compiling.
- Benches: `cargo run --release -p forge-mujoco --example physics_bench -- <model.xml>` (batch stepping by thread count) and `cargo run --release -p forge-train --example learner_bench` (one PPO minibatch, per layer; add any argument for the portable kernels).

### forge-train

- **CLI:** `forge-train --job <dir>` reads `<dir>/model.xml` and `<dir>/job.json` with the same fields as `train.py` (`task`, `minutes`, `command`, `root`, `joints`, `defaultPose`, `ctrlDefault`, `initialJoints`, `rootOffset`, `actionScale`, `controlDt`, and optional `seed`, `maxIterations`, `gateEvery`, `evalSeeds`, `gateSpeed`, `envs`; `threads` caps the physics threads; `algo` is `ppo` (the default), `fastsac` or `flashsac`; `warmStart` starts from a trained policy, below; `logStdMin` floors PPO's `log_std`). `forge-train --check` prints the MuJoCo version and CPU count. `forge-train --adam-vector <file>` writes the learner's Adam test vector (below).
- **Training conditions** (all optional; without them a job is `train.py`'s environment, line for line, and draws nothing extra from the random streams; `options.rs`, `conditions.rs`):
  - `reward`: a RewardLang program (`def reward(state):`) used instead of the hand-written Stand or Walk reward. It's compiled once per job and evaluated per robot per tick; a program that doesn't compile fails the job with its line number. The Motor Kit and the solver race send theirs (§8i).
  - `commands`: `{ ranges: [[lo, hi] × 3], resampleS: [lo, hi], stillShare }`. Each robot draws `[forward, left, turn]` at reset and again every `resampleS` seconds, all zero with probability `stillShare`; the observation and `state.command` read the robot's own command. `command` stays the one `policy.json` carries and the clean evaluation runs.
  - `delaySteps: [lo, hi]`: each robot's servo targets lag its actions by a whole number of control steps, drawn per episode (a ring buffer of past actions; `last_action` stays the policy's own).
  - `encoderBias` (rad) and `imuBias` (rad): per-episode joint zero offsets added to the observed joint positions, and a roll and pitch mount bias that tilts the observed gravity. Rewards read the true state.
  - `actorLinvel: false`: linear velocity (observations 6–8) never reaches the actor. The actor's `Mlp` carries an input mask (`mask.rs`, `Mlp::mask_inputs`): its forward pass reads a copy of the observation with those columns zeroed, so their first-layer weights get no gradient, and its backward pass uses the same copy. The critic reads the full observation. `Deployed` zeroes the masked weights, so `policy.json` and the ONNX graph give the same action for any value in those inputs (the app's normalizer clips them to ±5 first). PPO and both SACs mask from the job's options when they're built; nothing projects weights after an iteration.
  - `resetNoise` (rad, default 0.05), `standHeight` (the `z0` rewards and falls compare against, for starts that aren't standing), `fallResets: false` (a fall neither ends the episode nor counts as terminal), `pushes: false`, `episodeS`.
  - Clean evaluations, gates and `policy-check.json` run without any of these, on the job's `command`.
- **Events:** the same `status`, `progress` (with `phases`: physics, observe, reward, inference, gradient), `gate` and one `done` (`policy`, `steps`, `stopped`, `eval`, `gate`). The budget counts active time only (a gap over 30 s between iterations counts as 30 s). It stops on SIGTERM or SIGINT, or on a `stop` file in the job folder (Windows has no signals), then still saves and evaluates; `stopped` is true for either.
- **Outputs:** `policy.json` in the `src/sim/policy.ts` format (weights rounded to 7 decimals like `train.py`), `policy.onnx` written by our own protobuf encoder (`src/onnx.rs`: input `obs`, output `action`, the normalizer baked in, opset 17), and `policy-check.json` with 16 raw observations and the clipped mean actions, which `verify/` replays through the app's `act()` and ONNX. Beside them, `resume.json` (`warm.rs`, format `basecase-resume`) holds what `policy.json` leaves out: the algorithm, the actor and critic as raw f32 parameters with their layer sizes (SAC: both twins and their targets, and `logAlpha`), PPO's `logStd` and adaptive learning rate, and the normalizer's exact mean, variance and count. It's written at every save, so `policy.json` keeps its format for every reader.
- **Warm start** (`warmStart`, relative to the job folder or absolute): a folder starts from its `resume.json` (or its `policy.json` when there's none); a file is read as a `policy.json`, giving the actor and a normalizer from `obsMean`, `obsStd` and `trainedSteps`. The actor must have the job's layer sizes (a SAC actor also takes a `policy.json`'s mean head); otherwise the job fails before training with both shapes ("its network is 48-256-128-64-12 and this job's is 51-256-128-64-13"). The critic, `logStd` and learning rate come along only from a `resume.json` of the same algorithm and shape, else the status says the value estimate starts fresh. Masked inputs stay masked. A warm start onto new conditions also wants `logStdMin`: biped-servo's walking policy ended with four joints at a `log_std` near −6 (a standard deviation of 0.0025), where a 0.01 shift in the mean moves the log-probability by about 8, and two 12-minute continuations onto 0–40 ms servo delays held a reward of 3 for 7,500–10,000 iterations, then collapsed to −2 within 100 and never came back. With `logStdMin: -2.5` (the Motor Kit sends it with every warm start, §8i) the same continuation held for all 16,742 iterations; a floor applied only when loading collapsed nothing in one run but lost the top speed, and −1.5 stopped it walking at speed. `tests/warm_start.rs` resumes a 60-iteration run whose reward rose from 1.14 to 1.61: the resumed run's first iteration reads 1.61.
- **Same environment as `train.py`:** observation, action, reward (`forge_reward::handwritten`), termination, resets, shoves and domain randomization match it line for line. A clean run with the same actions gives bit-identical observations and rewards to `train.py`'s `Envs`. Random streams differ (per-environment xoshiro streams), so runs are comparable, not identical; a seed replays exactly.
- **PPO as `train.py` runs it, with more reuse and one rollout of overlap:** orthogonal init, ELU 256-128-64 actor and critic, `log_std` starting at −0.7, GAE (γ 0.99, λ 0.95), clipped surrogate (0.2), value loss 0.5, entropy 0.004, 4 minibatches of a 24-step rollout, gradient norm clipped to 1, Adam with the rsl_rl adaptive learning rate (KL target 0.01). `log_std` is capped at 0 after every step (`LOG_STD_MAX`, a standard deviation of one full action range): where a joint's mean action sits past ±1 the clip hides its noise, so the entropy bonus grew that joint's `log_std` without limit (to 2.6 on biped-servo, a standard deviation of 13) until the noise flipped the clipped action and the run collapsed from a reward of 3 to −1.6 in a few hundred iterations. Gradients are hand-derived (`mlp.rs`, `heads.rs`) and checked against finite differences in tests. Two things differ from `train.py`, both for time-to-skill:
  - **30 epochs instead of 5 at 64 robots** (`Hyper::for_envs`: 30 × 64 / robots, at least 5, so 1024 robots keep 5). The walk task has a slow tail: many seeds creep from 0.15 to 0.2 m/s over millions of steps. Steps to the walk gate over 8 seeds (load average 30–60, steps are the same at any load): 5 epochs needed a median of 2.4M (quad-servo, 2 seeds past 4.1M) and 2.8M (hexapod, 3 past); 10 epochs 1.0M and 1.0M; 20 epochs 350K and 540K; 30 epochs 232K, 309K and 155K (biped-servo), with every seed under 850K; 50 epochs 190K and 230K but at 5/3 the learner time. `train.py` needed 0.7–1.1M on quad-servo with 2 of 5 seeds past 8M.
  - **Learning overlaps collecting** (`ppo/mod.rs`): while the learner thread trains on rollout k, the main thread collects rollout k+1 with a copy of the weights from before that update (`Collector` in `ppo/collector.rs` holds the copy, its own inference scratch and the environments). Before learning, the rollout's log-probabilities and values are recomputed with the current weights, so the PPO ratio starts at 1 and the KL-adaptive step size isn't fooled by the one-update lag. The first iteration only collects. Over 8 seeds the lag cost no samples (quad-servo 3.0M against 2.4M, hexapod 1.0M against 2.8M at 5 epochs, within the spread).
  - **What didn't help:** 256 robots per iteration (more samples to the gate on quad-servo: 1.8–3.7M) and 256 robots with a 6-step horizon (3 of 3 seeds past 4.1M); no entropy bonus (no better than 0.004).
- **Physics is MuJoCo's own batch API** (`mjb_makeBatch` with one `mjData` per thread, not per robot), with friction, link masses and servo gains expanded per robot (`mjb_expand`). Each robot's state row keeps its warm-start, and results are bit-identical at any thread count. This answers the memory-contention finding (32 concurrent 0.9 MB `mjData` cost 3× their work): there are only as many `mjData` as threads, so `<size memory>` doesn't need trimming.
- **`backend: "simd"` opts a job into Forge's SIMD engine** (`physics.rs`). The model is lowered once by `forge-ir`; when it's in the subset, every environment (training, gates and the final checks) steps on `forge_sim::RowBatch`, which reads and writes the same state rows, takes the same `expand` tables and rethreads like `Batch`, and the run says "Stepping physics on Forge's SIMD engine". When it isn't, the job steps on C MuJoCo and the status line carries every refusal reason. Without the option nothing changes: the C batch path is untouched. `tests/simd_backend.rs` steps randomized robots on both engines with the same actions and finds the same observations and rewards (within 1e-4 in f32).
- **`backend: "metal"` opts a job into Forge's Metal engine** the same way: every environment steps on `forge_sim::MetalBatch` (same rows, same `expand` tables; `rethread` does nothing) and the run says "Stepping physics on Forge's Metal engine (Apple M5 Pro)". When the model is outside the subset, the Metal engine refuses it, or there is no Metal device (any OS but macOS), the job steps on C MuJoCo and the status line says why ("Forge's Metal engine can't step this job: …"). `tests/simd_backend.rs` checks the Metal engine against C MuJoCo the same way (within 1e-3 in f32 over 80 control steps of a randomized walk).
- **The learner:** on macOS, matrix products go to Accelerate's `cblas_sgemm`, which runs on the M-series matrix unit and measured 20× a NEON core (640 vs 30 GMAC/s on the 384 × 256 × 128 layer); the actor and critic run on two threads at once. Elsewhere `kernels/rows.rs` is portable, cache-friendly row kernels (FMA on aarch64, AVX2 + FMA detected at runtime on x86-64) split across a spin-then-park thread pool (`pool.rs`). `FORGE_PORTABLE_MATH=1` forces the portable path on a Mac. ELU uses a vectorizable polynomial `exp`; exported actions use the exact `expm1`.
- **Measured on the M5 Pro** (quad-servo, 64 robots, 60 iterations, `train.py` was about 21–25K steps/s): 84K steps/s on a quiet machine, 44–48K under heavy load from other sessions (the F1 gate measured 43.7K at a load average of 23). The portable learner, forced on a Mac, ran at 24–26K under that load. Per iteration: physics about 10 ms, gradient about 7 ms, inference about 1.3 ms. These are F1's numbers, at 5 epochs in turn.
- **Measured for F2** (every number names its load average; other sessions kept the machine busy): at 1024 robots (5 epochs, overlapped) 140.7K steps/s at load 7.7, 63.7K at load 32 and 25.9K at load 46, against 14.4K for F1's in-turn PPO at load 48. At 64 robots the 30-epoch learner is the bottleneck: 30.5K steps/s at load 9.6 (per iteration about 50 ms learning, 120 minibatch steps of 384 rows, against 12 ms collecting), 14–16K at load 34–48. Time-to-skill on quad-servo seed 0 at load 34: 32 s (460K steps), against `train.py`'s 70.6 s (1.08M steps) at load 15. `train.py`'s time-to-skill on quad-servo over 5 seeds at load 11–17: 34.5, 50.3, 70.6, 452.8 s and one seed past 20 minutes.
- **Off-policy learners** (`sac/`, `algo: "fastsac"` or `"flashsac"`, 256 robots unless `envs` is set): one iteration is one control step of every robot, then 2 updates on a batch of 1024 from a replay buffer of 262,144 transitions (raw observations, normalized when sampled; a timeout stores the observation before the reset and keeps bootstrapping, a fall cuts it). Both are SAC with twin categorical critics (101 atoms, cross-entropy against the projected target), a tanh-squashed Gaussian actor with a bounded `log_std`, and an automatically tuned temperature; they differ as their papers do:
  - **FastSAC** (Seo et al. 2025): critics 256-256 with LayerNorm and ReLU, the target averages the two critics, γ 0.97, τ 0.1, support −5…20, Adam β₂ 0.95 with weight decay 0.001, temperature from 0.001 toward a target entropy of 0, σ at most 1.
  - **FlashSAC** (Kim et al. 2026): critics 256-256 with RMSNorm whose weight vectors are projected back to unit norm after every step, the lower of the two critics in the target, rewards divided by the running return scale onto a −5…5 support, τ 0.01, actor every second update, learning rate cosine-decayed 3e-4 → 1.5e-4 over 100K updates, temperature from 0.01 toward the entropy of σ = 0.15, and exploration noise held for a Zeta(2)-distributed number of steps (at most 16). Its residual blocks and batch norm are left out: a plain normalized stack on the CPU.
  - The actor stays an ELU MLP so it exports like PPO's; its second head (`log_std`) is dropped on export. Gradients for LayerNorm, RMSNorm, the categorical critic and the squashed actor are hand-derived and checked against finite differences (`sac/dense_tests.rs`, `sac/actor_tests.rs`).
  - **They lose to PPO on time-to-skill here**, so PPO stays the default: an update costs about 5 ms on the matrix unit with these sizes, and a CPU learner can't afford the update counts the papers run on a GPU, while Forge's PPO reaches the walk gate in a few hundred thousand to a few million samples.
- **The Adam test vector** (`adam_vector.rs`): a 12-64-32-4 ELU MLP with random biases, 50 Adam steps (lr 1e-3) on the mean squared error of 64 random targets, using the same `Mlp` forward and backward and `Adam` as training. `verify/forge/adam_check.py` replays it in torch: worst difference 1.2e-7.
- **Delayed servos start primed.** Catalog servos carry MuJoCo's native actuator `delay` (§8d); an empty control history makes every reset kick the robot. `settle()` fills each delayed actuator's history with `ctrlDefault` (`Data::hold_delayed_controls`, `mj_initCtrlHistory` with `nsample` samples one timestep apart ending now) once before the settling second and again after the clock is reset to 0, as `train.py`'s `hold_delayed_controls` does. Batch rows hold `mjSTATE_INTEGRATION`, which includes the history, so every episode reset restores it. `forge-id` primes its start row with the experiment's first control. `tests/delayed_servo.rs` checks that a robot reset from the start row moves exactly like one without delay, and that an unprimed history would kick it.
- **Gate checks run beside training.** When `gateEvery` is due, the policy and normalizer are copied and checked on 32 clean robots on a scoped thread with at most 6 physics threads, while training goes on. The `gate` event carries the iteration and steps of the copy it checked, so time-to-skill reads the `progress` line of that moment; training stops once a passing result comes back. `train.py` checks in line, so its gate time counts against it.
- **Physics threads tune themselves** (`threads.rs`) unless `threads` is set: every 240 control steps one trial of 24 steps runs on a neighbouring thread count (all cores, ¾, ½, ⅓, ¼), and the count moves when the trial is 3% faster. `Batch::rethread` rebuilds the MuJoCo batch with the state rows and per-robot model fields, so a run is identical at any thread count (tested). On a loaded machine fewer threads win by 2× (quad-servo, 64 robots, load 47: 1.9 ms per control step on 10 threads, 4.1 ms on 18).
- **The policy view** (`deployed.rs`): export, ONNX, gates and the final checks take a `Deployed` actor (an ELU MLP, its weights and a `squash`), so every learner exports the same `policy.json`. Off-policy actors are tanh-squashed: `policy.json` then carries `"squash": "tanh"`, which the app's `act()` applies before clipping, and the ONNX graph gains a `Tanh` node.
- **Platform code is isolated** in `platform.rs` (signals, macOS thread QoS), `kernels/accelerate.rs` and the MuJoCo fetch.

### forge-ir: the subset Forge's own engines simulate

- `forge_ir::lower(&Model)` reads the compiled model (after `mj_setConst`, so `dampratio`, `invweight0` and mesh hulls are MuJoCo's own) and returns a `Kernel` or a `Refusal` listing every reason ("joint hip is a ball joint; it uses the PGS solver, and Forge runs Newton only"). Nothing outside the subset is approximated.
- **In the subset:** free, hinge and slide joints; position, velocity and motor actuators on hinge and slide joints, with `delay` (zero-order hold or linear history); armature, damping, frictionloss and limits (with margins); plane contacts against convex mesh hulls, spheres, capsules, cylinders and boxes, condim 1 or 3, pyramidal cones, any solref, solimp, margin, gap, priority and solmix; the Newton solver; the implicitfast integrator; warmstart, refsafe and clampctrl on or off.
- **Refused:** other integrators, solvers and elliptic cones; noslip; fluid forces; ball joints; joint springs and polynomial damping; actuator activations, affine, muscle, DC-motor and PID gains, cubic delays, actuator damping and armature, joint-level force limits; tendons, equalities, flexes, sensors, plugins, mocap bodies, explicit pairs and exclusions, gravity compensation, height fields; disabled constraints, contacts, limits, frictionloss, damping, gravity or actuation; enable flags other than energy; condim 4 and 6; surface velocity and adhesion; contacts between two moving bodies (no hull-hull yet); ellipsoid and SDF contacts; free bodies with no jointed children (MuJoCo integrates those with a gyroscopic 6×6 solve); simple bodies.
- Its tests build their models in code (`tests/common/mod.rs`) and are part of the F3 gate.

### forge-sim: the SIMD engine

- **Layout:** structure of arrays across worlds. Every quantity is a `V`, four `f64` lanes (`lanes.rs`), so one lane is one robot and the four lanes run the same instructions; LLVM lowers the lane loops to NEON on aarch64 and to SSE2 on x86-64, which `cargo check --target x86_64-pc-windows-msvc` with `FORGE_CHECK_ONLY=1` keeps compiling. AVX2 needs every stage compiled a second time under `#[target_feature]` and picked at run time; that isn't done. f64 throughout, because MuJoCo's Newton tolerance of 1e-8 needs it. The engine is bound by moving data rather than by arithmetic: 8 lanes ran slower than 4, and 2 lanes about the same.
- **Pipeline, in MuJoCo's order and with its formulas:** kinematics, `comPos`, CRB, the tree LDL factorisation (`sparse.rs`, a precompiled update list), collision, constraint assembly (frictionloss rows, limit rows, pyramidal contact rows with MuJoCo's `diagApprox`, impedance and regularisation), `comVel`, passive damping, RNE, actuation with delay history, `qacc_smooth`, MuJoCo's warmstart choice, the Newton solve and implicitfast.
- **Fixed slots, live rows:** each contact pair owns `max_contacts` slots and each slot its constraint rows, so every lane has the same structure; a row is live when any lane uses it, and every solver loop walks only live rows (that halved the solver's time). An inactive lane in a live row gets a zero Jacobian and a reference of −1, so it is always satisfied and adds exactly nothing.
- **Lockstep Newton:** the lanes iterate together; a finished lane is frozen with selects, never stepped again, so a world's result doesn't depend on its neighbours (`--batch-identity` checks this bit for bit at 1, 3 and 8 threads). The line search is MuJoCo's own (`search.rs`, `bracket.rs`) run with per-lane masks. The cost: a block iterates as often as its slowest lane (2.6 iterations against MuJoCo's 1.6 per world on the bench). `RowBatch` therefore regroups robots before every control step, sorting them by their last contact count so that robots in the same block need similar work; a robot computes the same result in any lane, so this changes nothing but speed (single-threaded on the bench, 265K to 332K robot-steps per second), and `--batch-identity` compares the regrouped batch with each robot stepped alone.
- **Per-thread scratch:** `State` holds what persists per block (qpos, qvel, ctrl, warmstart, time, delay history, the per-world tables) and is swapped into one `Workspace` per thread for each step, like MuJoCo's one `mjData` per thread. Kinematics, Jacobians and solver scratch for one block of quad-servo take about 200 KB, so keeping them per block put tens of megabytes in play at 1024 robots.
- **Per-world tables** (`tables.rs`): body masses, geom sliding friction and servo gains (`gainprm[0]`, `biasprm[0..3]`), the fields `forge-train` randomizes, with C MuJoCo's semantics (masses change, inertias and `subtree_mass` don't).
- **What differs from MuJoCo, and why it doesn't matter:** the Newton Hessian is rebuilt and refactored every iteration instead of updated by rank-1 steps; sin and cos are a vector port of musl's kernels (within 5e-16 of libm). Both change results only at rounding level.
- **Parity, measured against C MuJoCo 3.17 on the 200 fuzzed robots of the F3 gate:** worst L0 (xpos, cinert, qfrc_bias) 4.2e-16, L1 (qacc) 8.0e-14, L3 qpos 1.3e-15 and qvel 1.7e-12 after 60 steps; contact counts identical. The fixture robots stay within 1e-9 over 2000 steps. `tests/row_batch.rs` checks rows against C MuJoCo's batch with randomized tables, linear and held delays, and every primitive foot.
- **CLI:** `forge-sim --xml <model> --steps N --backend simd|mujoco|metal` prints the gate's parity JSON (`single` after `mj_forward`, then qpos and qvel every 25 steps under `ctrl = 0.2 sin(0.01 i)`); `--batch-identity`; `--bench --envs N --seconds S [--threads N]` runs the bench below on any backend (the Metal bench also reports `gpuShare`, the fraction of wall time the GPU was busy). `cargo run --release -p forge-sim --example stages -- <model.xml>` times each stage per world-step.
- **The bench workload** is the training path: state rows stepped by `RowBatch` (or C MuJoCo's `Batch` with `--backend mujoco`, same rows, same controls), ten substeps per control step, on a rayon pool with one `Workspace` per thread. Robots reset every 2 s to their start pose plus up to 0.02 rad per joint; controls are sines around the middle of each control range, with amplitude 0, 5, 10 or 15% of the range by robot, so a quarter stand still on all feet and the rest shuffle in place. The sines advance by rotation so writing controls costs almost nothing beside the physics. `contactsPerWorld` reports the average contact count (about 2 on quad-servo).
- **Measured on the M5 Pro** (quad-servo, other sessions kept the load at 8–20): one thread, best of five 2 s runs, 355K robot-steps per second against C MuJoCo's 135K (2.6×); 18 threads and 1024 robots for 30 s, a mean of 2.99M and a slowest second of 2.78M against C MuJoCo's 1.59M and 1.47M (1.9×). The F3 gate measured a mean of 3.35M and a slowest second of 3.21M at load 6–12. Per robot-step on one thread, about 55% is the Newton solve (factorisations, Hessians and line-search evaluations in about equal parts), 12% kinematics, 11% constraint assembly and 6% collision.

### forge-sim: the Metal engine

- **One GPU thread per world, kernels generated per model** (`src/metal/`). `forge-ir`'s `Kernel` becomes MSL source: the model's tables as `constant` arrays and sizes as `#define`s (`tables.rs`, `actuators.rs`, `layout.rs`), followed by the fixed stages in `shaders/` (kinematics, CRB, collision, constraint rows, RNE and actuation, Newton with MuJoCo's line search, implicitfast). Metal compiles it at run time in safe math mode; the first compile of a model takes about 3 s and Metal caches it after that. Per-world state and scratch live in one buffer, blocked by 16 worlds so each scalar of a block is 128 contiguous bytes; threadgroups are 16 threads. `MetalBatch` packs the f64 state rows into the GPU's buffer (rayon), runs every substep of a control step in one dispatch, and unpacks them.
- **Double-float arithmetic** (`shaders/df.metal`): Metal has no f64, and f32 can't meet L0. The gate's floor of 1e-4 at 5e-5 relative allows 5e-9 absolute near zero, and a free robot's gravity torques about its own centre of mass cancel to about 1e-16 in f64 but to about 1e-7 in f32. Every real is a pair of f32 (about 48 bits): additions are Knuth's two-sum without renormalising the low part between terms, products use `fma` for the exact error. Sums run through lazy accumulators that keep only one f32 add on the dependent chain, and long expressions are summed as trees, because the GPU is latency-bound and these chains set the time. Fast math would delete the error terms, so the library is always compiled with `MTLMathMode::Safe`; `tests/metal_df.rs` checks add, subtract, multiply, divide and square root against f64 to 1e-13.
- **Where f32 is enough:** the Newton Hessian, the factorisation of M and the implicitfast matrix are factored in f32 in threadgroup memory (`factor_h`, `solve_h`; the triangular solves also keep their vector there). The Hessian only shapes the search direction: the gradient, costs and line search stay double-float, so Newton still stops on MuJoCo's tolerances (same iteration counts, 1.62 per world-substep on the bench). `qacc_smooth` and the implicit step take one step of iterative refinement against M in double-float. This was 12–15% faster than double-float factorisations; it moves qacc from within 1e-9 of C MuJoCo's to within 7e-5 on the fuzzed robots (1e-6 on the fixtures), still 15 times inside L1, because Newton now stops a little further from the exact optimum. `HESSIAN_DF` in `layout.rs` switches it back. When 16 × (nm + nv) floats don't fit the 32 KB of threadgroup memory (56-DoF robots), the matrix lives in device memory instead.
- **Rows:** contact pairs keep F3's fixed slots, but each world compacts its own live rows (frictionloss, active limits, active contact rows), so it never walks another world's rows. Collision first lists each world's contacts, then the rows are built for every world's first contact together, then its second, so a SIMD group pays for its busiest world's contacts rather than for every pair any of its worlds touches. Jacobian rows are stored densely over all dofs for `J x` (every lane reads the same index, so loads coalesce) and as chain-compact rows for `Jᵀ f` and the Hessian. Data-dependent indices that differ across a SIMD group were the most expensive accesses measured: moving chain dof lists to device memory, a dense `Jᵀ f` and a dense Hessian were all slower.
- **What the time goes to** (`cargo run --release -p forge-sim --example metal_stages -- <model.xml> [envs]`, quad-servo at 4096 worlds, GPU time per substep at load 9): kinematics 0.15 ms, CRB and factor 0.20, collision and rows 0.28, RNE, actuation and `qacc_smooth` 0.29, warmstart 0.14, start 0.12, first Hessian 0.24, the remaining Newton iterations 1.06, implicit about 0, 2.5 ms in all. The engine is bound by latency, not arithmetic: making every df operation a plain f32 operation saved only 15%, and 1024 worlds take 70% as long as 4096. Newton dominates through divergence: a world needs 1.62 iterations per substep on average, but a SIMD group waits for its slowest world (3.8 iterations in groups of 32, which is why blocks are 16). Regrouping worlds by their last contact count and solver work (as `RowBatch` does) doesn't change that, because the iteration count varies from substep to substep.
- **Refused** (on top of `forge-ir`'s refusals, so `backend: "metal"` falls back with the reason): a `solimp` power other than 1 or 2, which would need `pow` in double-float.
- **Parity, measured against C MuJoCo 3.17 on the 200 fuzzed robots of the F4 gate:** worst L0 (xpos, cinert, qfrc_bias) 4.4e-11, L1 (qacc) 6.7e-5, L3 qpos 4.6e-9 and qvel 1.5e-6 after 60 steps; contact counts identical. Before the Hessian moved to f32, L1 was 8.0e-10 and L3 qvel 9.2e-12, so L1 is the field the f32 factorisation spends. The 12 fixture robots: L0 8.7e-11, L1 1.1e-6, L3 qpos 1.8e-9 and qvel 5.1e-7. `tests/metal.rs` steps randomized rows (masses, friction, gains), linear and held delays, every primitive foot and robots of 38, 46 and 56 DoF (past the 32 DoF where another Metal port's factorisation broke) for 60 steps against C MuJoCo's batch, within 1e-5 relative (worst about 5e-7).
- **Batch identity:** a world's result never depends on its neighbours. `forge-sim --batch-identity --backend metal` steps 37 worlds alone, together, and scattered through a crowd of 300 in a shuffled order, 400 steps each, and compares qpos, qvel and the warmstart bit for bit.
- **Measured on the M5 Pro** (quad-servo, 4096 worlds, every number with its load average): the F4 gate measured a mean of 1.57M substeps per second and a slowest second of 1.50M over 60 s (load 3.5 before, 3.1 after), against the 1M it asks for. At load 10 a 20 s run gave a mean of 1.45M and a slowest second of 1.33M. The GPU is busy 97% of the wall time; the rest is packing and unpacking rows and regrouping worlds on the CPU. C MuJoCo needed 18 threads for 1.59M at 1024 worlds and Forge's SIMD engine reaches about 3M there, so on this Mac the CPU engine is still the faster one; the Metal engine leaves the CPU free for the learner.

### forge-id

- `identify(model, specs, data, options)` fits `ParamSpec`s (armature, damping, frictionloss per DOF, position-servo stiffness per actuator, body mass) to recorded joint positions. Parameters move in log space within `[low, high]`; each iteration runs the nominal and ± steps of every parameter as one MuJoCo batch with per-simulation model fields and `mj_setConst`.
- **It flags what it can't identify.** The relative standard deviation of each parameter comes from the Gauss-Newton normal matrix (residuals scaled by the sensor noise, inflated when the fit is worse than the noise). Above `max_relative_std` (2%), or tied to a null direction, the parameter is flagged and keeps its preset value; it is never reported as measured.
- The test plants servo parameters 15–25% off on a hoisted two-joint arm, records 12 s of multisine excitation through a 4096-count encoder, and recovers all eight within 1.3%. An idle joint's damping and armature are flagged.

### forge-reward and RewardLang

- **RewardLang is a Python subset that is parsed, never executed.** A program is `def` functions only; `reward(state)` is the entry and returns a number. Statements are assignments to plain names and one final `return`.
- **Pure and bounded:** the state is read-only (`state.gravity`, `angvel`, `linvel`, `command`, `z`, `z0`, `control_dt`, `joint_pos`, `joint_vel`, `action`, `last_action`, `bodies` with `pos`, `vel`, `z`); the only iteration is `sum`/`mean`/`min`/`max` over `state.bodies`; a function may call only functions defined above it, so there is no recursion. Imports, loops, `if` blocks, lambdas, lists, `__` names and unknown names are refused with a line number.
- **Total operators:** `/` only by a nonzero number or a provably positive value (`max(x, 0.05)`, `exp(...)`), otherwise `safe_div(a, b)` (0 when `b` is 0); powers are whole numbers 0–8; `exp` caps its argument at 80, `log` and `sqrt` clamp at their domain. Also `abs`, `tanh`, `sin`, `cos`, `square`, `min`, `max`, `clamp`, `dot`, `norm`, conditionals (`a if c else b`), `and`, `or`, `not`.
- **Per-term logs:** `term("name", x)` records each term. A term that comes out NaN or infinite is set to 0 and blamed by name, so one broken term never poisons the total.
- `forge_reward::programs::{stand, walk}` are `train.py`'s rewards in RewardLang; tests check them against the hand-written ones on 500 states, including falls.

### Canaries in cargo tests

A canary test (`canary_*`) runs a planted fault through the same check as the real test and must fail. It does its work only when its full name is the test filter, so plain `cargo test` passes and `cargo test -p <crate> canary_<name>` exits non-zero, which is what the gate wants.

### In the app

- `electron/trainer.mjs` runs Forge when it finds `forge-train` (the packaged `Resources/forge/`, or `forge/target/release/` in a checkout), and falls back to `train.py` otherwise. `BASECASE_TRAINER=python` forces Python. With Forge, `status()` reports ready with no `trainer-env`, so nobody installs Python.
- `npm run build:forge` builds the trainer and stages it in the gitignored `forge/dist/` (`tools/forge/stage.mjs`). On macOS it copies `libmujoco.3.17.0.dylib` beside the binary and points the binary at it with `install_name_tool`, because DeepMind's `mujoco.framework` has no root binary and codesign refuses it as a bundle. electron-builder ships `forge/dist/` as `Resources/forge/` and signs both files; Windows ships `forge-train.exe` and `mujoco.dll`, signed through `signExts`. CI builds Forge before packaging (`check.yml`, `release.yml`).
