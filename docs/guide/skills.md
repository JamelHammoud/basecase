# Skills

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8i. Skills

Train any robot to do anything you ask. The pipeline is Intent Compiler, TaskContract, Feasibility Gate, Method Router, Solver Race, Arena, SkillCard. The core lives in `src/skills/` and `forge/crates/contract`; the gate is `s3-contract` (§0k).

- **The contract judges, the reward only teaches.** Reward authors can't edit a contract, so a hacked reward can't fake success.
- **A Skill is bound to what it was proved on:** contract hash, compiled-physics hash, actuator hash, observation and action schema, and Arena evidence.
- **Moving a Skill to another design warm-starts training and never carries "verified".**

### Task contract (`forge/crates/contract`, `src/skills/contract.ts`)

One Rust crate, built native (Forge) and to WASM (the app), so both judge with the same code. `evaluateContract(contract, trace)` resolves to `{ passed, margin, worstAt, failed }` and rejects (throws) on anything it refuses; `contractSignals(contract)` checks a contract without a trace and lists the signals it reads.

- **Shape:** `{ version: 1, success: Formula, failures: [{ label, formula }] }`. Formula: `all`, `any`, `always { window, state }`, `eventually { window, state }`, `hold_for { seconds, state, within }`, `sequence`. State: `all`, `any`, `not`, `atom { expr, cmp, value, scale }`. Expr: `signal`, `abs`, `delta`, `dist [[a,b,c],[d,e,f]]`, `angle [[a,b,c],[d,e,f]]` (each name is a signal). Window: `'whole'`, `{ from, to }` or `{ last }`, in seconds. Every object has exactly its fields; unknown or extra keys are refused.
- **Trace:** `{ dt, signals: { name: number[] } }`, every signal the same length, at least two samples. Sample `i` is at `i × dt`. `null` (what `JSON.stringify` writes for NaN and ±Infinity) reads as NaN.
- **Margins:** an atom is `(x − value) / scale`, negated for `<` and `<=` (strict and non-strict give the same number). `all` and `always` take the minimum, `any` and `eventually` the maximum, `hold_for` the best placement's minimum over the dwell (`ceil(seconds / dt)` samples, sliding minimum), and `sequence` the minimum over its steps. A step of a sequence starts at the tick where the previous step first held: `eventually` at its first positive tick, `always` at its window end, `hold_for` at the end of its first full dwell, `all` at the latest of its parts, `any` at the earliest. A step that never holds ends the sequence there.
- **`delta` is the change since the first sample** (`x[t] − x[0]`), not per tick, so it means the same at any timestep (Arena runs half the timestep). `angle` is in radians, from a deterministic atan, so native and WASM agree to the bit; a zero vector has no angle (NaN).
- **Pass:** `passed` is a success margin above 0 and no failure fired; a failure fires when its own margin is above 0. `margin` and `worstAt` are the success formula's (the tick that set it). Exactly 0 never passes.
- **Fails closed.** `not` is pushed down to the atoms (De Morgan), so a NaN or overflowed value is always the adverse value: −∞ in the success formula, +∞ in a failure formula (a NaN can never pass a success, and always fires a failure). An empty window, or one shorter than a dwell, is adverse the same way.
- **Refused, never passed:** unknown signals; more than 64 levels of nesting or 4096 nodes (formula, state and expression nodes together); JSON nested over 256; any parameter that isn't a finite number (scale above 0, `hold_for` seconds above 0, windows that start at or after 0 and end after they start, `last` at or above 0); empty `all`, `any` or `sequence`; another version; a success that looks only at the final state (`{ last: 0 }`, statically, and on each trace any window that covers only the last sample, through `all` and `sequence` when every part does, and `any` when one does). Failures may look only at the end.
- **Cost is linear** in trace length per node: each temporal node evaluates its state series once, and `hold_for` uses a monotonic deque.
- **The WASM:** plain `extern "C"` exports (`contract_alloc`, `contract_free`, `contract_evaluate`, `contract_check`), JSON in and out over linear memory, no wasm-bindgen; the reply's pointer and length come back packed in one `u64`. `contract.ts` reads the file with `fs` in Node and `fetch` in the browser, and drops the instance after a trap. About 105 KB, no dependencies.
- **`src/skills/contract.wasm` is a committed output** (§0g). `npm run build:contract` (`tools/build-contract.mjs`) runs `rustc` directly on `src/lib.rs` from the crate's `src/` folder (relative paths only, `--remap-path-prefix`, `opt-level=s`, fat LTO, one codegen unit, `panic=abort`, stripped), so the bytes match on any checkout path. Rebuild and commit it with every change to the crate; the gate rebuilds it and compares hashes, so a different `rustc` than the one that built it (1.99.1 today) fails the gate until it's rebuilt.
- **Fuzz parity:** `cargo run --release -p contract --bin contract-fuzz -- <n> [seed]` prints n accepted random contracts and traces with the native result; the gate checks WASM against them. Non-finite margins print as `±1e999`, which `JSON.parse` reads as ±Infinity.
- **The canary** `canary_planted_false_pass_fails` (`tests/canary.rs`) runs the false-pass check against an evaluator that passes everything. Run by its exact name, it asserts the check let that through, so it fails while the check works and the gate sees the canary fire. In a plain `cargo test` it asserts the opposite and passes. Rust in the crate keeps §0's spirit: no comments, small functions, `cargo clippy -- -D warnings` (also with `--target wasm32-unknown-unknown`), `cargo fmt`.

### Artifacts (`artifacts.ts`, `bundle.ts`)

- **Hashes over `SimModel`** (`modelHashes`): visual elements and attributes (`light`, `camera`, `visual`, `rgba`, `material`, `texture`, `group`) are stripped first. **Topology** is the body tree, joint names, types and axes, actuator kinds and robots. **Physics** is the rest of the MJCF (masses, sizes, hulls, ranges, contact, timestep) plus the start pose. **Actuators** is the `<actuator>` block plus each joint's effort and drive. All carry `SIM_MODEL_VERSION`.
- **`skillFreshness(skill, current)`:** another design, topology, observation or action schema → `needs-training`; no evidence, or a contract, physics or actuator hash that moved → `rerun-arena`; evidence that failed → `needs-training`; otherwise `fresh`. A colour or name change leaves every hash alone.
- **Training a hand-off** (`handoff.ts`): `trainHandoffSkill` adds a source's `states` to a move's environment, validates it, trains the move's job on the CPU backend from those starts with the old policy as `warmPolicy` (§8g), and judges the result with `proveSkill` on the move's environment unchanged, so its contract hash stays and `warmStartFrom` names the old skill when that was a policy.
- **Moving a skill:** `warmStart(skill, target)` gives a training seed (the skill's hash and controller, bound to the target). A skill trained from it has `warmStartFrom` set and no evidence until Arena runs on the new design; the source's evidence never moves. Install Skill (below) does this for a skill from the Hub.
- **Storage:** content-addressed, `library/skills/<sha256 of the canonical skill JSON>/skill.json` (`skillFolder` refuses anything but a hash). Rerunning Arena makes a new skill, so a folder never changes.
- **`.basecase` files** carry skills as an optional `scene.skills` list, with the file `VERSION` unchanged: older builds ignore the field, and `readSkillBundle` drops entries that don't parse.

### Environment interface (`environment.ts`)

One task description that lowers to WASM now and to native, SIMD and GPU later, so it holds only data: observation terms (`policyObservation(joints)` is exactly today's policy contract; a `depth-eye` term adds a camera's rays, its geometry inside the term, §8l), action spec, reset distribution (with an optional `startArea`, metres forward and sideways the start moves each episode, sent to Forge as `startArea`, and optional `states`: states drawn from another skill, `{ skill, joints, samples }`, each sample every joint's position and speed in `joints` order, the base height, quaternion and linear and angular speed, 1 to 256 of them; `resetProblems` refuses a joint the robot lacks or a sample that isn't finite, has the wrong length, a height of 0 or less or a quaternion off unit length. Train Hand-off (§8j) fills it from the source skill and sends it to Forge as `startStates`, §8g), randomization ranges, a reward reference (contract robustness or a RewardLang hash) and the contract, plus named signal sources the contract reads (time, joint position, velocity and effort, part position, base height, tilt and forward travel, contact). `validateEnvironment(env, model)` returns plain problems; an empty list means valid.

- **Per-servo draws** (`randomization.servos`, version 2): a list of `ServoSpread`s, `{ servo, joints, covariance }`, one per servo population the robot's joints run on (§8k). The covariance is over the six MuJoCo terms a servo sets (`DYNAMICS_TERMS`: kp, joint damping, armature, frictionloss, force limit, delay), in log space around the model as built, which is the population's median: kp follows the gain multiplier, damping, armature, force and delay their own, and frictionloss the mean of base and load friction. `withServoSpreads(model, env)` adds the model's spreads for the action's joints and sets version 2; with none the environment stays version 1, byte for byte what it was, so its hash and the evidence bound to it hold. Version 1 can't carry spreads, and `validateEnvironment` refuses spreads that aren't exactly the model's own for the action's joints, so an environment can't narrow them. The Kit and moves build their environments through it.

### Arena (`arena.ts`)

The independent verifier, on the WASM `SimEngine`. `runArena({ mj, model, contract, controller, environment })` refuses a contract that differs from the environment's, then runs three variants of 32 tries each: held-out randomized starts and physics, half the timestep, and random servo delays. Evidence gives passes per variant, a one-sided 95% Clopper-Pearson lower bound, the conditions in plain words. It passes when every variant's lower bound is at least 0.75 (29 of 32).

- **Agents can't change it.** `ARENA` is frozen; `runArena` takes no counts, bars or ranges. Randomization is the environment's ranges widened to Arena's floor (friction ×0.8–1.2, mass ×0.9–1.1, strength ×0.9–1, start joints ±1°, delays to 40 ms in the delay runs), and servo spreads are the model's own, so an environment can't make Arena easier.
- **Per-servo draws:** in a version 2 environment each joint of a `ServoSpread` draws its own unit every try (`drawServos`, `servoDraws.ts`: correlated normals clipped at 2.5σ, after every other draw, so a version 1 environment draws the same instances as before). `ArenaWorld` multiplies that joint's kp (`gainprm`, `biasprm`), damping, armature, frictionloss, force range and `actuator_delay`, on top of the instance's strength, and the delay runs add their extra delay to its drawn `actuator_delay`, so a drawn joint meets Arena's floors like every other joint. `kitValidation.ts` draws the same way.
- **Sealed instances:** each try's seed is the SHA-256 of a fresh random 32-byte salt, the variant, the try and the environment hash. Evidence holds counts and the salt's hash only, never seeds or drawn values, so feedback can't be fitted to the instances.
- **Evidence summaries scan for the lowest pass share.** `skillRecords.ts` selects the weakest variant and Motor Kit run without copying or sorting ordinary evidence. Skill rows and fleet twin verdicts share these helpers. Equal shares keep the first result, empty runs rank at infinity, and each call reads current counts. Imported counts that produce NaN retain the previous stable-sort selection. `arenaSelection.test.ts` checks selection identity against full sorting, unchanged report text, empty inputs, later edits and source preservation. Its 300- and 600-run fixtures bound pass-count reads to 1,200 and 2,400, down from 23,190 and 49,906. These are operation counts, without timing assertions or a claim about complete training time.
- **Contact signals read `data.contact` once per read and free it.** Every read of that getter allocates a new list in the WASM heap. Reading it per contact without freeing it ran out of 2 GB after about 20,000 reads, which crashed any contract with a contact signal (`arenaSignals.test.ts`).
- **Delay** wraps `mj_step` through `sim/controlDelay.ts`, shared with live physics settings (§8d). Its ring reuses control snapshots after startup, holds the first command until full and clears before each try. **Divergence** turns off MuJoCo's auto-reset and fails the try on a bad-state warning, and a NaN trace fails the contract.

### Method Router (`router.ts`)

`routeTask(analysis)` is pure and walks the plan's rungs in order: unverifiable, IK or motion plan, tracking (built for moves, below), Routine, LQR or MPC (12 state values or fewer, no rich contact), tracking RL with a reset curriculum, reward search (6 candidates at 5M steps, 2 at 25M, 1 at 100M, up to 3 rounds, warm-started after the first), ask for a demo, then not found with design relaxations. It returns the method, the rung and the reason. The ask-for-demo rung's solver is Train from Tries (§8h): a person's passed tries of a Case are the demo, and the skill it keeps records `ask-for-demo` as its method. The router doesn't send drafts to it, since a draft carries no Case.

### Feasibility, Tier 1 (`feasibility.ts`)

`openKin` prepares body membership and leaf lists once per compiled model through `feasibilityBodies.ts`. Subtree intervals answer robot and joint ancestry queries without walking parents. Foot discovery, mass and center-of-mass calculations, joint chains, link scaling and payload loads share this topology. Poses and masses are still read from the current model and data. Each relaxation opens a new model and index.

Stance weight sharing and the prompt solver's `anythingIk.ts` use `utils/matrixScans.ts` for pivot selection. IK also accumulates back-substitution terms through it. Both scan dense rows without copying tails, preserving arithmetic order and their existing zero-pivot behavior. `denseSolves.test.ts` checks offset force balance, empty and single-foot support, and planted targets on three- and six-joint MuJoCo arms with no tail copies.

`checkFeasibility(mj, model, task)` runs only checks that a model can settle, each marked `exact`, `estimate` or `sampled`, with plain messages:

- **Holding torque** from `mj_inverse` (constraints off, zero velocity and acceleration) plus foot and payload loads by virtual work. Stand checks the start pose and a crouch 15% lower (feet held by IK), with the weight shared over the feet by a minimum-norm force and moment balance. A joint fails above 0.60 of its torque, the Stance limit in the Build checks (§8b). Point-load projection shares `utils/holdingTorque.ts` with Build payload sampling. Revolute loads use scalar lever and moment components without temporary vectors, preserving arithmetic order. Prismatic loads still project force directly onto the joint axis.
- **Support polygon:** the center of mass over the hull of the feet's soles, margin in mm. Support polygons use `utils/convexHull.ts`, shared with Build checks and projected outlines. No contacts or a single contact retain a margin of negative infinity. Two contacts retain the negative distance to their segment.
- **Workspace:** fails exactly past the summed link lengths, else samples 2048 poses and refines the best six with damped least squares. `feasibilityReachSamples.ts` retains those six in distance order during sampling and reuses their pose buffers. Equal distances keep trial order. The random sequence, final sampled pose and refinement order stay unchanged across feasibility callers and relaxation attempts.
- **Gripper opening:** prismatic travel, or `2 × finger × sin(span / 2)` for hinged fingers, against the object plus 2 mm.
- **Relaxation ladder:** servos ×2, ranges +20° at each end, links +20%, in that order; the first that makes every check pass is reported, otherwise it says none does. `must-fail-weak-quad` comes back as too weak to stand, with servos ×2 as the fix.

### Motor Kit (`motorKit.ts`, `kit*.ts`)

Every legged robot gets Stand, Velocity tracking, Get up and Settle to neutral, trained through Forge and proved in Arena. Gate `s3a-motor-kit` (§0k) judges them again on its own contracts. Nothing here judges itself: the gate reruns `runArena` and `evaluateContract` on what comes back.

- **Training goes through the runner it's given.** `ForgeJob`, `ForgeOutcome`, `ForgeRunner` and `SkillSave` (`forgeRunner.ts`, re-exported from `motorKit.ts`): in the app the runner is `electron/trainer.mjs`, in the gate one that spawns `forge-train --job <dir>`. A skill's policy is the `policy.json` a runner returned, weights unchanged, and `cost.steps` adds up every run's `done.steps`.
- **`kitEnvironment(model, entry)` is pure:** the environment and contract the Kit trains and Arena judges for `model.robots[0]`, from the model alone (`kitModel.ts` reads the start height from the root body's `pos` in the MJCF, as the engine places it). A colour edit changes nothing; a mass edit moves the physics hash (Rerun Arena); a joint edit moves topology (Needs Training). Its bars are the gate's, published below, and its reward is the entry's RewardLang program (`kitRewards.ts`), referenced by hash.
- **Entries** (`kitEntries`): floating robots whose morphology is legged. Pose tracking is in the type but not trained yet; `trainKitEntry` says so. The top speed is 0.2 m/s on four or more feet and 0.15 m/s on two (`kitTopSpeed`, counted from leaf bodies).
- **`trainKitEntry({ mj, design, model, entry, forge, save, signal? })`:** Tier 1 feasibility first (the stand checks; the weak quad is refused with servos ×2 and spends nothing), then the tries in `kitSchedule`, run by `firstPassingTry` (`kitTries.ts`). A try is one or more Forge stages, each with its minutes, servo delays and optional delay ramp, trained for one or more seeds; a later stage warm-starts from the one before it (`warmStart`, §8g: the folder `runFolder` reads from the run's `done` event, or in the app the earlier run's id, which `electron/trainer.mjs` copies into the new run's `warm/` folder), and only one policy per try goes to Arena on the Kit environment. With several seeds, every seed trains back to back inside the same wall-clock schedule, and `kitValidation.ts` picks the one Arena judges. It uses fresh salted draws on Arena's floor ranges, independent of Arena's sealed verdict. Stand keeps its 60 contract draws. Velocity tracking uses 6 draws at top speed, half speed and zero, plus 2 moving turns each way at half speed and ±0.5 rad/s. Reverse adds 6 backward-speed draws when requested. Half the isolated draws use half the timestep. `kitTransitions.ts` also runs the Routine prover's eight seeds from the actual Settle controller and sampled phases of Walk and both turns. Starts, both in-place turns, Walk into Settle, and both turns into Walk and Settle must pass `kitBehavior.ts`: at least 0.08 m forward or backward as commanded, at least 0.3 rad in the commanded direction while drifting at most 0.02 m, or at most 0.02 m of travel in the last 0.5 s of a stop. Settle switches at its actual 1.5 s hand-off. Moving predecessors first run Settle for 1.5 s, then their own controller until a seeded phase from 1.5 to 2.5 s. The target runs for 2 s. A turn's yaw is accumulated at control ticks, including turns past π. Transition pass share ranks before the unchanged speed score, with a weight of 32 so one failing seed cannot outrank a candidate whose required transitions all pass. The weakest forward speed still ranks the isolated checks, with reverse coverage, moving turns and margins breaking ties. Every selected Velocity or Settle candidate is checked before Arena, including a single-seed continuation. Reports are cached per candidate, so judging does not redraw the selected seed. Failed transitions refuse the candidate before saving and name the movement requirement on its existing result row. Continuations rank by validation score plus Arena passes divided by 1,000 and keep the existing stages, seeds, delays and minutes. Each call draws its first seed fresh (1 to 1,000,000; `KitInput.seed` pins it), so two runs of the Kit, or of the gate, train different seeds. Velocity tracking takes one path on every robot (`kitSchedule`'s `velocity`). Its first try trains several seeds, each one 9-minute stage on the GPU loop (§8g: `backend: "metal"`, `gpuEnvs: 1024`, falling back to the CPU learner with the reason) at 0 to 40 ms delays ramped from none over the first 60% of the stage (`delayRamp`). Its second try continues the best for one seed at the full 0 to 40 ms. 1024 robots take the GPU loop's small-batch PPO, the CPU learner's settings: 24 steps, 5 epochs of 4 minibatches, KL 0.01, at about 72K steps/s. At 4096 robots the loop's large-batch settings (4 steps, KL 0.1, about 160K steps/s) never taught the biped commanded speed in 6 to 8 minutes. Its top-speed Arena results were 0/0/14, 3/10/11 and 18/17/23 on three seeds, and at nominal physics it covered −0.25 to 0.81 m of the 1.05 m asked. On one seed at 0 to 20 ms for 8 minutes, 24 steps at 4096 robots scored 32/32/32, 32/32/32 and 26/29/28, 16 steps at KL 0.03 scored 32/32/32, 32/32/32 and 15/21/22, and 1024 robots passed every run. The gate's budgets set the seed count: 2 seeds and a 4-minute continuation on four or more feet (22 of 30 minutes), 3 seeds and 6 minutes on two (33 of 45). At 6 minutes per seed, one hexapod seed failed the top speed (14/0/9), and the same seed at 9 minutes passed every run. Stand trains on the same GPU learner on every robot. On four or more feet the other entries are one stage per try at 0 to 20 ms: Stand 2 then 4, Get up 2, 6 and 8, Settle 2 then 4. Biped Stand trains two seeds of one 6-minute stage at 0 to 60 ms, ramped like Velocity tracking, then continues the best for 2 minutes (14 of its 15 minutes), below. A Velocity tracking policy must first pass Arena at half its top speed and standing still (`kitAcceptance.ts`, the same bars), because one seed walked at the top speed and drifted 0.1 m standing still under 40 ms delays. The first policy that passes is saved with its evidence and `origin = { method: 'motor-kit', cost }`; when none does, it comes back refused with no relaxation. `kitStatus({ design, model, skills })` gives one row per entry with the best freshness among skills named `kitSkillName(entry)`, or `missing`.
- **Start feedback and evidence** (`kitTransitions.ts`, `motorKit.ts`): training, installed warm starts and the browser Kit all use `trainKitEntry`. The app supplies the same ready scene skills and scripted drive that Routines uses. The worker adds the bundled fallback policies. The latest matching scene policy wins over the bundle. A failed selected candidate feeds its first failed stance's joint positions and root height into the existing continuation's `initialJoints` and `rootOffset`. Both Velocity and Settle continuation jobs add the failed stance's height offset to the scene root offset. This is a stance reset, not a replay of the predecessor's velocities or controller memory. Validation always runs the predecessor live and preserves its phase and momentum at the switch. Stand and Get up keep their own validation and Arena paths. Settle checks incoming Walk and Turn when a predecessor controller is available. `KitSkill.kitValidation` holds transition evidence separately from Arena evidence, bound to full controller data, physics and actuators. Its checks identify each direction separately. Routines proves its current controllers again rather than borrowing a skill's Arena verdict or a different pair's proof. `KitCost.validationS` and `validationRuns` record validation overhead alongside total `wallS`, training steps and Forge runs. No failed candidate replaces a saved skill.
- **Validation cost, 14 November 2026:** one paired probe used the committed quad Velocity tracking policy, its Settle policy, MuJoCo 4.0 and the same isolated salt. The old 60-draw validator took 11.43 s and simulated 480 s. The new 22 isolated draws plus 64 live hand-offs took 9.02 s and simulated 478.65 s, including 302.65 s of hand-offs. Other agents were using the host, so these wall times describe this pair only. The new proof refused both Settle into Turn directions in 8 of 8 seeds, while starts, stops and turns into Walk passed every seed. The unchanged quad and hexapod schedule is 18 training minutes for the first two seeds and a possible 4-minute continuation. Applying this probe's per-candidate cost gives 18.04 s of first-try validation and 27.06 s with the continuation, compared with 22.86 s before. These are validation overheads, not a new time-to-ready measurement. The measured policy remains unavailable for those turns. No new trained time-to-ready or announcement is claimed.
- **Jobs** (`kitJob.ts`): the scene's MJCF and the usual `job.json` fields, plus the entry's reward, `servoGains` when the robot's joints have servo spreads (`servoGains` in `servoDraws.ts`: 64 rows drawn from the spreads on the job's seed, each one kp multiplier per actuator, null where a joint has none; Forge varies only kp per robot, so damping, armature, friction, force and delay train at the median while Arena draws all six), and Forge's training conditions (§8g): action delays of 0 or 1 control step, encoder offsets ±0.015 rad, an IMU mount bias up to 0.03 rad, and an actor blind to linear velocity (the critic keeps it). Velocity tracking and Stand also send `squash: "tanh"` and `logStdMin: -2.5` with every stage, on every robot, through the GPU loop: with the clip, mean actions drifted far past the action range and Velocity tracking policies came out marginal at half speed, and squashing without a floor collapsed (§8g). On the CPU learner the squash slowed biped-servo's walk below the bar (§8g); on the GPU loop's small batches it doesn't. Get up and Settle keep the CPU learner and the clip. Kit policies act at `KIT_ACTION_SCALE` 0.5 rad around the neutral pose, recorded in the policy and the environment's action spec. Measured on quad-servo: at 0.25 rad, with resampled commands, it never left the spot in 8.6M steps; at 0.5 it walked all three judged speeds after 14.6M. Delays up to 2 steps with offsets stopped it learning to walk in the same time, so the Kit trains 0 to 20 ms and relies on Arena's 40 ms runs to show it holds. Bipeds sit on the edge of that trade: trained on 0 to 20 ms, biped Stand and Velocity tracking have fallen in 4 of 32 of Arena's delay runs (28 against a bar of 29); trained on 0 to 40 ms from the start, two of two 22-minute runs held every delay run but neither steered (one circled, one ignored the turn command). Biped Velocity tracking used to train in two stages: 20 minutes at 0 to 20 ms, then 12 at 0 to 40 ms, then 8 more from the best. The ramp above replaces the jump between them. Biped Stand used to train on the CPU learner, 3 minutes on 0 to 20 ms then 5 on 0 to 60 ms, always on seed 1. With fresh seeds it sat on the bar: of four seeds, one failed the gate's Stand judge at 26 of 32 delay runs, and one failed one of four fresh Arena reruns at 28 (bar 29). Ramping the delays on the same learner didn't help: one of three seeds was refused and one failed the gate's judge at 28. One 8-minute ramped stage on the GPU loop left one of three seeds at 28 in the gate's judge, while the other two held 31 or 32 on every rerun. Two 6-minute seeds picked by validation passed three of three fresh Kit runs of the gate's own Stand test on their first try, in 734 s of 900 (28.3–28.5M steps per seed), with no Arena variant below 31 of 32 in the Kit's Arena or in four fresh reruns each. Quad and hexapod Stand on the GPU loop passed at 32/32/32 in 129 and 130 s (7.3M and 5.3M steps). Every warm-started stage sends `logStdMin: -2.5` (Velocity tracking and Stand send it from the first stage): without it, both 12-minute continuations onto 0 to 40 ms collapsed after about 8,000 iterations (§8g). In the `s3a-motor-kit` run of 8 November both biped entries passed on their first try, the gate's own contracts and the steering timeline included: Stand in 486 s (6.5M steps at 0 to 20 ms, then 10.7M at 0 to 60 ms; Kit Arena 31, 32 and 31 of 32), Velocity tracking in 1,941 s of its 45 minutes (42.3M steps, then 25.4M; 31, 31 and 32 of 32). The quad's Velocity tracking needed its second try, which continued from the first (24.7M + 24.7M steps, 1,497 s of 30 minutes). In the rerun that recorded the pass, biped Velocity tracking needed its second try too: 42.4M and 25.5M steps, then 17.0M more from the best of them at 0 to 40 ms, 2,443 s of its 2,700 (Arena 30, 31 and 29 of 32), so the 45-minute budget has about 4 minutes to spare when every try runs. Stand and Settle start ±0.3 rad off neutral (Settle's reward pulls every joint home with wide and narrow kernels plus a quadratic, because a narrow kernel alone is flat 17° out and the policy settled into a crouch); Velocity tracking (rewarded on speed error scaled to the top speed, a linear penalty on speed error, and on four or more feet a linear penalty on turn-rate error, so a robot that veers loses reward as it loses travel; and, with a still command, harder penalties on joint motion, action changes and drift, drift clipped so a fall can't swamp the return. ### Solver race (`race.ts`, `race*.ts`)

- **Goals** are `reach` (a part through waypoints), `velocity` (a command), `track` (a Pose-tab animation, Moves below) or `open` (anything else: IK says it has no point to reach; reward search runs on a floating robot with the agent's RewardLang candidates plus the contract-robustness one, and says so when it has neither).
- **`runSolverRace({ mj, task, forge, save, rewardCandidates?, robustnessCandidate?, budgetSteps?, signal? })`** routes with `routeTask(task.analysis)` and tries that rung, then each later built rung, cheapest first. A skill comes back only with passing Arena evidence on `task.environment`, so a candidate with a high reward and a failing contract never wins. `solveWith({ ...input, method })` runs one method alone; a method that isn't built (Routine, LQR or MPC, tracking RL) returns `not-found` at once.
- **IK or motion plan** (`raceIk.ts`): for `reach` goals. Damped least squares on MuJoCo's own kinematics finds joint targets for the part's body, with restarts; then each target is settled 2 s under the hold controller and the aim moves by the sag, up to six rounds, until the settled point is within 0.5 mm. One waypoint becomes a hold controller; several become a linear keyframe animation that holds each pose for its share of the horizon and moves in 0.4 s. Steps cost 0.
- **Reward search** (`raceRewardSearch.ts`): for `velocity` goals on floating robots. Candidates are the agent's RewardLang programs (`rewardCandidates`, otherwise the Kit's velocity reward), then the contract-robustness candidate (`raceRobustness.ts`: each success atom over base height, tilt or forward travel lowered to a per-tick margin, clipped to ±1 and summed; a contract over other signals has none). Stages follow the router (6 at 5M steps, 2 at 25M, 1 at 100M), each run capped by what's left of `budgetSteps`, re-ranked by Arena's lower bound between stages. Every trained candidate goes through Arena; the first that passes wins.
- **Tracking** (`raceTracking.ts`): for `track` goals on floating robots, Moves below. On a `track` goal the IK rung plays the animation itself (`playMove`): the animation controller, proved in Arena on the move's contract, with no training and 0 steps, which is how a fixed arm's wave becomes a skill.
- **`Skill.origin = { method, cost: { wallS, steps } }`** records where a skill came from (optional, so older skill files read; `motor-kit` for Kit skills).


### Moves (`moves.ts`, `move*.ts`)

Any Pose-tab animation of a legged robot can be trained as a move: a policy that performs it under physics, where playing its keyframes as position targets tips the robot over. `trainMove({ mj, design, model, animation, forge, save, signal? })` builds the environment, routes with `moveAnalysis(model)` (a floating robot: the shape of the motion is the point, so `tracking`; a fixed one is quasi-static, so the IK rung plays the animation) and runs that one method through `solveWith`. A move's skill is named after its animation.

- **Reference** (`moveReference.ts`): the animation sampled with `sampleAnimation` once per 20 ms control step, each frame every actuated position joint (rad or m, `kitRobot` order) plus base height (the start height plus the animation's root lift) and tilt (from its root rotation). A looping animation repeats; one that doesn't loop holds its last key (`referenceAt`, `moveTube.ts`). The environment carries it as `reference` (`validateEnvironment` checks its joints and frame widths), and its observation is the Kit's plus a `clock` term at the animation's period.
- **Extrema** (`moveReference.ts`, `moveEnvironment.ts`, `moveTube.ts`): lowest height, highest tilt, action range and distance outside the tube accumulate directly from frames and bands. They retain no mapped or flattened sample arrays and spread no samples into function arguments. Each call reads current frames and rest positions, preserving thresholds, empty reductions and nonfinite results.
- **Contract** (`moveEnvironment.ts`, `moveTube.ts`): a tube around the reference, judged by the unchanged Arena over the plain `q_<joint>` signals. The horizon is split into windows (at least 0.1 s, as many as 3,600 contract nodes allow, so a 23-joint humanoid gets 38 windows over 12 s); in each, every joint must stay between the reference's lowest and highest value over the window widened by 0.2 s each side (lag) and by 0.25 rad (`MOVE_BARS.toleranceRad`). The root part must also stay within 0.3 m of its start along x and y the whole time, and the one failure is `fell` (tilt past 1 rad or the reference's highest tilt plus 0.5, or the base below 45% of the reference's lowest height). A one-shot move is judged over its length plus 2 s of hold (at least 4 s); a looping one over two periods, at least 4 s and at most 12 unless one period is longer. Since the reference is in the contract, editing the animation moves the contract hash; the record also keeps the reference's hash (`moveTag`), so a changed animation reads as needs training, not a recheck.
- **A zero policy must fail.** `moveProblems` refuses an animation whose tube contains the rest pose to within half the tolerance everywhere (it never strays more than about 21° from rest), since holding still would pass it; such an animation stays a plain animation.
- **Reward** (`moveRewards.ts`), in the style of BeyondMimic's single reward, reads `state.reference` (§8g): `exp` kernels on the mean squared joint error (widths 0.04 and 0.005 rad², weights 2 and 1), uprightness against the reference tilt, height against the reference height, and penalties on action change, roll and pitch rate, base drift and a fall.
- **Job** (`moveJob.ts`): the Kit's Stand job (GPU loop, `squash: "tanh"`, `logStdMin`, the Kit's delays, biases and blind actor) with the reference as `reference` (joint offsets from `defaultPose`, then height and tilt), starting at the first frame, `episodeS` the contract's horizon, `standHeight` the reference's lowest height (falls and the height term scale from it), no pushes, and an action scale wide enough for the motion (`moveActionScale`: 1.15 × the largest offset from rest, between 0.5 and 3 rad). Actions stay offsets from the rest pose, not from the reference, so a zero policy holds still.
- **Schedule** (`moveSchedule.ts`), through `firstPassingTry`: four or more feet train 6 minutes at 0 to 40 ms delays ramped over 60%, then continue the best for 4; two feet 9 then 6. Each try's policy goes to Arena on the move's environment; the first that passes is saved with `origin.method` `tracking`.
- **In the app:** every move is a row in the skills list (`skillRows`: target `move:<animation id>`, labelled with the animation's name), with Train, Try and the Arena line like a Kit entry. A passed run saves a `SkillRecord` with `move: { animation, reference }` and no environment (it's rebuilt from the animation). After a design edit, Kit retraining (`backgroundTasks`, below) rechecks or retrains moves that were trained before, as it does Kit entries. The agent's `train_skill` takes `move` (an animation's name) and `list_skills` lists moves.
- **Next steps** (big bet #155, teach a move by filming yourself): video in through a monocular pose estimator into the `.bvh` retargeter, so a clip becomes an animation and then a move; a Moves library that Routines (whose `do` steps run the committed Kit library, §8j) and the Robot Package can call, blended with Walk; and moves for the agent's Cases logic.

### Anything from a prompt (`anything.ts`, `anything*.ts`)

`trainAnything({ mj, prompt, design, model, approve, forge, save, budget, signal, method? })` runs the whole pipeline on one prompt and returns a `skill` (with its method and cost), an honest `not-found` (with what each method tried), `refused` or `unverifiable`. Gate `s3-anythingzoo` (§0k) judges it; the input and outcome types mirror `verify/zoo/anything.ts` structurally (`anythingTypes.ts`), so `src/` never imports `verify/`.

- **Intent compiler** (`anythingIntent.ts`, `anythingPrompt.ts`, `anythingClaude.ts`): Claude (`claude-opus-5-5`, effort `high`; `ANYTHING_MODEL` and `ANYTHING_EFFORT` override) through the Agent SDK with no tools, signed in the way PersonaLab is (§0k): the machine's `claude` CLI login, nested-session variables dropped, no key in the repo. The SDK is a dev dependency and is imported dynamically, so the app bundle never loads it; `trainAnything`'s second argument replaces it (tests script it). Claude gets the body (`anythingBody.ts`: class from the robot's morphology, the base, every part's rest position in robot-frame mm, every joint's rest angle and range) and answers `deformable` (unverifiable), `impossible` (refused) or a task: a contract in robot-frame terms, its deadline, a start offset, and an intent (keyframes of base travel, height and tilt, joint angles and part positions).
- **Intent pose sampling** (`anythingPoser.ts`): `keyStates` sorts intent keys by time. `frameAt` uses the shared binary `timeIndex` lookup to find the first state at or after the requested time, preserving the first state at duplicate times and holding the endpoint outside the clip.
- **Resting foot contacts** (`anythingFeet.ts`): spread uses `utils/planarDiameter.ts`, shared with four-bar fitting, without constructing a quadratic distance array. It reads the first two contact coordinates and retains the 0.01 m flat-foot threshold, zero floor and nonfinite results. The scan visits each unordered pair once, including self pairs. [Evidence](../notes/performance-joints.md#planar-diameter-measures-each-unordered-pair-once).
- **Robot-frame signals** (`anythingSignals.ts`): `forward`, `left` (travel since the start), `height`, `tilt`, `q:<joint>` in degrees and `<part>.right/forward/up` (mm from the base's rest position) or `.height` (mm above the floor). They lower to the environment's world signals by an offset, a gain and a flipped comparison, so the contract Arena judges is plain (§8i above), and the stand-in approver replays rollouts through those same signals.
- **Approval** (`anythingApproval.ts`): before each proposal the contract is checked against Claude's own intent (must pass), staying at rest (must fail unless the request is to stay still) and every rollout the person has labelled so far; a mismatch goes back to Claude with a table of the robot-frame signals. A rejection with a rollout is added to those labels and revised; one without (“That is not what I asked for”) refuses at once. At most 3 proposals. The approved contract and the labels are remembered per prompt and physics hash for the rest of the process, so a second attempt (another method) proposes the approved contract first.
- **Feasibility gate:** travel needs a floating base, crouching or leaning needs legs, and a legged robot must pass Tier 1's stand check (`checkFeasibility`, the weak quad is refused with its relaxation). Then the environment (`anythingEnvironment.ts`: the Kit's observation and action on position joints, the wheels' velocity action on a rover, the request's start offset through `offsetPose`) must validate.
- **Router and race** (`anythingRace.ts`): `routeTask` on the task's analysis (quasi-static unless a legged robot travels), then the ladder cheapest first; a forced `method` runs that one alone, and an unbuilt one returns `not-found` before Claude is asked.
  - **`ik-or-motion-plan`** (`anythingMotion.ts`, `anythingStatics.ts`, `anythingIk.ts`, `anythingFeet.ts`): each intent key becomes joint targets by damped least squares on MuJoCo's kinematics, with a legged robot's feet planted where they rest (the contact point under each foot, and flat feet kept level; a part goal that only restates where a foot rests, within 3 mm on every axis it gives, keeps the foot planted instead of replacing its plant, and stays out of the sag correction so a settled foot a few millimetres off can't drift its goal past that slack: Claude often writes `l_sole: { height: 12 }` beside a crouch, and with the plant dropped to a lone height target the feet slid and the biped crouch passed 0 of 8 checks, sending 7 of 43 draws to reward search), then settled under the hold controller and corrected for sag up to four times. The keys become a linear animation led by 0, 0.3 or 0.6 s; if it fails any of 8 pre-Arena checks (nominal plus fresh draws of Arena's floor ranges, a third at half the timestep, `anythingSim.ts`), a cross-entropy search over the moving keys' joint targets maximizes the worst contract margin over three fresh draws, in up to six rounds of narrowing spread and six minutes (`anythingAugment.ts` adds free keys first: a ramp out of the request's bent start pose, and a crouch 0.35 s before any key that rises above standing, then a deeper one 0.25 s before if that fails, because a pose plan can't rise above its legs' length without a leap). A rover's plan is a route instead (below). biped-servo can't stand tall from the 40° bent start: every leg joint 40° off (the hip rolls clamp at their 30° limit, both the same way) puts both feet to one side and the sole on its edge, and it tips past 0.4 rad within 0.2 s whether it holds rest at once, ramps there over 0.02 to 1.5 s, or swings both hips 10° to 30° the other way to catch itself. Recovering needs a step, which a pose plan doesn't make.
  - **`reward-search`**: a legged robot that travels trains the Motor Kit's Velocity tracking (`trainKitEntry`) and follows the route on it (`anythingWalk.ts`); other legged tasks run the race's reward search on the contract-robustness reward when 20 minutes are left; robots without legs are refused. On four or more feet it trains with `reverse` (`KitInput.reverse`; the Kit's own jobs are unchanged) and the route may command half the top speed backwards: a forward-only gait given a backward command stepped back about 5 cm and froze, and backing up 0.4 m in 8 s by turning around first doesn't fit (5.2 s to turn at 0.6 rad/s). A `reverse` job draws forward commands from −1.25 to 1.25 × the top speed, as far back as forward, and its reward (`kitReward(model, entry, { reverse: true })`, the environment's reward hash too) weighs the linear speed-error term `lag` 1.5 instead of 0.5; everything else in the reward is the same.
    - **Why both.** With the range from −0.75 × the top speed and the plain reward, 0 of 6 fixed hexapod seeds (9-minute stage, the Kit's first try) backed up 0.5 m in 8 s at −0.1 m/s, and 4 of 6 quad-servo seeds did. A command sweep showed why: the gait has a dead zone of about ±0.1 m/s, standing still for anything smaller in either direction and walking at full speed above it (one seed backed up 0.10 m at −0.1 m/s and 1.58 m at −0.15). −0.1 m/s, the route's backward speed and the validation's, sat at its edge, and so did forward half speed (validation 0.67, 0, 1, 0, 0 and 0.67 of 12 draws passing). The exponential tracking kernels are nearly as kind to standing still as to walking a moderate speed badly, so only `lag`, a constant pull per m/s of error, breaks the tie. The symmetric range alone made the backward gait as strong as the forward one and lifted forward half speed, but left the dead zone: 0 of 3 seeds backed up at −0.1 m/s while backing up 1.4 to 2 m at −0.15. Both together: 6 of 6 hexapod seeds backed up 0.61 to 1.37 m at −0.1 m/s, top-speed validation passed every draw on all six (baseline 1, 1, 1, 1, 0 and 0.92), half speed 1, 0.42, 1, 1, 0 and 1. On quad-servo, 5 of 6 seeds backed up 0.79 to 0.96 m (baseline 4 of 6, 0.07 to 0.83 m); the sixth backed up 0.37 m in the clean rollout but passed 9 of 12 backward draws (baseline 0 of 12). Its forward checks held or rose: top speed passed every draw before and after, half speed every draw on all six (baseline one seed at 11 of 12). The probe is `scratch/reverseProbe.test.ts` in the builder's worktree (not committed; it trains through `kitJob` and judges with `validationReport` and one clean 8 s rollout per command).
    - Before validation scored a backward command, the Kit could pick a seed that stood still backwards, and go-and-return came back not found in the gate's sample; scored, it picks one that backs up, which passed go-and-return, backing up and 8 of the 9 route tasks in the pre-Arena checks (all but the sidestep). Earlier, hexapod passed the Kit's own Arena (on its second try, 57.9M steps, 1,411 s) and 8 of 9 route tasks in the pre-Arena checks, backing up and going there and back included.
  - **Routes** (`src/sim/route.ts`, `anythingRoute.ts`): a `route` controller follows timed `forward`/`left` keys by feedback on the base position (feed-forward plus a position gain, a deadband at the goal, an optional acceleration limit), commanding a velocity policy holonomically within its trained ranges and turning to face the goal when the move is outside them, or a rover's wheel speeds from each wheel's side, radius and spin. The rover's plan also tries reverse-only driving: rover-diff pitches back about 0.45 rad whenever it drives forward, and still about 0.3 rad backing up slowly, so “without tipping more than 11 degrees” stays not found on it. The cause is the fixture: its wheels are 70 mm box meshes, so rolling one over its edge takes about as much torque as the chassis' weight holds down at the caster (0.33 N·m about the axle), and the reaction lifts the nose until the rear corner, 70 mm behind the axle, drags at 0.45 rad, at any speed from 0.02 to 0.15 m/s. Easing the wheels when the nose lifts (wheel speed cut by 80 rad/s per radian of nose-up pitch) keeps it level but stalls it: 0.13 m in 8 s. Backing up with the same feedback holds the tilt near 0.07 rad at 0.1 m/s, but the turn in place it needs first raises the middle wheels' axle 14.5 mm against the caster, so it tilts 0.14 rad on nominal physics and 0.2 to 0.3 rad on Arena's draws, past the 11° bar. No route controller was shipped for it; the fixture would need round wheels. Close to a stopped goal, a move the gait can't make (backwards, on a gait trained forwards only) holds still instead of turning around, which had walked the quad 10 cm past its mark. A walking route also tries a brisk variant (moves under half the top speed become steps at half the top speed, or none inside 3 cm), because biped-servo fell in 4 of 8 draws creeping at 0.03 m/s, and a turning variant with no sideways command, which turns to face a sideways goal.
- **Claims only with margin:** a skill comes back only when Arena passes on the approved contract with at least 31 of 32 in every variant and a second Arena run, 1.5 s longer so a hold must outlast a deadline Claude read too short, passes the same contract made stricter (`anythingTighten.ts`): every tolerance window 20% narrower, every one-sided bar 5 mm, 3 mm on a part, 0.5° or 0.015 rad of tilt further in, and every failure that much quicker to fire. A uniform shift by each atom's scale was too strict: on a ±7.5 mm crouch window it left ±1.5 mm, and a crouch that passed Arena 32/32/32 was thrown away. On a legged robot that doesn't travel, the stricter run also holds the body level (`claimSpec`, `levelSpec`): every `hold_for` or `always` state that reads `height` gains tilt below 0.3 rad past the most tilt the intent sketches (then tightened like the rest), because Claude leaves posture out of a contract the request doesn't spell it out for, and the stand-in's labelled rollouts never lean at the right height, so nothing catches the gap. The pose plan follows the intent's level base, but reward search optimizes the contract's letter: on crouch@biped-servo (seed `861bb4413dff…`) its policy lowered the base to 0.122 m by pitching the body 0.48 rad forward, passed the approved contract and the old stricter run 32/32/32, and the hidden judge (which wants a crouch upright) failed it 0/0/0. With the level bar the same policy fails the stricter run 0/0/0 and comes back `not-found`. Otherwise the outcome is `not-found` with the Arena line.

### Kit retraining (`electron/kitScheduler.mjs`, `kitPlan.ts`)

`new KitScheduler({ trainer, debounceMs })` with `request({ workspaceId, xml, job })`, `cancel(workspaceId)` and `dispose()`. Requests for one scene within `debounceMs` collapse to the latest. Before it starts, `trainer.release('kit:<scene>')` drops a queued Kit job for that scene or stops a running one and waits for it to close, so only the latest design trains; it then starts at `PRIORITY.kit`, behind every user job in the trainer's one global queue. `request` resolves `{ jobId }` once it starts, or `{ jobId: null }` when a newer request, `cancel` or a refusal replaced it, so the caller can follow its own job's events. Scenes are independent, and a Kit job never blocks the user's own training of the same scene (it runs under its own `kit:` key).

Compute priority is viewport, Gatekeeper lease, user training, Motor Kit (`electron/trainer.mjs`):

- **User training pauses the Kit:** starting a user job stops a running Kit job (the trainer's stop file), re-queues it unchanged behind the user job (“Paused for other training. Starts again after it.”) and starts it again from scratch after.
- **The gate lease holds the Kit:** with `useGateLease()` (the app's trainer; tests construct their own), no Kit job starts while `$TMPDIR/basecase-gatekeeper.lease` exists, and a running one is paused when the lease appears (polled every 30 s). User training isn't held.
- **The viewport comes first:** a Kit child process runs at OS priority 10 (`os.setPriority`).

In the app (`src/workspace/useSkills.ts`) the scene model is rebuilt 1.5 s after the last edit to parts, joints or servo calibrations, while the robot is legged or the scene has skills or policies; the policy rows in Train read its fingerprints too (§8d). On the desktop, when its topology, physics or actuator hash moved (`designMoved`; a colour or name edit moves none), `backgroundTasks` lists every Kit entry that was trained before and isn't fresh now: Arena again for `rerun-arena` (`recheckSkill`, no training), the Kit pipeline for `needs-training`. Entries nobody trained never start on their own. A newer design aborts the running one (latest wins); a user job aborts it too and the queue resumes after.

### In the app

- **Teaching anything** (`teach.ts`, `teachEnvironment.ts`): `draftSkill({ mj, model, design, request })` checks the agent's goal, contract, signals and RewardLang candidates (`draftProblems`, then `validateEnvironment`), builds the environment (the Kit's observation and 0.5 rad action scale on floating robots, 0.25 on fixed ones; free signals `time`, `q_<joint>` and, on floating robots, `height`, `tilt` and `forward`), routes it and runs nominal rollouts (`rollout.ts`, no randomization): holding still, which must fail (a pass comes back as a warning), and for reach goals the planned poses. A floating robot also gets the stand check, with its relaxation. `contractWords` says the contract in plain words. `raceDraft` runs the race on the draft and `raceSummary` lists what each method tried.
- **Where it runs:** `skills.worker.ts` runs `runSkillsJob` (`skillsJob.ts`: draft, race, Kit, Arena recheck or twin, below) off the main thread; its Forge and save calls come back to the page (`skillsClient.ts`). `skillsPlatform.ts` is the one place that picks where those go, by platform:

  - **Web demo:** Forge runs go to the tab engine (`tabForge`, §8g), imported the first time a run starts, so nothing of Forge loads before a row's Train; one engine per user job, so a later try warm-starts from the run before it. Its `status` and `progress` events become the row's message and share the way the trainer's do (`trainingProgress`), and Stop ends the Forge worker. Skills save through the `skill-save` route of the web backend (`web/webSkills.ts`, IndexedDB store `skills`, keyed by hash; the hash and the skill's shape are checked before it's stored), so they survive a reload and Try finds them. Background Kit rechecks don't run on the web.
  - The section shows on the web only when the browser can train: WebAssembly JSPI and a WebGPU adapter (`tabTrainingReady`, `src/forge/tabSupport.ts`, asked once). Without them it stays hidden, with no message. Teaching (the Teach field, draft and race) stays desktop-only: it goes through the agent's `/train`, which the web build doesn't have, so the web lists only the Kit. The Train section hides when it has nothing to show (no Teach field and no rows).
  - A gallery page's Train (§8h) runs Stand through the same platform, outside the studio: `src/gallery/galleryTrainer.ts` builds its own `SkillsRuntime` and shows only the Stand row.
  - **Tests:** `skillsPlatform.test.ts` covers tab-engine routing, progress, saving a passed skill, reloading it as ready and saving nothing after refusal, with the IndexedDB boundary held in memory. `e2e/webTrain.e2e.test.ts` presses Train in the studio, saves the scene and skill in real IndexedDB, reloads them, and presses Try to install the saved policy and advance simulation. Its `webTrainWorker.ts` fixture replaces Kit computation and Arena evidence at the worker boundary, while keeping the real worker message bridge, tab-engine routing, skill save and scene autosave. The real GPU path is `e2e/forgeTab.e2e.test.ts`.

The agent makes the dataset with `make_dataset`. Training it goes through this same path, never a second trainer. A skill that passes Arena becomes a `SkillRecord` in `project.skills` (`skillRecords.ts`: the skill without its controller, plus the Kit entry or the user's words and, for taught skills, the environment). `.basecase` files drop them, like policies.

Explicit assignments must be complete and include train and validation, and each emitted episode carries its split. Action scaling uses only training recordings. A stopped run reports nothing. A rejected retraining candidate leaves the last passing record ready and shows its refusal on that existing row beside the retained Arena line.

A ready row shows them as buttons labelled with their iteration; a click loads the kept copy and runs it in the live sim like Try. A recheck's new record keeps none.

### Coaching (`coach.ts`, `coachPrompt.ts`, `coachSignals.ts`, `skillsCoach.ts`)

Words change how a ready skill moves, never what it must do. A Walk that passes but stomps is coached from its own reward, warm-started from its own policy, and kept only if Arena passes the same contract.

- **What can't change:** the contract, the observation and the action. An answer that names `contract`, `observation`, `action`, `signals`, `environment`, `horizon` or `reset` is refused before training (`readRevision`), and so is a reward that isn't RewardLang (no `def reward(state):`, or an import, loop, lambda or `__` name), over 8,000 characters or unchanged. Forge parses the reward when the job loads and fails the job with its line number, which drops the candidate. The proved environment keeps its contract; only its reward reference moves to the new program's hash (`coachedEnvironment`).
- **Signals** (`measureCoachSignals`): one clean rollout on nominal physics from the environment's start pose. `foot_clearance` is each foot's (leaf body's) highest minus lowest height over the run, averaged over the feet, in mm. `contact_impulse` is the largest vertical constraint impulse on the root's free joint over one trace step (20 ms on the Kit), in N s. `joint_jerk` is the root mean square of every actuated joint's jerk from the trace's joint speeds, in rad/s³. `base_height` is the root's mean height in mm, and `speed` its forward travel over the run's length in m/s.
- **The minimum move** (`minimumMove`): the larger of a floor and a share of the value before. Foot clearance 2 mm or 10%, contact impulse 0.005 N s or 10%, jerk 50 rad/s³ or 10%, base height 5 mm or 3%, speed 0.01 m/s or 10%. The named signal is measured on the trained policy before Arena runs, so a candidate that misses it never spends an Arena run or saves a skill.
- **Training** (`coachJob`): the Kit entry's job with the revised reward, its last try's first stage (minutes and delays, `kitSchedule`), the old policy as `warmPolicy` and `logStdMin` −2.5. The kept skill's `warmStartFrom` is the old skill's hash, and its origin keeps the old method. Kit entries only: a move, a taught skill or a skill whose controller isn't a policy is refused.
- **`coachSkill({ skill, words, ask, forge, save, judge? })`** runs brief, Claude, revision and training in one call; `judge` swaps the measurement and Arena for tests (`coach.test.ts` scripts Claude, Forge and the judge, and measures the committed quad-servo Walk for real). In the app the agent is Claude, through `coach_skill` in two calls (§9): the first returns `coachPrompt`'s brief, the second trains the revision (`SkillCoach` on the runtime, a user job on the row like Train).
- **Records:** a kept skill is a new `SkillRecord` for the same Kit entry with `coach: { words, reward, signal, direction, before, after, from }`. The row picks it as the newest fresh record, so Try plays it. Coaching it again starts from `coach.reward`. The previous record stays in `project.skills`: **Undo Coach** re-adds it with a new `createdAt`, so it's the newest again. Background Kit retraining after a design edit trains the plain Kit reward, so a coached style doesn't survive a retrain. A recheck (Arena again on the same policy after a physics or actuator edit) keeps the `coach` tag, since the policy is still the coached one.
- **In the app** (`useSkillCoach.ts`): a ready Kit row's right-click menu has **Coach**, ⌘K has Coach ⟨row⟩ for each, and both scope the Teach field to that row: its label is the row's name, its button reads Coach, and Esc returns it to teaching. Enter sends `/coach ⟨row⟩: ⟨words⟩` to the agent. A coached row adds a second state line under its Arena result with the moved signal's two numbers (`130 → 119 mm`, through `signalNumber`, which reads mm through `lengthFigure`), and its menu adds **Compare**, which plays the old skill and then the new one on the canvas (one Kit horizon each), and **Undo Coach**; ⌘K lists both as Compare ⟨row⟩ and Undo Coach ⟨row⟩ under the same conditions (`coachCommands.tsx`). Coach wears `CoachIcon` (a whistle) in the menu, ⌘K and the agent feed. Desktop only, like Teach.

### Stress (`stress.ts`, `stressProbe.ts`, `stressTrain.ts`, `skillsStress.ts`)

Arena says whether a ready skill passes its sealed variants. Stress says where it stops passing: it pushes one physical setting at a time past the skill's training ranges, then all of them together, and judges every run with the skill's own contract. Train on These retrains on what failed and keeps the result only if Arena passes it.

- **Limits** (`STRESS_LIMITS`): friction ×0.2 to ×1.5 (every geom's sliding friction), link mass ×0.5 to ×2 (every link the same), servo strength 40% to 120% (every force limit) and servo delay 0 to 150 ms. They are fixed and reach past Arena's floors on every axis (friction ×0.8 to ×1.2, mass ×0.9 to ×1.1, strength 90% to 100%, delays to 40 ms). A run sets one value per axis. Everything else stays nominal: servo spreads at their median, no heading or position offset.
- **One start, its own seed.** `stressStart` draws one start pose from the environment's own joint noise under `stress-start|<seed>`, and every run starts there, so a margin depends only on the physics and every run replays. The seed defaults to the SHA-256 of `stress|<skill hash>`, so the same skill gives the same findings. Stress never calls `runArena` and never reads Arena's salt, seeds or evidence. It reuses `ArenaWorld` unchanged (the gate hashes `arena.ts` and `arenaWorld.ts`).
- **The margin** is the contract's success margin from `evaluateContract`. A run where a failure fired counts at most 0, and a diverged or non-finite run counts −10.
- **The search** (`stressSkill({ mj, model, skill, environment, budget?, seed? })`): the nominal run first, then each axis in turn: both limits, `cem()` (`anythingCem.ts`) from the nominal value minimising the margin, then bisection between the nominal value and the worst value found. The boundary is the bisection's midpoint, or `null` when no value inside the limits fails. Last, `cem()` over all four axes together, starting from each axis's worst value with a spread of 0.15 of its range. The result lists every axis (`axes`), the axes with a boundary nearest the nominal value first (`findings`), the worst combination with its margin (`worst`), the start pose, the seed and the run count.
- **Budget** (`stressPlan`): 48 runs by default (`STRESS_BUDGET`), at least 16. Each axis gets a fifth of the budget less one: up to 6 bisection steps (`ceil(0.6 × (share − 2))`), the rest as `cem()` samples of up to 4 a round. The joint search gets what is left, up to 6 samples a round. A run already measured costs nothing, and the count never passes the budget. With 48, a 6 s Stand on quad-servo takes 41 runs.
- **Measured on the fixtures:** the hold policy that stands in for a trained Stand passes the whole range on quad-servo (lowest margin 1.62 in 45 runs). The fixture stands on straight legs, so neither friction, nor strength down to 40%, nor link mass to ×2 moves its margin by more than 0.02, and a constant target makes delay irrelevant. The tests bend each swing joint 0.76 rad: that Stand passes Arena 32/32/32 and sags under the height bar above link mass ×1.67 (margin −0.04 at ×2). The app's model of the same quad has the same MJCF but a different physics hash (its start pose differs), and about 0.07 less margin: 0.76 rad was refused there (1 of 32), and 0.745 rad passes Arena 32/32/32 with Link mass > ×1.58 at the default budget, which the e2e uses. A hold policy with velocity feedback (gain −0.14) holds through 40 ms of delay and falls at some delays above 60 ms but not others (60 and 100 ms fail, 70, 80 and 150 ms hold), so a small budget can miss a boundary like that.
- **Time:** 41 runs take 15 to 23 s on an M5 Pro in Node (0.3 to 0.5 s a run for a 6 s Stand), and took 72 s with 28 other test files running beside it on a loaded machine, so no test asserts a time. Stress runs in the skills worker (`skills.worker.ts`, job `stress`), never on the main thread, and posts its share after every run.
- **Train on These** (`trainOnFindings`, job `stress-train`): `widenedEnvironment` moves each failing axis's edge past its boundary by an eighth of the axis's limit span (friction 0.1625, mass 0.1875, strength 10 points, delay 18.75 ms), clamped to the limits. Every other range stays. The contract, observation and action don't change, so the freshness hashes hold and the result is an ordinary Kit record. Forge trains the Kit job for the entry for its last try's first stage, warm-started from the skill's policy (`warmPolicy`, `logStdMin` −2.5) on the coached reward when there is one. `randomRanges` (§8g) covers both Forge's default and the widened friction and mass. `delaySteps` reaches the widened delay in control steps (at most 8). Forge has no per-robot force-limit draw, so a strength finding trains every robot at the widened range's weakest strength (the job's model has its force limits scaled). Arena then judges the policy on the widened environment, which Arena widens again to its floors. A pass saves a new skill with `warmStartFrom` the old one's hash and keeps the coach tag. Otherwise the old skill stays and the row reads “Refused in Arena: 28 of 32 tries”. Measured: the swung Stand on its widened range (mass to ×1.86) scores 28/27/31 and is dropped, and a straight hold policy scores 32/32/32 and is kept.
- **Limits of this step:** Train on These is for Kit rows, whose controller is a policy, on the desktop: the web demo's tab Forge has no warm start (`canTrainOnFindings`). Findings live for the session (the runtime's `SkillStress`, not the project) and go when the row's skill changes. A second Train on These widens from the Kit's ranges again, and a Kit retrain after a design edit trains the plain ranges.
- **In the app:** **Stress** in a ready row's right-click menu, and Stress ⟨row⟩ in ⌘K (`stressCommands.tsx`), runs as a user job with the row's busy state (“Stressing” and a share), and Stop ends the worker. Up to three findings show under the row as buttons (`findingLine`: “Link mass > ×1.67, margin −0.04”). A click replays the finding's worst run in the live sim: `setPhysics` (§8d) with its values, the skill's controller, and a reset to the stress start pose. Try clears it. With findings on a Kit row, the menu and ⌘K add **Train on These** (Train ⟨row⟩ on These). The agent's `stress_skill` runs the same job and answers with every axis's boundary or lowest margin and the worst combination (§9).
- **Tests:** `stress.test.ts` plants margins (mass above ×1.3, delay above 60 ms, friction below ×0.55, two weak axes, no failure) and checks seeds and budgets. `stressQuad.test.ts` stresses the swung Stand for real at a budget of 24 and checks the boundary by probing 0.15 either side. `stressTrain.test.ts` covers the widening, the Forge job and keep or drop. `workspace/skillStress.test.ts` drives Stress and Train on These through the commands, hook, runtime and row state with fixture worker replies, checking replay physics, controller and start pose, record replacement and cleared findings. The 135 s browser walkthrough was removed. Stress-specific menu and button clicks no longer have browser assertions.

### Twins (`src/fleet/twinArena.ts`)

The units of a fleet share one design but not one set of servos. Each unit gets a twin, the scene's model built from that unit's own calibrations, and Arena judges a ready skill on every twin.

- **The twin** (`twinModel(input, histories)`, which is `calibratedModel` in `src/sim/calibratedModel.ts`): `buildMjcf(calibratedInput(input, simCalibrations(histories)))`, with the unit's histories from `unitHistories` (§8k). A unit with no calibration uses the catalog presets. It never inherits another unit's measured fit. In the app, `buildModel({ calibrations })` (`useSimulation.ts`) builds the same twin from the scene's live meshes through `calibratedModel`.
- **The run** (`proveOnTwin({ mj, model, skill, environment, salt? })`): the unchanged `runArena` with the skill's controller and the environment's contract, so a twin meets the variants, floors and bar the skill met. It saves nothing and makes no new skill. In the app it's the skills worker's `twin` job, through `SkillsRuntime.twin(model, skill, environment)`, which runs outside the one user job, like a draft, so twins can run beside training.
- **The verdict** (`twinVerdict(unit, evidence)`): `{ unit, passes, trials, passed, line }`, with the counts from Arena's worst variant. A pass reads Arena's line (`arenaLine`: “31 of 32 tries, at least 86%”). A failure reads the contract failure label that failed most tries in the worst variant (a tie goes to the first by name), so a weak shoulder reads “Shoulder sags”. With no label fired it reads `refusedLine`.
- **On the record:** `SkillRecord.twins` keeps the latest verdict per unit, and `withTwins(records, hash, verdicts)` (`twinArena.ts`, verdicts keyed by unit) merges them in, so the skill's row (`SkillTwins` under `SkillsList`) displays every unit's pass counts and a failed twin's contract line. Operate also displays the latest rollout verdict on each unit's row.
- **Tests:** `twinArena.test.ts` builds four twins of `servoArm()` from one project: the scene's own and `arm-1` with no calibration, `arm-2` with a measured shoulder gain of ×0.9, and `arm-3` whose measured shoulder keeps a tenth of its force limit. A hold with the shoulder at 60° must keep it within 0.15 rad of where it started for 0.5 s, and the failure “Shoulder sags” fires past that. Only `arm-3` fails with the line “Shoulder sags”, and the same salt gives the same verdicts twice. Pure cases cover the lines, ties, the refused fallback and `withTwins`, and `projectCalibrations.test.ts` keeps units' histories apart.

Roll Out uses these verdicts before sending the saved network policy, first to the chosen canaries and then to the remaining passing units (§8k). `rollOut.test.ts` covers order, repeated seeds, held twins, empty and unknown canaries, proof exceptions and partial pin or climb failures. `climbUnit.test.ts` covers refusals and listener cleanup without retrying. `twinWorker.test.ts` checks the calibrated model reaches the skills worker and the worker terminates after proof.

### Retained policies in Leagues

League entries use the gallery bundle’s retained network policy or policy-backed skill without installing a different controller. Admission refuses other retained controller kinds before accepting a receipt. Adjudication and browser replay run that controller through the existing Case runner. Open Scene keeps the selected robot, Case and retained policy through the gallery import path. ### Publishing and installing (`hubSkill.ts`, `robotSchema.ts`, `policyMap.ts`)

A ready skill goes to a model repo on the Hugging Face Hub, and **Install Skill** brings one onto the open robot, where it trains again and Arena judges it on this robot's physics. Installation also works anonymously in the web studio and shared robot gallery when tab training is supported. Publishing remains desktop only. Both use `src/hub/hubBridge.ts`, with desktop Hub handlers and lazy browser worker routes.

- **Publish:** **Publish to Hugging Face** in a ready row's right-click menu, or **Publish ⟨row⟩ to Hugging Face** in ⌘K. Signed out, it opens Settings ▸ Accounts. `publishedSkillFiles` refuses a skill without passed evidence, and one whose environment no longer hashes to the evidence's. The repo is `<account>/<robot>-<skill>-<6 hex of the skill hash>` (`skillRepoName`), created as a model repo (`kind: 'model'`), holding `skill.json` (the whole skill), `policy.json` (its controller's policy, when it has one), `contract.json`, `environment.json`, `evidence.json`, `robot.json` and a `README.md` model card (`modelCard.ts`: body class, joints and limbs, each observation term and its size, the action, Arena's runs). The main process adds `policy.onnx`, encoded from `policy.json` by `policyOnnx` (§8k), so ONNX Runtime can run it.
- **`robot.json`** (`robotSchema`): the body class (`classifyRobot`, §8c), whether the base floats, each action joint's limb and depth (its place in the chain from the body), and each limb's anchor: where it leaves the root, forward and sideways, scaled so the farthest limb on each axis is 1.
- **Install:** **Install Skill** in ⌘K or a Train row's right-click menu lists published skills under its model repo link field. Each fitting row has **Install**, which uses the same install path with the listed commit pinned. A pasted link is parsed by robot import's `hubLink`. The platform Hub backend downloads `skill.json`, `policy.json`, `contract.json`, `environment.json`, `evidence.json` and `robot.json` (`SKILL_DOWNLOADS`), never the card or the ONNX. The ranking worker prepares installation with `readPublishedSkill` and `installPlan`. It parses them fail-closed and checks each against `skill.json`: the policy and the evidence by hash, the contract against the binding's contract hash, the environment against the evidence's environment hash and the binding's contract, observation and action hashes, and `robot.json`'s joints against the action's. The policy must pass `isRunnablePolicy` (sizes, finite numbers, at most 8 layers of 4,096). A mismatch names the file: “policy.json doesn’t match skill.json.”
- **Find:** the model card includes `basecase-skill`. `electron/hub/skillSearch.mjs` searches that tag and the older `basecase` tag, then checks that all six install files are present and each declares a size within 32 MB before downloading `skill.json` and `robot.json`. Each search reads up to 100 models and the combined candidate list is sorted by repo and capped at 100. Model metadata is capped at 2 MB. Only those two files are downloaded, each capped at 32 MB, at the commit returned by the Hub. The embedded policy and evidence must match the commit's file metadata: Git blob ids for regular files or SHA-256 for LFS. Git's SHA-1 object digest is a protocol identifier, not an authorization check. Candidate files are cached by Hub origin, repo and commit, with at most 128 entries and 64 MB. Concurrent searches replacing the same cache key count its bytes once. A result list also holds at most 64 MB of candidate files. A failed search returns an empty list while the link field remains usable.
- **Rank:** `skillRank.ts` is pure. It validates the skill, policy, schema, action joints and evidence bindings before listing anything. Source evidence must use the current Arena version, counts and bars, with enough passes in every variant. `skillFit.ts` shares the installer’s Motor Kit name and origin checks, joint mapping, floating legged target requirement and policy input checks. Unsupported skills and camera or clock policies stay refused with the same reason as installation. Discovery builds the target schema from `kitRobot`’s actuated position joints, as installation does. It sorts by installation compatibility, reported installation score descending, mean distance from each target limb anchor to its mapped source limb anchor, then total source Arena passes descending. Repo and revision break ties in code-point order. Refused candidates appear last with their installation refusal reason and a disabled Install. Parsing, ranking, installation preparation and outcome construction run in `skillRank.worker.ts`. Browser Hub downloads and outcome processing use a separate lazy worker and pass structured replies directly to the Hub bridge. A failed browser worker refuses the operation instead of falling back to package parsing on the main thread. `findSkills.ts` supplies the same ranking to the sheet and the agent's `find_skills`, whose optional query filters names and repos.
- **Which skills:** only Motor Kit skills (named after a Kit entry, `origin.method` `motor-kit`) with a policy and passed evidence. A taught skill or a move doesn't install: its contract names the author's joints and parts.
- **The joint map** (`jointMap`): the body class and floating base must match. Each of this robot's limbs takes the source limb with as many joints whose anchor is nearest (the first on a tie), joint for joint by depth. quad-servo's four legs cover the hexapod's six: the middle pair takes the front pair. A limb that branches, or one with no source limb of its length, refuses with the lengths: “This skill moves limbs of 3 joints, and this robot has limbs of 4.” (quad-servo onto biped-servo).
- **The policy map** (`mappedPolicy`): the observation is the Kit's `12 + 3n`, so the first layer's base columns stay, and each joint's position, velocity and last-action columns come from its source joint, divided by how many joints share that source so a shared leg isn't counted twice. The normalizer's columns follow, the last layer's rows follow the action joints, and hidden layers don't change. A policy that reads a camera or a clock refuses.
- **Training:** `installPlan` gives the Kit entry and `{ from, policy }`; `SkillsRuntime.installKit` runs the Kit's usual tries on the open design (`trainKitEntry` with `warm`), with the mapped policy as the first stage's `warmPolicy` (§8g, `logStdMin` −2.5). Arena judges on this robot. A pass saves a new skill with `warmStartFrom` the published skill's hash and its own evidence; the author's evidence never moves. The Kit row shows it like any other.
- **A run Arena refuses saves nothing,** for an install or any Kit run: the refused outcome carries the evidence of its best try that failed worst (`worstEvidence`: for Walk, the 50% or 0% speed run when that's the one that failed), and the row's line reads “Refused in Arena: 20 of 32 tries” (its worst variant) until the next run of that row starts or the design changes (`refusalModel` keys it by `modelHashes`).
- **Security** (§0h): every request is built from a checked account, repo and branch on the Hub's origin, each file is capped at 32 MB, a redirect off the Hub must be https and goes through `publicFetch` without the token, and the policy is data the policy runner loads, never code.
- **Tests:** `src/skills/hubSkill.test.ts` publishes a stubbed ready Stand (`hubSkillFixtures.ts`) and checks install plans from quad-servo to hexapod and back without training or Arena: source hash, target joint ids and policy dimensions. A round trip through `trainKitEntry` with Arena success results stubbed checks that the mapped policies reach Forge, each result saves under its own hash with fresh target evidence, and the installed hexapod skill publishes and installs back on quad-servo. It refuses a tampered `policy.json`, a skill that never passed, and quad-servo onto biped-servo, checks that a refused run saves nothing, and checks the mapped policy acts as its source. `artifacts.test.ts` checks that a warm start carries no evidence and uses the target binding. `electron/hub/skillRepo.test.mjs` covers the model repo, the ONNX, the downloads and the exploit cases (crafted names, an oversized file, an http redirect). `e2e/skillHub.e2e.test.ts` seeds a ready Stand bound to the open quad-servo, publishes it from its row against `e2e/fakeHub.ts`, and checks the model repo, all eight files, the saved skill and token isolation without training or running Arena. The discovery e2e below checks installation through ⌘K up to the training handoff.

### Reported installation outcomes

Install Skill records each finished attempt through `installOutcome.ts`, including failed Arena runs, cancellation and infrastructure failure. Each record has a distinct attempt id. Republishing that record keeps the same id. Records bind the source repo, pinned commit, skill hash and schema hash to the target schema, physics, actuators, contract, environment and Arena result. The Hub backend stores them under `library/skill-outcomes/` before attempting publication. Publication uses the installer's account and a content-addressed model repo tagged `basecase-skill-outcome`, never the source author's repo. Signed-out or offline records stay local and pending publication is attempted on later feedback operations.

Discovery reads local and remote reports through the existing Hub client. Ranking first separates compatible skills, then compares reported installation scores, limb-anchor distance, source Arena passes and deterministic repo and revision ties. A report must match the exact source revision, skill and schema. Its Arena version, counts, verdict and evidence bindings must agree with the target environment. Compatible target schemas contribute weights of `1 / (1 + limb-count difference + mean nearest-anchor distance)`. Success adds the weight and failure subtracts it, divided by total weight plus two neutral observations. Repeated identical records count once. Cancellation and infrastructure failure do not affect ordering, including an infrastructure refusal that retains Arena evidence from an earlier candidate. Missing feedback leaves the original ranking usable.

These are reported results, not authenticated proof of execution. A publisher can make internally consistent claims. Reports never confer readiness or replace the local Arena installation verdict.

### Cases on the one contract

`src/cases` keeps no evaluator. `parseCase` accepts any contract shape as plain JSON (version 1, depth 64, 4096 nodes, finite numbers, at most 16 failures) and leaves the rest to the crate; `runCase` and `scoreTry` judge with `evaluateContract`, and `CaseResult` carries the `trace` and the `failed` labels. A contract the crate refuses makes `runCase` reject. Scaling a Case to another arm scales every atom's value and scale except those that read an `angle`.

### Gate s3a-motor-kit: bars and why

The gate judges Kit skills twice with the unchanged `runArena` (its files and the shared `sim/controlDelay.ts` wrapper are hashed in the gate): once on the Kit's own environment, and once on the gate's own contracts in `verify/skills/judge.ts`, so an easy Kit contract can't pass. Every bar was checked against stand-ins before the gate was approved: a hold controller passes Stand, Get-up and Settle; limp fails Stand on all three robots and Get-up and Settle on quad-servo; a zero policy fails Velocity tracking. Where limp fails the gate's contract, the Kit's own contract must fail it too.

- **Stand**, 6 s from starts up to 15° off neutral: tilt under 0.35 rad, base above 75% of its start height, drift under 0.15 m. The 15° matters: these fixtures stand passively on straight legs, so limp passes from the neutral pose.
- **Velocity tracking**, 8 s: tilt under 0.6 rad, base above 60%, and after a 1 s ramp the distance covered sits between 0.5× and 1.5× the command (0.2 m/s for quad-servo and hexapod, 0.15 for biped-servo), judged at the top speed, half of it (the four- and six-legged robots) and standing still (under 0.1 m drift). Three speeds catch a policy that only knows one. 0.2 m/s is the time-to-skill bar (§0k).
- **Get-up**, 6 s, from the pose limp collapses to out of a 40° crouch: hold base above 80% and tilt under 0.35 rad for 1 s.
- **Settle to neutral**, 4 s, from 12° off neutral on every joint: every joint within 8° of neutral for 1 s, upright. The servo law is `kp = effort / 0.17 rad`, so a joint under stance load sits several degrees off its target; 8° leaves room for that and still fails a robot that stays where it started.
- **Biped steering**, a 13 s timeline in the WASM sim through the app's policy path: 1 s still, 4 s forward at 0.15 m/s, 4 s left and 4 s right at 0.1 m/s and ±0.5 rad/s. It must cover 0.3 m along its heading in the forward segment (half the command), turn at least 0.35 rad (20°) of the commanded sign in each turn segment, never tilt past 45° or drop under 60% of its start height, and no external force may act. 0.15 m/s on a 0.15 m leg is a Froude number (v²/gL, Alexander's dynamic similarity) of about 0.015, a slow, nearly quasi-static walk: people walk near 0.25 and change to running near 0.5. The run is one clean rollout, because Arena already covers randomized physics and servo delay for the same skill. The turn bar is a fifth of the command because biped-servo has no hip yaw joint, so it turns only by uneven strides and foot pivots; a robot that drifts one way can't pass both turns.
- **Wall-clock budgets** on the M5 Pro, Arena included, against Forge F1 at 40K steps/s or more: quad-servo Stand 10 min, Velocity 30, Get-up 20, Settle 10; hexapod Stand 10, Velocity 30; biped-servo Stand 15, Velocity 45. The race: 5 min per arm task, 45 min for the walk. These checks are `timed`.
- **The race suite:** arm-3dof reach (IK expected, a 20 mm box held 0.5 s), arm-6dof touch then hold (IK expected, 0.1 s at one point, then 1 s at another), quad-servo walk at 0.2 m/s (reward search expected, judged by the Velocity tracking contract). The 2× rule is checked by running every other method with a cap of half the router's wall time (10 min at most); any that passes Arena inside it fails the gate.
- **Canaries** fire only on their own assertion; a canary that crashes or doesn't load counts as not fired (`verify/lib/canary.mjs`). Limp on Stand and a zero policy on Velocity tracking are planted against the gate's own contracts; a reward-hacked RewardLang candidate (rewards staying upright) alone in the race with a 10M-step budget; the weak quad's Stand; a quad-servo Stand skill on the hexapod; and the biped driven on the same timeline with every turn command zeroed.

### Remote training recovery

Settings ▸ Training selects one Linux x64 computer for Motor Kit training, taught solver races, saved motions, frozen dataset cloning and their warm starts. These keep their job and skill formats. Automatic Motor Kit background work, coaching, stress training, hand-off training and legacy policy runs stay local. Without a selected computer, training runs locally.

The studio commits a recovery journal in its own IndexedDB database before a foreground worker dispatches Forge. The journal holds the existing worker request or frozen dataset job, its workflow identity, scene task context and model fingerprint. It contains no SSH credentials and is excluded from scene exports. Kit and motion seeds are frozen with the workflow so replay generates the same inputs. A separate random 32-byte key stays in the local journal and worker memory. It recreates the same ordered Arena and Kit-validation draws after restart, preserving candidate rankings, failed-start curricula and later warm starts. Each judgment still executes locally. A new workflow gets a new private key, and neither its key nor its derived judgment salts enter Forge inputs, scene exports or policy artifacts. Each Forge call uses the workflow identity plus its call index, and the backend refuses a different input fingerprint for that identity.

Reopening the scene builds its current model and restores the existing training row. Recovery runs the same local skill worker and validation path. Completed Forge stages are replayed, and an active stage reattaches to its remote job. Dataset recovery uses its frozen demonstrations and reconstructs the held-out Case judge from the open scene. A changed model, animation or Case refuses recovery. A design changed while a result returns also refuses retention. Remote readiness fields never create evidence. Arena runs locally, and only a locally accepted skill enters the saved skill rows. Stop uses the existing remote stop-file contract. Closing a scene detaches its remote job.

The journal resolves writes only after its IndexedDB transaction commits and caps a workflow at 64 MB. An unavailable or full journal fails before dispatch. The receiving bridge validates returned policies with `isRunnablePolicy` before sending them to a skill worker.

Journal cleanup failures report a refusal and release the training row and active workflow identity, so later training can start. Stop waits for an in-flight Forge start to identify its job before sending the stop request. Detaching a recoverable workflow leaves that job running even when its start response arrives after disposal.

Move refusals read the latest Forge error after the worker finishes, preserving connection failures instead of replacing them with a generic Arena refusal. `runtimeMove.test.ts` covers that boundary.
