# Joints, poses and motion

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

Joint-axis candidates group joins with `electron/cad-kernel/pairKey.mjs`, calculating the newline-separated lexical key once per join without sorting endpoint arrays (§0f). Candidate order, confidence and fastened-pair rules stay unchanged.

## 8c. Joints, Poses and Motion

`utils/kinematicsMembers.ts` groups a rig's owned parts by joint in ownership insertion order. MJCF body generation and the Weight and engineering-check body traversal share this helper. Each call owns new groups, so embedded-part adoption and later ownership edits are read from the current rig.

URDF link traversal (`utils/robotImport/urdf.ts`) groups joints by parent once per parse instead of filtering every joint at each visited link. File imports, expanded xacro, robot presets and articulated catalog parts share this reader. Siblings retain source order, transforms remain depth first, and disconnected links, repeated children and the depth-200 traversal guard keep their existing behavior. The index belongs to one parse. `urdf.test.ts` compares ordered joints and transforms against a full-scan reference across shuffled branching trees, disconnected links, cycles and the depth boundary. On macOS arm64 with Node 26.13.0, pre-parsed wide URDF documents with 100, 1,000 and 3,000 joints took median parse times of 0.309, 11.373 and 40.757 ms before, and 0.224, 2.241 and 4.193 ms after. Each implementation had two warmup batches followed by 11 alternating measured batches of three parses. Complete outputs matched. These measurements cover model parsing on a shared host, without XML decoding, mesh loading, a CI timing threshold or a claim about complete import time.

Robot mesh loading and Onshape part exports use the shared `electron/eachLimited.mjs` cursor without copying or shifting pending queues. Mesh loading keeps six active tasks at most, and Onshape keeps four. Onshape filenames retain each part’s original index when exports complete out of order. Robot mesh failures remain notes, while an Onshape export failure rejects the import.

A robot is posable once its degrees of freedom are declared. Posing never edits parts: the modeled pose is the design, and a pose only changes what the canvas shows.

- **Data** (`types/robotics.ts`, saved with the scene in `ProjectSettings`): `joints` (`RobotJoint`: revolute in degrees or prismatic in mm, parent and child parts, `parentJoint` when links between joints have no geometry, origin and axis, range, limb), `pose` (the pose on the canvas: values by joint id plus an optional whole-body `root` offset), `poses` (saved) and `animations` (`RobotAnimation`: keyframes with every animated joint, smooth or linear, loop).
- **Animation sampling** (`utils/animation.ts`): Pose playback, simulation controllers, motion references and agent pose checks share `sampleAnimation`. It blends joint values and root-position axes directly from four supporting keyframes, without temporary arrays per channel. Linear and Catmull–Rom interpolation keep the same endpoint clamping, loop seam and missing-value defaults. Root rotation uses quaternion slerp between the two span endpoints in both modes.
- **Several robots per scene:** `buildRig` finds each robot (joints linked through a parent joint or a shared part, plus unlisted parts grouped with one robot's parts) as `rig.robots` (key = its first base joint id, name = its parts' group). The scene pose holds every robot's joint values and each robot's body offset in `roots` by key; `robotRig` gives one robot alone for IK, gaits and mocap, and `withRobotPose` puts its result back without touching the others. Saved poses and animations carry `robot`; the Pose tab, ⌘K Rest Pose, walk cycles and Import BVH work on the selected robot only, and the agent tools take `robot` (default: the selected one, or the only one). Imported robots get unique joint ids (a second G1's are `left_knee_joint_2`), and scenes saved with repeated ids are renumbered when they open (`uniqueJointIds`). A set tracks ids in the current batch, starting a new batch at each repeated id without scanning the preceding joints. Each batch keeps one available suffix across its ids, parent links and linkage drivers.
- **Declaring joints by hand** (`src/joints/`): select two parts, parent first and child second, and run Add Hinge or Add Slider (right-click on the selection, or ⌘K; both appear only with exactly two parts selected). One module builds every joint: `declare.ts` (`jointProblem`, `jointFrom`, `withJoints` with first ranges) serves the agent's `define_joints` (`declareJoints` in `workspace/agentBuildRequests.ts`) and the hand-made joint (`handJoint`), so both give the same `RobotJoint`. Joint declarations and skeleton declarations share `joints/merge.ts`: existing joints retain source order unless an incoming id replaces them, then the complete incoming batch follows in its original order. The incoming id set is built once per merge. Full replacement copies the incoming batch without reading ids. First-range history stays unchanged, including when replacing every joint. Mirrored joints and hand-made joints use this same merge through `withJoints`. The axis comes from `axisFinder.ts`, run in the analysis worker (`jointAxisIn`, the viewport's `jointAxis`, one cached `MeshIndex` per part and pose):
  - `MeshIndex` welds the part's world triangles (1 µm), links triangles across shared edges and marks a triangle curved when a neighbour's normal turns between 0.25° and 65°. Flat faces and 90° creases are never curved, so a box face gives no axis. Shared-edge lists append neighbor entries in source order and classify curvature during linking, without filtered neighbor arrays or a separate curvature traversal. Normal comparisons run only in ascending triangle order. One comparison can mark both triangles, and pairs whose triangles are already marked need no comparison. Neighbor order, repeated edges and strict angle thresholds stay unchanged, including when several faces share weld-collapsed edges. `meshCurvature.test.ts` compares the previous topology and marks across transformed solids, open surfaces, nonmanifold edges, welded and degenerate faces, source edits and nonfinite inputs. Its 300- and 600-triangle paired-face fixtures reduce normal comparisons from 600 and 1,200 to 150 and 300. These are operation counts without timing assertions or a claim about complete axis-discovery time. Nearest-face picks reuse one three.js triangle and two query vectors across the scan, reading welded coordinates without per-face tuple arrays. Picks skip faces below 0.000000001 mm² and keep the first face at an equal distance.
  - A round face is the curved triangles reachable from the clicked one without crossing a 65° crease. `fitCylinder` takes the axis as the least eigenvector of the area-weighted normal moments (normals must lie in one plane), fits the centre and radius as a least-squares circle of the face's vertices in the plane across the axis, and accepts it when the vertices sit within max(0.05 mm, 2% of the radius); otherwise it drops the triangles off the circle and refits, up to three times. Each fit computes one residual per welded vertex from the coordinates already read for the circle. The error check and triangle trimming share those residuals, which are rebuilt after every refit. The circle fit accumulates only the upper half of its unweighted normal matrix and mirrors it before solving, keeping vertex order in each sum. Area-weighted normal moments keep their original multiplication order. Clicked faces and automatic shaft-and-bore matching use this same path. A clicked face needs 30° of arc.
  - With no click, `coaxialPair` looks for a shaft (convex, at least 180° of arc) on one part inside a bore (concave) on the other: parallel within 1°, axes within max(0.5 mm, 5% of the radius), radii within max(1 mm, 20%), overlapping along the axis. The origin is the middle of the overlap. Two bores with no shaft between them propose nothing.
  - The agent's `find_joint_axes` (`jointCandidates.ts`, the analysis worker's `jointAxes` over the parts it names, every visible solid part by default) runs `coaxialPair` on every pair of parts. A shaft part in two collinear bores on two other parts is a pin: it proposes one joint between those two, naming the pin. Two parts joined on two or more distinct lines (bolts, dowels) are reported as fixed and propose nothing. Parent and child follow the joint graph out from the part with the lowest bottom (the biggest box breaks a tie within 1 mm); fixed pairs carry the walk across. Each candidate gives axis, origin, Ø, engaged length, slide travel and a confidence: the fit (axis offset and clearance against their tolerances) times the engaged share of the radius, capped at 1. Round faces with no partner (up to 3 per part, at least as long as their radius) are listed too. Answers are in the agent frame (z up), and the prompt rigs an import from them, then sweeps each range with `animate`. Planar slides (rails, dovetails) aren't found.
    - Shaft clustering (`axisClusters.ts`) indexes clusters by shaft before testing collinearity, so a link never scans another shaft's clusters. The first matching representative still wins, and clusters retain global creation order with members in source order. Each query builds a fresh index, preserving later geometry and shaft edits.
    - Graph orientation (`jointGraph.ts`) indexes both ends of each kept joint and fixed pair once per query. Each body's adjacency retains joint order before fixed-pair order. A breadth-first queue with an array cursor visits each reached body once, retaining root priority, first discovery through cycles and joint metadata without rescanning every connection or searching for the joint behind an edge. No index survives the query.
  - When nothing is proposed, the canvas waits for a click on a round face of either part: the cursor is a crosshair over one and not-allowed elsewhere, the gizmo hides, clicks don't change the selection, and Esc or a new selection stops it.
  - The axis points along its largest component. A hinge's range is ±90°; a slider's is the travel that keeps the shorter part within the longer one along the axis (`slideTravel`). The joint takes the child's name and an id `hinge_N` / `slider_N`. It goes in as one undo step (`commitJoints` in `useSceneDocument`), the child is selected and the Pose tab opens on the joint, whose ring turns the child.
  - In the Pose tab, right-click a joint row for Range ▸ (two fields, lowest and highest; each change is one undo step) and Delete, which asks first (“Delete ⟨name⟩?”) and is one undo step. A range drag that never ends in a final change still becomes its own undo step as soon as anything else is edited or undone.
- **Joints follow their mount:** `frame` stores the pivot in its first parent part's own frame (`anchorJoint`); `resolveJoints` reads it back, so moving or undoing the robot keeps joints in place. Resolution builds each used mount's transform once per call and shares it across that mount's joints. Transforms never survive the call, so a moved or restored part is read afresh.
- **Kinematics** (`utils/kinematics.ts`): `buildRig` turns joints into a tree. Each part moves with the deepest joint that lists it as a child, and a joint's mount moves with the joint above it. An unlisted part follows its group only when the whole group moves with one joint (a group spanning a whole robot says nothing). Link ownership and robot membership each summarize groups once, then assign unlisted parts from those summaries without scanning the scene per part. Conflicting link owners, base mounts and groups spanning separate robots keep their existing assignment rules. Connected components index their joint ids once and receive depth-ordered joints in one shared pass, preserving robot keys, names, pivots and part membership without scanning all joints per robot. The index is rebuilt for every rig. `forwardKinematics` composes rest-frame rotations from the base out. `solveIK` is damped least squares (Levenberg–Marquardt) with joint limits. Its first unconverged iteration prepares one Jacobian vector grid and each target’s joint influence (`utils/kinematicsJacobian.ts`). Later iterations overwrite those columns from current axes and target positions, without cloning column or offset vectors or repeating ancestry lookups. The workspace belongs to that solve and is rebuilt after edits. Each trial copies the normal equations directly into one augmented matrix, adding damping and the right-hand side before in-place elimination. Rejected trials keep the original normal equations for the next damping value. Torso joints are stiffer so limbs reach first. `preBend` starts knees and elbows bent the way their range opens (straight joints are singular).
- **Joint motion workspace** (`utils/kinematicsMotion.ts`): each nonzero hinge evaluation reuses its axis vector for the rotated pivot after building the rotation quaternion. Pose playback, forward kinematics, IK and four-bar closure share this function. The original pivot stays intact, no workspace vector escapes and each rotating call reloads the axis and pivot. `kinematicsMotion.test.ts` checks exact agreement with the allocating calculation across 300 edited joints, mixed hinge, slider and fixed calls, zero and nonfinite inputs, pivot invariance and independent results. Its 300- and 600-evaluation fixtures remove 300 and 600 vector clones. These are allocation counts, without timing assertions or a claim about complete pose or solve time.
- **Linkages** (`src/linkage/`, `types/loopClosure.ts`): a four-bar from Sketch's Path mode or the agent's `synthesize_linkage` (§8, §9) is four printed bars compiled from the `four_bar` recipe at the drawn start (`cad.pending` until `useCadCompile` compiles them), grouped as Four-Bar, plus a Feetech STS3215 mated coaxially under the ground's pivot A (`planMate`). The whole mechanism is lifted so the servo stands on the sketch's plane with the bars above it. The crank is a revolute joint with that servo as its actuator, ranged over the drawn sweep, so the torque and sweep checks see it like any servo joint. The coupler (at B, under the crank joint) and the rocker (at D, on the ground) are fixed joints with `loop`: `forwardKinematics` turns each by the angle that closes the loop at the crank's value (`kinematicsLoop.ts`, the same open branch as `four_bar_pose`), so Pose, animations, sweeps of the pose and the canvas move the whole linkage. Everything else reads them as fixed: the Pose tab has no row for them, and the sweep check turns the coupler rigidly with the crank. Closed loops aren't simulated (§8d). `uniqueJointIds` renames `loop.driver` with the ids it renames. The four-bar fitter prepares its undamped normal equations once per Jacobian (`utils/linkageFitNormal.ts`), reuses them after rejected trials and rebuilds them after accepted steps. Each prepared system owns one elimination buffer. Every trial reloads the equations into it before damping and elimination, keeping the cached system intact. Returned steps own independent arrays, and a partially eliminated singular trial cannot affect the next trial. Residual evaluation writes path errors and all nine penalties directly into its result array. Derivative probes reuse one residual workspace per Jacobian, while accepted and trial states retain independent arrays.
- **Planar diameter** (`utils/planarDiameter.ts`): four-bar fitting and resting foot-contact classification share a direct maximum-distance scan. Each unordered pair, including self pairs, is measured once without a pair-distance array. Self pairs preserve NaN results for infinite coordinates. Empty paths retain negative infinity, and foot spread retains its zero floor. [Evidence](../notes/performance-joints.md#planar-diameter-measures-each-unordered-pair-once).
- **Linkage sampling** (`utils/linkageKinematics.ts`, `linkage/linkageFrames.ts`): curve generation, fit scoring and preview animation prepare the fixed placement rotation once per batch. Each crank sample still solves its own closure. Preparation stays within the call, so edits and undo are read afresh. `linkageSampling.test.ts` checks exact coordinates, reverse and stationary sweeps, unclosed poses, source preservation and later edits. It bounds placement-angle reads to one for a 721-point curve and one for a 61-frame preview, down from 721 and 305 respectively. These are operation counts, without timing assertions.
- **Linkage fit fallback** (`utils/linkageFit.ts`, `linkageKinematics.ts`): the shared `closeCrank` calculation accepts an already evaluated crank point. The fitter retains that point when exact closure fails, removing a second crank-point array and repeated sine and cosine from the clamped fallback. Sketch's Path mode and the agent's `synthesize_linkage` share this fitter. `linkageClosure.test.ts` compares exact and clamped residuals across 200 trial vectors and their edits, both sweep directions, tangencies, coincident pivots and nonfinite inputs. Its twelve-sample fixture with every closure failing reduces sine calls from 37 to 25 and cosine calls from 37 to 25. Valid closures retain their original arithmetic and call counts. These are operation counts, without timing assertions or a claim about complete synthesis time.
- **Linkage distance scoring** (`utils/linkageKinematics.ts`, `curveDistance`): fit errors prepare each sampled coupler curve's segment origins, directions and squared lengths once. Ranking prepares the drawn polyline once across all candidates. Queries retain the original projection and distance arithmetic, including repeated points and empty curves. Prepared coordinates belong to one synthesis call, so later edits and undo rebuild them. Sketch's Path mode and `synthesize_linkage` share both consumers. `linkageDistance.test.ts` compares exact distances across 100 seeded curves, degenerate and non-finite inputs, edits, source preservation and complete synthesis results and ranking. For 12 queries against 360- and 720-segment curves, source coordinate reads fall from 34,560 and 69,120 to 1,440 and 2,880. These are operation counts, without timing assertions or a claim about complete synthesis time.

- **Linkage path summaries** (`utils/linkage.ts`): candidate scoring accumulates maximum and squared errors while visiting targets, without an error array or later reduction. Ranking samples its coupler sweep directly into the worst-distance accumulator, without retaining the curve or its mapped distances. Both preserve sample order, projection arithmetic, empty-sweep results and ranking thresholds. Sketch Path and the agent share this synthesis path. Existing `linkage.test.ts` and `linkageDistance.test.ts` cover complete synthesis, error bounds, determinism and ranking. [Evidence](../notes/performance-joints.md#four-bar-path-summaries-accumulate-during-sampling).

- **Grippers** (`src/cases/gripper.ts`, `findGripper`): two movable leaf joints under the same joint whose parts face each other count as a gripper's jaws, when each one's motion at its part (a slide's axis, or a hinge's swing) points within about 45° of the other part and its range has a limit on that side, which is its closing limit. The joint above them is the palm. `robotFacts` reports it as `gripper` (jaws with open 0 and closed limit, the point between the jaws' parts, approach and across directions, the opening between their inner faces, finger depth and the palm-to-centre length) and the `gripper` capability, leaves the jaws out of the arm's chain, and makes the point between the jaws the end effector. `closedOpeningMm` measures the remaining gap at the closing limits, using each jaw’s placed face extent and its slide displacement or hinge rotation. Hand Off refuses a payload thinner than that gap. A gripper that is one catalog part with no jaw joints isn't one in simulation, since nothing would close. The fixture `arm-6dof` carries a palm and two 5 N sliding fingers 50 mm apart.
- **Payload** (§8b, `utils/payload.ts`): a fixed arm's chain is sampled inside its joint ranges, value 0 being the modeled pose, turning each joint about its rest axis from the base out as `forwardKinematics` does, with every link's parts lumped at their centre of mass.
- **Fasteners follow what they clamp** (`src/assembly/followers.ts`, `rigJoints.ts`): in verify, poses and the sim, a screw moves with the deepest joint whose moving set holds everything it clamps, ignoring that joint's own servo (the horn-screw exception); nuts follow their screw, inserts their host. Joints never list fasteners. On Ribbit it reproduced the agent's 672 hand-listed moving screws on all but one fixed pseudo-joint.
- **Driver clearance** (`src/assembly/driverAccess.ts`): each screw shares one expanded search envelope across scene parts. Each L-key sector shares its three sweep directions across the three arm heights. Straight, L-key and ball-end options retain their blocker order and segment lengths. Preparation stays within the call, so placement and skip edits take effect on the next check.
- **Fastener axial probes** (`src/assembly/fastenerChain.ts`) reuse one point per screw across thread engagement, tip searches, uncut-hole samples, stack samples and head rings. Each tip-search position is calculated once before testing candidate solids. Probe consumers read the point synchronously, rings copy their centers and reported coordinates own their arrays. Workspaces end with the call, so later placement and role edits read current inputs. `fastenerProbes.test.ts` checks complete chain evidence, rigid placements, multiple screws, edits, source preservation and independent results. On its 300 mm and 600 mm screw fixtures, source-point clones fall from 2,303 and 4,603 to two each. A scratch comparison matched complete reports across 120 transformed and edited fixtures, including countersunk heads and all four sleeve kinds. These are allocation counts and result comparisons, without timing assertions or a claim about complete assembly-check time.
- **Fastener evidence selection** (`src/assembly/fastenerChain.ts`) scans for the greatest threaded overlap, longest uncut-hole run and strongest sleeve contact without sorting candidates. Equal scores retain the first candidate in the original traversal order, including the first sampled solid for uncut holes. Washers stay excluded from threaded receivers, receiver overlap must exceed 0.2 mm and sleeve hosts need at least three ring contacts. Full stack ordering and standoff stud checks stay separate. Assembly checks, wiring and fastener followers share this tracer.
- **Joints belong to their parts.** Deleting parts deletes every joint whose moving side is gone and drops the deleted ids from the rest (`jointsWithoutParts` in `kinematics.ts`, run by every `commitParts` and Onshape update). Empty joints with no dependents are pruned through a leaf queue (`kinematicsPrune.ts`), counting parent references once instead of rescanning the remaining joints for every ancestor. Supporting ancestors and cycles stay, and surviving joints keep their order. Undo brings parts and joints back together.
- **Undo:** pose changes are on the scene's undo timeline. Each history step (`Snapshot` in `SceneWorkspace`) holds the parts, the joints, the pose, the marks and the skeleton (and, for a Routine edit, the scene's Routines, §8j); `usePosing` reports every pose edit (sliders, the ring, saved poses, Rest pose, the agent's `pose`) through `onPoseEdit`, and edits less than 700 ms apart fold into one step, so a drag undoes in one go. Playback, scrubbing and pausing aren't recorded.
  - Background robot upgrades (`upgradeDoc`) patch each distinct parts array once per upgrade across the current scene, undo, redo and live-edit base. Each distinct joint array in undo and redo is also patched once. The current project's joints are updated separately by `useRobotUpgrade`. Shared arrays stay shared after patching. Separate edits stay separate, and no cached patch survives the upgrade call.
- **Canvas:** `Viewport3D` takes per-part rest → posed motion (`pose`). Measurements, interference (check_scene), servo outputs and sweeps run in the modeled pose (`withRest`); renders show the pose. Moving a part while posed maps the edit back to the modeled pose.
- **Pose tab** (right panel, beside Inspect, while the selection is on a robot or the scene has a skeleton, or while Edit Skeleton is on: `posable` in `usePoseScope`; P opens it, selecting the first robot if needed). The Skeleton section heads it (Edit Skeleton, below); the robot sections show only while the selection is on a robot. It shows that robot's animations, poses and joints (right-click a joint row for Range ▸ and Delete): while it's open, clicking a part picks the joint that turns it, and a single ring on its axis (an arrow for a slider) turns it in 1° / 1 mm steps (Shift is free). Picking a toolbar tool leaves the tab. Contents: Animations (play, scrub, + ▸ Walk Cycle or Import BVH, or straight to Import BVH when the robot has no legs; right-click for Loop, Rename, Delete), Poses (Rest pose and Save pose in the header; click applies; right-click for Apply, Rename, Delete), then one collapsible section per limb (Head, Torso, Left arm…) with label · slider · value rows. A row's label is the joint's name without the words its section already says (`jointRowLabels` in `utils/jointNames.ts`): the side goes only under a Left or Right section, so a rover's wheels under Other read Left wheel and Right wheel, as Results' Peak torque names them. Two rows in a section never share a label: when shortening would make two match, both show their full name (`prettyJointName`). A limb's rows share one grid (`grid-cols-subgrid`), so the label column fits the longest label with its Measured badge (§8k), up to 60% of the width, and every slider in the section starts at the same x. Animations and poses rename from the right-click menu only: a click already loads the animation or applies the pose, so there's no double-click rename.
- **Pose joint grouping** (`utils/jointNames.ts`, `jointGroups`) appends movable joints to one locally owned array per section, without copying earlier members on each insertion. Section order, source order within sections, explicit limb assignments and joint identities stay intact. Every call builds fresh arrays from the current rig. `jointNames.test.ts` checks those contracts and bounds member-array allocations to one for both 300- and 600-joint sections. These are allocation counts, without timing assertions or a claim about complete panel rendering time.
- **Edit Skeleton** (`workspace/useSkeletonEdit.ts`, `components/pose/SkeletonSection.tsx`; the Skeleton section's switch at the top of the Pose tab, or ⌘K Edit Skeleton, which also opens the tab): edits `project.skeleton`, the plan the CAD agent designs from (§9 Relations), as a stick figure. With the switch on, the canvas draws the skeleton (§12) and the section lists every joint with its torque margin; in a scene with no skeleton it offers Arm and Biped, which come from the recipe templates (`armSkeleton` / `bipedSkeleton` in `electron/cad-mcp/recipes/templates.mjs`, the joint frames at each servo's horn, the STS3215 actuators and an estimated mass, read through `agent/skeletonTemplates.ts`), then you ask the agent to build around it.
  - **Dragging a joint ball** (`agent/skeletonDrag.ts`, `dragJoint`) moves its origin and its subtree (tips included) in 1 mm steps (Shift is free) on the plane facing the camera; ⌥ moves the joint alone, so the bones on both sides change length. The paired joint (`skeleton.pairs`) moves the mirror way, with its subtree. Both walks share one `SkeletonTree` child index for that drag, preserving breadth-first source order. Parts framed to a moved joint follow through `framedFollowOps` as live edits, and the end of the drag records one history step (`recordSkeletonEdit`), so ⌘Z restores the skeleton and the parts together.
  - **Margins** (`utils/skeletonMargins.ts`): `skeletonSizing` gives each joint's stance and hold loads from link lengths, actuator weights and `massG`; `jointVerdict` (the same grading `size_actuators` uses) rates them against the joint's actuator at its rated voltage. The margin is the share of stall torque left at the binding load, shown as a percentage beside the joint and as the ball's colour (pass, warn, fail; `MARGIN_COLORS` in `workspace/skeletonView.ts`); a joint with no actuator, or a skeleton with no mass, shows none. Sizing builds one joint and child index per call, shared by link measurements, leg chains, descendants and inertia radii. Each link measures its endpoints once for both its longest length and length-weighted center (`utils/skeletonLinkMeasure.ts`). Mass distribution and inertia reuse that length within the call, so later drags rebuild all measurements. Zero-length endpoints keep weight 1 for the center, and leaves without endpoints keep their origin. It recomputes on every drag step: eight joints take well under a millisecond, so it stays on the main thread (§0f). Under a subtree drag a joint's own load holds (everything it carries moved with it) and its parent's changes; a ⌥ drag changes both.
  - **Changing servos:** clicking a ball or a row opens a menu with the next stronger catalog servo on the same bus (`servoUp`, over 5% more stall torque, cheapest first among equals); picking it writes the joint's `actuator`, the field `define_skeleton` sets and `size_actuators` reads, as one undo step.
- **Design From Motion** (`utils/motionSkeleton.ts`, pure, through `src/motion/motionSkeletonClient.ts` in a worker): ⌘K opens a BVH picker. Importing a BVH into a scene with no movable robot opens the same sheet with one Height field in mm (300 to start). Its path tolerance is 2 mm. A scene with a robot keeps the retarget sheet. An unavailable or failed browser worker refuses the fit instead of running it on the page. The same pipeline runs locally outside the browser for Node and tests. The shared BVH reader rejects a missing `HIERARCHY` header before calling three’s loader, which logs malformed headers before throwing. The sheet shows the caught problem without adding scene content or console errors for that refusal.
  - **Fit** (`motionSkeletonSource.ts`, `motionSkeletonSearch.ts`): samples each source frame once in `motionSkeletonValidation.ts`, validating positions, rotation channels and link lengths before retaining root-relative position copies and the sampled channels. Chain fitting reuses those frames, including BVH End Sites, without resampling. Each visited bone unwraps its rotation channels and measures their spans once per call, sharing read-only angle arrays across endpoint chains. Each chain keeps its own joint records and applies static channels to its orientation before dropping their axes. A failed frame stops sampling immediately. This shared pipeline serves file import and the agent. The 64-frame planar-arm fixture previously sampled positions and channels 128 times each, and now samples each 64 times. It uses the BVH hierarchy and its ordered local rotation channels, not a human-only joint template. Every source leaf is an end effector, using its BVH End Site when present without changing the retargeter’s bone map. Optional `limbs` selects endpoint bone names or inferred limb names such as `rightArm`. Matching preserves digits so numbered endpoints stay distinct. Root translation is removed. Rest-pose Y extent scales to Height, with the longest extent used for a flat source. The first sampled posture is the robot's zero posture. Each rotating channel becomes a revolute axis, ordered as in the BVH. Axes use the skeleton handler’s stable normalized and rounded form before fitting, so placement preserves the checked axis. Channels spanning less than 0.0000001° are dropped. Source-axis subsets are searched by increasing joint count, including zero, with deterministic ties. The shared lazy `utils/combinations.ts` traversal retains one index array and copies only yielded candidates, preserving source order without recursive prefix copies. Each candidate runs `solveIK` and forward kinematics at every source frame, including the last, and must keep the terminal path within tolerance. Removing an axis joins its link to the next retained one. Fitting unwraps Euler channels across ±180° before deriving ranges, speed and acceleration, matching the BVH loader’s short interpolation across that seam. Ranges cover the fitted angles with 10% of their span added at each end. Finite differences give peak speed in °/s and acceleration in °/s². Range and dynamics summaries (`motionSkeletonStats.ts`) scan the fitted values directly, without angle, speed, acceleration or per-joint trajectory arrays. Dynamics retains the preceding angle and speed, preserving the original finite differences and frame interval. Summary storage stays constant as the frame count grows, and extrema use no argument spreads. Missing or non-finite source frames, changing source link lengths, and paths that no subset fits return no skeleton and name the endpoint. This finds a minimum among source axes per path, not among arbitrary invented mechanisms.
  - **Sizing** (`motion/motionServos.ts`): calls the shared `sizeActuators` picker with those speeds and accelerations. Links start at 15 g + 0.35 g/mm, with a 150 g base estimate, as in arm sizing. The picker considers priced feedback servos with a catalog output port and recorded weight, across its existing bus and supply families. Sizing starts with the lightest eligible catalog servo so a heavy initial estimate cannot exclude a feasible lighter family. Each candidate is checked again with the chosen servos' actual catalog masses. Conservative path-radius inertia bounds and coincident peak hold or stance, speed and acceleration screen the torque-speed envelope (§8b). A stronger servo can have a lower no-load RPM while meeting the faster clip’s loaded speed. These estimates do not prove inverse dynamics or physics playback.

- **Character shells** (`src/wrap/`): Wrap Robot (§7a) turns an imported mesh (`mesh.file`) and one jointed robot into one shell per link. `wrapPlan` splits the robot into links (the base, then one per revolute or prismatic joint; parts on a fixed joint stay with the link above it). In the wrap worker (`wrap.worker.ts`, Manifold), `wrapRobot` then:
  - fits the mesh to the robot's rest bounds (uniform scale and centring, 6 mm margin on each side) and trims it at the floor when the robot stands on it;
  - hollows it to a 2 mm wall: the outer surface is the mesh itself when it's a closed manifold (flipped if inside out), otherwise a level set of its winding-number distance field, and the inner surface is the level set 2 mm in, simplified to 0.1 mm;
  - cuts it at a plane through each joint's origin, square to the line from the parent link's centre to the child's, turned to lie across the axis of a joint that turns along that line (a pan or roll) and to contain the axis otherwise; sibling joints are split by the bisector of their origins;
  - carves away the robot's parts at rest, with a cell of clearance, then for each joint, base first: the sweep of the moving side's parts over the whole range and of its shells over half the range from the fixed side's shells, and the reverse sweep of the fixed side's parts and shells over the whole range from the moving shells. Splitting the shells' range that way leaves both sides of a joint with material; carving only ever removes, so each joint stays clear after the next ones are carved. A designed, non-leg joint's moving shells also lose what would dip below the floor;
  - drops pieces under 20 mm³.

  Hollowing and carving share `SolidField`. Each cached ray row sums its winding once and stores whether each prefix is inside. Point queries binary-search the crossings instead of summing them again. Crossings exactly at the query remain excluded. The winding accumulator retains overlapping surfaces and reversed cavity faces. Each row uses one extra byte compared with storing individual crossing directions.

  Signed distance and `nearSurface` share the coarse `CellMask` prefilter before querying the mesh BVH. Mask construction reads each triangle coordinate once and calculates expanded cell bounds in scalars, without temporary axis or bound arrays. Cell size, rounding, packed keys and inclusive bounds stay unchanged. Each mask owns its cells, so later geometry edits require a fresh mask.

  Sweeps are exact over the continuous range: `SweepRaster` bins surface samples by (radius, height) about the axis and tests the arc a point sweeps against each bin's sorted angles (along the axis for a slide).

  Raster construction reads each triangle's nine coordinates once and prepares its two interpolation edges before sampling. The outer barycentric weight is calculated once per sample row. Sample positions keep their arithmetic order and density, without per-sample coordinate reads, weight arrays or interpolation functions. Moving and fixed shell clearances share this sampler for hinges and slides. `sweepRaster.test.ts` checks triangle-interior queries against direct surface scans, including offset typed-array views and source preservation. `sweepSampling.test.ts` checks coordinate-read budgets, edited soups and independent rasters. Its 300- and 600-triangle fixtures reduce source-coordinate reads from 167,400 and 334,800 to 2,700 and 5,400. A scratch comparison matched complete raster state across 200 fixtures and 50,000 queries against the previous sampler. These are operation counts and numerical comparisons, without timing assertions or a claim about complete Wrap Robot time.

  Each raster retains four interval values and overwrites them for every hinge or slide query, reading the current range. Row searches use those intervals directly, without per-query coordinate arrays, nested interval arrays or per-row callbacks. Angle wrapping, inclusive interval ends, neighbor order and binary row lookup stay unchanged. `sweepRaster.test.ts` compares direct sample scans across axes, cell sizes, seam crossings, full turns, stationary and reversed ranges, edits and interleaved rasters. Its 300- and 600-query fixtures remove 300 and 600 row callbacks. A scratch comparison matched 120,900 queries across 100 generated triangle fixtures. On macOS arm64 with Node 26.13.0, 20,000-query batches took medians of 1.73 ms before and 1.40 ms after across 15 alternating measurements, after five warmups per implementation. This measures sweep queries alone, without timing assertions or a claim about complete Wrap Robot time.

  Carve fields are sampled on a grid, dilated by a cell and blurred before Manifold's `levelSet` (`gridField.ts`), because a binary field with a one-cell-thin sheet crashes it (`memory access out of bounds`); each cutter is limited to a band around the shells it carves (`nearSurface`). Each field prepares its interpolation origin and strides once, then blends eight grid values per query without temporary arrays or local functions. Sampling and blend order stay unchanged. Grids hold about 800,000 points, so the cell grows with the mesh (1.2 mm at least). Each shell is a printed `mesh` part named after the mesh and its joint, coloured like the mesh, in the robot's group; it's added to its joint's `child`, and the base shell to the root joints' `parent`, so it poses, animates, simulates and weighs like a link part. The mesh is hidden, and the parts and joints change in one undo step. The SO-101 takes about 20–35 s.

- **Leader arms** (`src/leader/`, `workspace/useLeader.ts`): Make a Leader (⌘K, or right-click a part of the arm) and the agent's `make_leader` turn a fixed-base arm (`classifyRobot` is `fixed`) whose movable joints form one chain into a hand-held leader, opened as a new scene tab named "⟨arm⟩ Leader". `leaderArm.ts` finds the chain and takes its last joint as the gripper when it's prismatic or named like one (grip, jaw, finger, claw, pinch). The leader keeps every movable joint's id, name, type, axis and range, in order, so forward kinematics turns its handle exactly as the follower's end effector turns at any joint values; its joint positions differ. `leaderFrames.ts` works in the CAD frame like the arm template: each link runs along the common normal of its two joint axes (for parallel axes, along the follower's offset at the first link and straight on after), leaning toward the follower's offset, then up, and never folding back past 120°; at rest the leader runs straight along those normals. Link lengths are the follower's scaled to half its reach (the sum of the distances between consecutive arm joints), but at least 56 mm, the shortest `servo_link` between two XL330s, so a small arm like the SO-101 comes out nearer 0.6×. Every joint has a Dynamixel XL330-M288 in the cradle of the part before it, read as an angle sensor; the printed parts are `servo_base`, one `servo_link(length, twist, s = XL330, m = 2)` per link, and a handle (`servo_u_link` plus a printed grip) on the last arm joint. With a gripper, the handle also holds a cradle for the trigger's XL330 (the grip pocketed around it), and the trigger (a horn-side `servo_u_link` with a lever) is the gripper joint, with its axis, type and range; a prismatic gripper keeps its type. The printed parts arrive as `cad.pending` placeholders sized to the compiled bounds and compile in the desktop app (`useCadCompile`); `leader.test.mjs` compiles them in the kernel. The leader stands on the floor, centred. Its project records what it leads (`project.leads`: the follower's scene id, robot key, and leader → follower joint ids, the same ids), and its servos are numbered 1…n in joint order (`servoLayout`).

## Passive robot joints

`RobotJoint.actuation` is optional. Omitted and `powered` retain legacy powered simulation. `passive` preserves the physical hinge or slider, axis, range and initial pose without an actuator. `damping` and `frictionloss` declare nonnegative finite resistance in SI units. Passive joints have no estimated damping, friction, armature or holding torque. They are distinct from fixed joints.

Pose's joint-row menu has Actuation with Powered and Passive. Choosing Passive clears actuator assignments in one `commitJoints` history step, leaving motor parts in the scene. Choosing Powered does not recreate those assignments. Undo and redo restore the complete declaration. `define_joints` accepts the same actuation and resistance fields. Contradictory passive declarations with actuator references are refused by declaration and MJCF building.

Scene files preserve the optional declaration. Existing saved imports with no declaration keep their previous behavior. New MJCF imports identify joints without actuators as passive and retain physical resistance. Exported URDF joints retain physical motion and use a `basecase` child with `actuation="passive"` to preserve intent when reimported. Ordinary URDF files without this marker retain legacy behavior. This does not implement tendon routing or cable physics. Help: [Make a joint passive](../../site/content/help/make-a-joint-passive.md).

Coverage: `src/sim/passiveHistory.test.ts` checks real scene-file compression, undo and redo, tool refusal, legacy imports and MJCF/URDF intent. `passiveJoints.test.ts` and `passiveMotion.test.ts` exercise ten mechanism models with real WASM MuJoCo. `e2e/passiveJoints.e2e.test.ts` covers the Pose menu, undo and redo, falling motion and motor count. Scene-file compression and reload remain in the fast history integration test. [Evidence](../notes/testing-joints-and-motion.md#passive-robot-joints).
