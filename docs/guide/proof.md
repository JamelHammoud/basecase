# Proof

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 0k. Proof

How the robotics build is judged while no human tests it. Forge, Cases, Skills, Routines and the robot runtime are built by agents, and only `verify/` decides what is done.

- **Gatekeeper is the only source of completion claims.** `npm run verify <gate>` runs gates from `verify/` and writes `verify/status.json`. Agent prose is never evidence.
- **`verify/` and the safety caps are read-only to builder agents.** Thresholds change only with a maintainer's OK.
- **Gates are `required` or `parked`.** A stuck item parks in the report and other streams continue.
- **Seeded canaries must fire or the gate voids.** Test counts ratchet. A vitest canary (`vitestCanary`, `verify/lib/canary.mjs`) fires only when its own test fails on an assertion; a crash, a skip or a file that doesn't load counts as not fired, so a missing module can't fake a caught fault. A canary that needs setup throws a plain `Error` when the setup didn't happen.
- **One run at a time, and timed checks wait for quiet.** Gatekeeper takes a machine-wide lease (`verify/lib/lease.mjs`, in the system temp folder) so gate runs never overlap. A check marked `timed: true` waits up to 15 min for the 1-minute load average to drop below a third of the cores, records `loadBefore` and `loadAfter`, and if the machine never quiets the gate is void (`machine busy`), never passed.
- **Committed baselines stay put.** `verify/baselines/` holds the numbers a gate compares against; a gate writes a baseline only when none exists, and later measurements go to `verify/out/`. `time-to-skill.json` is the Python trainer's median seconds to the walk skill per robot (5 seeds each, measured once on a quiet machine); Forge's speedup checks read it and are `timed`.
- **No human testing until Stage 8.** Exit criteria are automated. Stage 8 is one session on real hardware, and the first real evidence of transfer.
- **A parked gate says why** in its `parked` field; Gatekeeper prints it, and the Stage 7 rehearsal fails on a parked gate with no reason.
- **Where the plan is vague, gates take the stricter reading,** and the reading is written below with the gate.
- **The manifest pins everything a gate runs.** `verify/manifest.json` holds a hash of every file under `verify/` (except `verify/out/`, `status.json` and the manifest itself; the ratchet and baselines are pinned) and of the forge test files that hold gate bars (`PINNED_FORGE_TESTS` in `verify/lib/run.mjs`: L4/L5 and the time-to-skill replay, sysid, gradients, design sweeps, qualification, RewardLang). Any change drifts the manifest and Gatekeeper refuses to run until `node verify/gatekeeper.mjs approve`. A forge test that starts holding a bar joins that list in the same change.
- **Tests that open the web app run under `verify/vitest.app.config.ts`.** It adds `e2e/serve.ts` as global setup, which serves the bundle (or a dev server) and provides `appUrl` and `webUrl` to `openApp`. `vitestCheck` and `vitestCanary` pick it for any test file that calls `openApp(`; every other verify test keeps `verify/vitest.config.ts`, so it doesn't pay the servers' 10 s shutdown.
- **Run Stage 7 from a checkout with its own `npm ci`.** Its local steps package the app, and a worktree whose `node_modules` is a symlink to another checkout (without the native addons `prepare` builds) packaged an app that hung at launch on a main-process error dialog.
- **Gates write builds and outputs under `verify/out/`.** A Cargo build inside a pinned folder (its default `target/`) drifts the manifest on the next run, so `s3-servo-models` builds the BAM reference with `--target-dir verify/out/servo/bam-reference-build`.
- **A result says whether the tree was clean.** Every saved result records `tree` (`clean` or `dirty`), the uncommitted files seen before and after the run (`uncommitted`, with pinned ones apart in `uncommittedPinned`), so a pass is never stamped on a commit it didn't run against. Any uncommitted change outside `verify/out/` and `status.json` counts, since the code a gate exercises can be anywhere. Commit first, then run the gate.
- **Builder code never reads `verify/`.** `isolationCheck` (`verify/lib/isolation.mjs`) scans `src/`, `electron/`, `forge/` and `hw/` for imports of or paths into `verify/`; only test files reading `verify/fixtures` or `verify/out/fixtures`, and shell scripts that run `verify/gatekeeper.mjs`, are allowed. It runs in `s2-cases-play` and `s6-hidden-twin`, with a canary that plants a calibrator importing `verify/twin` and reading `verify/out/twin`. It's a gate check, not an ESLint rule, so the lint config stays the maintainer's.
- **A cargo canary fires only on its own assertion.** `cargoCanary` (`verify/lib/canary.mjs`) counts as fired only when the test fails and its output shows both the marker it prints just before the planted check and that check's message; a build error or a missing fixture is not a caught fault.

### Stage 1: time-to-skill (`s1-f2-learner`, `s1-f5-gpu-loop`, `s1-f7-shac-speedup`)

`speedupAtLeast` (`verify/forge/tts.mjs`) reads the plan's "time-to-skill at least N× the baseline" strictly:

- **Every robot, not the median.** Each of quad-servo, hexapod and biped-servo must reach N× on its own (the median of 5 seeds per robot). The median across robots once let F5 pass with biped-servo at 3.74×.
- **Wall clock, not the trainer's word.** A run's time is the gate's own measured wall time for the whole process, start to finished policy, not the `elapsedS` the trainer prints. The committed Python baseline keeps the time it was measured with.
- **Replayed in C MuJoCo.** After each run the gate replays the saved `policy.json` in C MuJoCo (`replay_folder_in_c` in `acceptance_replay.rs`, the L5 helpers, 32 seeds, 29 must pass). A run whose policy fails replay counts as a miss at the 60-minute budget, whatever the trainer's gate line said.
- **On the GPU loop, for F5.** Both F5 runs (throughput and time-to-skill) must print the trainer's `Training on the GPU: physics, policy and learner on …` status and never `… Learning on the CPU`; the CPU path alone beats the F5 bars, so a silent fallback is a failure.

### Stage 1: `s1-f5-gpu-loop`

- **L4 can't pass empty.** The statistics must be non-empty, equal in number and in the same order on the GPU and in C, and finite.
- **Canaries:** a policy trained on reversed knee axes must fail the C replay (L5), and GPU rollouts on reversed knee axes must fail the L4 comparison against C.

### Stage 1: `s1-f7-gradients` and `s1-f7-shac-speedup`

- **`s1-f7-gradients` (required)** holds the four cargo checks: gradients against finite differences, forward physics unchanged, batched sysid and design sweeps, with the planted wrong-gradient canary.
- **Sysid plants from a fresh seed.** `batched_recovers_planted` draws its planted values from a new seed every run (`FORGE_SYSID_SEED` in hex replays one) and prints the seed only in a failure. It needs one fit per planted world (16), each with a finite value and an identified flag per unknown. Canaries: a fit with one parameter 3.5% off, and a run with no worlds.
- **`s1-f7-shac-speedup` (parked)** holds the 15× time-to-skill check for the first-order (SHAC) learner, at the same bar. It was split out instead of lowered: SHAC finds no gait through stiff contact, and its ceiling at the gate's cadence is about 1× ([Forge](forge.md)). PPO stays the default. Only a maintainer can change the 15× bar.

### Stage 2: `s2-cases-play`

Finishes Stage 2 on top of `s2-m1-first-case` (`verify/cases/`).

- **One Case, different arms:** a Case is written once (Touch the Dots on `arm-6dof`, and a Touch Case on a Shelf on a gate-only five-joint arm the builder never tuned for), round-tripped through JSON, and run unchanged on `arm-3dof`, `arm-6dof` and the gate arm. The Case object must not change.
- **The gate arm is drawn fresh each run** (`gateArmShape` in `verify/cases/play.ts`, `GATE_ARM_SEED` replays one): base yaw, two pitches, a wrist that yaws or pitches, a last joint about either horizontal axis, every axis with a random sign, and links of 50 to 75 mm. Those ranges kept all 150 test seeds solvable on all three arms; a failure prints the seed and shape.
- **Limp margin negative, reference positive** for every Case the app offers, not just one: every fitting example, every New Case goal and world, on the arms, both rovers, the hexapod and the stable quads, plus every gallery Case on its bundled robot. The reference run must repeat to the bit. Bipeds stay in `s3a-motor-kit`.
- **Nothing offered drops out.** A goal and world the New Case card offers that `buildCase` refuses is a failure, not a skip. The counts are pinned at what the app offered when the gate was written (`PLAY_MINIMUMS`: one fitting example per robot; 2 goal-and-world Cases per arm, 9 per rover, 12 per legged robot) and at least 3 gallery links; fewer is a failure.
- **Drive e2e** (Playwright on the dev app): an arm's hand moves 20 mm or more on W and back against it on S, drifts under 3 mm idle and under 5 mm after release; a rover goes 0.1 m forward on W, 0.05 m back on S, drifts under 0.02 m idle and 0.03 m after release, and stops when the window loses focus; a hexapod walks 0.1 m on W without a fall.
- **The arm's hand is measured, not reported.** The gate taps the sim worker's messages (`verify/cases/workerTap.ts`) and computes the hand from the body poses the viewport renders: the hand point and its joint origin come from the fixture (`robotFacts`), the pose from the frame. Those rendered positions feed the arm bars, and the arm drive's `simState().effector` (mm, world frame) must sit within 1 mm of them at every sample. Rover and hexapod distances still come from the sim's `forward` stat.
- **Gallery at 1.0x:** the production web bundle (`vite build --mode web`) is served with `vite preview`; every gallery link loads in headless Chrome and, while driving, runs at 0.95x to 1.05x real time over 10 s, with no 1 s window under 0.9x, measured from the page's own clock against the sim clock. Some rendered body must also move at least 20 mm while W is held, so a clock that runs with a robot that doesn't fails.
- **Canaries are planted in the running app,** not fed to the judges as numbers: the gate's worker tap drops or rewrites the page's messages to the sim worker, so no `src/` hook is needed. A limp run that is really the reference; an arm whose W and S never reach the sim; a rendered arm frozen while the reported hand moves; a rover whose release never reaches the sim; a gallery whose sim speed is set to 0.5x and to 2x; a gallery whose W never reaches the sim. Each checks that its fault was really planted and otherwise errors instead of firing.

### Stage 3: `s3-anythingzoo` and `s3-anythingzoo-full`

The AnythingZoo (`verify/zoo/`). The builder implements `src/skills/anything.ts` exporting `trainAnything` (its input and outcome types are in `verify/zoo/anything.ts`): a prompt in, a skill, an honest not-found, a refusal or "unverifiable" out.

- **The generator is the separate agent.** 30 tasks (10 move, 7 posture, 10 arm, 3 deformable) on 6 bodies (`arm-3dof`, `arm-6dof`, `rover-diff`, `quad-servo`, `hexapod`, `biped-servo`): 180 pairs, 81 feasible, 81 infeasible (an arm asked to walk), 18 deformable. Each run draws a fresh seed; prompts, hidden judge contracts and labelled rollouts are drawn from it and written only to `verify/out/zoo/`. A hidden judge is refused unless its intended motion passes, standing still fails, a limp robot fails, and its labelled rollouts include at least two passes and two fails.
- **The stand-in approver:** the builder proposes a contract with its signals; the stand-in replays its labelled rollouts (kinematic qpos sequences) through the builder's signals and approves only when every label agrees, at most 3 rounds, pointing at one disagreeing rollout when it says no. A skill counts as claimed only when its binding names the approved contract, its own Arena evidence passed, and it is bound to the body's physics.
- **Judging:** the gate reruns Arena with the hidden contract (`verify/zoo/judge.ts`). A claim the hidden judge fails, any claim on an infeasible pair, or any claim on a deformable task is a false claim.
- **Bars:** zero false claims; every deformable pair labelled unverifiable; at least 70% of feasible pairs pass hidden Arena within budget (rounded up); on at least 80% of passed pairs no other method (`ik-or-motion-plan`, `tracking`, `routine`, `lqr-or-mpc`, `tracking-rl-with-reset-curriculum`, `reward-search`) also passes in under half the router's wall time.
- **Budget per pair** (the plan gives only the round total): one reward-search round, 180M environment steps counted from Forge's own records, and 75 minutes of wall clock, which is 225 machine-hours over 180 pairs.
- **Sample mode** is the default gate: 20 stratified pairs on the Mac (14 feasible across all six bodies, 4 infeasible and 2 deformable as controls). `node verify/zoo/cli.mjs --sample`, `--full --shard i/n --seed <hex>` and `--verdict` run it outside Gatekeeper; the full gate stays parked for rented machines.
- **Nothing hidden is printed:** the run's output is scanned for the seed and every hidden contract; a leak fails the check and withholds the log.
- **No contact signals in hidden judges, for now:** they were left out because Arena's contact reader (`src/skills/arenaSignals.ts`, frozen by `s3a-motor-kit`) leaked the contact list and exhausted the 2 GB WASM heap in about 20,000 reads. The reader now frees it (`arenaSignals.test.ts`); letting the generator use contact signals is the next change to this gate.
- **Canaries:** a do-nothing skill claimed as passing, a skill claimed for folding a towel, a rubber-stamp contract, giving up everywhere, a slow router, a log that prints a hidden contract, and a hidden judge that standing still meets.

### Stage 3b: `s3b-moves`

Pose-tab animations trained as moves (`verify/skills/moves.test.ts`). The cases are built in code in `src/skills/moveCases.ts`, so the unit test (`moveCases.test.ts`) and the gate share them: a 4 s squat-and-wave `.bvh` retargeted onto biped-servo by the app's retargeter, quad-servo's sit and a paw shake, a hexapod dance step on a 120 bpm clock, a hand-keyed bow on biped-servo, a right-arm wave on a humanoid with Unitree G1 joint names, and a wave on arm-3dof.

- **Judged again, not taken on trust.** Each case goes through `trainMove` with the gate's Forge runner, and the skill that comes back is rerun in `runArena` on a freshly built `moveEnvironment` with a new salt. It must pass there, and the environment `trainMove` used must hash the same as the fresh one.
- **The squat is the case playback can't do.** The mocap squat sits back with the thighs level and the shins near vertical, which a person balances with a forward lean the robot has no joint for. Played back as an animation it falls backwards (nominally in the unit test, and in Arena for this gate), so only a trained policy passes. It must reach 29 of 32 in every variant, and it trains on the tracking path.
- **Hand-keyed and retargeted take one path.** The bow and the squat on biped-servo route to tracking with the same observation terms and action joints.
- **A one-shot ends on its last key.** The trained sit's nominal rollout ends with every joint within the tube's tolerance (0.25 rad) of the last key, and the unit test checks that the tube's windows after the move are centred on it.
- **A fixed robot doesn't train.** The arm's wave routes to `ik-or-motion-plan`: the animation itself is proved in Arena, with no Forge run and zero steps.
- **Standing still fails every legged move,** in the unit test (one nominal rollout each) and in the canary.
- **Canary:** a zero policy (holding the rest pose) passes a move contract in Arena. It fires when every legged case's contract rejects it.

### Stage 6: `s6-hidden-twin` and `s6-hidden-twin-nad`

The HiddenTwin (`verify/twin/`) is gate-side TypeScript, so builders never see its parameters. The builder implements `src/reality/calibrate.ts` exporting `calibrateServo` (logs in, a calibration with a verdict `measured`, `consistent` or `cant-tell` out) and `calibratedInput` (applies calibrations to an `MjcfInput`, so MuJoCo predicts and the gate measures).

- **The twin:** a single servo on a pendulum, at 0.2 ms with firmware at 1 kHz, with per-unit BAM M6 spreads (kt, resistance, armature, friction, gain, delay) and effects outside the training model: backlash, series compliance, stick-slip, supply sag, thermal drift of resistance and encoder bias. Units are drawn fresh from a seed each run and written only to `verify/out/twin/`.
- **The twin's nominal values are its own.** `verify/twin/nominal.ts` pins the BAM fits and voltages the units spread around (copied from the catalog when the gate was written), so editing the parts catalog moves the preset the calibrator starts from but never the twin. The catalog preset still drives the "before" model and the preset-logs control.
- **Hidden units are written after the calibrator is done.** `runSession` (`verify/twin/session.ts`) calls the calibrator on every unit, the shuffled logs and the preset logs first, and only then writes that run's units to `verify/out/twin/`; it fails if any file for the run exists before or appears during a calibrator call.
- **Logs:** six calibration logs per unit (chirp, steps and multisine at two payloads, 100 Hz), then two held-out logs: a new trajectory at a training payload (held-out replay) and one at a third payload (different load).
- **Bar, per family** (STS3215 and XL330, 24 units each, at least 20): median per-unit reduction of held-out RMS tracking error at least 25%, the median error after at most 75% of before, and the 2.5th percentile of 10,000 bootstrap medians above zero.
- **Controls:** the gate checks itself first: each unit's true in-model parameters must reach the bar without the alarm, so the bar is reachable and the twin is outside the model class. Logs shuffled across units and in 1 s blocks must fail the bar and never read `measured`; logs from the catalog preset must read `consistent`. A median gain above 90%, or a median error under one encoder count, raises the alarm that the twin shares the model class, and fails the gate.
- **NAD is parked:** leave-one-payload-out on the public SO-101 logs (calibrated sim within half the teleport error and under a fitted FOPD per joint, the same bar as `s3-servo-models`) and the twin's anchor (its gap to the sim within 0.5x to 2x of the real gap per joint and payload) are written, but no public NAD download was found. A maintainer pins its URL, sha256 and a reader in `verify/twin/nad.json`.
- **Canaries:** a no-op calibrator, an in-class twin fitted exactly (must raise the alarm), gains straddling zero, 12 units, a calibrator that peeks at `verify/out/twin/` for this run's units (finds none, so fails the bar), and a planted calibrator source that imports `verify/twin` (caught by the isolation scan).

### Stage 7: `s7-rehearsal` and `s7-72h-run`

`verify/rehearsal/`.

- **Mechanised UI rules** on the start view, every rail view and the command palette: inputs, selects, menu items and text buttons at least 32 px, icon-only buttons 28 px (§4); no text under 12 px outside key caps; no tinted grey (a colour with 0 < max − min ≤ 24); the §3c copy lint; and axe with no serious or critical WCAG 2 A/AA violation (`axe-core` must be installed). Anything inside `[data-user-content]` (chat text, part colours) is exempt. The plan's §15 grid and pixel diff aren't in this gate.
- **PersonaLab** (`tools/persona/personaLab.mjs` exporting `runPersona`) gets only a screenshot, the accessibility tree and mouse and keyboard on the unsigned packaged app. Ten sessions each plant three faults from ten kinds (label removed, tiny, dead click, misleading label, low contrast, slow response, jargon error, silently disabled, jumpy, flicker) on named controls drawn at run time. A finding matches a fault when it names the control (case and spacing ignored, since the DOM joins a row's title and subtitle with no space) or points inside any place the control was during the session (the planted page records each new position every 250 ms, so a scrolled column or a jumpy control still counts); `verify/rehearsal/personaScore.test.ts` holds both and a miss. The plan only asks to report recall; the gate requires recall of at least 80% and at least half the findings on a planted fault.
  - It runs Claude (`claude-opus-5-5`, effort `high`; `PERSONA_MODEL` and `PERSONA_EFFORT` override) through the Agent SDK with its built-in tools off and ten tools of its own (look, tree, click, type, press, scroll, wait, report, withdraw, finish), signed in the way the app's agent is: the `claude` CLI login on the machine, or `ANTHROPIC_API_KEY`. No key lives in the repo. The nested-session variables (`CLAUDE_CODE_*`, `ANTHROPIC_BASE_URL`) are dropped so a run started from inside Claude Code uses the machine's own login.
  - Screenshots are scaled to CSS pixels before Claude sees them (Retina screenshots are 2×; the ratio is read from the screenshot width against the 1480px default window, `PERSONA_DPR` overrides), so its clicks and the `at` of each finding land in the page's coordinates. Faults are matched against where each control was before the session began, so a scroll is measured from the screenshots on either side of it (`scrollShift.mjs` lines up a strip under the pointer) and a finding in a scrolled column is moved back by that much. Findings are one per control, at most 12 a session.
  - The offline parts (frame scaling, coordinates, deduplication, the clock, the tool list, scoring a scripted run) are tested in `tools/persona/personaLab.test.mjs`.
- **Clean-checkout rerun:** clones this commit into a temp folder, `npm ci`, builds the trainer env once with `uv sync --frozen --exact` (a first sync racing between gates left a half-installed numpy), and reruns every required gate except Stage 7's own, inside the held lease; a void counts as a failure, the manifest must be approved, every parked gate must give a reason. The report is `verify/out/rehearsal/report.md`.
- **72-hour run (parked):** the unsigned packaged app, PersonaLab driving the emulated robot through the relay, a fault from the matrix injected every 10-minute cycle and shown on screen within 3 s, no page errors; the Windows x64 half adds up checkpointed segments in `verify/out/rehearsal/soak-windows/` from the new Windows driver.
- **Canaries:** a 20 px input, 10 px text, a slate grey, “No parts yet”, a silent persona, a persona that flags everything, a voided gate counted green, and a parked gate with no reason.
