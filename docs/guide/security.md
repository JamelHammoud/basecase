# Security

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 0h. Security (mandatory)

The agent reads untrusted pages and files and drives an app that can spawn processes, so treat every input from the renderer, the HTTP bridge, the agent and downloaded assets as hostile. The full checklist, attack surface and accepted risks are in the `security-audit` skill; these rules hold for every change:

- **HTTP bridge:** every `/api/*` middleware is wrapped in `guardBridge` (`electron/bridgeGuard.mjs`: loopback `Host`, same-origin `Origin` and `Sec-Fetch-Site`). Vite plugin middlewares run before Vite's own host check and CORS, so nothing else protects them. A website could otherwise POST `/api/bridge/acp-connect` and run a command.
- **IPC** registers through `trustedIpc` (`electron/appOrigin.mjs`, main frame of the app origin only). Compare origins with `isAppUrl`, never `startsWith`; open only `isExternalWebUrl` links.
- **Ids that become paths** go through `checkedFileId` / `isSafeFileId` (or `safeFileId`) in `electron/backend/constants.mjs`. `library/agent.json` holds the command the app spawns.
  - The tries store (`electron/library/tryStore.mjs`, §8h) checks every id before it touches a path: a try's id and its scene id on save, the id on reading a recording or filmstrip, and every id in a delete before any folder goes. A manifest is at most 256 KB, a recording 1 GB and a filmstrip 2 MB. The main process stores a recording's bytes and never parses them; the page decodes them with bounds checks (`decodeRecording`). Exploit tests in `electron/library/tryStore.test.mjs` (`..`, `../auth`, a backslash, a slash, `CON`, an empty or 200-character id, a number, a delete list with one bad id). `tries:manifests` checks every id and reads at most 500 a call. The search index (`library/.try-index.bin`) is at most 512 MB, written atomically, and parsed by the page, which refuses it whole when its format name or version is wrong (`searchIndex.ts`).
- **Outbound fetches the agent controls** use `publicFetch` and `readCapped` (`electron/publicFetch.mjs`): public addresses only, every redirect re-checked, bodies capped. The renderer fetches agent URLs over https only (robot import: `fetchBytes` in `utils/robotImport/sources.ts`). A repo link is read only from its own host: GitHub repos from `api.github.com` and `raw.githubusercontent.com`, Hugging Face repos from `huggingface.co` (`hub.ts` builds every URL from the parsed owner, repo and revision, encodes each path segment, drops listed paths that climb out of the repo, follows the listing's next page only on the same API path, and reads only listed files plus the one file a file link names; exploit tests in `hub.test.ts`); zips it unpacks drop entries that climb out of the archive (`archive.ts`, exploit test in `archive.test.ts`). A file link on `raw.githubusercontent.com` reads its meshes and includes, absolute links among them, only inside its own owner, repo and ref (`urlResolver`; a `refs/heads/<name>` or `refs/tags/<name>` link keeps to that ref, and a short branch name with a slash in it is scoped to its first segment, since the URL can't say where it ends; exploit tests in `sources.test.ts`). Xacro (`xacro.ts`) never runs code: expressions go through a small arithmetic parser (`xacroExpr.ts`) that knows only its operators and a fixed list of math functions, looks names up in a `Map`, and refuses any other call or attribute. `xacro:include` takes only paths inside the import (an `http:`, `file:` or drive-letter path is refused before reading; the tree resolver reads only listed files), includes nest at most 8 deep and 200 in all, macros nest at most 40 deep, expansion stops at 200,000 nodes, at a million characters in any one value, at 16 million characters of strings computed along the way (every joined value and string `+`, kept or not), and at 16 million characters in the whole expanded document (tags, attribute names and values, and text, counted as they're built), a property that refers to itself fails, and document type declarations (entity expansion) are refused. Exploit tests in `xacro.test.ts` and `xacroExpr.test.ts`.
- **Publishing to Hugging Face** (`electron/hub/`, §8h): the token lives only in the main process, sealed with `safeStorage` (`hub-keys.json`, memory only without encryption); the page gets a signed-in flag and the account name. Every Hub URL is built from the fixed origin (`https://huggingface.co`, or `BASECASE_HUB_URL` for tests, which must be https or loopback http so it can't send the token in plain text off this computer) and checked to stay on it; repo names and the account name must match the Hub's name rule (letters, digits, `.`, `_`, `-`, no `--` or `..`, at most 96) and file paths are plain segments, all checked before any request. Requests to the Hub refuse redirects. LFS upload addresses on another origin must be https and go through `publicFetch`, and never get the token; only verify calls on the Hub itself carry it. Error text from the Hub has the token cut out. `electron/hub/hub.test.mjs` holds the exploit tests. **Install Skill** (§8i) downloads from the Hub's resolve addresses only: `skillFiles` checks the account and repo with the same name rule and the branch as one plain segment before any request, reads a fixed list of six files (`SKILL_DOWNLOADS`), sends the token only to the Hub's own origin and only when signed in, follows at most 3 redirects, sends one off the Hub only over https through `publicFetch`, and stops reading a file past 32 MB (`readCapped`). The page parses the files fail-closed, checks each against `skill.json`'s hashes and loads the policy as data through the policy runner, never as code. Exploit tests: `electron/hub/skillRepo.test.mjs` (crafted accounts, repos and branches that try to leave the repo, an oversized file, an http redirect) and `src/skills/hubSkill.test.ts` (a tampered `policy.json`, a policy the runner can't load).
- **Shared robot links** (`app.basecase.so/r/<account>/<repo>`, §8h): the web page reads the account and repo from the path with the same Hub name rule (`sharedRobotPath` in `src/gallery/galleryLinks.ts`) and fetches only `https://huggingface.co/datasets/<account>/<repo>/resolve/main/basecase-robot.json`, built by `sharedBundleUrl` and checked to stay on that origin, without credentials. The bundle is read fail-closed (`fetchBundle.ts`, `readGalleryBundleBytes`): a `Content-Length` over 8 MB is refused, the body stops downloading the moment it passes 8 MB, and `parseGalleryBundle` caps parts and joints, checks every inlined mesh's indices against its vertices, and accepts a policy or skill only when it validates (a skill's record must hash to the skill it carries). A shared Case's code panels are the one part that runs: someone else's code, served on our origin. They run only as code panels do everywhere (above): the opaque-origin sandbox and the CSP, so a frame can't reach the page's IndexedDB (Open Scene's store), its cookies or the Hub. The page itself holds no Hub sign-in; the token lives only in the desktop app's main process. Exploit tests: `src/gallery/sharedRobot.test.ts` (crafted accounts and repos that try to leave the Hub, a bundle and a download over the cap, a code panel that takes a bundle over it), and `e2e/gallery.e2e.test.ts`, where a shared code panel on the web build tries to list the page's IndexedDB, read `document.cookie` (with a cookie set on the page) and post to `huggingface.co`, and each fails with nothing reaching the Hub.
- **Map tiles** (`electron/earth/`, Place on Map, §12): the Google Map Tiles key lives only in the main process, sealed with `safeStorage` (`earth-keys.json`, memory only without encryption); the page learns only whether one is saved. The page asks for a tile by path alone (`earth:tile`), and `tileUrl` rebuilds every request on the fixed origin (`https://tile.googleapis.com`, or `BASECASE_EARTH_TILES_URL` for tests, which must be https or loopback http): a path that isn't a plain `/v1/3dtiles/…` path (an absolute or protocol-relative URL, a backslash, `..` or its encoding, another API) is refused before any request, every query parameter but a well-formed `session` is dropped, and the key is added there. Requests refuse redirects, so the key never follows one off the host; replies are capped at 32 MB, and a refusal reads as a fixed sentence by status, never Google's text. The page checks the same host and prefix before asking (`tilePathOf`), and the tiles it gets are parsed as glTF only. Exploit tests in `electron/earth/earth.test.mjs` (hostile paths, a redirect to another server that must see nothing, the key never on disk or in a reply) and `src/earth/tileFetch.test.ts`.
- **Agent CLI downloads** (§0i) fetch only `https://registry.npmjs.org/` tarballs named in the build's manifest, refuse redirects, and install only when the sha512 matches the lockfile's `integrity`.
- **Print service quotes** (`electron/print/services/`, §8f): the Slant 3D API key lives only in the main process, sealed with `safeStorage` (`print-service-keys.json`, memory only without encryption); the page learns only whether one is saved. Every API request is built on the fixed origin (`https://slant3dapi.com`, or `BASECASE_PRINT_SERVICE_URL` for tests, https or loopback http only) and refused unless it stays under `/v2/api/`, with redirects refused, so the key, sent as a Bearer token, goes nowhere else. Part names never reach a URL: the upload's file name is the name with everything but letters, digits, spaces, `_` and `-` replaced, sent in the JSON body. File, platform and filament ids from the service must be UUIDs before they go in a path or a body. The STL upload address the service returns must be https on another host and goes through `publicFetch` without the key (or stays on the API origin itself). Replies are capped at 1 MB and parsed fail-closed: one that isn't JSON, a total that's negative, not finite or not a number, or a quote for a different quantity is refused, never shown. A refused part's text is the service's message cut to 200 characters with control characters removed. `electron/print/services/slant3d.test.mjs` holds the exploit tests.
- **Onshape** (`electron/onshape/`, §8c): the API keys live only in the main process, sealed with `safeStorage` (`onshape-keys.json`, memory only without encryption); the page learns which keys are saved and the account name. A pasted link must match `https://cad.onshape.com/documents/<24 hex>/w|v/<24 hex>/e/<24 hex>` (`documentOfLink`) before any request, and every id taken from Onshape's replies (documents, microversions, elements, translations, exported files) is checked the same way before it goes in a path; part ids are letters, digits, `_` and `-`. Every request is built on the fixed origin and refused unless it stays on `https://cad.onshape.com/api/`; redirects are followed only when they stay under it (Onshape sends exported files that way), so the keys, sent as Basic auth, never go anywhere else. Errors are fixed sentences by status, and a reply that isn't JSON is one fixed sentence too, never Onshape's reply text. Replies are capped (50 MB of JSON, 200 MB per STEP file), and the STEP files go only to the CAD kernel's sandboxed converter below. Update from Onshape (§8c) rebuilds the link from ids a scene file stores, so the page checks them against the same 24-hex pattern (`onshapeLinkOf`) before asking, and the main process checks the link again with `documentOfLink`; the scene stores ids only, never keys. `electron/onshape/onshape.test.mjs` and `update.test.mjs` hold the exploit tests.
- **CAD files the agent downloads or a person drops** (`electron/cadImport/`) are hostile: fetched by `publicFetch` with a 200 MB cap and parsed only in the CAD kernel's Chromium sandbox (below), never in Node; archives are capped at 600 MB unpacked and their entry names are never used as paths. Library ids go through `checkedFileId`. Links must be https. Page text from a link check is only searched for the part number, never shown to the agent as instructions.
  - The main process reads the downloaded file and sends its bytes as a kernel pool job (`SandboxKernel.convert`, checked by `checkedConvertJob` in `cadImport/convertPolicy.mjs`); the kernel page starts a fresh module Worker (`/convert.js`, built from `cadImport/convertWorker.mjs`) for each file and ends it after, so no file inherits another's state. It runs under the worker CSP (`connect-src 'none'`, `worker-src 'none'`; occt-import-js's embind needs `'unsafe-eval'`), gets the compiled OpenCascade module from the page, and answers with a JSON header, a newline and the GLB (`cadImport/reply.mjs`).
  - A dropped STEP or IGES (`openCadFile.mjs`, IPC `cad:open`) is checked only for its extension before its bytes go to the same pool job with `bodies: true`; the Worker answers with one header entry per body and their packed positions and indices (`bodiesCore.mjs`). `checkedBodies` (`bodiesPolicy.mjs`) refuses the answer unless the byte length matches the counts exactly, every position is finite, every index is in range, colours are `#rrggbb` and names short, and there are at most 1,000 bodies. Nothing is written to disk.
  - The main process trusts nothing in the answer: `checkedConversion` keeps only the size, origin, triangle count, holes (at most 500) and member names it knows, refuses anything malformed or a GLB without its magic, and is the only code that writes `mesh.glb`. A hung parse hits the 150 s limit, and a file that eats memory hits the pool's 4 GB limit; either kills the window, answers with the converter's own error and the next file gets a fresh one.
  - Converter and kernel jobs share the pool's windows. A file that broke out of its Worker would reach only what agent code in the kernel already can: the kernel page's four host calls.
  - Without the sandbox (the Vite middleware, tools) `import_maker_cad` refuses before downloading anything; nothing falls back to Node. `cadImport/nodeHost/` runs the same Worker in a Node `worker_threads` thread for unit tests and the gate's canary only, and isn't packaged (nor is `occt-import-js` in `node_modules`).
  - `e2e/app/cadImportSandbox.app.test.ts` runs the packaged app's converter self-test (`BASECASE_CADIMPORT_SELFTEST=<spec.json>`, `cadImport/selfTest.mjs`): fixed probes in the converter's Worker (`cadImport/probes.mjs`, no eval channel) try to read and write files under home, fetch, import, open sockets, spawn processes and read the environment, against a local server that must see nothing; a parse that never returns and one that eats memory must be stopped and the next file convert; a truncated STEP must fail to open while a two-body one opens. The report is rewritten before each stage with the stage it's in, so an app that dies mid-test names the stage. `verify/fixtures/cadimport/` holds a STEP, a zip of it and an STL with the bytes they converted to before the move, and the conversions must match, plus `two-bodies-inch.step` (two named, coloured bodies drawn in inches) for the bodies mode. With `BASECASE_CADIMPORT_UNSANDBOXED=1` the same self-test runs on the Node host, and the canary must catch the probes getting through (gate `s0-cadimport-sandbox`).
- **Room files a person drops** (RoomPlan's CapturedRoom JSON, `src/cases/roomPlan.ts`) are parsed as data in the page, never run: at most 8 MB and 1024 entries a list, every number finite, sides 0 to 50 m, transforms within 500 m, categories plain words, and any refusal throws `CaseFileError` before a Case is built. The scan app's `basecase` start is read the same way, three finite numbers within 500 m, but a bad one is dropped instead of refusing the room. Exploit tests in `roomPlan.test.ts` and `roomStart.test.ts`.
- **The CAD kernel** (agent-written OpenSCAD, and replicad run through `new Function`) runs only in a Chromium sandbox: a module Worker in a hidden `BrowserWindow` (`electron/cad-kernel/sandbox/`) with `sandbox: true`, no Node, context isolation, its own in-memory session (`basecase-kernel-sandbox`) and its own scheme (`basecase-kernel://kernel`).
  - The session cancels every request that isn't to that scheme (`webRequest`), denies every permission, download and device, and the protocol serves only `dist/kernel/` (bundle files by extension, no traversal, `bundleFile`) plus `/library.json`, BOSL2 and the robotics library read by the main process from `vendor/`.
  - CSP is default-deny: the page gets `'self'` scripts, `'wasm-unsafe-eval'` and `connect-src 'self'`; the worker, where agent code runs, gets `'unsafe-eval'` and `'wasm-unsafe-eval'` with `connect-src 'none'` and `worker-src 'none'`. The worker fetches nothing: the page compiles the WASM modules and hands them over with the libraries. Navigation, new windows and webviews are refused.
  - A Worker that ran replicad code is replaced before the next job, so no job inherits another's globals. Results come back as JSON bytes, matched to the job id, at most 64 MB; the main process parses only a STEP export's (below).
  - **STEP export** (`cad:export-step`, `/cad-export-step`) is a kernel job like a render, since its bodies include replicad code. `exportStepFile` (`cad-kernel/stepExport.mjs`) refuses without a kernel that has `exportStep` (the Vite middleware without `BASECASE_NODE_KERNEL=1`) and checks the renderer's job with `checkedStepJob` (`stepPolicy.mjs`) before it reaches the pool: sizes, counts, finite numbers, rigid placements, `#rrggbb` colours and known solid types only, rebuilt field by field. Part names are text inside the file, never paths, and `stepName` takes out what could close a STEP string; the file name is the scene name through `fileSafe`, and nothing is written to disk but the user's download. `checkedStepReply` keeps only a whole `ISO-10303-21;` … `END-ISO-10303-21;` file and a skipped count no larger than the body count. The exploit inputs are in `cad-kernel/stepPolicy.test.mjs` (forged replies, hostile jobs) and `stepExport.test.mjs` (names that try to close the string or end the file), and the packaged app's kernel self-test exports a replicad box with such a name.
  - The page talks to the main process only through its preload's four calls, on its own `webContents.ipc` behind `trustedIpc(…, KERNEL_ORIGIN)`; the app's IPC refuses it, and it refuses the app.
  - **`cad:tune`** (the Inspector's Dimensions, §7) takes exactly a part id, a workspace id and a map of names to finite numbers (`checkedTune` in `backend/cadTune.mjs`), never code. The main process asks the renderer for that part's stored code, and `rewriteDimensions` replaces only literals of names the code already assigns at the top level with digits it formats itself; an unknown name, a string, `NaN` or an extra key is refused before anything compiles. The rewritten code goes to the same pool job as `model_part`, and its answer bytes pass back to the page unparsed. The exploit inputs are in `security.test.mjs` (“tuning a part’s dimensions”).
  - The MCP server (a separate Node process) never compiles: `cad-kernel/client.mjs` sends `kernel_render` / `kernel_audit` / `kernel_warm` over the token bridge, which is behind `guardBridge` too.
  - The renderer's `cad:render` IPC (`/cad-render` on the Vite bridge) sends the code of pending parts to the same kernel pool (`backend/cadRender.mjs`: a known language, code under 200 KB, a fixed 90 s limit), never compiled outside the sandbox; the main process passes the reply bytes through unparsed, and the renderer keeps only a well-formed mesh, ports and audit (`checkedRender` in `src/utils/platform/renderedCad.ts`).
  - A sandbox that can't start answers every job with an error; nothing in the app falls back to Node. The Node host (`cad-kernel/nodeHost/`) is for tests, the bench and `tools/` only: the Vite middleware uses it only with `BASECASE_NODE_KERNEL=1`, and the packaged app doesn't ship it (`package.json` `build.files`).
  - `e2e/app/kernelSandbox.app.test.ts` runs agent-code probes (files, fetch, XHR, WebSocket, EventSource, beacons, `import()` from `file:` and `http:`, `process`, `require`, service workers, windows, other origins, the bridge) in the worker and the page against a local server that must see nothing; the canary runs the same probes on the Node host and must catch them.
- **A Case's code panels** (§8h) run code a Case file carries, which can come from the agent or a shared Case, so it's treated as hostile. Each runs in an iframe from `srcdoc` with `sandbox="allow-scripts"` and no `allow-same-origin` (an opaque origin: no cookies, storage or parent access, no top navigation, popups, forms or downloads). `codePanelDocument` writes a CSP ahead of the code (`default-src 'none'`, inline script and style, `data:` and `blob:` images and media, `data:` fonts, `base-uri` and `form-action` `'none'`), so it can't fetch, open sockets or load anything from the network; a policy the code adds can only narrow it. The app's own page carries `frame-src 'none'` (`index.html`), so a frame can't navigate itself to a URL either; `srcdoc` documents load without a request. Chromium runs sandboxed frames out of the studio's renderer process (the desktop app switches on `IsolateSandboxedIframes` in `electron/main.mjs`), so in the desktop app a frame that hangs never blocks the studio, and the bridge unloads it after 2 s without an answer, or 10 s without a hello. On the web (the demo and shared Case links) the frame runs in the visitor's browser, on our origin's page. Chrome and Edge on the desktop run a sandboxed frame without `allow-same-origin` in its own process (Chromium's `IsolateSandboxedIframes`, on by default since about version 132), so a hung frame never blocks the page. Firefox and Safari keep it in the page's process, so there a hung frame blocks the tab. The bridge counts its 2 s from the oldest unanswered ping. A tick more than 1 s late means the page itself stalled, and a healthy frame's answer may still wait in its queue, so the bridge pings again instead of unloading; a frame that misses that ping too is unloaded. The only way out is the bridge's port, handed to that frame alone; every message on it is validated field by field with sizes capped (32 signal names, 200-character values, 500-character errors, 300-character console lines, 240 messages a second), and the bridge can only read subscribed signals, drive through the `code` source, send named events and run `CASE_ACTIONS` the studio would allow anyway. Bridge v2 adds three more, each capped:
  - **World** (`world.set`): only objects the Case file marks `movable`, never the robot or a fixed object; positions finite and within 50 m, rotations finite (`readWorldChange`), then scaled to the robot's reach like the world (`stagedChange`); at most 60 calls a second per panel, the rest dropped. The sim worker checks the name again (`WorldMoves.apply`), so a call that slips past the bridge still can't touch anything else.
  - **Frames** (`frames`): only the Scene and stationary views and the robot's cameras (`cameraStream`), never the computer's camera, which sees the person: code that never sees them can't leak a picture of them through any channel the bridge has, now or later. `operator` gets the same refusal as any unknown name (`cameraStream.test.ts`). At most 4 streams per panel, 640 × 480 and 15 frames a second. They're rendered in the camera worker and transferred to the frame, never fetched, and none is posted after its stream stops or the bridge closes.
  - **Store** (`store.get`, `store.set`): one JSON value per Case, kept in IndexedDB on this computer under `<sceneId>/<caseId>` and never in the Case, so nothing the code keeps leaves the machine in a saved scene or a Share Robot bundle. The code stringifies its value in its own frame and only a string crosses (`readFrameMessage` refuses anything else), so a value that's a graph of shared references can't make the studio walk billions of nodes; the bridge refuses a string over 64 KB, by length before it counts UTF-8 bytes, or one that isn't JSON, and takes 10 store calls a second per panel. Writes go to disk one at a time per Case, the newest value next. A scene can read only its own Cases' values; an imported `.basecase` file gets a new scene id, so a crafted file can't claim another scene's store. Those values hold only what code panels kept: signals, frames of the sim and the person's clicks in the panel, never the computer's camera.
  - **The agent** writes these panels with `write_case_code`, whose reply carries a capture of the app window from the main process (`capture_window` on the token bridge, `electron/main.mjs`); the capture goes only to the agent, which already sees the scene in its captures.
  - Exploit tests: the probes and the hung frame in `e2e/caseCode.e2e.test.ts`; the shared Case probes in `e2e/gallery.e2e.test.ts` (below); the spoofed hello and port, a frame that froze the page, a non-movable object and a robot part refused, NaN poses refused, 10,000 world calls a second throttled to 60 and frames after a stream stops in the bridge tests; a 1 MB store write, a non-string store value, a function value refused in the frame, and the 11th store call in a second refused in `codeStore.test.ts`; `operator` refused in `cameraStream.test.ts`; the worker's own refusals in `src/sim/worldMoves.test.ts`.
- **Generated HTML** escapes every value (coerce numbers); the guide viewer strips scripts, handlers, links and non-image URLs. No `dangerouslySetInnerHTML`.
- **The robot daemon** (`electron/robot/`, §8k) is spawned only from the bundled `<resources>/hw/robot-daemon` (or `hw/dist` from source; `BASECASE_ROBOT_DAEMON` overrides it for tests), with no shell and a fixed argv that always has `--emulated` and never `--port` or `--interface`. `robot:connect` takes exactly the four spec keys of a plain object, or exactly `family: 'unitree-g1'` and `emulated` for the emulated G1, or exactly `family: 'ros2'`, `emulated`, `controller` (`kind` and `topic`) and `joints` for an emulated ROS 2 robot (`checkedRobotSpec`): a port, an interface, `emulated` not `true`, an extra or inherited key, an id outside 1–253 or a string smuggling a flag is refused before anything starts. A ROS 2 topic is never free-form: it must follow ROS 2 name rules (absolute, at most four segments of letters, digits and `_`, no `__`, at most 128 characters) and end in its controller's fixed segment (`commands`, `joint_trajectory`, `cmd_vel`), and joint names are 1 to 64 letters, digits and `_` (`electron/robot/ros2.mjs`). The daemon checks both again (`servo_wire::ros2::names`) and drops any `JointState` that doesn't decode, has a position that isn't a number, or names more than 64 joints. The emulated G1 and the emulated ROS 2 robot listen on two UDP sockets bound to 127.0.0.1 inside the daemon's process, never on another interface. `robot:command` rebuilds each documented command from its known fields (`checkedCommand`) and drops everything else, so the page can't write registers. `robot:policy` takes only an array of at most 16 plain `{ kind: 'policy', id }` or `{ kind: 'skill', hash }` objects (`checkedPolicyRefs`), never a path or bytes: the main process reads `library/policies/<id>/policy.onnx` for an id matching `policy-[a-z0-9-]+` (`Trainer.policyOnnx`) or a 64-hex skill hash through `getSkill`, encodes the skill with `policyOnnx`, which refuses mismatched layers and non-finite numbers, and writes the result only into that connection's artefacts folder. Exploit tests in `robotLink.test.mjs` (“reads policies only from the library”). Real serial and the real network (rustdds) aren't in the binary at all; `verify/hw/motorLock.mjs` checks the staged file, and the `s5-emu-daemon` gate fails on a bind outside the loopback emulator. The exploit inputs are in `security.test.mjs` (“robot daemon”), `electron/robot/ros2.test.mjs` and `servo-wire/src/ros2/hostile_tests.rs`.
- **Phone pairing** (`electron/phone/`, §8h): Pair Phone starts an HTTPS server (`PhonePairing`) that listens only while a pairing is on, only on the first LAN IPv4 address (with none it refuses, so no code points at loopback), on a random port, with a fresh self-signed P-256 certificate made in memory for that address (`selfSignedCert.mjs`, never written to disk). The QR URL carries a one-time token (32 random bytes): the page and the socket need it, the first WebSocket upgrade uses it up, a replay gets 403, and only one phone ever connects per pairing. Every request passes `guardBridge`'s rules for the server's own origin (`phoneRequest.mjs`): `Host` exactly `<ip>:<port>`, `Origin` (when sent) exactly `https://<ip>:<port>`, `Sec-Fetch-Site` (when sent) `same-origin` or `none`. The page is a fixed string with only a nonce in it, served with `no-store`, `nosniff`, `no-referrer` and a CSP of `default-src 'none'` plus nonce'd script and style and `connect-src` to its own `wss://` origin. The WebSocket reader (`wsFrames.mjs`) takes only masked, final text, close, ping and pong frames of at most 512 bytes; anything else closes the socket (1002, 1009 when too big) and ends the pairing, as does over 4 KB of unparsed input. Each message must match the schema exactly (`checkedPhoneMessage`: three keys, finite numbers in range, two booleans, rebuilt field by field) or it's dropped, and at most 60 a second reach the app. The pairing ends on Unpair Phone, on Esc while the code shows, when the phone disconnects, or after 5 minutes with no phone; the server then closes and every connection is destroyed. The device name comes from the user agent, cut to 40 letters, digits, spaces, `-`, `_` and `.`. Exploit tests in `electron/phone/phonePairing.test.mjs` (with the client in `e2e/phoneClient.ts`, which pins the pairing's certificate) and `phoneMessage.test.mjs`.
- **Permissions** (`electron/permissions.mjs`, installed on the default session by `main.mjs`): the app origin gets `clipboard-sanitized-write`, `fullscreen`, `midi` (Web MIDI without sysex; `midiSysex` is refused), the camera and the microphone, nothing else and no other origin anything. The camera and microphone are `media`: a request must come from the app origin with `mediaTypes` of `video`, `audio` or both (empty, missing or unknown types are refused), and a permission check passes only for the app origin with `mediaType` `video` or `audio`. On macOS the main process then asks the system once per device (`systemPreferences.askForMediaAccess('camera')` for video, `('microphone')` for audio, refused at once when access is `denied` or `restricted`) and grants only when every requested device gets a yes; the packaged app carries `NSCameraUsageDescription`, `NSMicrophoneUsageDescription` and the `com.apple.security.device.camera` and `com.apple.security.device.audio-input` entitlements for that. Device permissions (HID, serial, USB) stay at Electron's default of none. Camera frames and microphone audio stay in the page's memory and its workers: they never leave the machine and are never written to disk. The voice model is unpacked into Vosk's IndexedDB store; no audio goes there. Exploit tests in `electron/permissions.test.mjs`, including another origin's audio and MIDI requests.
- **The AprilTag detector** (`public/apriltag/apriltag.wasm`, §8l) is our own Rust (`tools/apriltag/`, no crates), built with plain `rustc` by `npm run build:apriltag` and committed, so nothing is fetched from a CDN or a registry at build or run time. The tracking worker fetches it from the app's own origin. The module imports nothing, so it can't reach the page, the network or the disk; it reads a gray frame the worker copies into its memory and returns at most 64 detections. The codebook stays in TypeScript (`tag36h11Codes.ts`) and is handed over at load. Frames from the camera stay in the worker's memory: they never leave the machine and are never written to disk.
- **No `shell: true`**, no string `exec` with interpolated input, no TLS verification off outside the Bambu LAN connector.
- Every security fix gets a test that feeds it the exploit input (`electron/security.test.mjs`).
