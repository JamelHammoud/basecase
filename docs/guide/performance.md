# Performance

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 0f. Performance (mandatory)

- **Print orientations share triangle calculations.** `three/printability.ts` scores all candidate poses in one triangle pass, reusing its normal, area and centroid across poses. Temporary storage scales with candidate count, never triangle count. Print reports, merge planning, manual faces and fit coupons use this scorer. `analysis/shapeReports.ts` also batches uncached requested faces, preserving rounded cache keys, first matches and request order. `printOrientation.test.ts` checks box contact areas, support hits and misses, angle and contact limits, tilted faces, degenerate triangles, source preservation, cache reuse and coordinate-read bounds for both batch paths. A scratch comparison matched complete reports on 30 transformed meshes and 90 manual-face requests exactly against the previous scorer. With ten candidates, 300- and 1,200-triangle fixtures reduced coordinate reads from 99,900 to 75,600 and from 399,600 to 302,400. Vector cross products fell from 7,602 to 4,902 and from 18,410 to 7,610, including BVH work. These are operation counts, without timing assertions.

- **Dense solvers scan matrix tails directly.** `utils/matrixScans.ts` selects pivot rows and accumulates solved terms without copying array tails. Calibration least squares, skill IK and stance weight sharing use it. Each solver retains its elimination order and singular-matrix policy. `leastSquares.test.ts` and `denseSolves.test.ts` check pivoting, source preservation, singular refusal, arm targets and force balance with no tail copies. A scratch comparison matched the former results exactly on 300 systems per solver, including empty, singular and row-swapped systems. At 16 variables, calibration and IK each remove 32 temporary arrays containing 256 entries per solve. The three-variable stance solve removes three arrays containing six entries. These are allocation counts, without timing assertions.

- **Captured-world camera rendering stays in workers** (§8l). Camera tiles, frame streams, agent shots and dataset videos reuse the canvas's Spark/mesh world layer inside their existing OffscreenCanvas stages. The imported asset is sent on scene changes, never with pose frames. Spark updates finish before a capture. An unchanged camera, world transform and image size reuse the prepared splats, so robot motion alone never regenerates a fixed view's splat buffers. One feed draw is in flight at a time. On demand, `node tools/perf/worldVideosBench.mjs` measures rendering and encoding a 10 s, 30 fps, two-camera kitchen episode against Open Floor, including stage creation. It prints both times and fails above a 3× ratio. Timing never runs in Check.
- **Training images stream in workers** (§8h, §8l). `trainingImages.worker.ts` owns scene variation, JPEG encoding, mask extraction, polygon tracing and frame hashes. Generation transfers one JPEG and depth buffer at a time and writes them before requesting another frame. The main thread retains annotation manifests, not a batch of depth images. Image validation, package merging and ZIP compression also run in workers. Label shaders, render targets and floor textures are reused across captures. Frame-set verification hashes one frame at a time to bound temporary copies of JPEG and depth buffers.
- **Training image acceptance budget** (`node tools/perf/trainingImagesBench.mjs`): on demand, 1,000 labelled 640 × 480 frames in under 120 seconds after one warmup capture. The first 500 frames compare every visible block box against independent projected corner bounds within one pixel. The command accepts `--cpu`, `--dist <dir>` and `--no-build`. The 120-second threshold is a contract, not a measured baseline. It includes worker transfers and JPEG encoding but excludes dataset persistence and archive export. Timing never runs in Check. `e2e/trainingImageBounds.e2e.test.ts` checks five seeded placements without a timing assertion. Other camera acceptance tests cover depth within 5 mm, fisheye projection, occlusion and byte-identical seeded captures.

Captured world parsing and V-HACD collision decomposition run in the world import worker. At most 64 hulls with 96 vertices each reach MuJoCo. The scene stores one content-addressed asset and each Case references its hash, so adding a Case does not copy its splat or mesh. Case workers receive collider items only. Spark sorts splats in its bundled worker and requests redraws as work completes through the existing on-demand render loop. `e2e/worldImport.e2e.test.ts` covers attachment of the rendered world.

Saved world assets restore in `worldAssetRestore.worker.ts`: base64 decoding, buffer validation, canonical serialization, hashing and texture or splat payload validation all finish before the page registers any asset. The worker transfers decoded binary buffers and returns cached canonical JSON for autosave, then terminates. An unavailable browser worker refuses the restore. The standard worker client runs the same operation locally only outside the browser for Node and tests. Hashing and serialization live separately from the registry, so neither world worker imports the worker client.

`node tools/perf/worldBench.mjs --dist dist --scene scratch/rover.json` imports a synthetic 1,000,000-point kitchen splat into a saved rover scene, waits for all points to enter Spark's active set, warms one orbit and measures a second four-second orbit at 1440 × 900. It uses the viewport benchmark's WebGL probes and Chrome's GPU-process trace, records CPU work p95, frame interval p95 and average GPU-process work per rendered frame, and fails when CPU work p95 or GPU-process work exceeds 16 ms. `--cpu` selects SwiftShader, `--budget` changes that explicit budget, and `--output` chooses the JSON report (default `scratch/perf/world.json`). No GPU measurement has been recorded for this change. GPU-process work measures Chrome's submission work rather than hardware execution time. The decomposition test’s 200,000-triangle worker budget is 10 seconds. Run `src/cases/worldDecomposition.perf.test.ts` with `vitest.perf.config.ts` for that measurement. It transfers a tessellated kitchen into a bundled worker and checks the gap under its table. The initial direct 200,000-triangle box measurement took 17.95 seconds before boundary-preserving collision simplification was added. This is a local measurement, not a CI result.

The app must feel instant. These rules came out of profiling real scenes (60+ CAD parts, 50+ MB saved files); don't regress them.

- **Containment stops when its ray votes settle.** Collision analysis and assembly probes share `three/analysis/collide.ts`'s containment query. The CAD kernel's `MeshQuery.inside` applies the same early decision to its own directions and crossing rules. Two agreeing rays settle a three-ray query, reducing three BVH traversals to two. Disagreement still casts the third ray. Renderer queries count forward hits without allocating a filtered hit array, retaining the strict 0.0001 mm cutoff. Kernel queries retain sorted, deduplicated crossings. `containment.test.ts` and `meshQuery.test.mjs` check every three-ray vote sequence, real solid and hollow meshes, boundary points and moved assembly frames. Custom renderer direction lists retain the two-vote threshold. A local before-and-after probe of 300 interior box points reduced BVH traversals from 900 to 600 in each of collision analysis, assembly probes and the kernel, with 300 inside results in both versions. These are operation counts, without timing assertions.

- **Worker batches build their indices once.** `electron/workerIndices.mjs` assigns each job index to one worker by striding through its share. Joint sweeps, strength analysis and OpenSCAD recipe port extraction share it, without mapping and filtering the full input once per worker. Worker assignments, order within each worker and result order stay unchanged, including empty chunks. `workerIndices.test.mjs` checks uneven batches, empty inputs and complete result restoration with null readings across one to eight workers. `analysisBatches.test.ts` checks both analysis dispatchers with four workers and one source read per job. A local operation-count probe compared identical payloads for four workers: 11 analysis jobs fell from 44 source reads to 11, and 10,000 jobs from 40,000 reads to 10,000. Recipe ports fell from 50,000 reads to 10,000 on the same batch size. These counts measure dispatch preparation, without timing physics or compilation.

- **Mesh measurements accumulate bounds and mass properties together.** `three/meshMeasure.ts` accumulates bounds alongside volume, area and centroid moments in one triangle pass. Part reports, fit coupons, simulation fixtures, guest parts and object measurements share this helper. Each coordinate is read once, with the existing signed-volume arithmetic and zero-volume midpoint fallback. Incomplete final triangles retain their bounds and return non-finite volume and area. `meshMeasure.test.ts` covers translated and reversed tetrahedra, planar and degenerate triangles, empty and incomplete inputs, source preservation and coordinate-read counts. The 300-triangle and 600-triangle fixtures fall from 5,400 and 10,800 coordinate reads to 2,700 and 5,400. These are operation counts, without wall-clock assertions.
- **Fixed simulation schedules advance by cursor.** `utils/timelineCursor.ts` copies and stably sorts a schedule once, then visits each due entry once without shifting the remaining array. It releases consumed references and empties the array when finished. Worker scripts, headless commands, pushes and requested frames, Case references and world events, fit checks and recorded reference fixtures share it. Equal-time entries keep their source order and the due boundary keeps its 1 ns tolerance. A local Node 26.13.0 measurement on shared macOS hardware consumed 40,000 events across 4,001 ticks, including the initial copy and sort. After three warmups, the median of nine runs was 2,135.40 ms with `shift()` and 1.96 ms with the cursor. This measures scheduling alone, not physics, and adds no CI timing assertion.
- **Insertion ranges scan scalar values.** `utils/centerSizeRange.ts` tracks the minimum and maximum of each axis without temporary coordinate arrays. Robot imports, articulated catalog parts, CAD body placement and agent robot-height reports share it. Existing-scene right edges reduce rotated or affine bounds without spreading scene counts into function arguments. `workspace/robotPlacement.test.ts` covers 150,000 incoming parts and scene obstacles, plus exact coordinate and dimension reads at 600 and 1,200 parts. Articulated placement now reads each dimension once per part, down from six reads per dimension. These are operation counts, without timing assertions.
- **Base64 goes through byte arrays.** `src/utils/base64.ts` uses native `Uint8Array` base64 methods when available, avoiding temporary binary strings and per-byte JavaScript conversion. Older browsers use the chunked encoder and `atob` decoder. All renderer conversions, including sourced meshes, SimReady files, dataset fixtures and file-picker test hooks, use these helpers. Encoding respects a typed array's offset and length. Decoding returns an owned buffer of exactly the decoded length. The [native API](https://tc39.es/proposal-arraybuffer-base64/) uses the standard alphabet, padding on encode and loose final chunks on decode, matching the fallback's accepted bytes.
- **The viewport never rebuilds everything.** `src/three/viewport/` is a plain TypeScript engine behind the thin `Viewport3D` component. `PartLayer.sync` diffs parts by object identity: unchanged parts are kept, a transform-only change moves the group, and only changed or re-selected parts are rebuilt. Parts are immutable; always replace a part object to change it, never mutate one. Builds are time-sliced (about 10 ms per frame), so opening a big scene never freezes; queries that need the whole scene (captures, measurements, picking, framing) finish pending builds and spawn animations first (`NEEDS_WHOLE_SCENE` in `engine.ts`): a part caught mid pop-in is scaled down, and the print report caches what it measures.
- **Parts draw in batches, not one draw call each.** `PartBatches` (`three/viewport/partBatches.ts`) draws every plain part mesh in a three.js `BatchedMesh` per material (`MeshBatch`, one geometry slot shared by every copy of a shape, colour per instance) and every part's edge lines in one `LineBatch` per line material (one buffer, instance index per vertex, matrices in a float texture). `my-robotics-design` (488 parts) went from 1,273 GL calls per orbit frame to 9, main-thread work from 3.2 to 0.9 ms and GPU-process time from 1.5 to 0.9 ms.
  - Part groups stay exactly as before for picking, snapshots, bounds, the gizmo and the outline; their batched meshes and lines just move to `BATCHED_LAYER` (off layer 0, so the main and shadow passes skip them). Every part raycaster comes from `partRaycaster()`, which enables that layer. Code that hides a part uses `visible`, never layers.
  - `scene.onBeforeRender` syncs matrices, visibility, colours and in-place geometry edits (attribute versions) after three updates world matrices. Materials are replaced, never edited in place: a new material or geometry object re-tracks the mesh.
  - Batchable: an opaque, untextured, non-glowing `MeshStandardMaterial` mesh with position and normal and at most 32k vertices (`batchKey.ts`); selected parts glow, so they draw alone. Bigger meshes draw alone: a draw call is nothing next to their vertices, and copying them would cost more. Lines: plain `LineBasicMaterial` segments.
  - Freed geometry slots are reused best-fit (`setGeometryAt` re-uploads only that range); a batch compacts only when half of it is waste and grows by doubling. Deleting a geometry in `BatchedMesh` never frees its space, and growing or compacting re-uploads the whole buffer: an edit to one part once stalled `look` for 284 ms.
  - Captures that isolate parts, swap materials or draw silhouettes run inside `batches.unbatched(...)`, which puts the originals back on layer 0 for the call; plain captures and screenshots stay batched. Edges that arrive late from the worker announce themselves with `noteLateChildren(group)`.
  - `warmShaders` also compiles the batched program.
- **Derived geometry is shared and released.** `buildPartGroup(part, selected, { shareGeometry: true })` takes creased normals, edge lines and hardware booleans from a reference-counted cache keyed by the source data (`partMesh/sharedGeometry.ts`). Every group built that way is freed with `releasePartGroup`, which also disposes the materials and owned geometry. Anything you remove from a scene must be disposed.
- **Sculpt brushes reuse per-stroke workspaces.** `three/sculptStroke.ts` allocates one brush-state object per stroke and reuses its scratch normal vector for Inflate, Carve, Flatten and Pinch. Smooth and Grab share the same state reuse. `sculptStroke.test.ts` checks all six brushes' displacement, falloff, mirrored regions and input preservation, and bounds vector clones at three for 300 and 600 vertices without symmetry. The previous 300-vertex fixture cloned 203 vectors for each of the four direction brushes. This is an allocation count, not a wall-clock measurement.
- **Heavy geometry runs in workers, never on the main thread.** The geometry worker (`three/geometry.worker.ts`, ops in `geometryOps.ts`, client `geometryWorker`) parses robot meshes, welds and simplifies links, assembles link soups, computes creased normals, edge lines and component GLBs. Before a big `mesh` / `cad_part` is built, `PartLayer` waits for `preparePart` (`partMesh/prepare.ts`) to seed the shared cache from the worker, so the main-thread build only wraps ready arrays; edge lines over 500 triangles arrive later (`partMesh/lateEdges.ts`, `lateEdges: true` in the viewport only) and redraw through `requestRedraw`. Builds are also capped by vertices uploaded per frame, so a robot's GPU uploads spread over frames. Send mesh arrays to workers as typed arrays (`packedMesh`): structured-cloning a JS number array costs several times more. `workerRpc` falls back to running in-thread where there are no workers (tests, Node). Never pause builds while the camera moves: make the build cheap instead.
- **Booleans cut in the geometry worker** (§7a). The main thread only hashes the operands, hands their mesh arrays over with a matrix each, and turns the reply into the result's mesh. For two 50,000-triangle meshes (`booleans.perf.test.ts`) that is about 2 ms to hand off and 3 ms to take the reply, while the cut (welding, Manifold) takes about 180 ms in the worker; it used to run on the main thread in three-bvh-csg. The test fails if any main-thread step reaches 16 ms.
- **Agent checks never run on the main thread.** Interference (`check_scene`, pose checks), the posed floor height (`posedFloor`, exact vertex heights, never a rotated bounding box), range-of-motion sweeps (`verify_design`), printability and part measurements run in a pool of analysis workers (`three/analysis/`: `analysis.worker.ts`, client `analysisPool`). The viewport only snapshots plain data (`snapshotShapes`: per part a shape key, its geometry and a rigid frame matrix) synchronously, so a snapshot always matches the pose at call time; the work is awaited. Workers keep each shape's geometry, BVH (built lazily) and samples by shape key, so identical parts share one shape and later calls reuse them; geometry is copied to a worker once, in 8 ms slices. Checks use matrices on cached shapes, never a mutated live scene. Sweeps fan out one joint per worker and skip pairs that move together. Strength solves fan out one part per worker and are cached by shape, frame and load; the stiffness matrix is assembled once into 3×3 blocks, which halves the work per iteration against multiplying element by element. A 3 mm bracket (about 1,900 cells) solves in 0.2 s, a 124 mm hollow arm (8,900 cells, the cap) in 0.9 s on an M-series Mac; `engineeringStrength.test.ts` holds the bracket under 2 s of CPU time, which a busy test run doesn't inflate the way it does wall time. The engineering report runs twice: once to collect the sweeps, strength jobs and payload maps it needs, then with their results (`engineeringNow.ts`). Every `Viewport3DHandle` query that does real work is async (`interference`, `posedInterference`, `sweepClashes`, `measureParts`, `printShapes`, `captureViews`).
- **Lighten** (`strength/lighten.ts`, analysis task `lighten`) uses the same worker pool and cached local meshes as Strength. It refuses a renderer fallback. A 100 × 18 × 9 mm solid PLA bracket at 0.5 target mass, 1.5 mm wall and 500 N·mm takes 6.702 s, including the first Manifold load, on an M5 Pro with macOS 27.0.1 and Node 26.13.0. It solves 4,824 cells in 14 updates and produces 33,872 triangles, reducing estimated solid grams from 20.412 to 10.001. Fixed 1.5 mm maximum cell spacing never becomes coarser for large parts. Work exceeding 40,000 solid cells or 1,500,000 bounding-grid cells is refused before optimization. Fine-grid and wall-filter work are bounded before allocation too.
- **Collision filters plan eligible partners once.** `three/analysis/collisionPairs.ts` classifies parts by focus and straddle membership, then builds ordered partner lists for the four combinations. Advancing cursors exclude earlier parts without rescanning them. Planning takes linear work plus the eligible pairs, so a joint sweep visits moving-to-stationary pairs directly. Whole-scene checks still visit every pair. The shared planner serves interference, posed checks, output-riding servo cases and range-of-motion sweeps. It preserves scene pair order, skip rules and the 0.1 mm box padding. The former 0.5 mm focus-neighborhood pass is redundant with the tighter pair-box check and is removed. `collisionPairs.test.ts` compares every focus and straddle subset against the previous algorithm, including empty lists, missing ids, skipped pairs, touching boxes and padding boundaries. Its 600-part and 1,200-part one-part sweeps each read part ids once per input part, without wall-clock assertions.
- **Visible-share projections reuse one workspace.** `three/analysis/visibility.ts` measures world-sample bounds once and reuses depth and winner buffers across its five views. Projection axes and limits are read before each view's sample loop, which uses scalar coordinates without temporary arrays. Craft review and `model_part` visibility auditing share this analysis-worker calculation. Seeded surface samples, pixel coordinates and first-owner depth ties stay unchanged. `visibility.test.ts` checks exact shares for overlapping, rotated, scaled and far-translated meshes, empty geometry and collapsed ranges. A local operation-count comparison on one and two meshes, each with 4,000 cached samples, reduced bounds scans from five to one. Projection-limit reads fell from 40,020 and 80,020 to 20 in both cases. These are operation counts, without timing assertions.
- **Wrap Robot runs in its own worker** (`src/wrap/wrap.worker.ts`, §8c), with Manifold loaded only there. The main thread takes a rest-pose snapshot of the mesh and the robot (`restShapes`) and copies its geometry in 8 ms slices (`copyGeometries`, shared with the analysis pool); the worker returns the shells as transferred typed arrays, and `prepareParts` seeds their geometry before they're committed.
- **Captures encode off the main thread.** `captureViews` and `captureScreenshot` render with the live renderer, copy at the requested size into an `OffscreenCanvas` right after rendering (`transferToImageBitmap`, synchronous: a WebGL canvas has no preserved drawing buffer, and `createImageBitmap` on it reads blank), and encode in the image worker (`utils/image.worker.ts`, `encodeBitmap`). Helpers are restored before encoding finishes. Export Image and Save to Library await a full-size PNG. A scene tab's preview requests its final 560px JPEG directly, without encoding a full-size PNG and decoding it again. `downscaleDataUrl` goes through the same worker. Never `toDataURL` a capture on the main thread.
- **Export STL never rebuilds a part.** It snapshots the canvas's own rest-pose meshes of the visible solid parts (`exportStl`, `restSolids`) and writes the binary STL in an analysis worker (`stl` task, `sceneStl.ts`, through `binaryStl`), the way 3MF plates are written; `__studio.stlBase64` reads the same file.
- **Sheet detection and cut files** (§8b) stay off the main thread. `shapeReports` caches each local sheet profile with its shape measurement in the analysis worker. Detection projects each face vertex once per candidate normal, retaining minimum and maximum depths for thickness, side validation and both cap boundaries. It builds no cap edges for rejected side geometry and no closed-edge map for rejected profiles. `sheetProjection.test.ts` checks profiles, reversed winding, reordered faces, moved meshes, unchanged inputs and dot-product budgets. On plates with 2,404 and 4,804 triangles, vector dot products fell from 21,678 and 43,278 to 9,637 and 19,237. These are operation counts for detection, without wall-clock assertions. Cut Files sends only names, manufacturing settings and detected loops to its own worker for DXF writing and zip compression. Resizing a tilted sheet changes child matrices, without copying or rewriting its vertex arrays.
- **Printing never blocks the UI** (§8f): orientation candidates are found in the analysis workers (cached per shape), each scene's 3MF is welded, written and zipped in an analysis worker (`threeMf` task), and slicing runs as a child process in the main process. Plate layout and packing are plain data on the main thread (microseconds per part).
- **Thumbnails render in a worker** (`thumbnail.worker.ts`, OffscreenCanvas, encoded with `convertToBlob`): Library, Parts, scene previews and robot previews all go through `renderPartGroups`, which is async. A try's filmstrip draws and encodes in `filmstrip.worker.ts` (§8h), and the agent's camera shots encode in the image worker (`encodeBitmap`). Never `toDataURL` or `convertToBlob` a thumbnail, filmstrip or camera shot on the main thread: reading a canvas back there is a synchronous GPU round trip, which waits behind every frame the GPU process has queued.
- **Shaders are compiled before they're needed.** `warmShaders` compiles the scene (gizmo included) and the part materials with `compileAsync` at startup, finishes one program per idle callback, then renders one hidden shadow pass, so the first part, selection or shadow never stalls. On software GL (SwiftShader, llvmpipe: CI and VMs, `softwareGl()`) it doesn't run. There each program's link blocks the main thread, and the idle callbacks' 2 s timeout let them run mid-work: driving the G1 with the camera on 2 CPUs, warm-up held the main thread for 20 to 850 ms at a time for about 12 s after the command, and 92% of a 35 s window under heavy load. Without it, the first render compiles only the programs it draws.
- **Render on demand.** `RenderLoop` draws only when something changed (`invalidate()`), the camera moved, an animation runs, or a texture finished loading, plus a 1 s idle refresh. Code that changes the scene outside the engine's own paths calls `invalidate()`. Never add an always-on `requestAnimationFrame` render. Camera moves call `noteInteraction`, not `invalidate`: the shadow map (`autoUpdate = false`) re-renders only when the scene changed, and the key light refits once the camera settles. Anything that renders a changed scene itself (captures) sets `shadowMap.needsUpdate`. Nothing redraws for a change no one can see:
  - `setPose` returns early when every delta is within 0.01 mm and 1e-5 of the one shown (`samePose.ts`), so a live sim's resting robot doesn't re-render the scene and its shadows at 60 Hz.
  - `update` returns early when no prop changed but callbacks (`shownPropsChanged`), and agent frames rebuilt with the same parts keep their identity (`steadyProps`). A Case try re-renders the workspace ten times a second for its stats; each one used to redraw the canvas.
  - A new LiDAR scan redraws through `redraw()`, which leaves the shadow map alone, and only when a hit moved more than 0.01 mm: `LiveScans` (`src/dataLayers/liveScans.ts`) keeps the layer's last track when no hit moved.
  - In a Linux container like CI's (software GL), these redraws ran during a LiDAR Case's dataset export and slowed it from about 40 s to over 200 s. The viewport has no `preserveDrawingBuffer`: read the canvas only right after rendering it, in the same task.
- **Sensor data costs only what changed** (§12). A data layer redraws when its track is replaced or its message, color field or playhead span changes, never per frame: an unchanged layer costs a string compare. A `PointCloud2` with float `x`, `y`, `z` takes a typed-array path: positions in one pass, colors in a second through a 256-entry turbo table, both into the layer's own buffer. A million points rewrite in about 6 ms solid and 11 ms colored by intensity on an M-series Mac, and an unchanged update takes under 0.1 ms (`dataLayers.perf.test.ts`, best of 8, run with `npm run perf:booleans`, which takes every `*.perf.test.ts`); a first version with a function call per point took about 170 ms. The test fails past one 16 ms frame solid and 24 ms colored, and when an unchanged update takes 1 ms.
- **Scan maps fuse off the main thread** (§8h, §12). `src/dataLayers/map.worker.ts` owns voxel accumulation and point-to-plane matching. Recorded results are cached by recording, scanner setup and matching choice. ICP uses at most 180 sampled points per flat sweep and targets 600 for 3D sweeps. Every decoded return still feeds voxel accumulation. Live sim updates transfer only touched voxel indices and centroids, including existing cells, and clear their worker session on stop. The client keeps a growing point buffer and publishes snapshots without rescanning the map for height bounds. The map caps occupied voxels at 1,000,000. Live `MapSession` transform history keeps 256 samples per edge and 4,096 placed sweeps, while imported tries retain the history needed for interpolation. `src/dataLayers/map.perf.test.ts` bundles the real core into a Node worker and checks a 200,000-point map against a 10-second budget. On an Apple M5 Pro with Node 26.13.0, 400,000 returns across 40 sweeps produced 200,518 occupied voxels in 512.3 ms with matching on. This is a local measurement, not a CI result. Run that one performance file with `vitest.perf.config.ts` to measure the budget on CI without adding timing assertions to Check.
- **Scan reconstruction stays in the mapping worker** (§8h). Make World reads complete supported sensor frames, retains ray origins and observed free cells, and greedily merges only occupied adjacent cells into at most 64 exact convex pieces. It never drops obstacles or fills gaps to meet the budget. Prepared world geometry and pieces transfer back as buffers, using the existing content hash and scene asset storage. Each job is bounded to 2,000,000 returns, 4,096 placed sweeps and 250,000 cells in each occupied/free set. A fresh Node worker per existing fixture on an Apple M5 Pro, Node 26.13.0, matching on, measured reconstruction plus hashing as follows. Heap and ArrayBuffers are end-of-call worker memory, not process peak RSS, and include retained intermediate allocations before GC. The machine was shared with other builds. - **Map tiles stream by distance and draw on demand** (§12). The Earth layer updates the tiles renderer only inside `RenderLoop.beforeRender`, so tiles load and refine only when a frame draws; a tile arriving asks for one redraw (`needs-update`, `needs-render`), and nothing renders once the view and the loads settle. Screen-space error picks each tile's detail from the canvas camera, so a tile near the camera loads finer and the rest stay coarse. Draco decoding runs in `DRACOLoader`'s workers, and `3d-tiles-renderer` loads as its own chunk the first time a scene has a place.
- **Autosave never re-serializes unchanged parts.** `sceneJson` caches each part's JSON by object identity, slices the work across frames and sends one string (`saveSceneJson`).
- **Comment attachments resolve in linear work.** `utils/annotationAttachments.ts` builds one part index per batch for canvas pins and scene exports. JSON and Markdown share the export's resolved comments instead of searching the scene four times per comment. `annotationAttachments.test.ts` checks positions, names, replies, missing parts and edits through both pipelines, with linear ID-read budgets for 300 and 600 parts and comments. The previous export read 721,200 part IDs on the 600-item fixture. Spatial relationship inference is separate and still compares visible part pairs.
- **No canvas reallocation during panel animations.** `CanvasSizer` keeps the canvas centred in its card, grows the drawing buffer once and shrinks it only after the size settles, and redraws synchronously after a resize so there's never a blank frame.
- **Image floods queue each open pixel once.** `utils/pixelFlood.ts` shares four-neighbor traversal between silhouette backgrounds and image-analysis backgrounds and holes. Candidates are marked before classification, so border duplicates and converging paths never repeat classification or queue an open pixel twice. Hole fills allocate no neighbor arrays per pixel. Corner-radius estimation applies the same rule to its two inward directions. `pixelFlood.test.ts`, `imagePixelAnalysis.test.ts` and `targetFit.test.ts` check boundaries, enclosed regions, measurements and traversal counts. A blank 128 × 96 photo took 49,152 stack removals before this change and 12,288 after it. This is an operation count, not a wall-clock measurement.
- **Photo border medians use fixed histograms.** `utils/silhouette.ts` counts RGB border samples into three 256-bin arrays instead of copying and sorting three channel arrays. It keeps the upper median, doubled corner samples, spread threshold and color-distance threshold. `silhouette.test.ts` checks those boundaries, RGB extremes, enclosed background, narrow images and source preservation. A scratch comparison matched the previous masks and refusal results on 600 seeded images. On macOS with Node 26.13.0, rejecting one seeded 900 × 900 busy image took a median of 2.23 ms before and 0.13 ms after, over 25 alternating measurements after five warmups per implementation. This measures the busy-background refusal path, without a CI timing assertion or a claim about full photo-tool latency.
- **Heavy work never blocks a click.** Cache by input identity (a `WeakMap` on immutable parts, or shape keys) and spread uncached work across frames with `await` between small chunks (`components/build/useBuildReport.ts`). Profile anything over 16 ms.
- **Ordered motion samples use binary lookup.** `utils/timeIndex.ts` locates time boundaries without copying or indexing a clip. Animation playback and validation, route control, intent pose sampling and tracked-base resampling share it. Exact-key and duplicate-key rules remain with each caller. The lookup test bounds a 65,536-key search to 17 timestamp reads, and motion sampling tests bound the full animation and route calls without wall-clock assertions.
- **Skeleton operations index the hierarchy once.** `utils/skeletonTree.ts` groups children in source order and indexes joints by id. Sizing, mirrored drags, agent skeleton text and motion link-mass estimates each create one index per operation. No index survives edits or undo. Subtree walks use an array cursor and a visited-id set. Sizing still computes every returned descendant radius and scans its point masses per joint, so total sizing work can remain quadratic. `skeletonHierarchy.scale.test.ts` bounds full-list reads on 100- and 200-joint chains, including a leg chain, and on wide drags. Before indexing, the 200-joint chain took 10,787,999 list reads for sizing, 40,400 for dragging and 80,200 for text. The tests now require fewer than 3,000, 1,600 and 1,000 respectively, including their source-preservation assertions. These are operation counts, without timing assertions.
- **Sketch solves prepare entity references once.** `utils/sketch/solver.ts` builds its entity map and arc list with the variable layout, then reuses them throughout the solve. Residual probes read current variable values without rebuilding the map or searching all entities for arcs. `solver.scale.test.ts` bounds entity-array reads to five per input entity, independent of the number of numerical probes. Its 80-line fixture with a circle and an arc previously took 161,868 reads.
- **Layers indexes groups once.** `layerRows.ts` builds each group's members in one pass, then uses those lists for expanded rows and search matches. It never scans the whole scene per group. `layerRows.scale.test.ts` checks scene order, complete group selection and collapsed/search results on 600 interleaved parts in 200 groups, with a linear budget for group lookups rather than a wall-clock limit.
- **Align and Spread index the selection once.** `utils/selection.ts` filters unlocked parts through an id set shared by both commands. Align applies positions through a set of the selected part objects. Membership work is linear in scene and selection size, with Spread also sorting the selected parts by position. The Inspector, right-click menu and command palette use these same helpers.
- **Duplicate naming indexes taken names once.** `workspace/helpers.ts` builds a set before checking copy suffixes for parts, groups, scenes and Library models. It keeps the first available suffix without rescanning every name for each occupied suffix. `copyName.scale.test.ts` checks gaps, case sensitivity, duplicate entries and unchanged input, and bounds name reads to twice the input size for 600 and 1,200 existing copies. Those fixtures previously took 180,900 and 721,800 reads.
- **Selecting groups uses membership sets.** `expandToGroups` scans the scene twice, collecting selected group ids and then their missing members. Ordered additions, group toggles and drill-in detection also use sets, keeping membership work linear in scene and selection size. `workspace/selection.scale.test.ts` checks interleaved groups, selection order and every selection subset for click modifiers, with array-read budgets on 600-part fixtures. Group expansion previously took 271,500 reads and a fully selected group toggle through a click took 543,301 reads on those fixtures.
- **Deleting parts prunes empty joint chains in linear work.** `utils/kinematicsPrune.ts` counts parent references once and queues empty leaves, releasing their ancestors as each last dependent disappears. `jointsWithoutParts` shares this cleanup between scene edits and Onshape updates. `kinematicsRemoval.test.ts` checks the resulting joints and bounds array-length reads on a 600-joint chain, without a wall-clock limit. The previous repeated scans took 180,302 reads on that fixture.
- **Joint renaming indexes each batch once.** `uniqueJointIds` tracks current-batch ids in a set for imported robot placement and scene normalization. Detecting a batch boundary never scans the preceding joints. `kinematicsIds.test.ts` bounds id reads for two 600-joint copies and checks suffix collisions, parent links, linkage drivers and unchanged-list identity. The previous batch scans took 726,603 id reads on that fixture. Suffix availability checks still search for one suffix free across the whole batch.
- **IK trials copy their matrix once.** `utils/kinematicsIk.ts` adds damping and the right-hand side while copying the normal equations into an augmented matrix, then eliminates that owned copy in place. Pose, gait, retargeting, arm fitting and driving share this solver. `kinematics.test.ts` checks mixed joints, root transforms, weighted targets, pose preference, excluded joints and unchanged inputs. Its locked-joint fixtures force six rejected steps: copied matrix values fall from 768 to 384 for eight joints and from 3,072 to 1,536 for sixteen joints. These are operation counts, without timing assertions.
- **Joint frame resolution shares mount transforms.** `resolveJoints` builds one matrix per used mount within each call, reusing it for every joint framed to that part. Unused mounts build no matrix, and no matrix is retained across calls. `kinematicsFrames.test.ts` checks rotated pivots and axes, moved mounts and undo, missing frames and unchanged-list identity. Its 600 joints on three interleaved mounts read three transforms, down from 600, without a timing assertion.
- **Print connected-component lookups compress their full paths.** `print/componentRoot.ts` shares an iterative map lookup across print-merge groups and print-label faces. Each caller keeps its existing root choice and output order. Both append to their own member arrays instead of copying a growing array per member. `print/componentGrouping.test.ts` checks membership, ordering, repeated joins, cycles, unchanged inputs and map-read budgets at 300 and 600 items. On the 600-item fixtures, total map reads fell from 721,798 to 4,792 for descending print joins, and from 368,996 to 10,198 for descending coplanar triangles. These are operation counts, without wall-clock assertions.
- **Rig group adoption indexes groups once per pass.** `utils/kinematicsRig.ts` summarizes each group's link owners before assigning unlisted parts, then summarizes robot components before adopting unlisted parts other than references into robots. An inferred owner only repeats its group's sole owner, so the first summary stays valid throughout adoption. Both passes take linear work in scene size, including one large group. `kinematicsGroups.test.ts` checks assignments and bounds group-property reads below 12,000 for 600 parts in one or 200 groups, with moving links and base-only mounts. The moving-link fixtures previously took 719,999 and 481,000 reads.
- **Agent mirroring indexes sources and existing twins once.** `agent/agentMirror.ts` builds both lookup maps in one scene pass, preserving first-match and request-order behavior. `agentMirror.scale.test.ts` bounds scene reads for 600 sources with and without existing twins, and checks all axes, renames and collisions. The previous searches took 540,300 reads without twins and 720,600 with twins. This bounds lookup work, not geometry mirroring or collision suffix searches.
- **Damping trials reuse unchanged matrix products.** Sketch and four-bar fitting prepare their weighted products or normal equations once per linearization, as IK and servo fitting already do. A rejected trial changes only damping, and an accepted step prepares the next system. `utils/dampedSteps.test.ts` checks repeated damping, singular recovery, source preservation and bounded Jacobian reads. Sketch keeps its original diagonal addition order.
- **Keep views alive.** Panels that switch (sidebar views, inspector tabs) mount on first use and then stay in React's `<Activity>`, so switching back is instant and hidden views run no effects.
- **DOM overlays follow viewport renders.** Comment pins and agent cursors project through the handle's `onRender` subscription, not separate animation loops. An empty comment layer and a hidden cursor subscribe to nothing. Comment cards also reflow through a `ResizeObserver` on the layer and card. A cursor animates toward its last projection only until it settles within 0.05 px, then stops requesting frames. Effect cleanup removes render listeners, resize observers and pending cursor frames.
- **A Case's code panels cost only what they draw** (§8h). The studio adds no render loop for them: a frame runs its own, out of the studio's renderer process. The bridge sends a frame only the signals it subscribed to, at most 20 times a second (a trailing timer, so the last value always arrives), never the whole bus, and the heartbeat is one small message every 500 ms.
- **Small payloads across IPC and HTTP.** Lists are summaries (`SavedSceneSummary`: counts, size, a small WebP preview); full records load on demand (`platformBridge.getScene`). Library JSON is written compact. Never send a whole library over IPC. Saving, renaming, duplicating or deleting a Library model, a scene in the Scenes menu or a chat changes the list on screen at once, then writes that one record (`withModel`, `sceneStore`); the list is read again only when the write fails. A scene's writes run in order, and opening it waits for them (`queueSceneWrite`). The desktop models-folder watcher sends only the record that changed, and skips the app's own writes (`ModelChanges`).
  - The browser lists `sceneSummaries` directly from IndexedDB, so listing scenes never clones every scene's parts and project. Saves read the previous preview and dimensions from the summary instead of cloning the old scene. Saves, previews and deletes keep the scene and summary together in one transaction (§5a). The version 4 upgrade reads old scenes one at a time to seed the summaries.
- **Plot ranges scan samples without copying them.** `design-system/tracePaths.ts` accumulates finite bounds directly from each trace's arrays for both axes, including explicit limits and zero. It retains only two bounds, regardless of recording length. All `TracePlot` callers share this path: console time and XY plots, try timeline lanes, calibration replay and torque envelopes. `traceRanges.test.ts` checks empty and flat ranges, non-finite samples, typed-array views, source preservation and one read per sample. A local Node 26.13.0 measurement on macOS used eight traces of 6,001 samples, both axes, five warmups and 25 measured runs. Median range calculation fell from 7.75 ms to 0.24 ms. This measures range calculation alone, not a complete repaint, and isn't a CI timing assertion.
- **Playing a try through its console costs one seek** (§8h, Playback). Opening a try builds every console signal once, in a task after the timeline opens (`recordedTrack`), and the half-second verdicts run in the judge worker; a seek then only moves the bus's frame and repaints the panels. Whole-try plots draw through `TracePlot`, which keeps a min and a max per pixel column, and the map keeps at most 600 points of the path. Camera panels render in the feed worker from the poses each seek posts. Measured on an M-series Mac for a two-minute try (6,001 frames, 26 signals): the scrub's efforts and forces take 169 ms in the sim worker, the probe trace 27 ms and the track 26 ms on the main thread, a seek 0.002 ms, and a seek with six panels repainted 3.5 ms (`playback.perf.test.ts`, run on demand with `vitest.perf.config.ts`, which fails over 16 ms).
- **Tries list from manifests only** (§8h). `TryStore.list` reads each `try.json` once and keeps its summary in `library/.try-summaries.json`, refreshed by the manifest's mtime and size like the scene library; a recording or filmstrip loads only when a tile or the timeline opens it. `npm run perf:tries` (`tools/perf/triesBench.mjs`) writes 5,000 tries through the store and lists them from a fresh store, failing over 200 ms. On an M5 Pro shared with other builds it took 70–90 ms with the cache file (up to 300 ms at a load average over 80), and about 1 s the first time, before the cache file exists; the list is 1.9 MB of JSON and parses in about 6 ms. The bench takes the best of three runs. Summaries leave out joint ids and faults to keep the list small.
- **React Compiler friendliness** (§0c) is a performance rule: one rule break makes the compiler skip the whole component, and everything under it re-renders on every change. One that isn't a Rules of React break: the compiler can't lower `try` without `catch`, so a handler in a component that resets a flag after an awaited call chains `.finally(...)` instead (`agent/ConnectionBanner.tsx`).
- **Boot never waits on anything it doesn't need to draw.** The window opens before the agent connects (`connectAcpAgent` runs in parallel; it used to delay the window 0.7–2 s, and status reads `connecting` meanwhile, so nothing says “disconnected”). Anything that needs a session awaits that first connect (`AcpAgent.pending`) instead of starting a second. Only the active tab mounts at first; background tabs mount one per idle callback after its first frame (`useMountedTabs`), since each builds its own WebGL context, environment map and shaders (about 60–250 ms apiece). Events for a tab that hasn't mounted are dropped, not refused: on mount it adopts its runs from the journal and the bridge replays unanswered requests. Measure boot with real scenes reopened (`open-scenes` in `localStorage`), not an empty one.
- **The CAD kernel never touches the renderer or boot.** Its sandbox windows open in the main process on the first compile (or 2 s after an MCP server starts), never during boot, and paint nothing (`show: false`, `paintWhenInitiallyHidden: false`, no WebGL); results pass through the main process as bytes it doesn't parse. A first compile costs about 0.15 s more than the old forked process (opening the window); later ones match it (guide examples: OpenSCAD 0.06–2.1 s, replicad 0.06–0.25 s, either host).
- **Dataset snapshots restore each source once** (§8h). Recording inspection, canonical hashing, context encoding and range restoration run in `src/datasets/snapshot.worker.ts`. Selected ranges sharing a recording hash load and decode it once per restoration. Worker replies and export jobs deduplicate shared transfer buffers. Frozen image restoration appends to locally owned arrays, and export indexes frames and classes once per set. `snapshotImages.test.ts` bounds frame-ID reads to three per image while restoring and exporting 40 images, avoiding repeated full-set searches.
- **Try search runs in a worker** (§8h). The index lives in `trySearch.worker.ts`; the main thread only passes query strings and manifests. `src/cases/trySearch/trySearch.perf.test.ts` builds 10,000 tries and fails a text query over 50 ms or More Like This over 200 ms. On an M5 Pro at a load average of 25: text queries took a median of 6.5 ms (p95 17.3 ms), More Like This 3.1 ms, the build 402 ms, and the 8.8 MB snapshot was written in 47 ms and read in 55 ms.
- **Measure in production:** `npm run build && npm run preview`, then time interactions with a `PerformanceObserver` for `longtask` entries. Dev mode adds 30–130 ms per interaction and misleads.

- **Repair planning** (§8b) runs in `guide/repair.worker.ts` after the analysis worker measures the target's exit paths. Its dependency search and reassembly proof receive plain topology, boxes and the guide plan. No mesh rebuilding or search runs on the renderer thread. The existing Build Along animator touches only moved parts and stops once each outward removal or inward placement finishes.
- **Removal and repair index screw relationships.** `assembly/fastenerIndex.ts` indexes screw ids and the parts each stack clamps once per operation. Removal order, service depth, minimum teardown, repair directions, insert preparation and reassembly proof use those lookups. Related screws keep source order, and no index survives the operation. `fastenerPlanning.test.ts` and `repairProof.test.ts` bound stack reads on 150- and 300-part fixtures while checking the resulting plans. On the 300-part fixtures, the previous implementations read stacks 45,150 times for blocked removal, 180,000 for minimum teardown and 90,000 for reassembly proof. Each now stays within 600 reads. These are operation counts, without timing assertions or a claim that the entire search is linear.
