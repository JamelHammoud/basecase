# Cases

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8h. Cases

A Case is a world with one to four robot slots, controls and goals that any compatible robots can enter. It lives in `src/cases/`.

- **A Case is the test.** A Skill (§8i) is a solution to it.
- **Case objects never edit parts.** They render on their own layer, and stay out of the BOM, Build Check and picking.

### Format

`src/cases/schema.ts` holds the Case type and `parseCase`, a hand validator that fails closed. A file with another `formatVersion`, an unknown shape, too many objects or a non-finite number throws, in plain words. A Case holds:

- **Slots:** a Case carries `slot` (one robot) or `slots` (1 to 4, each with an `id`); `parseCase` keeps whichever the file has, so an old one-slot file reads and writes back byte for byte, and `formatVersion` stays 1. `caseSlots` reads either as a list (a lone `slot` is named `robot`). The first slot is always the scene's own robot, where it stands. Every other slot has a `pose` (`position`, where the robot's pivot goes, and `yawDeg` about up) and is filled by another open tab's robot (§5a): `fillSlots` (`src/cases/caseCast.ts`) takes, for each slot in order, the first open robot that fits it. `placementOf` (`src/cases/slots.ts`) moves that robot to its pose and prefixes every part, group and joint id with `<slot>.`, so two copies of one arm never share an id; `castRobot` and `castSlots` join them into one robot list and work out each slot's robot key, facts and end effector (a guest's binding is checked on its own robot, then placed). `slotRefusals` reports each slot's misfit on its own; a slot no open robot fills says “This Case needs ⟨n⟩ robots. Open the others in tabs.” Reference commands may name a `slot` (the first when left out), and probe ends may name a slot's hand (`{ effector: <slot> }`); `parseCase` refuses a name that isn't a slot. Each slot holds the capabilities it needs (`arm`, `gripper`, `wheels`, `legs`), the bindings it was authored with (end effector, wheels, base), and the reach and anchor its world was authored at. `src/cases/robotFit.ts` works out what a robot has (a gripper through `findGripper`, §8c); `slotRefusal` says plainly why one doesn't fit. A bound end effector only counts on a robot where that part ends a chain (gripper jaws aside) and the bound point lies on the part, otherwise the fit finds its own (`boundEffector`), so a Case written on one arm binds the hand of the next.
  - **Anchor and reach are the shoulder's:** the anchor is the first chain joint that swings the hand (a base yaw under a straight-up arm doesn't), and the reach is the chain's length from there. Measured from a yaw joint, a five-joint arm with its shoulder 60 mm up read a reach no pitch could cover, so its scaled targets fell out of other arms' reach.
- **World:** `ScenePart`-shaped objects (`worldItem`), each `static`, `dynamic` or `marker` (no collision). An object marked `movable: true` (any other value is refused) can be moved, hidden or recolored by the Case's code while it runs (§ Code panels). `src/cases/scale.ts` scales the whole world and the reference to the entering robot's reach, so one Case runs on arms of different sizes. Objects and reference targets always scale in one frame: about the anchor, except that a Case whose slot needs a `gripper` (Pick Up a Block) measures heights from the floor. Scaled about a shoulder 50 mm up, its loose block would float on a smaller arm and start inside the floor on a bigger one. The frame comes from the slot, not from the objects: a Touch Case stays about the anchor even when the agent adds a loose ball, because its spots are only reachable relative to the shoulder. Pinning only the objects to the floor left the targets in another frame, so a shelf no longer sat under its touch point and a gripper closed above the block.
- **Controls:** typed inputs (`move`, `turn`, `lift`, `grip`).
- **Reference:** a command timeline (each command drives its `slot`). A command may carry `joints`, targets by joint id in degrees (mm for a slider), at most 64; an arm drive then holds exactly those targets and skips IK until a later command moves its aim (`ArmDrive.follow`), and a pose drive moves toward them as it does for the keys. An empty one must not pass, and the Stage 2 gate's canary checks that. `runCase` drives it with the same drive classes as live play (§ Live drive: arm, rover, legs). For an arm, `target` is where the hand goes and `aux[1]` closes its gripper (0 to 1). For a robot that moves around, `target` is a floor waypoint for its base, followed in order by `GroundSteer` (`groundSteer.ts`) from the base's pose each record tick: a rover turns toward it (in place past 60°), legs walk straight at it, forward and sideways at once, since their gait turns poorly in place. `v[0]` with a target caps the speed, and `push: <object id>` makes the target where that object must go: the base aims behind the object along its line to the target (legs aim past it), and stops when the object arrives. A command without a target is a plain velocity and clears the route. `ReferencePlayer` (`referencePlayer.ts`) plays the timeline for the live sim every frame.
- **Task:** seconds, probes (distances that become trace signals), a task contract, and an optional `score` rule (§ Logic).
- **Console** (optional, `src/cases/console/`): how the Case looks and drives when it runs: its input sources, its own signals, its panels and their layout (§ Running a Case). `consoleReader` checks it inside `parseCase` with the Case's probes in scope, so it fails closed like the rest. A Case without a console opens `DEFAULT_CONSOLE`, written in the same format, so the field fits the validator's optional fields and `formatVersion` stays 1; an old Case file parses and round-trips unchanged.
- **Logic:** an optional Routine (§ Logic). A Case without it runs as before, and a file written before it existed parses unchanged.
- **Gestures** (optional, `src/cases/gestures.ts`): the movements the person teaches this Case (§ Input sources, Gestures). Each is a lowercase `name` and up to 3 `examples`, each up to 45 frames of exactly 39 numbers within ±10; at most 8 gestures, no repeated or built-in name. A list over a cap is refused before its items are read. A gesture with no examples is one the Case waits for the person to teach.

A Case's task contract is the one contract of §8i, judged by the Rust crate through `src/skills/contract.ts`; `src/cases` keeps no evaluator of its own. `src/cases/contract.ts` only reads it as bounded plain JSON (version 1, depth 64, 4096 nodes, finite numbers, at most 16 failures) and scales it with the world (every atom's value and scale, except atoms that read an `angle`). `runCase` (`src/cases/runCase.ts`) runs a Case headless in Node or a worker: it checks every slot's fit (`options.partners` fill the slots after the first), scales the world, builds one model with every slot's robot, drives each slot (`teamDrive`: one `TeamSetup` whose members are the slots' own drives, and a command's `slot` picks the member) and judges the trace with `evaluateContract`; `options.limp` leaves named slots limp (their actuators get no force); `CaseResult` carries that `trace` and the `failed` labels, and a contract the crate refuses makes `runCase` reject. `scoreTry` judges a recorded try the same way.

### Seeded runs

A clean run in a perfect world says little about the real robot, so Checks judges every Case across randomized runs (§8b).

- **`RunOptions.seed`:** without one, `runCase` runs the perfect world as before. With one, it draws the same `Randomization` Arena uses (§8i: friction, link masses, servo strength, servo delay; default `CASE_RANDOMIZATION`, Arena's floor with delay up to 20 ms) from a stream seeded by `case-run|<seed>` (`caseRandom.ts`), and applies it through Arena's own `ArenaWorld` (`prepare`), with no joint noise and no change to the start pose, since the reference's waypoints assume it. A second stream (`worldRandom`: `caseRandom(-seed - 1)`) moves each `dynamic` world object up to 15 mm each way along the floor (`jitteredWorld`); a static object with a `jitter` (`{ mm, deg }`, a room's furniture, § Rooms) moves up to `mm` each way and turns up to `deg` about up; other static objects and markers stay put, unless the caller passes `{ spots: true }`, as Multiply does (§ Tries). The same seed always gives the same result.
- **Controller:** the reference, or with `RunOptions.walk` a ready Walk policy for any robot that moves around (not a fixed base), bipeds and wheels on legs included, as Drive picks it (`driveAccess`). An arm Case still drives the arm. The Walk follows ground targets like scripted legs (`LEGS_FORWARD`, forward and sideways at once), and the steering commands go through `policyCommand`, like the keys. `caseRunner(…).controller` says which one a Case will use.
- **`caseRunner`** does everything that doesn't depend on the seed once (rig, fit, scaling, the drive setup and its baked gait), and `run(seed)` builds the jittered world's model and rolls it. `runCase` is `caseRunner(…).run()`.
- **`runCaseTimes`** (`caseRuns.ts`) runs seeds 1 to N (`CASE_RUNS` = 20) and returns the passes, the median margin, the failure labels ranked by how many runs failed each (`failures`, the first is `commonFailure`; `missed` for a run that failed no named failure) and `worstSeed`, the seed of the failed run with the lowest margin (the lowest of all when every run passed). `runSeeds` and `summarizeRuns` are the same split in two, so the Checks workers can each take a batch of seeds (`caseCheckJob.ts`). `runSeeds` refuses before any run: with `slotRefusal`'s words (`misfit`), else with `options.stop`, the robot's fit (§8b).
- **Tests** (`caseRuns.test.ts`): same seed, same result; a limp robot gets 0 of 20 on every template, each on a fixture it fits; the fixture rover reaches the flag 18 or more of 20; the weak quadruped fails Walk Without Falling by falling; a misfit's row carries the refusal; a biped, a wheel-legged robot and a quadruped with a Walk run on the policy, and a fixed arm ignores it. Seeded fault: the rover on 0.25 N·m wheel motors passes Reach the Flag 20 of 20, and cut to 30% it fails every run.

### Comparing two robots

Two versions of a robot, say one per gripper, are compared on the same Case: duplicate the scene, change the design, and run the Case on both.

- **Compare With** (the open Case's right-click menu in the Cases view, and ⌘K as Compare with ⟨scene⟩) lists the other open tabs whose robot fits the Case (`comparableRobots` in `src/cases/caseCompare.ts`: `slotRefusal` on the Case's slot, read through `studio.robotsBeside`, §5a). Only Cases with one slot are offered. `useCaseCompare` (`src/workspace/`) refreshes the list in an effect while the tab is in front, since `robotsBeside` is never read during render.
- **Runs:** `compareCase(kase, robots, { runs, purchases })` gives every robot the same `runs`. In the app that's `caseVerdict` (`src/workspace/caseChecks.ts`, the same call as `run_case`), the Checks row's own path: seeds 1 to 20 in the Case workers, the Case scaled to each robot's reach by `caseRunner`, and one verdict cache keyed by the Case, model and Walk hashes, so a robot whose Checks row already ran answers at once. Model readings are cached per geometry (8 kept). Comparison jobs carry an empty tag, so a Checks rerun's `keepOnly` never drops them.
- **Cost and mass** come from the existing code: `buildBom(…).totals.estimatedUsd` (`utils/bom.ts`, with no print report, so without support filament) and `robotWeight(…).all.grams`, the Weight check's mass (`utils/engineering.ts`).
- **Results** shows the two robots first, as two rows: the scene's name, passes out of 20, then cost and mass. A robot the fit check stops (it falls on hold, its model won't compile, it fails the fall check) shows the stop's words in place of the count, truncated, with the whole text in its tooltip. The median margin stays out of the row: it has no unit a person can read, so only `compare_case` returns it. `betterOf` marks the higher pass rate with the accent; a refusal counts as no passes, and a tie marks neither. Clicking the other robot's row calls its tab's `openCase` (it opens that scene's Case with the same id, or adds this one) and selects the tab.
- **Reruns:** nothing is saved. A result is keyed by the Case's hash, this scene's readiness fingerprint and the other tab's (`handle.fingerprint()`), and checked again when the Case or this scene changes and when the tab comes back to the front; another scene can only be edited while it's in front, or by its agent. `newestComparison` (`src/workspace/newestComparison.ts`) keeps the key last asked for, and a run that lands for any other key is dropped, so a run started for an edit that was then undone never replaces the rows. A failed run keeps the last rows and shows its error as a toast. Runs in flight are shared by key, so `compare_case` on the open Case and the rows it starts measure each robot once.
- **Agent:** `compare_case` returns the same rows (§9).
- **Tests** (`caseCompare.test.ts`): the fixture rover on full wheel motors beats one cut to 30%, on the same 20 seeds; an arm never lists for Reach the Flag; cost and mass equal `buildBom` and `runEngineering`'s. `newestComparison.test.ts` covers an edit undone while its run is going, a redo, and a failure. `caseChecks.test.ts` checks that a comparison's runs carry an empty tag and that the robot's Checks row reuses their verdict. `e2e/buildCheck.e2e.test.ts` opens two tabs with the rover, weakens the second's servos, runs Compare With from ⌘K and checks both counts and the mark.

### Exploring servo versions

**Explore** (an icon in the open Case's header in Simulate, Stop while it runs, and ⌘K) runs the open Case on versions of this scene's own design and lays them out in Results, so a person learns which servo to buy before ordering.

- **The space** (`src/cases/exploreDesigns.ts`): `exploreSpace` makes one group per movable joint, in `servoLayout` order, whose actuator parts are all one catalog component with two or more variants that carry an `actuator` (a part already in an earlier group skips the joint). The current design is each group's variant and `servoSupplyVolts` (the Servo torque check's supply: the battery or regulator rail, else the tether, set or suggested). Voltages are the current one, then every variant's `atVolts` that the robot's other servos suit; a robot with a battery (`findPowerSources`) keeps its voltage. Mass doesn't change: a component's variants share its catalog weight.
- **Designs:** `exploreDesigns` yields the current design first, then each variant on every group at once, then one group at a time, then two, and so on, each at every voltage; it keeps a design only when every servo, swapped or not, `suitsVolts`, drops repeats, and stops at `MAX_DESIGNS` (64) or after 4,096 candidates. The order is fixed by the joints and the catalog, so the same scene gives the same list.
- **Runs:** `exploreCase` (`src/cases/explore.ts`) builds each design with `designScene` (the parts with their `componentVariant` swapped, and on a tethered robot a `tether` at the design's volts when the supply wouldn't already be that) and calls `runs` with the design's `servoVolts` (§8d: every servo rated at that voltage). In the app that's `exploreVerdict` (`src/workspace/caseChecks.ts`): a `model` job, then `EXPLORE_RUNS` (8) seeded runs batched across the Case workers with the reference controller, with an empty tag so a Checks rerun's `keepOnly` never drops them, and no verdict or model cache, so a sweep never pushes the Checks rows out. Designs run one after another; Stop (or a newer Explore, or the agent's) stops before the next design. `CaseRuns.worstMargin` is the lowest margin of the runs.
- **Cost and mass** per design are `robotTotals` (§ Comparing two robots): `buildBom` and the Weight check's `robotWeight`.
- **Results** (`ExploreRows.tsx`) shows a header to sort by Passes (the default, highest first), Cost or Weight (`sortRows` in `src/cases/exploreSort.ts`, ties broken by the other two, then the run order), then one row per design: its label (`designLabel`: the changed joints and the variant's short name, `All` when every group changed, and the volts when they changed; the first design's row carries the scene's name), passes of 8 or the stop's words, cost and mass, and a progress bar while it runs. The row whose design matches the scene now (`sceneDesign`) is in the accent and has no Apply.
- **Apply** (on a row's hover) calls `commitDesign` (`useSceneDocument`): the swapped parts and the tether in one history step. A snapshot that carries `tether` restores it on undo and redo; other steps leave the tether alone, since tether edits in Build aren't history steps.
- **Reruns:** nothing is saved. `useCaseExplore` keys its rows to the Case's hash and `exploreBase`, the readiness fingerprint of the parts with the explored servos' variants blanked, so applying a row or undoing it keeps the rows, and any other edit hides them.
- **Agent:** `explore_case` returns the same rows (§9).
- **Tests** (`src/cases/explore.test.ts`, on `servoArm` in `src/sim/fixtures/servoArm.ts`: `arm-3dof` with an STS3215 per joint, C001 at the shoulder and C044 beyond, and a 500 g hand): the space and its 7.4 V and 12 V; 64 designs, the current first, the same every time, no C001 at 12 V; `designScene` and `sceneDesign` round trip and pin a tether when the suggestion would differ; the arm as built passes Touch the Dots 8 of 8 and a C046 shoulder passes fewer, with cost and mass equal to `buildBom` and `robotWeight`; Stop. `agentCaseRequests.test.ts` checks `explore_case`'s reply and refusals. `e2e/explore.e2e.test.ts` loads the servo arm with Touch the Dots, limits Explore to 2 designs through `__studio.exploreLimit`, runs it from ⌘K, applies the other row, sees the BOM lose its C044 line, and undoes it with ⌘Z.

### Headless

`basecase check <scene.basecase> [--case <id>] [--json]` (`tools/cli/basecase.mjs`, the package's `bin`, run through jiti like `npm run gallery`) runs a saved scene's Cases in Node, so a robot's Cases can gate CI. No window, no Electron and no network: the bin replaces `fetch` with one that refuses. jiti can't load Vite's `?url` imports, so the bin aliases each one the scene code reaches (Manifold's wasm) to an empty URL (`tools/cli/assetUrl.mjs`); Node finds the wasm on its own. Help: `site/content/help/check-your-robot-in-ci.md`.

- **One loader, one runner.** It reads the file with `decodeSceneFile`, the parser Open uses, and every Case through `parseCase`; a Case the validator refuses (a path-traversal id, a bad number) refuses the whole scene, where the app quietly drops it. `sceneRobot` (`src/cases/sceneCheck.ts`) builds the robot as the canvas does: `headlessParts` (`src/three/headlessParts.ts`) builds every part with `buildPartGroup` (the part layer's options), measures them with the analysis pool's `measuresIn`, takes each part's triangles with `localTriangles` (what `viewport.partTriangles` calls) and adds fastener followers with `jointsWithChains`. `checkCase` runs a Case through `runCase` with the reference controller.
- **Meshes:** catalog parts load their GLB from `public/parts/` (ids checked with `isSafeFileId`). Parts the agent modelled use the mesh the scene stores (`part.cad`), so the CAD kernel never runs. A sourced part (Added by Agent) keeps its mesh in `library/`, outside the scene file, so it builds as its placeholder box.
- **Runs:** each Case runs once in the perfect world, unseeded. The line gives passes of runs, the margin and the failed label: the refusal, the first named failure, or Missed (the word Results uses for a missed try). A Case is under its bar unless every run passed.
- **Output and exit codes:** one line per Case (name, “1 of 1”, margin, failure), or `{ cases: [{ id, name, runs, passes, margin, failed }] }` with `--json`. It exits 0 when every Case passes, 1 when any is under its bar, and 2 when it can't check: no such file, not a scene, a refused Case, an unknown `--case`, no Cases, or bad arguments.
- `basecase export <scene.basecase> --package <dir>` writes the Robot Package (§8d) from the same loader (`scenePackageFiles`, `src/sim/robotPackage/scenePackage.ts`): rest pose, the scene's active calibrations, no policies (a scene file carries none). Every file path must land inside `<dir>`.
- **Tests:** `tools/cli/basecase.test.mjs` runs the bin as a child process on a scene made in code, the fixture rover on 0.25 N·m wheel motors with Reach a Spot: exit 0 with its JSON; wheels at 30% strength exit 1 with Missed; a missing file, a file that isn't a scene, bad arguments and a `../../etc/passwd` Case id exit 2; the CLI's verdict and margin equal `runCase` on the same robot built from the fixture's own meshes; export writes the package.

### Making a Case

`src/cases/caseBuilder.ts` turns a goal, a world and numbers into a Case and runs it through `parseCase`, so a built Case is the same format as any other. It's pure, so `caseBuilder.test.ts` builds every goal in every world it suits on the fixture robots and runs some in MuJoCo.

- **Goals** (`caseGoals.ts`), each with editable numbers and defaults sized to the robot (`goalDefaults`): Reach a Spot (stop on a spot ahead; wheels or legs), Push a Box (a dynamic cube onto a spot; wheels or legs), Follow a Path (spots in order, swaying left and right; wheels or legs), Walk Without Falling (travel from the start; legs), Touch a Point (the end effector on a sphere; arms), Pick Up a Block (an arm with a gripper lifts a dynamic cube and sets it on a spot) and Hand Off to a Spot (`handoffGoal.ts`: two arms; offered only while another open tab holds an arm, `CaseGoal.pair`). `goalsFor` lists only the goals the robot can try. Touch a Point has a Dots count (1 to 3). With one, the point starts on the lowest spot ahead from `dotSpots` and Distance and Height move it. With two or three, the dots are the first spots `dotSpots` finds (Distance and Height hide; `CaseGoal.fields`), touched in order (a `sequence` of holds, the reference moving to each 1.8 s apart), and the Case is named Touch the Dots (`CaseGoal.title`); an arm that reaches fewer spots is told to lower Dots. Either way the Case carries the arm's reach and anchor, so it scales to other arms. `dotSpots` (`dotSpots.ts`, computed once per robot in `builderRobot`) puts spots in the vertical plane straight ahead of the anchor, at 0.85 × reach and 60°, 30° and 0° up (more angles if one is too low), keeping those the arm's IK reaches; any arm with two pitch joints can reach that plane, so the spots carry to arms that only bend forward. Only an arm that reaches none of them falls back to posing its joints.
- **Pick Up a Block** (`pickGoal.ts`, offered only when `robotFit` finds a gripper, open floor only): a cube 0.7 × the gripper's opening (density 0.5 g/cm³) on the floor straight ahead of the anchor (Distance, default 0.4 × reach) and a marker spot farther out on the same line (Spacing, default 0.25 × reach, down to 50 mm here where other goals stop at 200 through the goal's `bounds`), so an arm that only pitches can carry it. The contract is a `sequence`: the cube rises more than half its size (`delta` of a probe from the cube to a point 1 km under it, so it reads the same after scaling), then its centre is within Radius of the spot for the last 0.3 s. Pushing it there never lifts it, so it fails. The reference is a timeline built from the scaled world: above the cube, down to grip height (the cube's centre, or higher so the fingertips clear the floor by 4 mm), grip, up to twice the cube plus the finger depth, over the spot, down, release, up; each step waits its distance at the drive's speed × 1.4 plus 0.4 s, 0.6 s to grip or release, and Time defaults to the last step plus its move and 2.2 s, rounded up to a whole second.
- **Hand Off to a Spot** puts the point where Touch a Point would, and the second arm (slot `b`) facing the first (slot `a`, `yawDeg` 180) with its shoulder mirrored through the point, so the point sits the same distance from both. The reference sends `a` to the point at 0.2 s, then at 3 s sends `a` back to its resting hand and `b` to the point. The contract is a `sequence`: `a` holds within the radius for 0.2 s, then `b` holds there for 0.2 s while `a` is outside it. It's the stand-in for handing off a block, until arms with grippers can pick one up. The fixture six-joint arm paired with itself passes it in MuJoCo, and fails with `b` limp (`slots.test.ts`). The robots' geoms don't collide with each other (§8d), so the two hands can meet.
- **Ground references** are waypoints (`GoalPlan.waypoints`), routed around every static object by `groundRoute` (`groundRoute.ts`; a world's pushable objects count as static here, so a room's chairs are passed, not shoved): a leg that crosses an object grown by the robot's half-size plus 80 mm detours past its nearer side (an object whose bottom is above the robot's top, like the wall over a doorway, isn't in the way), and a waypoint inside the grown box shrinks the growth until it's outside. Reach a Spot and Walk go to their spot (Walk to 1.25 × its distance), Follow a Path through each spot, Push a Box lines up behind the box and pushes it onto the spot at 0.3 × speed. The box is sized to the robot: half its width, and on legs 1.3 × the body's height, so it meets the body instead of passing under it or between a rover's front wheels. In the Block world, Push a Box puts the block between the robot and the box, with room to get around it and line up again, and every ground goal gets more time (5 s on wheels, 8 s on legs). Every ground goal on a legged robot also fails on a fall (the `fell` failure: the base drops below half its start height). Height is a distance probe to a point 1 km under the start (`FLOOR_PROBE_DEPTH_MM`), since probes only measure distances.
- **Worlds** (`caseWorlds.ts`): Open Floor (every goal); Corridor (a wall each side of the route) and Block (one in the way) for ground goals; Rough Ground, Steps and Slope for every ground goal but Push a Box (§ Terrain); Shelf (a box under the point) for Touch a Point; and a scanned room once one is dropped (§ Rooms). A static object over the robot's footprint is refused with the fix (“Move the goal farther ahead…”).
- **Terrain** (`terrain.ts`): three `ground` worlds, built only of static boxes, so MuJoCo needs no height field. Each carries one number of its own (`CaseWorld.param`), shown after the goal's numbers (`caseFields`) and clamped like them: **Height** (`riseMm`) for Rough Ground and Steps, **Incline** (`inclineDeg`, 2–40°) for Slope. Defaults come from the robot's pivot height, which is the hips on legs and the axles on wheels: Rough Ground 0.1 × on legs and 0.3 × on wheels, Steps 0.1 × and 0.5 ×, Slope 8° on legs and 12° on wheels. On the fixtures that's 14 mm for the small quadruped, 10 mm for the hexapod, and 10 mm rough or 18 mm steps for the rovers; the quadruped trips on an 18 mm step and the hexapod on 24 mm, so the defaults sit under what they can do. Rough Ground is a grid of tiles across the route's width, from just ahead of the robot to a body length past the goal, each `riseMm` × 0.2–1, drawn from a fixed stream (`roughSeed`) and shaded lighter as they rise. A tile is half the foot spacing on legs (the closest pair of root joints, `BuilderRobot.footSpacingMm`) or a wheel's diameter, grown until the grid holds 192 tiles. Steps is one platform `riseMm` tall, a body long, to climb onto and step off. Slope is a ramp up, a top a body long and a ramp down; each ramp runs 1.5 body lengths, so its height is that run × tan(incline) and a steeper Slope is taller over the same ground. Steps and Slope start a quarter body ahead of the robot, and all three give every ground goal Block's extra time. Push a Box isn't offered on them: the box slides on the floor and catches on a tile or the platform's riser, so its reference failed on every fixture robot on Rough Ground, the rover and quadruped on Steps and the rover on Slope. The route crosses terrain: `groundRoute` takes `stepMm`, the terrain's top (`topOf`, a turned box's highest corner), and ignores any static object no taller. Ground worlds never scale, since a ground slot carries no reach.
- **Seeded terrain:** a seeded run (§ Seeded runs) also reshuffles the Rough Ground heights among its tiles from `worldRandom(seed)` after the jitter (`reseededGround`), so every run meets another grid with the same heights. A higher Height or Incline never lowers the ground anywhere for the same seed. A replayed try keeps its grid, since a variation must keep its model. `terrain.test.ts` builds every ground goal on every fixture robot on each terrain, checks the route crosses it, the same seed gives the same grid, and a higher number never lowers the ground. In MuJoCo, the quadruped and hexapod walk across default Rough Ground and miss it limp, and the weak quadruped misses Steps. The rover climbs the default Slope. A rover with round wheels and 0.06 Nm motors climbs it too, and at 30% strength misses it while still crossing Open Floor; the box-wheeled fixture rover climbs any Slope at 30%, since flipping its square wheels takes more torque than the incline does.
- **Name** is the goal and world (“Push a Box in a Corridor”); the id is its slug, made unique by `add` (`uniqueCaseId`). New Case has no Name field: Rename (the Case's right-click menu, or Rename Case in ⌘K for the open Case) opens the shared rename field on its row (`useCaseNames`), up to 80 characters (`MAX_CASE_NAME`). The id never changes, so its tries, the skills trained for it and its Checks row stay with it. A skill keeps the name it was trained under, and a dataset published afterwards takes the new name.
- **Presets** (`CASE_PRESETS`, `presetsFor`, `presetCase`) are named specs for Cases other code needs by id: `touch-the-dots` (Touch a Point with 3 dots) and `reach-the-flag` (Reach a Spot on Open Floor, a 320 mm marker 900 mm ahead). The gallery bundles and the Stage 2 gate build them; the app offers no list of them, since New Case makes the same Cases.
- A limp robot must miss every built Case; Walk Without Falling exists instead of a bare “stay up”, because joint friction holds a limp robot standing.
- `useCaseBuilder` (`src/workspace/`) holds the builder's open state, the robot's facts, the partner arm it read from the other open tabs when it opened (`BuilderRobot.partner`), and `create` (adds through `useCases.add`, then opens it). New Case is the only way to start a Case in the app, besides Ask the Agent.

### Cases from the robot

A run the robot faulted on becomes a Case the design must pass from then on (§8k Run buffer and Replay in Sim).

- **Built** by `replayCase` (`src/cases/replayCase.ts`), through the builder's own `builtCase` (`parseCase`), from the run the store kept: the first measured pose is a command at 0 s, then every intent sent after it plays at its own time from `REPLAY_LEAD_S` (1.5 s), so the arm has reached the start pose first (`replayTimeline`). Intents are joint targets in degrees, rounded to 0.001°; repeats within 1e-4 rad are dropped and the rest thinned to 4,000. The slot needs an arm and carries no reach or anchor, so nothing scales. The world is the open Case's, scaled to this robot, or Open Floor. It's named “Fault at ⟨time⟩” (`clockTime`, “Fault at 2:32 PM”) and briefed with the daemon's message, and lasts the last command plus 1.5 s, rounded up.
- **Contract:** the `torque` signal stays under `STALL_SHARE` (0.98) from the lead to the end. `torque` (a Case signal, `CASE_SIGNALS`, so it never scales) is each record tick's highest joint torque as a share of that actuator's force cap, the most its servo can push (`torqueShare`, `src/sim/torqueShare.ts`); `runCase` and `LiveCase` read it from the engine, and the `Recorder` keeps it per frame (`Recording.torque`), so `scoreTry` judges a try on it. Tries recorded before it have none.
- **In Results** the live run's Peak torque rows show each joint against its stall, the faulting joint among them, and the Case's Checks row reruns it after every edit like any Case.
- **Tests** (`replayCase.test.ts`): the timeline starts at the measured pose and plays every intent within 0.02 rad at its time; the Case round-trips through `parseCase` and refuses a joint id that isn't plain; a shoulder lift recorded with a 700 g hand fails on a C046 shoulder (torque at its cap) and passes on a C018 (peak under 0.8).

### Rooms

A room scanned with Apple's RoomPlan becomes a Case world at true size. Dropping its CapturedRoom JSON (the Codable form RoomPlan apps write) on the canvas opens New Case with the room picked as the World, named after the file (“Reach a Spot in Living Room”). Only the JSON is read, not RoomPlan's parametric USDZ: three's `USDLoader` parses USDC, but its output was never checked against a real RoomPlan export, and the JSON already carries every category and box.

- **Reader** (`roomPlan.ts`, pure, in the page): reads `walls`, `doors`, `windows`, `openings` and `objects`, each with `dimensions` (metres) and a 4×4 column-major `transform` (16 numbers, or four columns of four), and a `category` (a string or Swift's one-key object, `{"table": {}}`). It fails closed with `CaseFileError`: over 8 MB, over 1024 entries in a list, a non-finite number, a side over 50 m or under 0, a transform that isn't a turn and a move or sits over 500 m away, a category that isn't a plain word, or nothing in it. The drop shows “Couldn’t import ⟨file⟩.”
- **Mapping** (`roomWalls.ts`): metres become mm, the room turns so its walls run along the axes (the length-weighted mean wall angle, folded to 90°), and the lowest wall bottom becomes y = 0. Each wall becomes static 100 mm thick boxes, split along its length at its doors, openings and windows (by `parentIdentifier`, else any parallel one within 300 mm of its plane): a door or opening clears the wall from the floor to its top, a window keeps the wall under and over it. Each object becomes a box named after its category (`washerDryer` → “Washer Dryer”, `roomFurniture.ts`); a chair, or storage no side of which is over 600 mm, is dynamic (5 kg and 8 kg), the rest static. A table keeps only its top, 40 mm thick at the top of its box: RoomPlan gives no legs, and a solid box would hide the floor a rover drives on beneath it. Each static piece carries a `jitter` from the scan's `confidence` (Swift's one-key object or a string): high or none ±50 mm and ±5°, medium ±75 mm and ±7.5°, low ±100 mm and ±10°. Doors stay out of the world (`roomDoors`, `Room.doors`, markers named Door) so they can be targets. A box within 1° of square to the axes gets no rotation (a quarter turn swaps its sides) so routing sees its true footprint. Over 256 objects keeps the largest by volume, never fails.
- **World** (`roomWorld.ts`): `roomWorld(room)` is a `CaseWorld` with `trueSize`, so the Case is built without the slot's reach and anchor and `scaledToReach` never rescales it. The room moves so the open floor spot nearest the middle of its walls lies under the robot (`openSpot`: a grid from the middle out, the first spot no wall or object grown by `routeClearance` covers, using `groundRoute`'s `occupied`), and goals plan from there as on the floor. It offers Reach a Spot, Push a Box and Follow a Path; Touch a Point only when a static object whose top is 400–1100 mm high lies within the arm's reach of its anchor (`tableInReach`). A table is only its top, so the arm must reach the tabletop itself: the fixture arm on the floor doesn't reach the fixture's 750 mm table, and `roomWorld.test.ts` lowers it to 400 mm for Touch a Point. Room objects fill what's left of the 256 after the goal's own.
- **Tapped start** (`roomPlan.ts`, `roomWorld.ts`): a file from the scan app (§8m) carries a top-level `basecase` object, `start` in metres in RoomPlan's frame and `heading` in radians about +y (0 faces +z). The reader turns both with the room and sets the start on the floor (`Room.start`, mm). `placedRoom` uses it when it lies within the walls' bounds and no wall or object grown by `routeClearance` covers it (`tappedStart`): the room turns about the start by the quarter turn nearest the heading less the robot's own forward (`BuilderRobot.forward`: `roverForward` of the wheel axes for a rover, +z for legs, as `runCase` steers), so the robot faces it, and moves so the start lies under the robot. Anything else falls back to `openSpot` with the room unturned: a start that isn't three finite numbers within 500 m, a heading that isn't a finite number, a start inside a wall or furniture, or outside the room. A bad `basecase` never refuses the file, and other unknown fields are ignored.
- **Named targets** (`roomTargets.ts`, `namedSpots.ts`): in a room, Reach a Spot's spot and each of Follow a Path's spots can be a target by name instead of by distance (`CaseSpec.targets`, one name or `null` per spot; `GoalSpot` in the goal's `plan`). `roomTargets` lists each door, then each static piece, numbered when names repeat (“Table 2”), placed the way `placedIn` places the room. A target's spot is the open floor nearest the object on a 50 mm grid: no wall or object below the robot's top, nor the target itself, grown by `routeClearance` covers it; ties go to the spot nearest the object's middle (the middle of its longer open side), then to the robot. A door's is in its doorway. A static piece whose underside clears `BuilderRobot.heightMm` (a table's top, for a rover) also gives Under ⟨name⟩, centred beneath it, when the floor there is open. `targetNamed` matches the words a person uses: every word of the target's name, and each asked word that's “under”, a number or a word of some target's name, so “under the kitchen table” is Under Table and “table 2” never falls back to Table. An unknown name is refused with the room's names (“Pick a target in ⟨room⟩: Door, Sofa, Table, Under Table.”); a target outside the room world asks for it. Named spots skip the goal's distance problem. Unless the time is given, it grows to the straight trip from the start through every stop in the plan's `waypoints`, named or placed by distance, at 100 mm/s on wheels or 60 mm/s on legs (`tripTimed`, which replans with the new time; Under Table in the fixture room gets 23 s), and New Case shows it (`specValues`). `roomTargets` keeps its list per room (a `WeakMap`) and per robot start, facing, footprint and height, so New Case's hook, `specValues` and the preview share one grid search, and a rebuilt robot object that stands the same way searches again only when one of those changes. `create_case` refuses a path whose `target` names fewer or more spots than Follow a Path allows (“Name 2 to 8 spots for Follow a Path.”) instead of filling the rest by distance, and a Reach a Spot whose `target` names more than one (“Name one spot for Reach a Spot.”) instead of using the first. The reference route (§ Making a Case, Ground references) treats the room's pushable chairs and storage as in the way too, so it passes them instead of shoving them. New Case shows a **Spot** row for Reach a Spot in a room (**Spot 1**… for each of Follow a Path's spots, `RoomTargetPicker`) with Ahead and the targets; picking one hides Distance.
- **Jitter** (`roomJitter.ts`): seeded runs move each static piece within its `jitter` (§ Seeded runs). Walls and doors never move. A draw that leaves a piece overlapping a wall more than it did is drawn again, up to 8 times, then the piece stays. `roomWorld`'s objects narrow each piece's jitter so its farthest reach, `mm` plus its half diagonal times the turn, stays outside the robot's start box (its pivot, ± half its larger footprint side), and drop it when there's no room. The same seed gives the same layout.
- **Entry:** `useCanvasDrop`'s `routeFiles` sends `.json` files to `readRoomFile` (`src/workspace/roomImport.ts`), then `showRoomCase` opens the Cases tab and `useCaseBuilder.startInRoom`, which keeps the room for New Case until another is dropped. The room renders on the world layer like any Case world.
- **Tests:** `roomPlan.test.ts` reads the fixture room (`roomFixture.ts`: two rooms joined by a door, a window, a sofa, a table and a chair) and checks the gap at the door, the table's box, a room scanned at 25°, the 256 cap and crafted files that must be refused; `roomWorld.test.ts` checks the goals offered and the start spot, and runs a rover's Reach a Spot through the doorway in MuJoCo (the reference passes, limp misses). `roomTargets.test.ts` checks the targets offered to the rover and to a robot taller than the table, the door's spot in the doorway, Under Table centred beneath it, Follow a Path Sofa → Door → Table through open floor, the words matched, Under Table in MuJoCo (the reference passes, limp misses) and 20 seeded runs, each with its own layout (all 20 pass). `roomJitter.test.ts` checks over 50 seeds that walls never move, furniture stays within its jitter and never further into a wall or onto the start box, the same seed's layout, the narrowing near the start, and Multiply's turn. `agentCaseRequests.test.ts` makes the Cases from the agent's words. `roomStart.test.ts` checks a tapped start and heading, a rover turned to drive along x, a room scanned at an angle, the scan app's own file (`e2e/fixtures/scanned-room.json`) and every start that must fall back (exploit tests, §0h). `e2e/room.e2e.test.ts` drops the room through `__studio.dropFiles`, makes Reach a Spot in it, drives the rover through the doorway with W and records a passing try; makes Reach a Spot with Under Table from New Case and records the reference drive's passing try; it also drops the scan app's file and checks the table lies where the tapped start puts it, within 10 mm.

### World layer and guest robots

World items go into `MjcfInput.world`, written by `src/sim/mjcfWorld.ts`. They are bodies in `SimModel.bodies` with `parts: []` and `world: [id]`, so `simDeltas` never sees them and `worldDeltas` gives their poses. They never join `parts`, so they skip the BOM, checks and stop-on-edit.

Opening a Case stages it (`stageCase`): the world is scaled to the scene's robot, the extra slots are filled from the other open tabs, and `sim.setWorld(items, guests)` hands the live sim the world items and the guests' placed parts and joints. `buildMjcf` gets them through `withGuests` (`src/sim/simGuests.ts`): their parts join `parts`, their joints join the rig, and their measures come from their triangles. The canvas shows guest parts on the world layer (`sim.guestParts`), posed from `simDeltas` while the model holds more than one robot, so they never join the scene's parts, BOM or picking either.

On the canvas they live in a second `PartLayer` on `stage.worldRoot` (`ViewportProps.worldParts`). Picking, USDZ export, interference, measures and framing all read `ctx.layer` and `partsRoot`, so they never see the world. Silhouette, label and `onlyIds` captures hide it. `setPose(deltas, worldDeltas)` routes poses to both layers.

### Live drive

Drive works in the live sim, never as a physics-off puppet. A command is `{type: 'command', v: [vx, vy, wz], target?, aux?, joints?}` in `SimRequest`: forward, left and counter-clockwise turn, each −1 to 1 (ROS order), an optional end-effector target in scene mm, `aux` (arm lift, grip), and optional joint targets by joint id (degrees, or mm for a slider). `src/sim/drive.ts` turns it into actuator targets by class, chosen by `driveAccess` (`src/sim/driveAccess.ts`) from the robot's morphology:

- **Arm:** a warm-started `solveIK` at 50 Hz in the worker, on a `Rig` cloned without `rig.parts` (`rigForWorker`). The aim moves at 0.9 × reach per second and stays inside the reach sphere. An arm with a gripper drives the point between its fingers and holds the gripper pointing down with its fingers across the line from the anchor (`driveGrip.ts`: two IK targets at weight 0.05, a point behind the hand and one beside it, so the hand's position still wins), and `aux[1]` moves each jaw from its start toward its closing limit; Space and the gamepad's first button send 1. When the keys let go, the drive holds the hand where it is: the engine hands it the measured joints plus each servo's gravity sag (`qfrc_bias / kp`), so the hand neither catches up the servo lag nor droops (it used to run on 22 mm). The drive then holds those joints as they are, with no IK, until a key or a target moves the aim; a new drive holds its start pose the same way. Solving again from the measured joints let the gripper's pointing-down targets pull the hand about 8 mm off where it stopped; `driveGrip.test.ts` checks the joints stop changing from the first control step after key-up.
- **Rover:** a differential mix over the `<velocity>` wheel actuators. Each wheel's spin sign is `(axis × up) · forward`, so reversed axes still roll forward; its lateral offset is from the wheels' centre along the robot's left. Forward speed ramps toward the command, 0.25 s from stop to full and back (`SPEED_RAMP_S`): a step from 0 to 8 rad/s asks a velocity actuator for four times its force range, so every wheel read 100% in Peak torque for the first 50–70 ms of any drive, and the jolt reared the first-launch rover 17° onto its tail. Ramped, its wheels peak near 32% and it stays within 1° of level (`app/firstRobotSim.test.ts`). Turn isn't ramped: it's GroundSteer's feedback, and a lag inside that loop made rover-four's skid-steer weave and miss Push a Box in the block world.
- **Legs (four or more):** `src/sim/driveLegs.ts` bakes stand, forward, strafe and turn cycles with `buildGait` (per-foot directions, true alternating phases for six feet, point feet), each in both directions, then blends them by command each tick, ramping in from the pose over 0.5 s. A negative command plays the reversed bake, never the cycle backwards in time: played backwards, its stance falls on the other cycles' swing, so walking while turning right barely turned. The bake is kept per setup object (`bakeCycles`), so a respawn or a second controller change doesn't bake again. Drive unlocks only after a 5 s headless fall check (`fallCheckPassed`: no fall, tilt under 35°, at least 3 cm forward, height above 60%). The fixture hexapod and all three quadrupeds pass; the weak quadruped is refused.
- **Pose** (`src/sim/drivePose.ts`): a live body pose (§ Input sources) drives a robot with arms joint by joint. `poseJoints` takes every movable joint that isn't a leg (a joint marked `limb: 'leg'` or under a hip `autoMapRobot` finds), so arms, waist, head and hands follow and legs never do. `PoseDrive` moves each toward its target at 50 Hz, clamped to the joint's range and to 240°/s (`POSE_RATE_PER_SECOND`). `driveAccess` with `pose` picks it for any robot whose rig maps a left or right shoulder and elbow (`hasArms`); a fixed arm without them takes the arm class and follows a hand target instead. A robot without arms whose arm joints are all its look pair (`lookJoints`, §8l: a pan-tilt camera head) takes the pose class too, so the `face` source can aim it; an arm with a wrist camera still takes the arm class. A legged robot with a ready Walk runs that policy with the pose drive on top (`Controller` `policy` with `pose`; the engine writes the arm targets after the policy's). Without one, the drive pins the base: `useDrive` restarts the sim through `startSim(robot)`, which builds the model with `fixedBase` for that robot, so the legs never decide whether the arms can be tried. Any later drive without a pose source, or with a Walk ready, restarts it unpinned; stopping doesn't, because a Case try and the try timeline stop the drive and go on using the same model. `drivePose.test.ts` clamps and rate-limits; `drivePoseAccess.test.ts` pins the G1-style fixture, runs a Walk under its arms, and moves a shoulder in MuJoCo while the base and knees stay put.
- **Through a skill:** a legged robot with a ready Walk (the Motor Kit's velocity tracking, §8i) drives through that policy, bipeds included, with no fall check; it comes before the scripted gait.
- **Never a refusal** (`driveOffer`, `withVelocity`): two legs, wheels on legs, or a walker that fails its fall check get **Teach It to Move** in place of Drive, which trains the Kit's Walk (or sends `/train move` when the robot has no Kit, like wheels on legs); a robot with nothing that moves it around or reaches gets no Drive control. Stand, Push and Grab stay. The agent's `start_drive` answers with the same action in words.

**Input sources** (`src/sim/inputSources.ts`, types in `inputTypes.ts`): every way of driving is a source with an id, registered once with `registerInputSource`, whose `read` turns the moment (the drive class, the held keys and, on a sim frame, the sim's `time` in seconds) into a drive command or nothing. `camera`, `hand`, `face`, `midi`, `voice`, `phone`, `gamepad`, `keys` and `code` (a running Case's code panels, § Code panels) are registered today. A source gives the interface's two shapes: continuous targets through `read`, and named events through `emitInputEvent(name, value)` (`src/sim/inputEvents.ts`), which `useDrive` sends to the sim worker's `input` request, so Case logic reacts to them (§ Logic); the phone's button presses go the same way. The last 200 events are kept for `__studio.inputEvents()`. A source may have a lifecycle: `open(robot)` answers `null` or why it couldn't start, and `close()` stops it. A source that follows a body sets `pose` and opens only when the drive has a robot for it: an `InputRobot` (a fixed arm's hand start and reach in scene mm, or a rig without parts, a table of its rest points, the joint ids to drive and its `look` pair); other lifecycle sources (`midi`, `voice`) get `null` and open for any robot. The drive reads the sources it's given (`drive.setInputs`; the studio's are `phone`, `gamepad` then `keys`, or `drive.start(team, { inputs })` for one session), and the first one that's moving drives, so a tilted phone overrides a stick, and a stick still overrides the keys. A command with a target or joints is never idle. When a session's sources include a pose source, `drive.start` asks `driveAccess` for pose access, opens the lifecycle sources with `openInputs` (a refusal closes what opened and comes back from `drive.refusal()`), keeps them open through restarts (a Case try starts the drive again with the same session), and closes them on stop, Esc, or the sim stopping. `drive.inputs()` holds each source's last reading. A source may also give `raw()`, its raw values as plain numbers: a gamepad's axes then buttons, the phone's tilt, pad and buttons, the camera sources' latest landmarks (§8l), the last MIDI note then each controller and its value. `liveInput()` names the source the last `readInputs` picked, with its raw values or else its command's numbers, at most 512. It's null once no read has come for 500 ms. `NAMED_INPUTS` lists the sources arc #184 plans (`camera`, `phone`, `midi`, `leader-arm`, `voice`, `policy`, `script`) so a console naming one this version doesn't register is refused as missing rather than as unknown. A new source registers itself and plugs into the drive and every console without touching how a Case runs. A leader arm isn't a source: the daemon only emulates (§8k), and an emulated leader can't be moved by hand.

- **Phone** (`phone`, `src/phone/`): **Pair Phone** (⌘K, Simulate group; desktop app and the dev bridge, never the web demo, which can't open a LAN socket) starts the pairing server (`electron/phone/`, Security §0h) and shows its URL as a QR code (`PairPhoneHost`, `uqr`). The phone's page sends tilt (DeviceOrientation β and γ), a touch pad's x and y and two buttons about 30 times a second; the app hears them over IPC (`phone:event`) or the bridge's event stream (`/api/bridge/phone-events`). The code closes once the phone connects; Esc while it shows, or **Unpair Phone**, ends the pairing, and so does the phone leaving. The store (`phoneStore.ts`) listens from the first Pair Phone until a pairing closes, ignores the old run's close while a new pair request is out, and adopts the main process's pairing at boot (`phoneState`, like `robotState`), so a reloaded page shows the code or the connected phone again. With no LAN IPv4 address, Pair Phone refuses with “Connect to a network to pair a phone”, never a code for a loopback URL. `phoneCommand` (`phoneDrive.ts`): tilt is level within 4° and full at 25°; tipping the top down drives forward and tipping the left edge down turns left, as `v` for rovers and legs and as the hand target's motion for arms; the pad's x strafes legs, its y lifts an arm's hand, and A grips. Each new press is a named event, `phone` with the value `a` or `b`, sent to a running Case's logic (§ Logic), so a Routine reacts to it like `voice`. A reading older than 500 ms counts as none, so a phone that locks stops the robot. `phoneDrive.test.ts`: a 20° tilt walks `quad-servo` and drives `rover-diff` forward and a level phone stops them, and a tilt moves the arm's hand forward without leaving its reach.
- **Camera** (`camera`, `src/cameras/operator/`, §8l): **Drive with Camera** (the Simulate tab's Control section, and ⌘K's Simulate group, for robots `poseOffer` accepts: `hasArms`, or a fixed robot with an end effector) starts a session with `CAMERA_INPUTS` (`camera`, then the studio's), so keys still walk a robot whose Walk runs under its arms. For joints it sends the retargeted upper body, and nothing grips. For a fixed arm it sends the right wrist's motion relative to the shoulder as `target`, and `aux[1]` as the left hand's pinch, so it grips. If the camera can't be opened, the toast says “Couldn’t open the camera.” A Case try records as usual, so a camera-driven try exports like any other.
- **Hand and face** (`hand`, `face`, §8l): the same camera session and worker as `camera`, each with its own landmarker. `hand` sends a fixed arm the wrist's move since the first hand seen as `target`, scaled to the arm's reach, and its pinch as `aux[1]`; a robot with joints gets nothing from it. `face` sends the face's bearing as targets for the robot's look pair (pan, then tilt). Neither has a studio command: a Case's console names them.
- **MIDI** (`midi`, `src/midi/`): Web MIDI devices (`midiDevices.ts`, `requestMIDIAccess` without sysex; every input, and inputs that connect later) and a dropped `.mid` or `.midi` file (`useCanvasDrop`'s `routeFiles` hands it to `loadMidiSong`; the newest drop replaces the last; a file that won't parse gets “Couldn’t import ⟨name⟩.”). A note-on becomes the event `midi` with the note's number, a control change `midi.cc.<n>` with its value from 0 to 1 (`namedMidi`, shared by devices and files); a note-off or a note-on at velocity 0 gives nothing. The file (`smf.ts`: formats 0 and 1, running status, the tempo map) plays on the sim clock: `read` advances `midiPlayer` to each frame's `time`, starting the song at the session's first frame and over again when time goes backwards, and once it ends it stays silent. `read` always answers `null`: MIDI drives nothing itself, a Case's logic maps its events. Opening never refuses and never waits on the permission prompt, so missing Web MIDI only means no device events. `smf.test.ts`, `midiPlayer.test.ts` and `midiSource.test.ts` parse a fixture song built in code (`fixtures/song.ts`, a tempo change from 120 to 240 bpm at 1 s), play its notes on 20 ms ticks 0, 25, 50 and 75, sweep CC 1 from 0 to 1, and hear a fake device until close.
- **Voice** (`voice`, `src/voice/`): keyword spotting on the device with Vosk (`vosk-browser`, its own worker; the small English model, 41 MB, in `public/models/`). We use Vosk over a Whisper-tiny build because it takes a grammar, so it only ever hears the Case's words, where Whisper transcribes freely. The words are the ones the running Case's logic compares the fact `voice` against (`voiceWordsOf`: single words in reactions, watchers, If and Wait conditions), set by `useCaseRun` while the Case is open. The recognizer's grammar is those words plus `[unk]`; only final results count, and only words at a confidence of 0.75 or more (`voiceSpotter.ts`: across 6 macOS voices, a real “sit” scored 0.83–1.0 and sound-alikes 0.41–0.63; “set” and “fit” can score 1.0, so no threshold tells those apart). Each word heard is the event `voice` with the word as its value. With no words it opens and listens to nothing. The microphone is its own audio-only stream, read by an AudioWorklet (`voiceCapture.worklet.js`) in 100 ms chunks straight into the recognizer; audio is never stored, sent or written to disk. If the microphone or the model can't open, the toast says “Couldn’t open the microphone. Allow Basecase to use it in Privacy & Security.” From the end of a word to its event takes about 990 ms (10 runs, headless Chrome on an Apple M5 Pro), nearly all of it Vosk waiting for silence before a final result; the model loads in 1.6 s the first time and 0.73 s after, from Vosk's IndexedDB copy of the unpacked model. The web build leaves the model out (`vite.config.ts`: a file over 25 MiB can't be served there), so on the web the voice input refuses with “Voice works only in the desktop app.” (`voiceSource.ts`). `voiceSession.test.ts` runs the real recognizer in node (`voskNodeHost.mjs` runs vosk-browser's worker code in a `node:vm` context with the model from the repo): a recorded “sit” (`fixtures/sit.wav`) fires `sit`, and six noise clips fire nothing.
- **Gestures** (`src/cameras/gestures/`, §8l): while the camera source runs, a recognized movement is the named event `gesture` with its name as the value (`wave`, `raise-hand`, `raise-both-hands`, `point-left`, `point-right`, `thumbs-up`, `open-palm`, `clap`, `nod`, `shake-head`, or a taught name), sent to a running Case's logic like a phone press. **Teach Gesture** (⌘K's Simulate group, while the camera is open and a Case is active) asks for a name (filled with the Case's first untaught one), then three times counts down from 3 and records up to 3 s (`useTeachGesture`); a recording where nothing moved is taken again. The three examples are saved on the Case (`cases.saveGesture`, replacing one of the same name), and `TeachGestureHost` sends the active scene's taught gestures to the worker whenever they change.
- **e2e** (`e2e/inputs.e2e.test.ts`, with Chrome's fake camera): runs Pair Phone, connects a socket from the test with the URL and certificate from `__studio.phone()`, tilts it until the rover moves, and checks the socket is refused after Unpair Phone. Hand and voice go the way a person does, through a Case (`e2e/inputCases.ts`): it opens the Case from the Cases tab, runs it with Run Case and clicks the console's **Try It**. `handMovesRight()` (`__studio.feedHand`) under a console listing `hand` shows the operator tile in its `camera.operator` panel and moves `arm-6dof`'s hand right; the recorded “sit” fed through `__studio.feedVoice(samples, rate)` gives one `voice` event in `__studio.inputEvents()`, with the word taken from the Case's logic, not the test. Face and MIDI start sessions through `__studio.driveWith(inputs)`: `faceOffCentre()` (`__studio.feedFace`) turns `panTilt()`'s pan joint to its target, and a fixture song dropped through `__studio.dropFiles` gives its four notes and a sweep ending at 1.

`useDrive` (`src/sim/useDrive.ts`) owns the drive state and the fall check; `useDriveKeys` (`src/workspace/useDriveKeys.ts`) reads W A S D or the arrows, Q E, Space (grip), R (start over: `engine.respawn` puts the robot back without touching the world) and Esc (stop). While driving, `useWorkspaceKeys` runs no plain or ⌘ key, so S, F, Backspace and undo never edit parts (any parts edit still stops the sim). Keys zero on window blur and when the page hides; with a text field focused the canvas says “Click the canvas to drive”, and a click on the canvas takes focus back. Gamepads are read in the sim's frame handler (`frameHookRef`), with no extra animation frame; a stick inside its deadzone never overrides the keys. A command is sent only when it changes (`sameCommand`, which compares the target too).

An arm drive reports its hand in `SimStats.effector` (mm, world frame, from the drive's bound part and point); the dev `simState()` passes it on. The canvas shows stats ten times a second, but `sim.latestStats()` returns the newest frame's, and the dev `simState()` and the gallery's `__gallery.state()` read that: a reading 100 ms stale put a stopped rover 3 cm short of where it really stopped.

**Playing the reference live:** `drive.follow(autopilot)` hands the drive a function of each sim frame (poses and time) that returns the command. `useDrive` sends it only when it changes, and the first key or stick press drops it for good, so the person takes over at once; starting or stopping the drive drops it too. `useOpeningCase` uses it on first launch (§5a): it opens the seed's Case (`playCase`) in the Simulate tab, puts the canvas on the Scene camera's view of the robot and its world (`sceneCamera`), starts Drive and follows the scaled Case's reference through `livePlayer`, the same `ReferencePlayer` and `GroundSteer` route `runCase` uses. Nothing records, so the reference adds no try. `referencePlayer.test.ts` plays the rover's reference at 60 frames a second and checks it stops on the flag.

The canvas overlay (`DriveOverlay`) shows “Fell. Press R.”, speed in m/s for robots that move around, and Esc with Stop Driving, the name the button and ⌘K use. The side panel's key list leaves Esc out: the overlay and the Stop Driving button already show it. The camera follows the robot's base (`followPart`, `FollowCamera`), and the key light keeps fitting while it follows.

### Tries

**Try It** on a Case with more than one slot drives the first slot from the keys and runs every other slot from the Case's reference: `useCaseTry` builds a `DriveTeam` (each guest slot's drive on the joined rig, and the reference commands for those slots), `useDrive` starts one team controller, and the worker plays the commands as a `script` against sim time. The dev `__studio.referenceTry()` scripts every slot, the first included, and `simState()` reports each slot's hand in `effectors`. A ground robot's waypoints, which `GroundSteer` follows from poses, play only in `runCase`; a script carries plain commands.

A try's clock starts at the newest frame's time when it begins (`sim.latestStats()`); the stats the panel shows lag up to 100 ms and, just after the Case's model loads, can still be the old run's, which ended a try seconds early. A try records at 50 Hz in the worker (`src/sim/recorder.ts`, hung on `SimEngine.stepHook`, the second step slot): time, actions, qpos, qvel, every body's pose (kinematics refreshed first, so poses match qpos) and, when the robot carries a LiDAR, its newest scan (`Recording.scan`, `scanWidth` values a frame, §8l). It ends when the Case's time runs out, on Stop Try, or when driving stops. `scoreTry` runs the Case's probes and contract over it; `tryManifest` stores the Case and model hashes, seed, frame count and step. Faults set during a try (§8d) go on the recording (`Recorder.fault`): joint, kind, start time from the try's start, and `until` once cleared; faults already on when it starts are logged at 0. It also records the drive commands it was given (`Recording.commands`: each `SimEngine.command` call, its `slot`, `v`, `target` and `aux`, at the sim time it came, through `SimEngine.commandHook`; the commands already in force when it starts are logged at 0) and the controller that drove it (`Recording.controller`, the worker's drive controller), so the try can be replayed. `tryManifest` keeps the faults as `faults`, and the command count as `commands`, and each try row in Results shows a badge per fault, whose tooltip names the joint and time.

**The tries store** (`src/cases/tryStore/`, backend `electron/library/tryStore.mjs`): every try from every scene, in one place. A recording is a try whatever made it (a driven try, a variation, a real try), and every source saves through the same store.

- **On disk** each try is `library/tries/<id>/`: `try.json`, `recording.bin` and, once a filmstrip was drawn, `strip.webp`, and, for an Operate try filmed by the operator camera, `video.mp4` (§8l, at most 512 MB, kept only once `try.json` exists). The manifest (`StoredTry` in `src/cases/tryFile.ts`) holds the id, scene id, robot (name, model hash, joint ids), Case (id, name, contract hash), source (`case`, `generated`, `real` or `operate`), input (`script` for a reference try or a variation, `mat` for a real try, empty for the studio's live inputs, the live input's id or `policy`, `sim` or `by-hand` for an Operate try), start time, duration, rate, frame count, outcome (`passed`, `failed` or `unjudged`, with its margin), seed, source try, faults, and the command and world event counts. `readStoredTry` refuses any other shape. `list` keeps each summary in `library/.try-summaries.json`, keyed by the manifest's time and size, and rewrites that file at most once a list; saving, deleting or keeping a strip or a video changes only the copy in memory, and the next list picks up a strip or video that's new.
- **Operate tries** are written by the main process while a robot is connected (§8k Operate tries). They have no Case, an `unjudged` outcome and, when set, `policy` and `fault`. Their `recording.bin` holds the robot's take (`decodeTake` in `electron/robot/robotTake.mjs`), not a sim recording. Tries mode titles a try with no Case by its start time and badges it Operate.
- **The recording is binary** (`src/cases/recordingFile.ts`, the container in `electron/library/arrayFile.mjs`, which the take shares): a 12-byte preamble (`BCTR`, version, header length), a JSON header with the scalars, faults, commands, controller and world events, then each typed array at an 8-byte boundary, little-endian. The header tags every typed array, `Map` and `Set` it holds with its type and restores it: a drive controller carries the robot's rig, whose `parentOf` and `ownerOf` maps came back as empty objects when plain JSON wrote them, and Multiply on such a try failed in the worker. `decodeRecording` refuses a file whose arrays don't match its frame count and sizes, or that runs past its end. The page encodes and decodes; the main process stores bytes and never parses them.
- **Two backends, one module.** The desktop app reaches the store over IPC (`tries:*`, `electron/library/tryRoutes.mjs`, bytes as they are) or the Vite bridge (`/tries-*`, bytes as base64). The bridge runs the first route a URL starts with, so no route name is the start of another (`tries:keep-strip`, not `tries:save-strip`, which `/tries-save` would catch). The web demo keeps manifests, recordings and strips in IndexedDB (`basecase-try-manifests`, `basecase-try-recordings`, `basecase-try-strips`, `tryStore/webTries.ts`). It keeps no videos: `saveTryVideo` does nothing there and `loadTryVideo` answers `null`. `useTries()` is one list shared by every scene tab; saving or deleting updates it in place.
- **`project.tries` holds references.** Each scene keeps its `TryRecord`s, which Results reads, and `sharedScene` strips them from `.basecase` files with `triesStored`, like policies. A try is saved to the store before its record joins the scene (`useStoredTries`), and once a scene's `triesStored` is set, Results lists only the records still in the store, so a try deleted in the Library leaves every scene that names it.
- **Moving old tries.** Before the store, recordings lived in IndexedDB (`basecase-tries`). The first time a scene opens without `triesStored` (and, after a failure, on the next change to the tries list), `moveTries` writes each record's manifest with its IndexedDB recording, keeps its id, deletes the IndexedDB copy, then sets `triesStored`. A record this browser has no recording for is kept without one. The flag makes it run once, so a try deleted from the Library while its scene was closed never comes back.
- **Filmstrips** drawn for Results are kept as `strip.webp` (`saveStrip` in `useFilmstrip`), so the Library shows a try from a scene that isn't open. A tile in Tries mode reads or draws its strip only once it's within 400px of view (`useSeen`), so a store of 5,000 tries doesn't read 5,000 strips when the mode opens.
- **Deleting** a try from Results, the Library or with its Case deletes its folder; generated tries go with their source (`goingWith` in `tries.ts`).
- **Tests:** `src/cases/tryFile.test.ts` (the manifest round-trips, a crafted id or a wrong shape is refused, the recording round-trips with the typed arrays, maps and sets inside its controller, and a cut or lying file is refused, a source takes its generated tries), `src/cases/tryMigration.test.ts` (moved once with their ids, kept without a recording, references only), `electron/library/tryStore.test.mjs` (folders, cached summaries, strips and videos without a cache rewrite, a video's size cap, deletes, base64 over HTTP, every route reached through the bridge's prefix lookup) with its exploit cases (crafted ids refused before any path is touched), and `e2e/tries.e2e.test.ts`, which records a try in each of two scenes, lists both in Library ▸ Tries, opens one on the timeline and deletes the other through the confirmation.

**The try timeline** (`useTryTimeline.ts`, `components/simulate/TryTimeline.tsx`): a try row's Replay opens it under the canvas, above the toolbar. It stops driving, loads the sim if it's off, and sends the recording to the worker (`Simulation.scrub`, §8d); a recording that doesn't fit the current model opens nothing. One lane per actuated joint (`timelineLanes`): the target (recorded ctrl, position joints only) in grey and the position (qpos through `jointQpos`) in the accent on one plot, and the effort (absolute actuator force) on a second with the servo's limit dashed, both in degrees or millimetres and N·m; the name column shows the values at the playhead. The Case contract's failed labels show as red markers at the frame each first tripped (`tripFrames`: `evaluateContract` on growing prefixes of the try's signals, bisected), and the timeline opens on the first of them, or at the start. It also opens from Library ▸ Tries (§5); there the markers show only when the try's Case is the open Case. Pressing on a lane selects its joint's link (`linkParts`, as Peak torque rows do); pressing or dragging on a plot seeks there. Keys while it's open (`useTimelineKeys`, capture phase, so the canvas and selection don't see them): ← → one frame, ⇧← ⇧→ one second, Home End, Space play and pause, Esc closes. Closing resets the sim to where it was: off again, or reset and playing if it was. Deleting the open try or the sim stopping closes it. An Operate try opens through `showTake`. It loads the robot's take (`loadTake`) and hands it to the worker (`Simulation.scrubTake`, §8d). The worker resamples it at 50 Hz into a recording (`takeRecording`), holding the latest status and intent at each frame. Each joint the take read gets its measured position. Joints it never read stay at `qpos0` and get no lane. An unread value holds the last reading, or the first one before any. The target is the latest intent sent, else the measured position. The effort lane shows measured effort when the take has it, else the simulated force. An Operate try with a `video.mp4` shows the operator camera's video left of the lanes, following the playhead (§8l). Tests: `src/sim/recordedFrames.test.ts` (recomputed peaks within 2% of the live Peak torque, through a measured servo's delay too; a seek sets the frame's qpos exactly), `src/sim/takeRecording.test.ts` (irregular statuses and held intents at 50 Hz, unread values, unnamed joints, measured effort first, the engine left as it was), `src/cases/tripFrames.test.ts`, and `e2e/tryTimeline.e2e.test.ts`, which records an arm try, opens it from Replay, presses → and End, checks the worker's qpos against the last frame (`__studio.simState().timeline`), presses on a lane and checks its link is selected, and closes it with Esc with the scene unchanged.

The filmstrip (`src/cases/filmstrip.ts`, drawn by `filmstrip.worker.ts` on an `OffscreenCanvas`, through `filmstripClient.ts`) projects each part's box and the world's objects at four moments of a try, in the same three-quarter view as captures. The worker draws on a CPU-backed 2D canvas (`willReadFrequently`) and encodes the image type its caller asks for itself (WebP for a try, PNG for `run_case`); the main thread only gets the blob. `useFilmstrip` keeps one strip per try, model and boxes, so the Run Case tries panel and the Simulate tab's Results share a render. Encoding on the main thread (`convertToBlob` on a `bitmaprenderer` canvas) is a synchronous GPU readback. It waits behind every frame the GPU process has queued, and the live sim keeps the viewport and camera feeds rendering after a try. On CI's software GL that blocked the main thread for 0.2 to 7.5 s per strip, long enough that `caseRun.e2e.test.ts` read no try for 30 s and the next test couldn't click a tab. Results list tries worst first. `useFilmstrip` revokes a strip's blob URL only once a newer strip has replaced it on screen (or the row is gone): a re-rendered row that loads a revoked URL logs `net::ERR_FILE_NOT_FOUND`, which fails the Cases e2e.

A recording also keeps each joint's `qpos` address (`Recording.jointQpos`, from `SimEngine.jointAddresses`), so a dataset can read joint state without loading MuJoCo. Tries recorded before it existed have none and can't be exported.

**Multiply** (a passed try's right-click menu in Results, and ⌘K for the open Case's newest one) turns one driven try into up to 50 passing variations (`MULTIPLY_RUNS`) for the dataset. Only a try with recorded commands can be multiplied (`multipliable`: passed, not generated, `manifest.commands` set); tries recorded before commands were have none, so their menu has no Multiply. The try's `modelHash` must match the current model, as for Export, or the toast says it's from an earlier design.

- **A variation** (`replayTry` in `src/cases/tryReplay.ts`) builds an engine for the try's own model with `startEngine` (`runCase.ts`): seed `null` is the perfect world, any other seed draws the Case randomization through Arena's `ArenaWorld` as Checks does (§ Seeded runs). `worldOffsets` jitters the dynamic objects and the spots (markers) with `jitteredWorld(…, { spots: true })` from `worldRandom(seed)`, except objects the Case marks `movable`: they keep a zero offset, since the recorded `world` events put them back where the code did and a mocap body ignores `body_pos`. `shiftedCommands` moves each arm target by the offset of the object nearest it at the command's time, reading an object the code placed since the last recorded frame from its `world` event; a movable object within 1 mm of the nearest wins the tie, so a target on a lit spot that sits on a jittered one stays put. The start state is the try's first frame (qpos and qvel), with each moved dynamic object's free joint shifted, and each moved spot's or furniture's `body_pos` shifted and its `body_quat` turned (`turnedQuat`, the same turn the MJCF writer gives a rotated object), so the model and its hash stay the same. It replays the recorded commands and faults at their sim times, one physics step at a time, under the recorded controller, and records with the same `Recorder`.
- **Targets follow their object.** `shiftedCommands` moves every command `target` (an arm's hand, or a ground waypoint) by the offset of the moved object or spot it was nearest at that moment in the source try (the object's pose from the recording's frame). A command without a target replays as it was, so a try driven with keys alone moves nothing with the objects.
- **Judged by the contract.** Each variation is scored by `scoreTry` with the source's staged Case; probes and Case facts read objects and spots through `worldDeltas`, so they see where the jitter put them (`caseFacts` places each spot by its delta too). `multiplyTry` keeps only passes.
- **In the workers.** `useTryMultiply` (`src/workspace/`) sends batches of 5 seeds as `multiply` jobs (`caseCheckJob.ts`) to the Checks pool (`caseCheckPool`) in their own `multiply` group, so they share its worker slots and a Checks rerun's `keepOnly` never drops them (`keepOnly` only touches its own group); recordings come back transferred. Seeds start after the highest this try already has, so multiplying again adds new variations. A progress toast (“Multiplying…”) has Stop, which drops the queued batches; the row shows a progress bar. The end toast says how many were kept of how many ran. Each run holds its own turn (`turn` in `useTryMultiply`), and Stop, an error or the end of the run moves it on, so a batch already running on a worker when the run ends lands under a stale turn and is dropped, its saved recordings deleted: it never adds tries under a later run on the same try, whose seeds may repeat it. Deleting the source try, or its Case, stops its run first, so no generated try outlives its source.
- **Generated tries** (`generatedTry` in `tries.ts`) are passed tries with `generated: true`, id `<source>-<seed>`, and `manifest.seed` and `manifest.source`; their recordings go in the tries store like any other. Results lists only driven tries; a source row shows its count (“50 generated”, `generatedFrom`). Deleting it asks with that count (“Its 1 generated try goes with it.”) and deletes them with it, including any that landed while the dialog was open: the tries to drop and the recordings to delete are read from the project when you confirm (`dropTries` in `useCases.ts`), and the same goes for deleting a Case.
- **Tests** (`tryReplay.test.ts`, a try recorded the way the live worker does by `referenceTry` in `src/cases/testing.ts`): the recording holds the reference's commands and the drive controller; replaying with no jitter passes with qpos equal to the try's; each target moves by its nearest dot's offset; one Touch the Dots try on the fixture three-joint arm keeps 20 or more of 50 (it keeps 50); a try cut to its first command keeps none; Pick Up a Block's block starts at its offset and the grip target moves with it; a generated try carries its seed and source and is never multiplied again. `codeWorldRuns.test.ts` multiplies a whack-a-target try whose code lights a movable spot: no target moves, and all 3 variations pass. `e2e/drive.e2e.test.ts` records the reference try, runs Multiply from ⌘K with 5 runs (`__studio.multiplyRuns`), checks the row's count and exports the source plus the passes.

### Real tries

A ground Case (its first slot needs wheels or legs) can be printed as a floor mat and tried on the real robot, judged by the same contract as its sim tries. Real motors stay locked: whatever moves the robot today (its own remote, a script) moves it, and Basecase only watches.

- **The mat** (`src/cases/mat/matLayout.ts`, `caseMat(staged, { rig, parts }, paper)`, null for any other Case): portrait A4 or Letter sheets (`paperFor(navigator.language)`: Letter for US, CA, MX, PH, CL, CO, VE, PR and GT, else A4) laid edge to edge, covering the start box (the robot's footprint at its pivot), the spots, the path from the pivot through each spot, and the other world objects' footprints, plus 100 mm. Looking down, scene +z is up the page and +x is to the left, so the robot drives up the mat. Mat tags are AprilTag 36h11, black square 140 mm, one centred on a sheet (`matGrid.ts`): the four corner sheets, then sheets along the edges so neighbours are at most 1 m apart, never over the drawing (the grid grows when a corner would cover it). Ids run from 0; the base tag is id 100 (`BASE_TAG_ID`), sized to the root link's top (80% of its smaller side, 48–120 mm), at the root link's top centre with its top along the robot's forward. Rover-diff's Reach a Spot is 21 A4 sheets and 6 tags; quad-servo's Follow a Path is 45 sheets and 9 tags.
- **The PDF** (`matPdf.ts`, hand-written PDF 1.4 in `pdfWriter.ts`, no dependency): one page per sheet from the top left, each labelled `A1`, `B3`…, then the base tag page with an arrow to the robot's front. Each tag is one Form XObject placed with `cm`, so a test can count them. **Export Case Mat** (the open Case's right-click menu in Cases, and ⌘K; desktop only) stages the Case and saves the PDF as `⟨case-slug⟩-mat.pdf` (`useCaseMat.ts`). Its tag positions are the ones the tracker solves against; `matPdf.test.ts` reads every placement back out of the PDF and checks it against the layout for every ground goal on rover-diff, rover-four and quad-servo.
- **Try on Real Robot** (`useRealTry.ts`, under Try It, and ⌘K's Try ⟨Case⟩ on Real Robot): the person tapes the base tag on top of the robot and points a camera at the mat. It opens the mat tracker (§8l) and records its samples from the first one for the Case's time, or until Stop Try. The try's clock is the samples' own: each camera frame's own timestamp (a browser that hands over `ImageBitmap`s instead stamps it when it reaches the worker), feed times from a test feed. It never starts the sim or the drive and sends nothing to motors. A scale refusal toasts it; a worker error toasts “Mat tracking stopped. Try on Real Robot again.”; either records nothing. Try It and Try on Real Robot are disabled while the other runs, and Try on Real Robot in every scene tab while another tab's real try holds the tracker (§8l).
- **Judged like a sim try** (`src/cases/mat/realTry.ts`): `realRecording` resamples the base at 50 Hz, interpolating position and yaw between samples up to 0.15 s apart, and moves every robot body rigidly with the tracked base (height and tilt stay as at rest); world objects stay where the Case put them. A longer gap is NaN, so a probe can't read it: a success never passes on it and a failure fires on it (the contract fails closed, §8i). A quadruped whose base tag is hidden therefore trips Fell. `scoreTry` judges the recording unchanged and the record carries `real: true`. A real try has no qpos, commands or joints, so it stays out of what needs them: Export Dataset, Multiply (`multipliable`), Train from Tries (`simTries`), the try timeline and filmstrips.
- **Results:** the row shows Passed or Missed like any try, with a **Real** badge. Its Replay draws paths instead of opening the timeline (`useRealReplay.ts`, `src/three/viewport/matTrack.ts` on `stage.overlays`, so captures never show them): its base path (`basePathOf`) in the accent over the best passing sim try's in grey, until another Replay, the Case closes, the try is deleted, or Esc. While tracking, the canvas draws the real base as an accent ring with a heading tick and its path so far; one preallocated buffer per line is updated in place, and the canvas redraws only when it changed.
- **Test hooks** (dev and test builds, `src/workspace/devStudio/areas/mat.ts`): `__studio.feedMatFrames({ seconds, hide })` stands in for the camera with frames rendered from the open Case's mat (the base tag driving to the last spot over the first 60% of the time, then holding; no base during `hide`; a 70° camera 1600 mm up and 300 mm behind the mat, 640 × 360, since from 900 mm behind it found the tag near the spot in only 8 of 21 frames). `__studio.caseMat()` returns its sheet and tag counts and `__studio.matTrack()` the tracking state.
- **Tests:** `src/cases/mat/realTry.test.ts` renders frames from sim tries with `renderMatFrame` and tracks them: rover-diff's Reach a Spot tracks within 10 mm of the sim's base tag and passes, a stalled rover misses, the base tag hidden for 1 s leaves a gap of at least 45 frames and the try still passes, and quad-servo's Follow a Path on a walking path with sway and yaw wobble passes within 15 mm. `src/cameras/mat/matTracker.test.ts`: two mat tags in view, a camera tilted 40° and rolled 10°, a 100° lens, a 97% print refused, and the same frames giving the same trace. `src/cameras/mat/matTracking.test.ts`: one try holds the tracker, and another can't claim, close or read it. `e2e/drive.e2e.test.ts` exports the rover's mat, counts its pages and tags through `__studio`, feeds rendered frames through `__studio.feedMatFrames()`, runs Try on Real Robot and checks a passing Real try.

### Logic

A Case's rules are a Routine (§8j), never a second format: `logic` holds one, `parseCase` checks it with `validateRoutine`, and `compileCaseLogic` (`src/cases/caseLogic.ts`) compiles it against the scene's skills plus the Case's own `drive` skill. This is how a Case reacts ("when voice is sit, do sit"), keeps score, or ends a game.

- **`drive` is the person's drive.** A Routine whose base is `do drive` leaves the robot to the Case's drive (live keys, a pad or the agent in a try; the reference in `runCase`), so a game on an arm needs no trained skill. `CASE_DRIVE` holds the body, stops through itself and has no proven transitions, so a Routine that hands the body from `drive` to a skill is refused (`unproven-transition`) until that hand-off is proven; a Routine that runs body skills uses a skill as its base (`settle`, for a robot dog). While the Routine runs any other body skill, that skill drives through the Routine's physics body (`controlFor`, §8j) and the person's commands are held back; when it ends, the drive takes the robot back. Body skills need a robot on legs (`NO_BODY`).
- **Case facts** (`caseFacts.ts`, pure, from the poses and the time): `elapsed` and `timer` (seconds left of `task.seconds`); for each dynamic object `<id>-x`, `-y`, `-z` (mm, scene frame), `-floor` (its centre within half its largest side plus 5 mm of the floor), `-over` (turned more than 45° from upright) and `-spot` (the marker it's inside, or empty); for each marker `<id>-count` (dynamic objects inside it: within its footprint, and no higher than its top plus the object's largest side); and `score` when the task has a rule: `{ spot, counts: 'in' }` counts the objects in that marker, `counts: 'out'` the objects that started in it and left. `passed` and `failed-<label>` judge the contract over the trace so far, every 0.25 s.
- **A Routine reads them through watchers** with model `case-fact`, and named live-input events through model `live-input` (§8j): the watcher's id is the fact's name. An event is published with its own time as the stamp, so with a short `maxAgeMs` (300 ms) it goes stale on its own and the next one is a new rising edge: each `sit` fires the reaction once.
- **The contract reads them too.** `score`, `elapsed`, `timer` and each `<spot>-count` are trace signals beside the probes, so "score above 1.5 within the Case's time" is an `eventually` atom on `score` (atoms pass on a strict margin, so a count is compared against half a point under the target); no new contract term. `scaledToReach` never scales these signals (`caseSignalNames`).
- **Headless:** `runCase(mj, kase, robot, { controller, kit?, skills?, inputs? })` compiles the logic first; a Routine the compiler refuses makes `CaseResult.refusal` the compiler's own message, and nothing runs. Otherwise the coordinator runs on the record clock (`CaseLogicRun`, the L0 schedule of §8j fed by the Case facts through `ScenarioHost.feed`), `inputs` are recorded events (`{ at, name, value }`, seconds), and `CaseResult.logic` holds the trace, what was said and the last facts. One seed gives the same trace, facts and poses.
- **In a try:** Try It compiles the logic (`caseLogicPlan`, `src/workspace/`: without the Kit when the Routine runs no body skill, so an arm game starts at once) and toasts the compiler's message instead of starting when it's refused. The sim worker then runs the Case (`case` request, `LiveCase` in `liveCase.ts`) in 20 ms steps beside the drive, sends the facts with every frame (`Simulation.latestFacts()`), and stops when the try ends (`caseEnd`). Named events reach it through `Simulation.input(name, value)` (the `input` request), stamped with the Case's time. `scoreTry` computes the same signals from the recording, so a try is judged on the score it got.
- **Hand-offs:** Case logic compiles against the scene's trained moves and taught skills and the scene's stored hand-off proofs (`project.handoffs`, §8j), in the view, in Try It (`caseLogicPlan` takes the same `RoutineSkills`) and for `create_case`, which proves each unproven hand-off first and refuses one that fell with its fall count. A logic switch from walking to Sit is refused until that pair is proved; `caseLogic.test.ts` runs it end to end on a voice event once it is.

Deleting it there drops the Case's logic; ⌘Z brings it back as a scene Routine, not into the Case.
- **Tests:** `caseLogic.test.ts` (fixture robots built in code, `fixtureGames.ts`): a quadruped Case with `when voice is sit, do sit` runs sit within 200 ms of a recorded `sit`; Knock the Blocks on the six-joint arm scores one per block off its pad and passes in 7.5 s but not in 4; a sorting cell counts the blocks inside its bin; a refused Routine refuses the Case with the compiler's message; two runs match. `e2e/caseLogic.e2e.test.ts` adds Knock the Blocks through `__studio.addCase`, sends `KNOCK_COMMANDS` through `__studio.drive` on the sim clock, reads `score` 2 from `simState().facts` and checks the try passed.

### Datasets

**Export Dataset** (Results section and ⌘K, shown once the open Case has a passed try) turns the open Case's passed tries into one zip holding the dataset twice: LeRobot v3.0 at the root, which `lerobot-train` loads and streams as it is, and LeRobot v2.1 with GR00T's `meta/modality.json` in a `v2.1/` folder. It's the demonstration data that GR00T, LeRobot or any vision-language-action model fine-tunes on: Cases with live drive are the teleop, the contract is the success label, and the Case's brief is the instruction. Code in `src/datasets/`.

- **Only tries that match the robot now** (`usableTries.ts`). A try counts when it passed and its `manifest.modelHash` equals the SHA-256 of the current model's XML (the open Case's world included); the toast says how many were left out. Missed tries never go in: a dataset is demonstrations of the task done right.
- **Rows** (`episodes.ts`): every second 50 Hz record frame, so `DATASET_FPS` = 25. `observation.state` is the robot's joint positions (rad or m, `SimModel.joints` order for `robots[0]`), `action` is each joint's actuator control at the same frame (the position target, or the velocity on a wheel). A Case with more than one slot writes every slot's joints into the same two features, slot after slot (`datasetJoints`, `DatasetJob.slots` from `slotKeys`), each joint named `<slot>.<MJCF joint>` (`b.j9_b_arm3`), and `modality.json` gets one state and one action group per slot in place of `joints`. LeRobot reads only `observation.state` and `action` as a policy's state and action, and GR00T reads per-arm groups from `modality.json`, so one feature split by group is what both train on (ALOHA's two arms are laid out the same way). A robot with LiDARs adds `observation.scan`: every scan's values at that frame, LiDAR after LiDAR in `SimModel.scans` order, each distance ÷ the sensor's range and 1 for no return; `meta/basecase.json` lists the sensors (`scans`: part, name, rays, range, rate, field) so a reader can turn them back into metres and angles. A try recorded without a scan on a robot that now has one is left out, like a try from another model. One task per Case: its brief, else its name. `next.reward` is 1 on the last frame (every exported try passed), `next.done` marks it, and `annotation.human.task_description` repeats `task_index` for GR00T.
- **Shared rows** (`lerobotRows.ts`, parquet through `hyparquet-writer` with an explicit schema so state and action are `list<float>`): both versions write the same frame rows (`framesParquet`, one or many episodes per file), the same features and the same per-episode stats (min, max, mean, std and count; images per channel in 0–1, shaped 3 × 1 × 1). `meta/basecase.json` is in both: the Case, model hash and each episode's try id, margin, `seed` and `source` (the try it was generated from, or null for a driven try), and the LiDARs. Generated tries (§ Tries) are passed tries like any other, so they go in.
- **v3.0 at the root** (`lerobotV3.ts`, `lerobotV3Files`), as LeRobot 0.7's `LeRobotDataset` reads it: `data/chunk-000/file-000.parquet` holds many episodes and rolls over to the next file before it would pass 100 MB (`FILE_LIMITS.dataMb`, LeRobot's `DEFAULT_DATA_FILE_SIZE_IN_MB`), measured by each episode's own parquet size as LeRobot's converter does; `videos/observation.images.<camera>/chunk-000/file-000.mp4` joins every episode's video for that camera, up to 200 MB (`videoMb`); `meta/episodes/chunk-000/file-000.parquet` has one row per episode (its `tasks`, `length`, `data/chunk_index` and `data/file_index`, `dataset_from_index` and `dataset_to_index` into the frame rows, each camera's `chunk_index`, `file_index`, `from_timestamp` and `to_timestamp` in its joined video, and the stats flattened as `stats/<feature>/<stat>`); `meta/tasks.parquet` (`task_index` and `task`, with the `pandas` key-value metadata that makes pandas read `task` back as the index, which LeRobot looks tasks up by); `meta/stats.json`, the episodes' stats pooled as LeRobot's `aggregate_stats` does; and `meta/info.json` with `codebase_version: "v3.0"`, the two size limits, the path templates and each non-video feature's `fps`. Each `timestamp` stays relative to its episode; LeRobot adds the episode's `from_timestamp` to seek its video.
- **Joining videos without re-encoding** (`joinVideos.ts`, in the dataset worker): each episode's MP4 is read with `mediabunny`'s `EncodedPacketSink` and its packets are written into one `EncodedVideoPacketSource` track, shifted by the episodes before it, so frames are never decoded or encoded again. Every episode starts on a key frame (one a second), so the joined stream decodes from any episode's start. Packets can share a track only when their decoder config (codec string, size and `avcC` or equivalent description) matches; an episode whose config differs, or that would push the file past the limit, starts the next file, which the episodes parquet points at. Joined files have no creation time (`creationTime: null`), so the same tries give the same bytes.
- **v2.1 in `v2.1/`** (`lerobot.ts`, `lerobotFiles`), for GR00T, whose loader reads LeRobot v2 only and converts v3 back with its own script: `data/chunk-000/episode_000000.parquet`, `videos/chunk-000/observation.images.<camera>/episode_000000.mp4`, and in `meta/`: `info.json`, `episodes.jsonl`, `tasks.jsonl`, `episodes_stats.jsonl`, `modality.json` (one `joints` group for state and action, a `scan` state group whose `original_key` is `observation.scan` when there is one, each camera, the task annotation) and `basecase.json`. GR00T computes its own `stats.json`. Point GR00T at the `v2.1` folder. The zip carries every frame's video twice, once per episode and once joined. `lerobotExport.ts` (`datasetFiles`) writes both from one spec.
- **Rendering off the main thread** (`renderVideos.ts`, `dataset.worker.ts`, client `datasetClient.ts`): the worker builds the visible solid parts and the world with `buildPartGroup` (meshes sent as in thumbnails), lights them with `createStudioScene` on a grey floor at y = 0, poses each sampled frame with `simDeltas` / `worldDeltas`, renders 640 × 480 per camera on one `OffscreenCanvas` and encodes it with WebCodecs through `mediabunny` (H.264, else VP9, else AV1; one key frame a second; `moov` first). The parquet, joined videos and metadata are written in the same worker (`buildDataset` returns the files); its `zip` call also zips them (`src/utils/zipFolder.ts`: media stored, metadata deflated) for Export, and its `files` call hands them over as they are for Publish. The main thread only downloads or forwards the bytes. Nothing renders while a try records.
- **Tests:** `src/datasets/*.test.ts` check camera placement and field of view, read state and action back against a MuJoCo replay, and read the parquet back with `hyparquet`, a LiDAR rover's `observation.scan` included. `lerobotV3.test.ts` builds a three-episode fixture (`fixtures.ts`: two cameras whose MP4s repeat two 64 × 48 H.264 key frames, a LiDAR, generated-try sources) and checks one data file and one video per camera whose index ranges and packet times line up with each episode, the counts and stats against the v2.1 copy, the tasks as pandas reads them, the same bytes from the same tries, a roll-over into a second file past the limit, and a new video file for an episode with another decoder config. `tools/lerobot/check.mjs` (Check's `lerobot` job) exports the same fixture through Vite's SSR loader and runs `tools/lerobot/check_dataset.py` with `uv`, pinned to `lerobot[dataset]==0.7.0` and CPU-only torch: `LeRobotDataset` loads the root at v3.0 and the check reads every episode's frame count, decodes the last frame of each camera (the last episode's, so the time offset counts) with PyAV, and reads the task and stats; then it reads the `v2.1` copy the way GR00T's loader does, through `modality.json` and the `info.json` path templates. `e2e/drive.e2e.test.ts` exports a real arm try in the browser through `__studio.datasetFiles()` (the export's zip, unzipped, on any try) and checks both versions' rows, the codec and each video's size and frame count with `mediabunny`.

### Publishing to Hugging Face

**Publish to Hugging Face** (Results section under Export Dataset, and ⌘K; desktop only) sends the same files, as two commits, to a dataset repo on the signed-in account, `<account>/<case>-<hash>`, and the toast's Open goes to it. The six hex characters are the start of the SHA-256 of the scene id and the Case id (`repoName` in `useDatasetExport.ts`), so a Case like Touch the Dots gets its own repo in each scene and publishing from one scene never replaces another's dataset. Two clicks in a row start one publish. Signed out, it opens Settings ▸ Accounts instead (§6a). There's no second writer: the dataset worker's `files` call builds them, `src/hub/hubBridge.ts` passes them to the main process (IPC `hub:*`, or the bridge's `/hub-*` routes in the browser), and `electron/hub/` does every Hub request. The page never holds the token; it only learns whether someone is signed in and the account name.

- **The Hub's HTTP API** (`hubClient.mjs`, `publishRepo.mjs`): `POST /api/repos/create` (public; 409 means it's there), the repo's tree, `preupload` (the Hub says which files go through LFS: the parquet and videos), the LFS batch API with basic and multipart uploads and verify, then one NDJSON commit (`header`, `file` inline in base64, `lfsFile` by SHA-256, `deletedFile`). Publishing again replaces the dataset: files under the same top folders (`data/`, `videos/`, `meta/`) that the new set lacks are deleted, `README.md` and anything else stays. Then the `codebase_version` from `meta/info.json` is deleted and tagged again on the new commit, because LeRobot's reader loads a dataset at its version tag and refuses one without it. A folder named for a version (`v2.1/`) whose `meta/info.json` says that version is committed first, unprefixed, and tagged with it; then the root files replace it and get their own tag. So `main` holds v3.0 tagged `v3.0`, and v2.1 stays whole at the `v2.1` tag, the way LeRobot's `convert_dataset_v21_to_v30` leaves a converted repo. LeRobot 0.7 picks the revision with `get_safe_version`: the tag equal to its `CODEBASE_VERSION` (`v3.0`), else the newest with the same major version, so it never loads the v2.1 commit; GR00T users download `--revision v2.1`. The two commits are separate requests: if the second one or its retag fails, `main` holds v2.1 and an older `v3.0` tag still points at the last publish, so LeRobot loads that one until publishing again replaces both. The same client publishes a skill as a model repo (`kind: 'model'`: `/api/models/…` and `/<repo>.git/…` in place of the dataset paths, §8i) and downloads one from its resolve addresses (`HubClient.download`).
- **Tests:** `electron/hub/hub.test.mjs` runs against a fake Hub (`e2e/fakeHub.ts`, an HTTP server that keeps repos, LFS objects, commits and tags in memory): repo creation, the commit payload, LFS and multipart uploads, updates, the token sealed on disk and absent from logs, errors and replies, and the exploit cases (§0h). `e2e/drive.e2e.test.ts` records a try on an arm, marks it passed (`__studio.passTries()`, dev only), clicks Publish, signs in through Settings with the fake's token, double-clicks Publish, and reads the v3 files back from the fake's `main` and the v2.1 files at the `v2.1` tag (`filesAtTag`: the fake keeps the files of every commit). It polls for the `v3.0` tag rather than reading it once the commit lands, since the retag is a separate request after the commit. The harness lets `hub-*` bridge calls through to Vite's real backend, pointed at the fake by `BASECASE_HUB_URL` (honoured only for https or a loopback http address).

### Training from tries

**Train from Tries** (Results section and ⌘K, desktop only, shown once the open Case has 5 passed tries) clones a policy from the Case's passed tries in Forge (§8g) and keeps it only when the Case passes it. Code: `src/workspace/useTriesTraining.ts`, `src/skills/triesTraining.ts`, `src/datasets/demos.ts`.

- **Which tries:** the passed tries that match the robot now (`usableTries.ts`, shared with Datasets) whose recording also carries each joint's velocity address and the root's (`Recording.jointDof` and `root`, recorded by every try since; `canTrain`). With fewer than 5 it says what Export Dataset says about an earlier design.
- **Rows** (`demoEpisode`): one per `episodeData` row but the last. The observation is `observe()`'s, so it's exactly what the sim's policy reads: a fixed base's constants, the Case's target as the command (`caseCommand`: the first probe end that's an object or a point, in metres), joint offsets from the default pose, joint velocities and the previous row's action. The action is the next row's actuator targets, less the default pose, over `actionScale` (the widest offset in the tries × 1.05, at least 0.25). Rows are 25 Hz, so the policy's `controlDt` is 0.04 s.
- **The job** (`triesJob`) is `trainingJob`'s fields with `algo: "bc"`, `stateNoise: 1` (§8g says why) and `demos`. `electron/trainer.mjs` writes `demos` to `demos.json` beside `job.json`, and refuses it without Forge, since `train.py` would train something else. It runs through the skills runtime's Forge (`learnFromTries`), the same user queue as other skills, so Train shows a training row named after the Case.
- **The judge:** `caseVerdict` with the policy (`CaseControl`) on 32 seeds (Arena's trial count) in the Case workers, each starting with every joint moved up to ±5° (`RunOptions.jointNoiseDeg`, drawn through Arena's `drawInstance`; seeds without it draw what they always did) on `CASE_RANDOMIZATION`. `controller: 'policy'` runs the policy in place of the reference, with the run's own target as its command and no reference timeline.
- **Kept only on a pass:** the evidence has Arena's shape with one held-out variant (`triesEvidence`), and its one-sided 95% Clopper-Pearson bound must reach Arena's 0.75: 29 of 32. Then the skill saves like any other, and its `SkillRecord` carries `case: { id, model }`, the Case and the robot model hash the Checks row reads. Train lists it as ready, and Try runs it. Below the bar nothing is saved. Either way Results shows a row with the count, such as 30 of 32 (red when it isn't kept), and, when a run failed, the worst run's filmstrip.
- **The Checks row** runs a Case with the newest skill kept for it whose `case.model` matches the robot now, in place of the reference; the verdict cache keys on the policy. `caseVerdict` picks the same skill when no control is passed, so `run_case` and Compare With judge what the row judges and still share its cache.
- **Not yet:** Drive doesn't run a Case's skill, and the method router's ask-for-demo rung doesn't send to it, since a draft carries no Case (§8i).
- **Tests:** `src/datasets/demos.test.ts` (rows against `episodeData`; a try from an older model or without velocity addresses is left out), `src/skills/triesTraining.test.ts` (the job, a refused policy saves nothing, a kept one is a ready row in Train, a policy on a fixed arm from moved start joints), `electron/trainFromTries.test.mjs` (runs once Forge is built, through `forgeBinary` and the trainer's `writeJobFolder`: 10 scripted passing tries of arm-3dof's Touch a Point train a policy that passes 32 of 32; the same tries with their actions shuffled pass 0), `electron/trainer.test.mjs` (the demos file), and `e2e/trainFromTries.e2e.test.ts` (5 driven tries passed with `__studio.passTries()`; Train from Tries with `__studio.stubTrainer` returning a policy that holds still, which the Case refuses with its count and the worst run's filmstrip; then ⌘K Train from Tries with a policy that holds the arm on the point, kept as a ready row in Train whose Try runs it).

### Running a Case

**Run Case** (the expand button in the Case's header in Simulate, and ⌘K, with a Case open) runs the open Case in the whole window, laid out by its console. It has no name of its own: what a Case shows when it runs is part of the Case. It's a mode of the scene's workspace like Print (§8f), not a second scene: `useCaseRun` (`src/workspace/`) holds it, and `CaseRunProvider` gives both sides of the canvas one signal bus and one camera feed.

**The console** (`src/cases/console/format.ts`) is four parts:

- `input`: one to four input source ids (§ Live drive). Running the Case hands them to the drive; leaving gives the studio's back. A source no one registers is refused: `leader-arm can’t drive a Case in this version` for a planned one, `is no input source` for anything else.
- `signals` (optional): the Case's own, each a plain name. A `timer` counts the try's seconds (down from `seconds` when it has one); a `counter` counts each time a signal goes `above` or `below` a value during a try; a `score` sums signals times weights. Each reads only built-in signals and the ones declared before it.
- `panels`: up to 24, each an `id`, a `kind`, an optional `title` and its kind's settings. A panel without a title shows no header, never its signal names.
- `layout.areas`: up to six columns in order, exactly one `{ "canvas": true }`, the rest `{ "size": 200–720 px, "panels": [...] }`. The canvas area can take `overlays`: code panels drawn over the canvas (§ Code panels). Every panel is placed exactly once, in an area or as an overlay.

**Signals** (`signalNames.ts` names them, `signalBus.ts` holds them) are what any panel reads. A panel naming a signal that can't exist is refused at parse with its path.

- `joint.<id>.target`, `.position` (degrees or mm) and `.effort` (the actuator's torque in N·m on a revolute joint, its force in N on a prismatic one), from the sim's frame (§8d);
- `robot.height`, `.tilt`, `.speed`, `.travelled` (the sim's robot stats) and `robot.x`, `robot.z` (the base on the floor, scene mm);
- `probe.<name>`: each of the Case's probes, live;
- `input.<source>.forward`, `.left`, `.turn`, `.lift`, `.grip`, for the console's sources;
- `goal.passed`, `goal.margin` and `goal.failed` (the labels so far) while a try runs;
- `camera.<name>`: each camera view, keyed like dataset cameras (`wrist_camera`); `camera.operator` needs the `camera`, `hand` or `face` input;
- `gesture.<name>`: 1 for half a second after that gesture, else 0, for a built-in or one of the Case's gestures; it needs the `camera` input, and a `counter` on it counts the gestures;
- `time`, and the Case's own signals.

`joint.*.position` and `camera.*` match every joint or camera, in a plot, a camera panel or a signals table; a value panel and the Case's signals read one number, so they refuse a wildcard. `useConsoleSignals` feeds the bus while the Case runs and the sim runs: from each sim frame (`subscribePoses`) at most 20 times a second of sim time, with the probes sampled from the same poses. While a try runs, `liveGoal` samples the probes at the record rate, holding the newest pose across gaps, and every half second sends the samples taken since the last judgement to a worker (`workerJudge` in `goalJudge.ts`, one per try), which appends them to the trace and judges it with the Case's contract, so the main thread never evaluates the growing trace. A judgement still pending skips the next tick, and one that comes back after its try has ended is dropped. `scoreTry` still gives the try its verdict from the recording. The bus keeps two minutes of each number for plots, starts the Case's signals over when a try starts, and notifies the panels, which read it through `useSyncExternalStore`.

**Panel kinds** are registered in one place, `PANEL_KINDS` (`panelKinds.ts`: each kind's settings reader, whether it needs the desktop app (`desktopOnly`) and whether it needs the studio's tries and cameras (`studioOnly`)), with its view in `PANEL_VIEWS` (`src/components/caseRun/panelViews.ts`), typed so a kind without a view doesn't compile. Adding a kind is those two entries. Each panel renders in a `case-run-panel` wrapper with `data-panel` and `data-kind`.

- `camera` (`signal`: one camera or `camera.*`; studio only): the camera strip's tiles, as wide as the card, from one feed for the whole running Case (`useCameraTiles`, §8l);
- `value` (`signal`): one number, large; a timer reads as seconds;
- `plot` (`signals`, up to eight, `seconds` 2–120, default 20): lines over time, the first in the accent;
- `table` (`of`): `servos` (desktop only: Operate's header with the servo count, run state and Stop, the newest daemon message and the servo rows, or Connect Emulated Robot), `joints` (each joint's `columns` of target, position and effort) or `signals` (a list of name and value);
- `button` (`action`, optional `gesture`): Try It, Stop Try, Drive, Stop Driving, Start Over, or Reset (puts the sim and the Case's signals back, only between tries, since resetting puts sim time back under a running try's clock); disabled when it can't run. With `gesture` (a name `gesture.<name>` accepts), that gesture presses it too (`gestureActions`), so a thumbs up can start a try;
- `list` (`of`): `tries` (Try and Results from Simulate; studio only) or `failures` (the contract's failed labels so far, in red, shown only while there are some);
- `text`: `of: "brief"` (the Case's brief) or its own `text`;
- `map` (`trail` seconds, default 30): the world's objects from above, the robot's base and its trail.
- `code` (`source`, `height` 80–900 px, default 320): the Case's own code, below.

**Code panels** let a Case carry its own interface: a piano, a joystick on a canvas, a HUD, four picture buttons. A `code` panel's `source` is one HTML document with its script and style inline, at most 256 KB (`CODE_SOURCE_MAX_BYTES` in `electron/caseCodeLimits.mjs`, read by `parseCase`, the agent's prompt reference and the descriptions of `create_case` and `write_case_code`); a console holds at most four code panels (`parseCase` refuses the fifth and a bigger source by path). It's placed in an area like any panel, or over the canvas as an overlay: `{ "panel", "anchor", "width", "height", "pointer" }` in the canvas area's `overlays`, anchored to a corner (`top-left`…`bottom-right`, width and height), an edge (`top` and `bottom` take a height, `left` and `right` a width, and span the canvas) or the whole canvas (`fill`), 12 px in from the card's edge. An overlay lets clicks through to the canvas unless `pointer` is true. `consoleLayout` returns the overlays apart from the areas, and `CaseRunOverlays` draws them in the canvas card.

- **The frame** (`CodeFrame`, `src/components/caseRun/code/`): an iframe from `srcdoc` with `sandbox="allow-scripts"` and no `allow-same-origin`, so the code gets an opaque origin. `codePanelDocument` (`src/cases/console/codeDocument.ts`) writes a CSP, the design tokens and the bridge's client ahead of the source (Security, §0h).
- **The bridge** (`codeBridge.ts` on the studio side, `codeClient.ts` in the frame, messages in `codeProtocol.ts`, version 2): the client says hello to the parent, and the studio answers that frame alone (`source` must be its `contentWindow`) with a `MessagePort`; everything after goes over that port, and each message is read field by field (`readFrameMessage`) and refused when it's malformed. The code sees `window.basecase`:
  - `signals(names, onValue)`: the bus's values for those names (a name or a list, with the same wildcards and checks panels use, numbers and labels only), sent when the bus changes and at most 20 times a second (`codeSignals.ts`). Only subscribed values cross, never the whole bus.
  - `drive(command)`: `{ v: [forward, left, turn], aux?, target? }`, each axis −1 to 1, or `null` to let go. It's the `code` input source (`codeDrive.ts`): the console lists `code` in `input` like any source, the drive's precedence applies, the newest command of any code panel wins, and it lasts until the panel sends another or unloads.
  - `event(name, value)`: a named event to the Case's logic through `Simulation.input` (§ Logic); `value` defaults to `true`.
  - `action(name)`: one of `CASE_ACTIONS`, answered `{ ok, problem? }`; refused while it can't run, as a button panel would be disabled.
  - `world.set(name, { pose?, visible?, color? })`: moves, hides or recolors one of the Case's world objects, sent without an answer like `drive`. `pose` takes a `position` in mm (each axis within 50 m) and a `rotation` in degrees (within 3600), `color` is `#rrggbb`, and a NaN or infinite number makes the message malformed (`readWorldChange`, `src/cases/worldSet.ts`). The position is in the Case's own mm, as authored. The studio refuses an object that isn't in the Case's world, which every robot part isn't, or isn't `movable` (`worldRefusal`), before anything reaches the sim. It maps the rest through the scaling `scaledToReach` gives the world (`stagedChange` with `movableWorld` in `scale.ts`, kept on `PanelContext.world`), so a spot the code lights lands on the scaled spot on any arm, and sends them to `Simulation.world`. The try records the scaled pose. A bridge takes 60 calls a second (`WORLD_CALLS_PER_SECOND`) and drops the rest, noted once a second.
  - `frames(camera, { width?, fps? }, onFrame)`: a camera's picture as an `ImageBitmap`, through `CameraTiles.stream`, and a function that stops it. The Scene and stationary views and the robot's cameras stream, never the computer's camera (Cameras, §8l). `width` is a whole number from 16 to 640 px (default 320), the height is three quarters of it (at most 640 × 480), and `fps` is 1 to 15 (default 10) (`codeStreams.ts`). A panel holds at most four streams. The bridge paces each stream to its rate and closes a frame that comes before the stream has earned one, so a fast camera never beats it; a stream may bank up to one and a half frames, so a camera that sends at the rate with a little jitter isn't halved. It transfers each frame it keeps over the port instead of copying it. A frame that comes after its stream stopped or its bridge closed is closed and never sent.
  - `store.get()` and `store.set(value)`: one JSON value per Case, such as a high score or a setting, kept on this computer and never in the Case (`codeStore.ts`). The client stringifies the value in the frame and sends the string, so the studio never walks an object graph the code built: a graph of shared references that would expand to billions of nodes costs the studio nothing, and only the frame that stringifies it pays, unloaded by the heartbeat if it hangs. The bridge refuses a string over 64 KB (`STORE_MAX_BYTES`, by length and then by UTF-8 bytes) or one that isn't JSON, and takes 10 store calls a second (`STORE_CALLS_PER_SECOND`), answering each refused call `{ ok: false, problem }`. `get` resolves the value or `null`; `set` resolves `{ ok, problem? }`, and `set(null)` clears it. Values live in IndexedDB (`basecase-case-stores`, keyed by the scene's id and the Case's id, `caseStoreKey` → `<sceneId>/<caseId>`, since a Case id is a slug of its name and is unique only within its scene; through `indexedDbStore` in `src/utils/keyValueStore.ts`, which the tries store uses too). `CASE_STORES` keeps each Case's newest value in memory, so every panel of one Case reads the same value at once, and writes one value at a time per Case: values set while a write runs wait, and only the newest is written next. Keeping it out of the Case means a new score never changes the Case's hash, so Checks, Compare, Explore and the verdict cache never rerun for it, and the score never leaves the machine in a saved `.basecase` file or a Share Robot bundle. The cost: a shared Case, an imported `.basecase` file and a duplicated scene start with an empty store, since each gets a new scene id. Reset and Start Over never touch it; deleting the Case deletes its value (`useCases`), and deleting the scene deletes every value under its id (`CASE_STORES.deleteScene` in `useSceneLibrary`, one IndexedDB key range). The web gallery has no store: `get` answers `null` and `set` is refused.
  - CSS variables for the studio's greys, accent, type sizes and radii (`CODE_PANEL_TOKENS`, Design system §14), so a panel can match the app.
  - Esc and ⌘K pressed inside the frame go to the studio as a `keydown` on its window, so they work as they do outside it.
- **World changes in the sim** (`src/sim/worldMoves.ts`): `buildMjcf` writes a movable `static` or `marker` object as a mocap body (`mocap="true"`) and a movable `dynamic` one with its free joint as before; `SimBody.moves` says which, with the object's rest rotation. The sim worker's `WorldMoves` applies each `world` request (`Simulation.world`): a pose sets a mocap body's `mocap_pos` and `mocap_quat`, or teleports a free body (its `qpos`) with zero velocity; hiding zeroes the object's geoms' `contype` and `conaffinity`, so a hidden wall lets the robot through and a hidden crate falls through the floor until it's shown again, where it was hidden unless the same call places it; a color sets the geoms' `geom_rgba`. It checks the name again and drops anything not movable without telling the panel; the bridge has already checked against `PanelContext.world`, so that happens only when a loaded model's world differs from it. Looks (visible and color) go back to the main thread as a `world` message; `Simulation.worldParts` carries them (`withLooks`, one object per changed look, so only that part's mesh rebuilds), so the canvas and the camera worker show them. Reset and a new model put every object back at its rest and its looks back as authored (R's respawn moves only the robot); a try that starts a new model starts from that world, so code that shapes the world does it once the try runs.
- **Recorded on the try.** `Recorder.worldChange` keeps each applied change on `Recording.world`, stamped with the try's time like a command, and the world as it stood when the try began is logged at 0 (`WorldMoves.state`). `tryManifest` counts them in `world`. A mocap body's pose is in the recorded body poses, so `scoreTry`, probes (`{ object }` ends read a movable object's live pose through `worldDeltas`) and Case facts see the moved world with nothing extra. `replayTry` (Multiply, § Tries) applies the changes at their times, the try timeline's seek replays them up to the frame (`WorldMoves.replay`, without moving free bodies, whose `qpos` the recording holds), and `runCase` takes `world` events on its record clock in the staged (scaled) frame, as a try records them, not the Case's authored mm the bridge takes. One seed and the same events give the same poses.
- **Sound** needs no bridge: Web Audio runs in the frame, and Chromium plays it only after the person's first click or key press inside that frame.
- **Errors:** each bridge keeps a report (`bridge.report()`): whether the panel loaded or failed, its first 10 uncaught errors with their line counted from the source's first line (`codeSourceFirstLine`, since the client and tokens sit ahead of the source in the document), its first 20 console lines (the client forwards `console.log`, `info`, `warn`, `error` and `debug`, 20 at most) and its first 20 refused calls with why. `useCodeBridge` registers each running panel's report under its Case and panel id with its source (`codeReports.ts`), where the agent's `write_case_code` and the bench read it. The client sends an error's own sentence, without Chromium's “Uncaught” or an “Error:” prefix (§3b-9). Once it has handed over the port, the studio pings every 500 ms. A panel that hasn't answered a ping for 2 s, hasn't said hello within 10 s (`HELLO_MS`), or whose script throws before its document has loaded, is unloaded and shows one line in its place: “Couldn’t run ⟨title⟩. ⟨first error⟩” (“It didn’t answer.” for a silent one). The hello limit is what catches a panel that hangs while it loads: Chromium sends a frame's `postMessage` to another process from a later task, so a script that never yields never gets its hello out. The 2 s run from the oldest unanswered ping. A tick that comes more than 1 s after the last one means the page's own thread stalled (a model build, a big scene opening), and a healthy panel's answer may still be queued behind the tick, so the bridge pings again instead of unloading; a panel that misses that ping too is unloaded, even when the page stalls again (Security, §0h). A panel that sends more than 240 messages a second has the rest dropped.
- **Remounting:** a code frame is keyed on its bus and a hash of its source, the console's inputs, its declared signals and the Case's probes (`codeFrameKey`), so a changed source or console gets a fresh frame, bridge and port, and the bridge never checks `drive` or a signal against an old console. The bus itself is keyed on the Case, the console's inputs and its signals only (`useConsoleSignals`), so a new source for one panel reloads that panel alone: the sim, the try and the other panels go on. Each bridge drives as its own owner in `codeDrive.ts`, so two scene tabs with a panel of the same id never clear each other's commands.

### The agent writing a Case's code

The agent builds a Case app the way a person would with a web page: it writes a code panel, sees it run, reads what went wrong and writes it again, while the person watches the Case. `create_case` (§ Making a Case, Agent §9) still picks the robot, inputs, built-in panels and world; code panels are written and revised with their own tools.

- **Edits** (`src/cases/console/codeEdits.ts`, pure): `withCodePanel` writes or replaces one code panel, starting from `DEFAULT_CONSOLE` when the Case has none. A new panel goes to the column beside the canvas on its `place`'s side (`{ side, size }`, the right by default, a new 320 px column when there's none) or over the canvas (`{ overlay: anchor, width, height, pointer }`); a replaced one keeps its title, height and place unless the write names new ones. It adds `code` to the console's input while there are fewer than four, and refuses to turn a built-in panel into code. `withoutCodePanel` takes one out of the panels and the layout, dropping a column it empties. Every result goes through `parseCase`, so a source over 256 KB or a fifth code panel comes back with its path and changes nothing.
- **Requests** (`src/workspace/agentCaseCodeRequests.ts`): `write_case_code`, `read_case_code` and `delete_case_code` find the Case by id or name (the open one, or the only one, when left out). A write or delete is one undo step: `commitConsole` (`useSceneDocument`) pushes that Case's console onto the scene history as `consoles`, keyed by the Case's id, and undo and redo put back only those consoles (`travelProject` in `docHistory.ts`), so ⌘Z walks the agent's revisions back one by one and Case edits made outside the history stay. While a Case runs, undo and redo step only entries that carry `consoles` and stop at the first that doesn't (`codeOnly`), so the parts, joints and marks never change during a run. A write opens the Case running when it isn't (`cases.open`, `useCaseRun.enterCase`); when it is, nothing but that panel reloads. It then waits for the new source's report (`settledReport`: up to 12 s to load or fail, then 2 s more). For its first second it reads only a bridge registered after the write (`codeReportsWatched` in `codeReports.ts` counts registrations), so a write that remounts the frame with the same source never answers with the old frame's report and replies `{ ok, case, panel, running, loaded, errors, logs, refused }`. The window capture is added by the agent's tool (Agent §9).
- **The loop:** while a Case runs, the agent panel stays beside it when it was showing (§ Running a Case), and a message sent from it carries a note naming the running Case (`runningCaseNote`, `useAgentRun`), so the agent changes that Case's app, as with `/case`.
- **Tests:** `codeEdits.test.ts` places, moves and removes panels; `agentCaseCodeRequests.test.ts` runs writes through the real client and bridge in the test frame: a syntax error replies with its line, a refused call and console lines are listed, a write to a running Case neither reopens it nor enters it again, two writes are two undo steps that restore the earlier source and keep a Case edit made between them, undo during a run stops at a parts edit before the writes, and a source over 256 KB is refused through `parseCase` with nothing committed. `codeReference.test.ts` keeps the prompt's reference in step with the bridge. `e2e/caseCodeAgent.e2e.test.ts` runs a rover Case, starts a try, sends recorded `write_case_code` requests through `__studio.agentRequest` and checks the panel appears and changes while the try keeps running, that a broken write replies with its line and that ⌘Z puts the earlier source back; a second test checks that ⌘I shows the Agent tab alone beside the running Case, and that a message sent there carries the running-Case note with the try still going; a third grades micro-eval task W6 in the app (Benchmark guide), the empty Case failing and the reference remote passing.

### Web gallery

`app.basecase.so/c/<slug>` opens one Case in the browser, and `app.basecase.so/r/<account>/<repo>` opens a robot someone shared from the desktop app. `src/webMain.ts` turns the path into the bundle's address (`galleryBundleSource` in `src/gallery/galleryLinks.ts`: a slug is letters, digits and dashes only; an account and repo follow the Hub's name rule) before anything heavy loads; phones keep the landing page. The gallery page (`src/gallery/`) is its own small app: the canvas, the Case card (name, brief, Drive, Train for a legged robot, Open Scene; `GalleryCard.tsx`) and the drive overlay. It starts the simulator as soon as the canvas is up, so MuJoCo's WASM is fetched while the visitor reads.

- **A Case's console** runs on the page as Run Case runs it in the studio. When the bundle's Case has a console, `GalleryApp` loads `GalleryConsole.tsx` (its own chunk, fetched only then) before the page mounts, so the canvas mounts once. `consoleLayout` with `{ desktop: false, studio: false }` leaves out the servos table, camera panels and the tries list. The rest sit in their areas around the canvas, code overlays over it, and the Case card heads the last area, or floats on the canvas when the console has no areas. Docked, the card leaves out the keys and the “Checking it stays up…” line, so its height never changes: a card that grew when a code joystick started the drive moved the joystick's frame under the pointer, and Chrome stopped sending that frame the press's moves. The console's `input` drives (`drive.setInputs`), so a code panel drives through the `code` source; a Case action runs what the page has (Drive, Stop Driving, Start Over, Reset), and Try It and Stop Try are refused. Code frames mount once the simulator is ready, so they start after the canvas. The frames are the studio's (`CodeFrame`, the same sandbox and CSP), and the code is someone else's on our origin (Security, §0h). A panel's `world.set` moves the Case's movable objects as in the studio (`PanelContext.world` holds the Case's world objects and their scaling for both) and `frames` sends nothing, since the page has no camera views. A Case without a console opens as before. Nothing autosaves; Open Scene turns the bundle into a scene with `bundleScene` (`galleryBundle.ts`, also what first launch opens, §5a), saves it once into the web app's IndexedDB, opens it as the first tab and goes to the studio.

- **Bundles** (`public/gallery/<slug>.json`, `index.json`) carry everything they need: the robot's parts and joints, the Case and, when there is one, a trained policy or skill, validated by `parseGalleryBundle` on read and capped at 8 MB (`GALLERY_BUNDLE_MAX_BYTES`). One builder makes them, `galleryBundleOf` in `src/gallery/buildBundle.ts`: `npm run gallery` (`tools/gallery/build.mjs`, entries in `src/gallery/galleryEntries.ts`) feeds it the fixtures, and Share Robot feeds it the open scene. The two-wheel rover, which is also the first-launch scene (§5a), is `roundWheelRover`: `rover-diff` with cylinder wheels turned onto x. `rover-diff` itself has box wheels, whose hulls are cubes that roll on their corners (the first-launch rover came to rest 17° off level on them); the Case tests and the `verify/` margins gate are tuned to that fixture, so it keeps them until both are retuned. The Case goes in whole, with its console's code panels and its logic, so Open Scene opens the same app in the studio's Run Case, where the agent can revise it. A part whose mesh the web app can't load (a component whose GLB isn't shipped in `public/parts/`, such as a part the agent sourced) becomes a `mesh` part with its triangles inlined from the viewport (`partTriangles`, welded at 0.01 mm), and a SimReady part drops its textured visual for the mesh it already carries. A unit test fails when the shipped fixtures drift from the code.
- **Share Robot** (Results and ⌘K, desktop only, with a robot and an open Case; `src/workspace/useShareRobot.ts`, `shareRobot.ts`) builds a bundle from the open scene: the parts in the sim model's robot bodies, the joints, the open Case, and the newest policy that stood its evaluation (`eval.fellAt` null, not stale) or skill whose row is ready, whichever is newer. The bundle must encode under 8 MB and parse back, or it stops with “Couldn’t share the robot.” and the reason. It goes to a dataset repo on the signed-in account through the same commit path as Publish (`hubBridge.publish`: `basecase-robot.json`, and a `README.md` whose card holds one tag, `basecase-case` (`SHARED_CASE_TAG`), so the Hub's search finds every shared Case; sharing again rewrites that card), named `<scene>-<hash>` with the start of the SHA-256 of the scene id and the Case id, so sharing again from the same scene and Case updates the same link. The link, `https://app.basecase.so/r/<account>/<repo>`, is copied to the clipboard and the toast says Link copied; signed out, it opens Settings ▸ Accounts. The web page fetches the bundle from the Hub's resolve URL (see Security, §0h) and opens it in the same `GalleryApp`. Open Scene also stores a carried policy or skill in the web app's IndexedDB (store `trained`, read by the `policy` and `skill` routes in `webBackend.ts`) and adds its record to the scene. A Stand trained on the page (below) takes the bundle's place.

- `src/workspace/shareRobot.test.ts` builds the Share Robot bundle from a fixture scene with a sourced part and a trained policy or skill, checks the files it publishes (the bundle and the tagged card), and `src/gallery/sharedRobot.test.ts` resolves a shared link to its bundle, carries a Case's code panels and logic through the bundle and into the scene that Open Scene saves, and refuses a code panel that takes the bundle over 8 MB with the same message. Share Robot has no e2e test: `e2e/gallery.e2e.test.ts` already drives a shared bundle in the web build and opens it with Open Scene.
- **Train** (Forge F6, §8g): on a legged robot, when `tabTrainingReady()` finds JSPI and a WebGPU adapter (`trainingOffered.ts`), the card shows Train between Drive and Open Scene; phones and browsers without WebGPU never see it. Pressing it imports `galleryTrainer.ts`, which runs Stand through the studio's own `SkillsRuntime` and `skillsPlatform` (the tab engine, and skills saved through `webSkills.ts` to IndexedDB store `skills`), and builds the robot's model without the Case's world (`buildModel({ alone: true })`), so the design hash matches the studio's scene. Nothing of Forge, the trainer or the skills worker loads before the press. The button then gives way to Stand's row from the studio's `SkillsList`: progress with Stop, then the Arena line with Try, or, when Arena refuses, the untrained row with Train again. When Arena passes and the visitor isn't driving, the live sim runs the skill's policy (`useGalleryTraining.ts`). `window.__forge` (`src/forge/forgeHook.ts`) calls the same path: `train()` resolves with the Stand record, or null, and `events()` lists Forge's status and progress lines. `window.__gallery` adds the sim's controller kind, the running skill's hash and trained steps, Stand's row, and `stubTabEngine`. `e2e/forgeTab.e2e.test.ts` ("forge tab trains", gate `s1-f6-webgpu`) presses Train on the hexapod link in headless Chrome on the GPU, and needs Arena's pass, the WGSL engine's status line and a policy with trained steps within 15 minutes.
