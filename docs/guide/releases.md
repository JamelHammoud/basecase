# Releases and updates

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 0i. Releases and updates

- **Releasing:** Actions → Release → Run workflow (`.github/workflows/release.yml`), with a version like `0.2.0`. Three jobs:
  - `mac` builds on `macos-latest` (arm64 only), signs with a Developer ID Application certificate, notarizes, reads both back off the app (`codesign` authority, `stapler validate`, `app-update.yml`, both native addons) and runs `test:app` on the signed app.
  - `windows` builds the NSIS installer on `windows-latest` (x64), signs it with Azure Artifact Signing when signing is set up, checks the signature (`Get-AuthenticodeSignature`) and the update files, then uploads them, as Crew's release does. It doesn't install or drive the app: `electron.launch` hung on the installed copy on the runner, and Check already drives the unpacked Windows build.
  - `publish` runs once `mac` passes, so a failed Windows build never holds back the Mac release; that release then has only the Mac files (with a warning), and the Windows latest download link 404s until a release carries both. It creates release `v<version>` with `Basecase.dmg`, `Basecase-Setup.exe`, the zip, the blockmaps and every channel feed (`latest*.yml`, `beta*.yml`, `alpha*.yml`; `generateUpdatesFilesForAllChannels`). The version bump lives only in that run: `package.json` keeps its version, so pass one every time, higher than the last.
- **Secrets:** `CSC_LINK` (the `.p12`, base64), `CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`, the same five crew uses. The workflow makes its own signing keychain, since electron-builder's breaks on the macOS 26 runner.
- **Windows signing:** repository variables `AZURE_SIGNING_ACCOUNT`, `AZURE_SIGNING_PROFILE`, `AZURE_SIGNING_ENDPOINT` and `AZURE_SIGNING_PUBLISHER` (the certificate's subject name), plus secrets `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` and `AZURE_CLIENT_SECRET` for an app registration with the Artifact Signing Certificate Profile Signer role. They're passed as `-c.win.azureSignOptions.*`, so local builds stay unsigned. Without `AZURE_SIGNING_ACCOUNT` the installer is unsigned (SmartScreen warns) and is published anyway, as Crew's is.
- **The latest download** is `https://github.com/JamelHammoud/basecase/releases/latest/download/Basecase.dmg` (`LATEST_DMG_URL` in `electron/updates.mjs`). GitHub redirects `/releases/latest/download/<file>` to that file on the newest release that isn't a draft or prerelease, so the dmg's name never carries a version (`build.dmg.artifactName`). The zip keeps its version: it's what updates download, and `latest-mac.yml` names it. The installer works the same way (`build.nsis.artifactName`, `latestDownload` in `updateState.mjs`): `…/latest/download/Basecase-Setup.exe`, and `latest.yml` names it. Never publish a release as a draft, and never publish a stable version as a prerelease: neither the link nor the updater sees it.
- **Betas:** a version with a prerelease tag (`0.3.0-beta.1`) is published as a prerelease. Only apps with Help (App menu on macOS) → Get Beta Updates checked see it (`channelOptions`: channel `beta`, `allowPrerelease`, never `allowDowngrade`; saved in `update-channel.json` in user data). Beta apps also take stable releases, since every stable release carries `beta*.yml`. Ship to Windows (and anything risky) as a beta first, have testers on real machines run the QA list in [docs/Windows plan.md](../../docs/Windows%20plan.md), then release the same commit as stable.
- **Updates** (`electron/updates.mjs`, pure stages in `updateState.mjs`): a packaged app checks GitHub at launch and every hour, downloads in the background, and only when the download lands shows the update button in the view rail (§2). Clicking it quits, installs and relaunches (`quitAndInstall`); nothing installs on a plain quit. App menu → Check for Updates answers in a dialog. An install that hasn't happened 60 s after the click says so and offers the latest dmg (the installer on Windows). The log is `updates.log` in user data. `electron-updater` is imported as a default and `.autoUpdater` read from it: its named export is a getter Node's ESM loader can't see. Updates need a signed app: an unsigned build installs the dmg by hand once.
- **Packaged vs source** (`fromSource = process.defaultApp` in `main.mjs`; `npm start` and `electron:dev` are from source):
  - `library/` and `ai-reference/` live in user data (`~/Library/Application Support/Basecase`), not in the read-only app; from source they stay in the repo (`dataRoot`).
  - The app always loads the built bundle.
  - A Finder launch gets launchd's PATH (`/usr/bin:/bin:…`), so `adoptShellPath` (`electron/shellPath.mjs`) reads PATH from the login shell before the agent starts. With no `node` on it, agents, the CAD MCP server and the kernel run on Electron's own Node (`BASECASE_NODE`, `ELECTRON_RUN_AS_NODE`; `nodeRuntime` in `agentProcess.mjs`). That Node is 24, so the kernel then runs without the permission model (§0h).
- **Packaging** (`build` in `package.json`, `npm run dist`; output in the gitignored `release/`): no asar, since the agents and the kernel run the app's own files with an outside Node. `dependencies` are only what the main process and its child processes load (agent adapters, MCP and ACP SDKs, the CAD kernel's packages, three, zod, electron-updater); the renderer's packages are dev dependencies, since Vite bundles them. The macOS app is a 196 MB download (443 MB installed); it was 520 MB (1.3 GB) when it carried the agent CLIs and uncompressed part meshes. Only English Electron locales ship (`electronLanguages`), and `replicad_multi` and `three/src` are left out.
- **Agent CLIs download on first use** (`electron/backend/agentRuntimes.mjs`). The Claude Code, Codex and Gemini CLIs (`@anthropic-ai/claude-agent-sdk-<platform>`, `@openai/codex-<platform>`, `@google/gemini-cli`: 263, 340 and 95 MB) aren't packaged; their adapters are. Before spawning an agent, `AcpAgent.connect` asks `AgentRuntimes.ensure`: from source it uses `node_modules`; packaged, it reads `electron/backend/agent-runtimes.json` (version, tarball URL and sha512 for this platform from `package-lock.json`, written into the app by `tools/release/afterPack.mjs`, which also fails the build if a CLI got packaged), downloads the tarball into `library/agents/<platform>-<arch>/<pkg>@<version>/`, checks it, extracts it with the system `tar` (no shell) and drops older versions. The adapter is pointed at it with `CLAUDE_CODE_EXECUTABLE` or `CODEX_PATH`; Gemini's script path is rewritten. Progress reaches the Agent tab as `status.download` (“Downloading Claude Code…”, a percent and a bar, `ConnectionBanner`); a failed download is the connection error, and Reconnect retries. Never point an adapter at the user's own installed CLI: its version drifts from the one the adapter pins. electron-builder drops every `examples/` folder from `node_modules`, so the two three.js modules the main process imports come back through `extraResources`; so do `manifold-3d`'s `manifold.js` and `manifold.wasm` for the CAD kernel's hull fallback (the package stays a dev dependency: its own dependencies pull in sharp); a new deep import from a package's `examples`, `test` or `docs` folder needs the same. A local build: `npx vite build && CSC_IDENTITY_AUTO_DISCOVERY=false npx electron-builder --mac --arm64 --dir -c.mac.forceCodeSigning=false`; `--dir` skips `app-update.yml`, so it can't update.
