# Joints, poses and motion

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8c. Joints, Poses and Motion

A robot is posable once its degrees of freedom are declared. Posing never edits parts: the modeled pose is the design, and a pose only changes what the canvas shows.

- **Data** (`types/robotics.ts`, saved with the scene in `ProjectSettings`): `joints` (`RobotJoint`: revolute in degrees or prismatic in mm, parent and child parts, `parentJoint` when links between joints have no geometry, origin and axis, range, limb), `pose` (the pose on the canvas: values by joint id plus an optional whole-body `root` offset), `poses` (saved) and `animations` (`RobotAnimation`: keyframes with every animated joint, smooth or linear, loop).
- **Several robots per scene:** `buildRig` finds each robot (joints linked through a parent joint or a shared part, plus unlisted parts grouped with one robot's parts) as `rig.robots` (key = its first base joint id, name = its parts' group). The scene pose holds every robot's joint values and each robot's body offset in `roots` by key; `robotRig` gives one robot alone for IK, gaits and mocap, and `withRobotPose` puts its result back without touching the others. Saved poses and animations carry `robot`; the Pose tab, ⌘K Rest Pose, walk cycles and Import BVH work on the selected robot only, and the agent tools take `robot` (default: the selected one, or the only one). Imported robots get unique joint ids (a second G1's are `left_knee_joint_2`), and scenes saved with repeated ids are renumbered when they open (`uniqueJointIds`).
- **Joints follow their mount:** `frame` stores the pivot in its first parent part's own frame (`anchorJoint`); `resolveJoints` reads it back, so moving or undoing the robot keeps joints in place.
- **Kinematics** (`utils/kinematics.ts`): `buildRig` turns joints into a tree; each part moves with the deepest joint that lists it as a child, a joint's mount moves with the joint above it, and an unlisted part follows its group only when the whole group moves with one joint (a group spanning a whole robot says nothing). `forwardKinematics` composes rest-frame rotations from the base out. `solveIK` is damped least squares (Levenberg–Marquardt) with joint limits; torso joints are stiffer so limbs reach first; `preBend` starts knees and elbows bent the way their range opens (straight joints are singular).
- **Fasteners follow what they clamp** (`src/assembly/followers.ts`, `rigJoints.ts`): in verify, poses and the sim, a screw moves with the deepest joint whose moving set holds everything it clamps, ignoring that joint's own servo (the horn-screw exception); nuts follow their screw, inserts their host. Joints never list fasteners. On Ribbit it reproduced the agent's 672 hand-listed moving screws on all but one fixed pseudo-joint.
- **Joints belong to their parts.** Deleting parts deletes every joint whose moving side is gone and drops the deleted ids from the rest (`jointsWithoutParts` in `kinematics.ts`, run by every `commitParts`); undo brings parts and joints back together.
- **Undo:** pose changes are on the scene's undo timeline. Each history step (`Snapshot` in `SceneWorkspace`) holds the parts, the joints and the pose; `usePosing` reports every pose edit (sliders, the ring, saved poses, Rest pose, the agent's `pose`) through `onPoseEdit`, and edits less than 700 ms apart fold into one step, so a drag undoes in one go. Playback, scrubbing and pausing aren't recorded.
- **Canvas:** `Viewport3D` takes per-part rest → posed motion (`pose`). Measurements, interference (check_scene), servo outputs and sweeps run in the modeled pose (`withRest`); renders show the pose. Moving a part while posed maps the edit back to the modeled pose.
- **Pose tab** (right panel, beside Inspect, only while the selection is on a robot; P opens it, selecting the first robot if needed). It shows that robot's animations, poses and joints: while it's open, clicking a part picks the joint that turns it, and a single ring on its axis (an arrow for a slider) turns it in 1° / 1 mm steps (Shift is free). Picking a toolbar tool leaves the tab. Contents: Animations (play, scrub, + → Walk Cycle or Import BVH, or straight to Import BVH when the robot has no legs; right-click for Loop, Rename, Delete), Poses (Rest pose and Save pose in the header; click applies), then one collapsible section per limb (Head, Torso, Left arm…) with label · slider · value rows. The selection bar hides while posing.
- **Animation** (`utils/animation.ts`): `sampleAnimation` (Catmull-Rom or linear; whole-body turns slerp), `buildKeyframes` (values and IK goals per keyframe), `buildGait` (any number of feet; stance feet stay planted, swing feet lift; stride, lift, period, duty, crouch, bob, sway, heading and oscillators default from the leg length). Playback runs in `usePosing` and drives the canvas directly; pausing commits the frame as the pose.
- **Posable hands** (`data/articulatedParts.ts`): catalog parts whose maker publishes a URDF / MJCF with the joints (Amazing Hand, LEAP, ORCA, Ability, Dex3-1, Dex5-1, Allegro, Linker L10 and O6) go in from Parts → Hands (click, + or drag) as that articulated model: links as `mesh` parts, fingers as joints, turned by the same `rotate` as their catalog mesh (`importRobot`'s `rotate` option uses tools/parts' `(x, z, −y)` frame), framed and selected. The palm carries `componentId`, so the Inspector shows Product and the BOM counts the hand once. If the description can't be downloaded, the fixed catalog mesh goes in instead. Hands without a published description (Inspire, HOPEJr, Aero) stay one mesh.
- **The maker's data is never missing:** an import captures everything the checks and tools use (link masses and centres of mass, joint ranges, torque and speed limits), and every link records where it came from (`ScenePart.robotLink`: robot, link, source link, `rotate`, data `version`). When imports start capturing something new: add it to `publishedData` (it feeds both the import and the upgrade) and bump `ROBOT_DATA_VERSION`. Robots below the current version are upgraded from their description alone (no meshes), matched by link and joint name so poses and edits are kept: open scenes when they load (undo history included), saved scenes in the background when the app starts (saved back in place, `keepUpdatedAt`). Older robots without a recorded source are found by name (a preset, a Parts hand, Robots → Imported); one that can't be found gets a toast to insert it again. Animations report joints faster than their speed limit.
- **Published robots** (`utils/robotImport.ts`): URDF, xacro and MJCF (defaults classes, includes, hinge chains on one body, visual geoms) with STL / OBJ / DAE / GLB meshes from a link, a GitHub or Hugging Face repo, a zip or a folder (Git LFS works; `package://` is resolved against the repository). Each link with geometry becomes a `mesh` part (simplified with meshoptimizer toward a ~220k-triangle budget, never past 0.2% error, so cracked published meshes keep more triangles instead of tearing; not printed, not resized); every revolute / prismatic joint keeps its axis and limits. Robot frame (REP-103) → scene: `(y, z, x) × 1000`. Collada keeps the file's own axes. Every import from a link renders a preview (`robotPreviewImage` in `utils/robotPreview.ts`: the Library's thumbnail renderer, cropped to the robot, WebP) after the robot is inserted and remembers it (`localStorage` `robots-imported`). Presets ship theirs in `public/robots/<id>.webp`, made by the same import: `node tools/robots/previews.mjs [id…]` (rerun it when a preset is added). Presets (`ROBOT_PRESETS`, each checked to import whole): Unitree G1, H1, H1-2, Apptronik Apollo, Booster T1, Berkeley Humanoid; ROBOTIS OP3, Open Duck Mini v2; Unitree Go2, Go1, B2, ANYmal C, Spot; SO-101, Franka Panda, UR5e (the Robots view, ⌘K, File → Import Robot). MJCF `<frame>` elements are followed, and collision-class or group-3 geoms are skipped.
- **Motion capture** (`utils/mocap.ts`): BVH through three's `BVHLoader`, bones matched to landmarks by name (Mixamo, CMU, Daz `lShldr`, UE `upperarm_l`…), robot joints matched by name (`left_knee`, `LL_KFE`, `FL_calf`…). Retargeting points each robot segment the way the performer's segment points (so proportions and rest poses can differ), moves the body by the hips scaled by leg length, and keeps feet on the floor while the performer stands. The Retarget sheet shows the match (changeable), In place, Loop and frame rate.
- **Where robots come from** (`utils/robotImport/`): one import, one field (Import Robot sheet). It takes a link to a `.urdf`, `.xacro`, `.xml` / `.mjcf` or `.zip`, a GitHub repo, folder or Download ZIP link (`github.com/o/r`, `…/tree/<ref>/<folder>`, `…/archive/<ref>.zip`: the file list comes from the GitHub trees API, files from `raw.githubusercontent.com`, only paths in that list are read), a Hugging Face Hub model or dataset repo, folder or file link (`huggingface.co/o/r`, `…/datasets/o/r`, `…/tree/<rev>/<folder>`, `…/blob|resolve/<rev>/<file>`, `hub.ts`: the file list comes from the Hub's public tree API `api/<models|datasets>/o/r/tree/<rev>?recursive=true`, following its `Link` next page only on that same API path; files from `…/resolve/<rev>/<path>`, only paths in that list are read; a file link lists the repo and imports that file only, never another robot in the repo, and fails naming the link when a complete listing lacks it; the listing stops at 20 pages, after which a file link still reads its file straight and a repo or folder link fails as unopened; a `.zip` file is downloaded like any zip link; `datasets`, `spaces`, `docs` and the Hub's other top-level pages aren't repos), a chosen folder, or a folder, zip, `.urdf`, `.xacro`, `.mjcf` or `.xml` dropped on the canvas (`useCanvasDrop` → `droppedRobot.ts`, which walks dropped folders and skips `.git` / `node_modules`; a dropped `.xml` that isn't a description gets the import's error toast). Links, zips and folders become one file tree (`tree.ts`), and `chooseEntry` (`entry.ts`) picks the description: an MJCF with a `<worldbody>` that isn't a `scene*.xml`, then a URDF (a `.urdf`, or an `.xml` whose root is `<robot>`), then a scene, then a xacro (below), then an MJCF whose bodies sit in its `<include>`s. A plain URDF beside its xacro still wins. Among `.xacro` / `.urdf.xacro` files whose root is `<robot>`, the import takes the top-level one: files another xacro includes (matched by file name) drop out, then those in `urdf/`, `description/` or a `*_description/` folder and those named after their `<robot name>` or package win, then the shallowest. A link with no description fails with one toast naming the link (`noRobotAt`); a repo that can't be listed (missing or private) names it too (`unopenedRepo`). ROS package files (`package.xml`, launch, config, rviz, worlds, tests) never count, and only the shallowest candidates compete. One left: it imports. Several at the same depth: the sheet opens with the list (`RobotChoiceError` → `robotChoice`), and the pick comes back as the source's `entry`. The agent's `import_robot` gets the list as text and passes `entry`. A part's `robotLink.url` is the file the import read, so a repo import upgrades like a file link, and Robots → Imported remembers that file, not the repo. **Xacro** (fusion2urdf packages, ROS description repos) is expanded in the page before `urdf.ts` reads it (`xacro.ts`, with `xml.ts`, `xacroScope.ts` and `xacroExpr.ts`): `xacro:include` (read through the import's own resolver; `$(find pkg)` becomes `package://pkg`), `property` (value, default, block, `scope`), `macro` with params (`:=` defaults, `^` and `^|` from the caller, `*` and `**` blocks), `insert_block`, `if` / `unless`, `call`, `element`, `arg` defaults, `$(arg)`, `$(find)`, `$(dirname)`, `$(optenv)` with a default, `$(eval)`, `$$` escapes and `${}` expressions. Expressions are Python's arithmetic, comparisons, `and` / `or` / `not`, `a if c else b`, strings, `pi` and a fixed list of math functions (`radians`, `sin`, `atan2`, `min`…), parsed by `xacroExpr.ts`, never `eval`. Root attributes are read after the body, so `<robot name="$(arg name)">` works. Anything else (`xacro.load_yaml`, `$(env)`, namespaced includes, `xacro:attribute`, lists and dicts, any other call) fails the import with `Couldn’t read <file>`, naming the file it was in; nothing is skipped silently. gkjohnson's `xacro-parser` was checked and not used: it needs DOM nodes, pulls in `yaml` and `yargs`, and evaluates through `expr-eval-fork`, a general expression language (its parent `expr-eval` had a code-execution advisory), where this importer wants a parser that knows only arithmetic and fails closed.
- **Zips** unpack in the geometry worker (`archive.ts`, fflate). An entry that climbs out (`..`), starts at `/` or a drive, or sits in `__MACOSX` is dropped. Each zip unpacks to at most 600 MB and 20,000 entries, and a zip link downloads at most 200 MB (checked against `Content-Length`, then counted as it streams); GitHub file links to a zip go through `raw.githubusercontent.com`, so Git LFS zips work. A description's references resolve only inside the tree, so `../../secret.stl` reads nothing (`archive.test.ts`). Every fetch is https only (`fetchBytes`).
- **Agent tools:** `get_rig`, `pose` (values, IK goals, body offset, save / apply), `animate` (keyframes or a gait; reports IK misses, limits, collisions and the floor at 8 times, including the last pose of a motion that doesn't loop, with the worst reading of each problem; preview frames), `retarget_motion` (an attached .bvh or a URL), `import_robot` (preset, URL, repo or zip; `entry` picks one robot when a repo holds several); `define_joints` takes prismatic joints and `parent_joint`.
