# Running and testing

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 0d. Running the app

- `npm start` builds once and runs Electron against the production bundle, which it loads from `dist/` as `app://basecase` (`electron/appProtocol.mjs`: no preview server, no `wait-on` poll; the scheme has Electron's `codeCache` privilege, so V8 caches the compiled bundle). Use it to use the app or judge how it feels: dev-mode React is several times slower.
- `npm run electron:dev` (`tools/electron-hmr.mjs`: Vite on 5173 with `BASECASE_HMR_PORT` set, then `tools/electron-dev.mjs`) runs Electron against the Vite dev server with hot reload, for development. It's a node script so it runs the same in zsh, cmd and PowerShell.
- **One origin, isolated.** Both modes load `app://basecase`: `electron:dev` proxies the Vite dev server through the same handler (HMR connects to `localhost` through `BASECASE_HMR_PORT`), so dev and production share `localStorage`. Every response from the handler, the Vite dev and preview servers and the bench servers carries COOP `same-origin`, COEP `credentialless` and CORP `same-origin`, so the page and its workers are cross-origin isolated (`SharedArrayBuffer`, `Atomics`). `credentialless` still lets cross-origin images (SimReady thumbnails) load; a cross-origin `fetch` needs CORS, as before. IPC, permissions and navigation trust only `app://basecase` (`appOrigin.mjs`; Node's `URL` gives custom schemes an origin of `'null'`, so `originOf` builds it from protocol and host).
- **The old origin's storage moves once.** The first launch on `app://` reads `localStorage` from `http://localhost:5173` in a hidden window (served in memory, `electron/storageMigration.mjs`) and inlines it into the first `index.html` before any app code runs; `userData/storage-origin` marks it done. A user data folder with no `Local Storage` folder (a fresh install, every packaged-app test) has nothing to move, so it's marked done without opening the window: Playwright's `firstWindow()` used to pick up the reader just before it closed. The reader window closes only after the main window exists: closing the last window fires `window-all-closed`, which disconnects the agent.
- **Packaging from a git worktree** (`electron-builder --dir`, the packaged-app gates) needs a real `node_modules`, not a symlink. On macOS clone it copy-on-write, `cp -cR ../../../node_modules .` (APFS `clonefile`), so it takes almost no disk; a plain copy costs 1.3–2 GB per worktree. When a worktree's work is merged, delete its build output (`release/`, `dist/`, `forge/target/`, `hw/target/`, a copied `node_modules`); it all rebuilds.
- `npx basecase check <scene.basecase>` (or `npm run basecase -- check …`) runs a saved scene's Cases in Node and exits 1 when one stops passing; `npx basecase export <scene.basecase> --package <dir>` writes its Robot Package. Neither opens the app or the network (§8h, Headless).
- `BASECASE_USER_DATA=<folder>` runs the app on another user data folder (tests, a second copy next to the one you use). Add `STUDIO_AGENT_OFFLINE=1` to keep the agent offline. With both set, the app uses Chromium's mock keychain (`use-mock-keychain`) instead of the login keychain: an unsigned packaged build reading the real “Basecase Safe Storage” item makes macOS ask for keychain access, which blocks the main process until someone answers, so an unattended run (e2e, PersonaLab) would hang.
- **The CAD kernel needs its bundle** (`dist/kernel/`, §9): `vite build` makes it, and `npm run electron` / `electron:dev` rebuild it when `electron/cad-kernel/` changed (about 0.2 s). The Vite dev server in a plain browser has no kernel; the bench and `tools/parts` set `BASECASE_NODE_KERNEL=1` to compile on the test-only Node host.
- **Web demo** (app.basecase.so): `npm run build:web` (`vite build --mode web`) builds a static app with no backend; `npm run dev:web` serves it locally on 5174. `IS_WEB_DEMO` (`src/utils/platform/webDemo.ts`) is true only in that mode.
  - The renderer's HTTP transport sends every `/api/bridge/*` call to `webRequest` (`utils/platform/web/webBackend.ts`) instead of fetching it. Scenes, models, prices, build guide HTML and trained skills live in IndexedDB (`web/idb.ts`, database `basecase`; adding a store raises its version, which works only because every connection closes on `versionchange`, and an open blocked by an older build's tab fails with “Close Basecase’s other tabs, then reload this one.” instead of hanging); chats, images and live runs are empty; there's no event stream. Any other route answers 501 with “Download Basecase to …” (the agent, SimReady inserts, the app's trainer, slicing and printing), which surfaces as the toast or error text.
  - **Motor Kit training runs in the tab** on a browser with JSPI and a WebGPU adapter: Simulate's Train rows train on Forge's tab engine and save the skill to IndexedDB ([Skills](skills.md) §8i, [Forge](forge.md) §8g). Without them the Train section is hidden.
  - **Gallery links** (`/c/<slug>`, and shared robots at `/r/<account>/<repo>`, §8h) open a single Case with its own small page; `npm run perf:gallery` holds them to their size, time-to-drive and real-time budgets. Both are client routes: `wrangler.jsonc` serves `index.html` for any path that isn't a file (`not_found_handling: single-page-application`), so they need no rewrite.
  - **Phones get a landing page, not the app.** The web build's `index.html` loads `src/webMain.ts` (swapped in by `webEntryPlugin` in `vite.config.ts`; Electron keeps `main.tsx`), which picks one entry before anything heavy loads: a window whose shorter side is under 600 px at load (`showsLanding`, the window and not the screen, so a narrow desktop window gets it too) gets `src/landing/` (“Build real robots”, a drifting strip of the preset robot previews, Download for Mac and Windows, Open on GitHub, then seven feature rows: a plain title and one short line each, no product names), everything else gets the app. The landing is a 5 KB chunk; the 3 MB app never downloads on a phone. `?landing` shows it on any screen, for review.
  - **basecase.so** is the same landing on its own (`site/`, `npm run build:site` → `site/dist`, `npm run dev:site` on 5175): `site/index.html` loads `src/landing/siteMain.tsx`, and the build copies only the favicon and `public/robots/*.webp` (plus a `_headers` caching `/assets/*`), about 250 KB in all. The same build prerenders `/changelog` (with `/changelog/rss.xml` and `/changelog.json`), `/help`, `/blog` once it has a post, and each post and article from the markdown in `site/content/` (`src/landing/pages/`, emitted by `site/vite.config.ts` as `changelog.html`, `help/<slug>.html` and so on, which Workers serves without the `.html`), plus `sitemap.xml`. Help also gets a page per collection (`help/<collection>.html`) and a search index (`help/search.json`). Those pages are static HTML on the landing's stylesheet; markdown renders through `react-markdown` with raw HTML skipped. Only help pages load a script: the help search (`src/landing/help/search/helpSearchMain.ts`, emitted as its own chunk by `site/vite.config.ts`, about 3 KB gzipped), which fetches the index on first focus and shows key caps in Windows keys on Windows. Collections, front matter and search are in [The loop](loop.md#the-help-center). The landing's footer links Changelog and Help (only on basecase.so, not the app's phone landing). `npm run dev:site` serves only the landing; check the pages with `npm run build:site` ([The loop](loop.md#writing-posts-and-help)). There, a window that isn't small leads with Open in Browser (app.basecase.so), then the download for the visitor's platform (Mac unless it's Windows), then Open on GitHub; small windows get both downloads. Hosting: a Cloudflare Worker (Workers Builds) from the repo root: build `npm run build:site`, deploy `npx wrangler deploy --config site/wrangler.jsonc`, previews `npx wrangler versions upload --config site/wrangler.jsonc`, variable `ELECTRON_SKIP_BINARY_DOWNLOAD=1`. `site/wrangler.jsonc` points the assets at `site/dist`, and its `name` must match the Worker's name in Cloudflare.
  - The landing has its own stylesheet (`src/landing/landing.css`: Tailwind scanning only `src/landing` and `glyph.tsx`, plus `design-system/preview.css`, which the app's `index.css` shares). Its robot strip holds all 16 preset previews three times and moves by exactly one copy, so it loops seamlessly on any window width; it pauses on hover and sits still under reduced motion.
  - **Download banner** (`src/app/DownloadBanner.tsx`): a 40px `#0d99ff` strip above the studio, “Build with the agent in the desktop app” + [Download for Mac] (or Windows) in white, with Close at the right. The studio sits on it with 12px top corners, so the blue shows behind each corner. Close slides the studio up over it (240ms) and saves `download-banner-dismissed` in `localStorage`, so it never comes back. Electron renders the studio without the frame.
  - The Agent tab shows `DesktopDownload` instead of the chat: an `EmptyState` with the banner's own line, “Build with the agent in the desktop app” (`DESKTOP_AGENT_LINE`, so the two never drift), + [Download for Mac] (or Windows), the latest release download. Settings and ⌘K hide the Agent, Printers and Accounts panes, and the printer menu has no Add Printer.
  - Hosting: Cloudflare Workers Builds from the repo root (build `npm run build:web`, deploy `npx wrangler deploy`, previews `npx wrangler versions upload`, variables `ELECTRON_SKIP_BINARY_DOWNLOAD=1` and `NPM_CONFIG_IGNORE_SCRIPTS=true`). Cloudflare installs with npm 10, which ignores `allowScripts`, so without that variable every dependency install script runs (keytar and node-pty download prebuilt binaries); the web build needs none, and `npm run` still runs `build:web`. `wrangler.jsonc` serves `dist/` as static assets; its `name` must match the Worker's name in Cloudflare. `public/_headers` sets the same COOP / COEP / CORP headers as the dev server and caches `/assets/*` forever.
  - Workers Builds deploys both sites on every push to `main`, and every merge has already passed review and Check, so a merge going live is the deploy. Don't add a deploy workflow or a deploy token to Actions.
  - A new bridge route needs a `ROUTES` entry in `webBackend.ts` (or it reads as desktop-only), and new desktop-only UI checks `IS_WEB_DEMO`.

## 0e. Tests

- **Vitest** (`npm test`; `*.test.ts` next to the code, `vitest.config.ts`). The whole suite takes minutes, so don't run it for a change: `npm run check:changed -- <your files>` (`tools/check-changed.mjs`) formats, lints and typechecks them and runs only the tests that import them (`vitest related`), in seconds. `npx vitest run <file>` runs one test file. CI runs the full `npm run check` on every push; run it yourself only when a maintainer asks or you change tooling, configs or dependencies.
- **A test earns its place by being fast, steady and broad.** An e2e test proves one thing a person relies on in under about 15 s; a longer story is split or cut to that one thing, and a detail a unit test can check goes in a unit test. Delete a test that's flaky, slow or narrower than what users notice rather than nursing it: never raise a timeout, add a retry or skip it to keep it. Timing budgets run on demand (`npm run perf:booleans`), never in Check. The loop's flakes lane files a step to speed up or delete any test over 30 s on `main`, and to fix or delete any test that passes only on a re-run.
- Prefer integration tests that drive a real pipeline with real data (a saved scene through BOM and engineering checks, a URDF through import and kinematics) over unit tests of internals. Add a test when you fix a bug or change a pipeline; don't test trivia or styling.
- Every test must earn its keep: if it's slow, flaky or breaks on harmless refactors, fix or delete it.
- `npm run perf:agent` (`tools/perf/`): builds production into `node_modules/.cache/perf-agent/dist`, opens it in headless Chrome (Metal on macOS, `--cpu` for SwiftShader) with a fixture robot built in code (225 CAD parts, about 300k triangles, 14 joints), replays what an agent run sends (streamed chat, `model_part`, `look`, `check_scene`, `get_bom`, `verify_design`…) and prints each tool's time, its longest main-thread task and worst frame. `--budget 100` fails when any task runs longer; `--profile <phase>` saves a CPU profile; `--dist <dir>` measures another build (an older one, for before/after). Run it after any change to agent tools, captures, autosave or the viewport. Plan and history: [docs/Performance plan.md](../../docs/Performance%20plan.md).
- `npm run perf:booleans` (`vitest.perf.config.ts`): runs every `*.perf.test.ts`: the boolean of two 50k-triangle parts, which must never hold the main thread for a frame, and the mat tracker's detecting and solving of a 1280 × 720 frame within a 30 fps camera's 33 ms (§8l). Timing tests run on demand, never in Check: a shared CI runner's wall clock drifts past 16 ms on its own, so the unit run excludes them. Run it after any change to booleans, the CSG worker or the mat tracker.
- `npm run perf:viewport` (`tools/perf/viewportBench.mjs`): the perf fixture robot plus 400 fasteners and 12 servos (the mix in real agent builds), or any saved scene (`--scene <file>`), orbited for 4 s in headless Chrome. It counts GL calls and draws per frame (the WebGL context and `requestAnimationFrame` are wrapped from an init script, so it needs no engine hooks), main-thread work per frame, GPU-process time per frame (from a Chrome trace) and idle frames with the shadow pass. `--dist <dir>` measures another build, `--profile <file>` saves a CPU profile of the orbit. Run it after any change to the viewport, part meshes or materials.
- `npm run test:e2e` (`e2e/`, `vitest.e2e.config.ts`): opens the app in headless Chrome (playwright-core) with the backend routes stubbed (no agent is started and `library/` isn't touched), and checks adding, selecting, duplicate/undo/redo, every panel switch and panel toggle with no console errors.
  - **It serves the built bundle, the way users get it.** `e2e/serve.ts` (Vitest's `globalSetup`) starts two `vite preview` servers once per run: the desktop build from `dist/` (`npx vite build`, with the bridge middleware, so unstubbed `/api/*` routes answer as in dev) and the web build from `dist-web/` (`npx vite build --mode web --outDir dist-web`, for gallery `/c/<slug>` links and Forge). Both send the COOP / COEP / CORP headers and fall back to `index.html` like `public/_headers` and `wrangler.jsonc`; tests read the URLs with `inject('appUrl')` and `inject('webUrl')`. CI builds both before the suite.
  - **Live routes.** `openApp(lists, live)` lets bridge routes whose names start with a `live` prefix through to the served app's real backend instead of the stub. `drive.e2e.test.ts` passes `hub-`: `e2e/serve.ts` points `BASECASE_HUB_URL` at a port it reserves (`inject('hubPort')`), and the test starts the fake Hub from `e2e/fakeHub.ts` there, since the server runs in Vitest's main process and never sees a test file's environment. `earthTiles.e2e.test.ts` passes `earth-` the same way: `BASECASE_EARTH_TILES_URL` points at `inject('tilesPort')`, where `e2e/fakeTiles.ts` serves the fixture tiles from `src/earth/tileFixture.ts`. A third argument adds Chrome flags after the software-GL defaults: `cameraDrive.e2e.test.ts` passes `FAKE_CAMERA` (Chrome's fake capture device, permission granted).
  - **Locally, a missing or stale build falls back to the Vite dev server** (a build older than any file in `src/`, `public/`, `index.html` or `vite.config.ts`, test files aside), so the suite never runs old code; it says so in the output. `BASECASE_E2E_SERVER=dev` forces the dev server. On CI (`CI` set) a missing or stale build fails the run instead.
  - **Fixtures built in code.** Robots come from `src/sim/fixtures/robots.ts` and a RoomPlan room from `src/cases/roomFixture.ts` (two rooms joined by a door, a window, a sofa, a table and a chair; `turnDeg` scans it at an angle, `extraObjects` crowds it past 256 objects, `basecase` adds a tapped start). The one fixture not built in code is `e2e/fixtures/scanned-room.json`, the file the iPhone scan app writes for that room with a tapped start, which its XCTests check it still writes (§8m). `__studio.dropFiles([{ name, base64 }])` hands files to the canvas drop's router (`routeFiles` in `useCanvasDrop.ts`) as if they were dropped.
  - **Test hooks in the production bundle.** `window.__studio`, `__studios` and `__studioTabs` exist in dev, and in a production build only when the page sets `window.__basecaseTestHooks = true` before the app loads (`exposesTestHooks`, `src/utils/platform/testHooks.ts`); the harness does it with `exposeTestHooks(page)`, the app never does. `openApp` prints how long the studio took to be ready.
  - **`__studio` has one module per area** (`src/workspace/devStudio/areas/<area>.ts`: scene, viewport, pose, sketch, sim, cases, datasets, routines, skills, robot, calibration, cameras, mat, print, build, agent, earth). Each default-exports a function that takes the studio context (`types.ts`: the workspace's `core`, `actions`, `agent` and `routeFiles`, read fresh on every call) and returns its hooks by name. `useDevStudioHook.ts` assembles every module from one `import.meta.glob` list (`studioAreas.ts`), so a new hook goes in its area's module, or a new module for a new area, and never in a shared file: the two files it replaced met 23 conflicts in the merges behind Nov 13's four conflict batches ([Loop](loop.md#digest)). `studio.test.ts` fails when two modules define one name, and checks the full list of names, so a new hook adds its name there too.
  - Why: a dev server per file cost each file about 17 s on Linux CI before its first test, transforming unbundled modules on demand. `expect.poll` waits up to 10 s there (the config's default), since CI renders WebGL in software and a loaded runner misses Vitest's 1 s; a poll still returns as soon as it passes. Each test gets 180 s (`testTimeout`): a test's own waits (a Case's drive starting, a try recording) can add up past a minute on CI, and a budget below them failed tests that would have passed and left the app mid-state for the next test. A wait that fails still reports at its own poll. A test that drives a robot holds the key until the robot has gone far enough (`holdKeyUntilForward`), not for a fixed time: a runner that simulates slower than real time covers less ground per second. A test that records a try only to export or publish it ends the try when its clock reads a fixed time (`endTryAt` in `drive.e2e.test.ts`), not when Playwright gets round to clicking Stop Try: the dataset renders and encodes every frame in software, so a try that ran on while the runner was busy cost up to two minutes to export and timed the test out. A test waits on the app's own outcome (the Published or Couldn’t publish toast), not on a server it polls, so a failed publish reports its message at once. Never wait with `expect.poll` in a hook: Vitest throws there; use `vi.waitFor` or a Playwright `waitFor`. `harness.ts` records every request from boot (`app.requests`), so a test that asserts on a fetch can't miss one the app made before the test began. `forgeTab.e2e.test.ts` trains on Metal WebGPU and runs only on macOS; a runner with no GPU can't train Stand in its budget. `drive.e2e.test.ts` skips four tests on Windows (the text-field canvas prompt, Touch the Dots, Hugging Face publish and New Case) until #205: MuJoCo's wasm stalls in instantiation on the Windows runner against the built bundle, while the same tests pass on Linux.
- **Quarantine** (`tools/quarantine.json`, [Loop](loop.md#ci-repair)): `npm test` and `npm run test:e2e` skip a listed test until its `until` date (`tools/quarantine-setup.mjs`), and a whole file when its `test` is empty. `npm run test:quarantine` runs only the listed tests and never fails; `npm run check:quarantine` validates the list. `BASECASE_QUARANTINE=off` runs everything. `node tools/loop/linux-e2e.mjs <e2e file> --runs N` runs an e2e file N times on x86-64 Linux in a container, as CI does.
- `node tools/lerobot/check.mjs`: exports the dataset fixture (`src/datasets/fixtures.ts`) and loads it with a pinned `lerobot` through `uv` (§8h). Check runs it in the `lerobot` job when a pull request touches `src/datasets/`, `tools/lerobot/`, `check.yml` or the lockfile, and nightly.
- `sh ios/test.sh`: builds Basecase Scan (`ios/`) for an iPhone simulator and runs its XCTests (§8m). Check runs it in the `ios` job on macOS when a pull request touches `ios/`, the scan app's e2e fixture or `check.yml`, and nightly.
- `npm run test:app` (`e2e/app/`, `vitest.app.config.ts`): drives the **packaged** app, main process included, with playwright-core's Electron driver. It runs on a fresh `BASECASE_USER_DATA`, the offline agent and a bare PATH, and checks the window and title bar for the platform, adding, duplicating and undoing parts, the agent starting on the Node the app ships with, and the CAD kernel sandbox (`kernelSandbox.app.test.ts`): `model_part` through the real MCP server (a capture agent records the session's MCP command), denial probes in the worker and the page, and recovery from a hung part and a memory hog. About 20 s. `kernelCanary.app.test.ts` runs the same probes on the Node host and fails by design (the gate's canary, §0h); `vitest.app.config.ts` skips it unless `-t` names a test. `cadImportSandbox.app.test.ts` starts the packaged app without Playwright in its converter self-test mode (`BASECASE_CADIMPORT_SELFTEST`) and checks the fixture conversions, denial probes and recovery (§0h); with `BASECASE_CADIMPORT_UNSANDBOXED=1` it runs the same self-test on the Node host instead, for the canary. CI runs it on Windows too. It finds `release/<platform>-unpacked` or `release/mac*/Basecase.app`, or takes `BASECASE_APP_PATH`. Build first: `npx vite build && CSC_IDENTITY_AUTO_DISCOVERY=false npx electron-builder --dir -c.mac.forceCodeSigning=false` (with `--mac --arm64` or `--win --x64`). CI runs it on macOS for every push (`check.yml`, job `app`, which also packages Windows but doesn't drive it: `electron.launch` hangs on the runner more often than not); the release runs it on the signed Mac app. On Windows the job runs the packaged app's kernel self-test instead: `BASECASE_KERNEL_SELFTEST=<file>` makes the app compile an OpenSCAD and a replicad part in the sandbox, probe file, network and Node access from agent code, write the result to `<file>` and exit 0 or 1, with no window (`cad-kernel/sandbox/selfTest.mjs`).
