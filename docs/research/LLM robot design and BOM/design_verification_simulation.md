# Design verification and simulation for AI-designed robots (kinematics, collisions, torque, stability, structure)

Scope: concrete checks an AI CAD agent (Electron/Node app, CAD parts + real servos) can run automatically to show a design is buildable and works before fabrication. Research done 2026-10-17. Where a claim had no source I could fetch, it is in Gaps or labeled as a standard derivation in Inferences.

## 1. Generating URDF/MJCF from a CAD assembly or an LLM, and how LLM/evolutionary robot-design papers used simulation-in-the-loop

### Takeaway
There are mature CAD-to-robot-description exporters for Onshape (onshape-to-robot, which writes URDF, SDF and MuJoCo with `dof_` mate naming) and Fusion 360 (fusion2urdf forks). Code-CAD (CadQuery/build123d) has no standard exporter, so an app that already knows its parts, joints and meshes should write URDF/MJCF itself. Published robot-design papers (Text2Robot, RoboMorph, RoboGen) check designs by training a controller in a physics simulator. Their manufacturability checks are mostly built into the design space (fixed servo count, fixed topology, clearances, a grammar) rather than run as separate verifiers. That is the gap a CAD agent's static checks can fill.

### Cited Findings
**CAD → URDF/MJCF exporters**
- onshape-to-robot exports Onshape robots to "URDF, SDF or MuJoCo". Its docs have sections on configuration (config.json), handling kinematic loops (closing constraints, MuJoCo `<equality>`), processors and cache. v1.0.9 had URDF + MuJoCo; the latest docs add SDF. — [onshape-to-robot docs (latest)](https://onshape-to-robot.readthedocs.io/en/latest/); [v1.0.9](https://onshape-to-robot.readthedocs.io/en/v1.0.9/index.html)
- Joints come from naming conventions: "To create a degree of freedom, you should use the `dof_` prefix when placing a mate connector." Revolute/cylindrical mates become revolute joints, sliders become prismatic, and fastened mates become fixed. An `_inv` suffix flips the axis. Gear relations export as URDF mimic or MuJoCo equality constraints. Onshape joint limits "will be understood and exported." `frame_*` connectors become MuJoCo sites. Orphaned links "will be fixed to the base link, with a warning." The first instance in the assembly is the base link. — [onshape-to-robot design-time considerations](https://onshape-to-robot.readthedocs.io/en/latest/design.html)
- Third-party (unverified) guide: parts with no material or mass setting in Onshape can export with near-zero mass. — [wikidocs guide](https://wikidocs.net/384466)
- Related: K-Scale's `kscale-onshape-library` provides `kol urdf` / `kol mjcf` commands. The "Onshape URDF Exporter" is a URDF-only spin-off of onshape-to-robot. — [PyPI kscale-onshape-library](https://pypi.org/project/kscale-onshape-library/0.0.21); [Onshape URDF Exporter docs](https://onshape-urdf-exporter.readthedocs.io/en/latest/)
- fusion2urdf is a Fusion 360 script that writes URDF, launch files and STL meshes, and each link has to be its own component. There are forks for Fusion's Python 3.12 and a derivative, fusion360descriptor. — [syuntoku14/fusion2urdf](https://github.com/syuntoku14/fusion2urdf); [SpaceMaster85 fork](https://github.com/SpaceMaster85/fusion2urdf); [nilutpolkashyap fork](https://github.com/nilutpolkashyap/fusion2urdf)
- For build123d, the closest match is the "text-to-cad" project, where a Python script defines `gen_urdf()` and a CLI writes URDF plus meshes. I found it only through third-party summaries, not the repo. — [instagit summary](https://instagit.com/earthtojake/text-to-cad/how-to-create-robot-urdf-files-with-build123d/)
- "Jointly", a web tool announced on the OpenRobotics forum, claims to turn an uploaded STEP assembly into a draft URDF with inferred joints and inertia (unverified). — [OpenRobotics Discourse: CAD to URDF conversion](https://discourse.openrobotics.org/t/cad-to-urdf-conversion/55892.md)

**LLM-generated URDF**
- URDF-Anything (NeurIPS 2025) uses a 3D multimodal LLM to produce URDF parameters for articulated objects from point clouds. — [arXiv 2511.00940](https://arxiv.org/pdf/2511.00940)
- Articraft (2026 preprint) is an agentic system that generates articulated assets. Its URDFs were imported into NVIDIA Isaac Sim, and an LLM assigned mass and damping. — [arXiv 2605.15187](https://arxiv.org/pdf/2605.15187)
- Community tools: Artifex (AI-generated URDFs with a visual error-checking loop: render, find wrong joint axes, scale or orientation, fix, iterate) and UrdfArchitect. — [Artifex thread](https://discourse.openrobotics.org/t/artifex-ai-generated-urdfs-with-visual-error-checking-seeking-feedback/51511); [UrdfArchitect thread](https://discourse.openrobotics.org/t/urdfarchitect-a-ai-powered-visual-editor-to-build-robot-models-without-manual-xml-coding/51484.md)

**Simulation-in-the-loop design papers**
- Text2Robot (Duke, ICRA 2025): text → Meshy mesh → Fusion 360 repair → scaled to 6,300 cm³ so every robot starts with the same mass. The CoM is set assuming uniform density. Legs are split at minimum-area slices, with a shoulder joint at the slice centroid and a knee at the maximum-area slice. Knee traversal stops 2 cm above the ground to leave room for motors. — [arXiv 2406.19963 (html)](https://arxiv.org/html/2406.19963v1)
- Text2Robot manufacturability is built into the design space: fixed topology (4 legs × 2 joints), 8 Hiwonder HTD-45H servos, a Raspberry Pi 4, a 3S 5200 mAh LiPo, printed PLA servo boxes with snap-in pegs, 4 cm limb offsets and "extrusions cut to avoid self-collision". The paper describes no automated printability, joint-limit or mass checks. — [arXiv 2406.19963](https://arxiv.org/html/2406.19963v1)
- Text2Robot simulation: IsaacGymEnvs with 4,096 parallel environments per robot, PPO for 2.46×10⁷ steps (minutes per robot), and a PD controller turning position offsets into torques. Fitness combines velocity tracking with an energy term (Σ|q̇ᵢτᵢ|) and a torque penalty. Each conversion to URDF took about 30 s. Sim-to-real was "primitive" (open-loop replay at 0.1 m/s), and robots walked with "sufficient performance", with no quantitative gap reported. — [arXiv 2406.19963](https://arxiv.org/html/2406.19963v1); [arXiv abs v3](https://arxiv.org/abs/2406.19963v3)
- RoboMorph: GPT-4o acts as the mutation operator in an evolutionary loop. Designs are encoded in a grammar so outputs are "physically valid and fabricable", and they are scored by RL-trained control on four terrains. Simulation only. — [arXiv 2407.08626](https://arxiv.org/html/2407.08626v2); [ICLR 2025 FM-Wild workshop](https://mlanthology.org/iclrw/2025/qiu2025iclrw-robomorph)
- RoboGen (EPFL, 2014): an open-source platform that co-evolves bodies and controllers. It has a built-in physics simulator, generates 3D-printable body files and compiles neural controllers for Arduino. Modules are servo-driven active hinges, bricks and a core holding the board and battery. Evolution runs entirely in simulation, and only the fittest robot is built. — [EPFL Infoscience](https://infoscience.epfl.ch/record/200995); [EPFL news](https://actu.epfl.ch/news/lis-releases-robogentm-open-source-platform-for-ev); [arXiv 2111.09851](https://arxiv.org/pdf/2111.09851)

### Inferences
- Common pattern: constrain the design space (catalog servos, grammar or modules, fixed clearances), then let simulation judge function. For an LLM CAD agent with open-ended geometry, the constraints have to become explicit checks, because the generator no longer guarantees them.
- This studio already holds part geometry, catalog servos and transforms, so a direct MJCF writer is simpler than round-tripping through Onshape or Fusion. The output would be one body per moving link, a hinge at each servo's output-shaft axis, `range` from the servo spec, mesh geoms from the exported STL and inertia from mesh volume × density. onshape-to-robot's conventions (`dof_` names, `_inv`, frames as sites, warnings for orphaned links) are a good model for the agent's own joint annotations and error messages.
- Text2Robot's near-zero-mass issue (via the wikidocs note) and its uniform-density CoM assumption both argue for an explicit mass-model check: every link has non-zero mass, and catalog servos use datasheet mass, not printed density.

## 2. Running physics in or near a JS/Electron app

### Takeaway
Google DeepMind now publishes official MuJoCo JS/WASM bindings on npm (`@mujoco/mujoco`, versions tracking MuJoCo, 3.9.0 at time of search). They load MJCF from an XML string and step the simulation, but they are explicitly "still a WIP" and incomplete. Rapier (Apache-2.0, has multibody joints and a cross-platform deterministic build) is the most mature pure-JS-ecosystem option, but it is a game engine. MuJoCo is the right engine for robot verification. A Python MuJoCo/PyBullet subprocess (like the existing sandboxed CAD kernel child process) is the most complete fallback.

### Cited Findings
- Official bindings: `npm install @mujoco/mujoco`. ESM, ships the WASM module, JS glue and TypeScript declarations, with versions matching MuJoCo releases. Status quotes: "These bindings are still a WIP." and "These bindings are not yet complete"; `mjspec.h` APIs are "untested in real web applications". Developed mainly on Linux + Chrome, macOS tested in CI, and "Windows support remains experimental." — [MuJoCo wasm README (GitHub)](https://raw.githubusercontent.com/google-deepmind/mujoco/main/wasm/README.md); [npm README @mujoco/mujoco 3.9.0](https://cdn.jsdelivr.net/npm/@mujoco/mujoco@3.9.0/README.md)
- API: `MjModel.from_xml_string(xml)`, `new MjData(model)`, `mj_step(model, data)`. Large arrays (`data.qpos`) are live views into WASM memory, while `data.contact` returns a copy that must be re-read each step. C++ objects aren't garbage-collected, so call `.delete()` exactly once per object. — [MuJoCo wasm README](https://raw.githubusercontent.com/google-deepmind/mujoco/main/wasm/README.md)
- Builds: the default single-threaded build needs no special headers. The `/mt` multi-threaded build uses Web Workers + SharedArrayBuffer and needs `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, or it fails to initialize. Building from source uses Emscripten 4.0.10. — [MuJoCo wasm README](https://raw.githubusercontent.com/google-deepmind/mujoco/main/wasm/README.md)
- The older npm package `mujoco` 3.1.16 is listed under Apache-2.0. Community predecessors include zalo/mujoco_wasm, and a React Three Fiber wrapper (mujoco-react) builds on the DeepMind bindings. — [jsdelivr mujoco 3.1.16](https://cdn.jsdelivr.net/npm/mujoco@3.1.16/README.md); [krishpop/mujoco_wasm fork](https://github.com/krishpop/mujoco_wasm); [three.js forum: mujoco-react](https://discourse.threejs.org/t/mujoco-react-a-react-three-fiber-wrapper-around-mujoco-js-wasm-bindings/89991)
- MuJoCo inverse dynamics: τ = M v̇ + c − Jᵀf. "Once the forward dynamics are computed, the inverse dynamics are essentially free." `mj_inverse` outputs `mjData.qfrc_inverse`, which "equals the sum of external and actuation forces". The bias force c ("Coriolis, centrifugal and gravitational forces") is `mjData.qfrc_bias`, computed by RNE "with acceleration set to 0". — [MuJoCo Computation docs](https://mujoco.readthedocs.io/en/stable/computation/index.html)
- MuJoCo collision filtering: geoms on the same body are always excluded. Parent-child pairs are excluded "unless the parent is the world body" (can be disabled). Pairs pass contype/conaffinity if "(contype1 & conaffinity2) || (contype2 & conaffinity1)". `<exclude>` removes body pairs, and `<pair>` forces geom pairs. Mesh geoms "are replaced with their convex hulls" (qhull) for collision. — [MuJoCo Computation docs](https://mujoco.readthedocs.io/en/stable/computation/index.html)
- Rapier: Apache 2.0. The JS packages support rigid bodies, impulse joints and multibody joints. The standard `@dimforge/rapier3d` build isn't guaranteed cross-platform deterministic, while `@dimforge/rapier3d-deterministic` is (less optimized). Check with `world.createSnapshot()` + MD5. — [Rapier docs](https://rapier.rs/docs/); [Rapier JS determinism](https://rapier.rs/docs/user_guides/javascript/determinism); [rapier3d-deterministic README](https://cdn.jsdelivr.net/npm/@dimforge/rapier3d-deterministic@0.19.3/README.md)

### Inferences
- Recommended for this app: load `@mujoco/mujoco` (single-threaded build, so no COOP/COEP needed in Electron) in the renderer or a worker. Generate MJCF from the scene, then run (a) `mj_forward` + read `qfrc_bias` for static gravity torques per pose, (b) `mj_inverse` for torques along a scripted trajectory, and (c) a short `mj_step` drop test (spawn above the floor, let it settle, measure base tilt and whether it falls). Note: the README I fetched shows only `mj_step`. Check whether `mj_forward`/`mj_inverse` are bound in the current npm version before relying on them.
- MuJoCo's convex-hull collision means concave printed brackets will report false contacts in simulation. Self-collision checks should keep using exact triangle meshes (three-mesh-bvh, already in `src/three/interference.ts`), with MuJoCo used for dynamics and ground contact. Alternatively, run a convex decomposition (e.g. CoACD/V-HACD) before building the MJCF.
- MuJoCo's default parent-child exclusion hides collisions between a servo body and the bracket it's bolted to, which is desirable. But it also hides a real clash between adjacent links at extreme angles, so do the joint-sweep collision check outside the simulator.
- cannon-es and ammo.js are game engines without articulated-body (generalized-coordinate) dynamics or inverse dynamics. I would not use them for torque or stability verification (not researched in depth; see Gaps).

### Gaps
- Not verified in this pass: cannon-es (believed MIT, maintained by pmndrs), ammo.js (Bullet port, zlib), PyBullet (zlib, effectively in maintenance mode), and MuJoCo-WASM performance numbers (steps/s for a 20-DoF model). I found no benchmark.
- Not confirmed: whether `@mujoco/mujoco` runs under plain Node.js (e.g. in the Electron main process) and not just in browsers. The README only mentions Node for tests and the demo.

## 3. Static checks without full simulation (self-collision sweeps, workspace, torque, safety factors, mass, CoM, tipping)

### Takeaway
Most "does it work" questions for a servo robot can be answered statically and in milliseconds: sweep each joint through its range and test mesh-mesh intersection with a BVH, compute the gravity torque per joint at the worst pose and compare it to the servo's rated (not stall) torque with a margin, sum masses (printed volume × density × effective fill + catalog masses), and check that the CoM projects inside the support polygon with an angular tipping margin. Margin advice differs by source (1.2× to 5×). A defensible default is required torque ≤ 50% of stall torque (2× on stall), plus a speed check at that load.

### Cited Findings
- How professional CAD presents motion interference: SolidWorks' motion-study Check Interference takes components, a start frame, an end frame and an increment, then lists "the frame, simulation time, parts that cause the interference, and the volume of the interference detected"; clicking an entry moves the assembly to that pose. Clearance Verification "reports clearances that fail to meet the minimum acceptable clearance you specify." Dynamic Clearance shows the live minimum distance while dragging, and Collision Detection stops or flags contact during the drag. — [SolidWorks: Detecting Interference (motion)](https://help.solidworks.com/2019/english/SolidWorks/motionstudies/t_detecting_interference_motion.htm); [SolidWorks: Clearance Verification](https://help.solidworks.com/2020/English/SolidWorks/sldworks/c_Detecting_Problems_SWassy.htm); [Interference check dialog](https://help.solidworks.com/2020/english/SolidWorks/motionstudies/HIDD_INTERFERENCE_CHECK_DLG.htm); [Solid Solutions: collision detection](https://solidsolutions.co.uk/SOLIDWORKS/3d-cad/features/collision-detection.aspx)
- Torque sizing advice (mostly vendor blogs or forums, commercially motivated): don't size directly to stall torque, use the worst-case payload position. Speed under load falls with the required/stall torque ratio. Suggested margins: +20–30% over calculated maximum load; stall ≥ 1.5× load; static × 2–3 for dynamic loads and × 4–5 with high acceleration or disturbances. A RobotShop forum rule of thumb says stall ≈ 3× rated torque. — [Kpower: servo selection](https://www.kpower.com/insight_servo/6656.html); [Kpower insight](https://www.kpower.com/insight_driver/7455.html); [RobotShop Robot Arm Torque Tutorial thread](https://community.robotshop.com/forum/t/robot-arm-torque-tutorial/31349/60); [ThinkRobotics servo guide](https://thinkrobotics.com/es/blogs/learn/how-to-choose-a-servo-motor-a-comprehensive-guide-for-beginners-and-professionals)
- Tip-over stability builds on the CoM and the support polygon ("the convex area spanned between the ground contact-points"). The Force-Angle stability measure (Papadopoulos & Rey 1996, revised 2000) is the minimum, over tip-over axes (edges of the support polygon), of the angle between the net force and the axis normal times the force magnitude. It covers dynamic and external forces. Kelley et al. (2015) used FA to trigger anti-tip behaviors on a mobile manipulator. — [UTS: statistical approach to uncertain stability](https://opus.lib.uts.edu.au/handle/10453/27997); [UTS paper PDF](https://opus.lib.uts.edu.au/bitstream/10453/27997/4/2012007804%20am.pdf); [Springer IJIRA 2025](https://link.springer.com/article/10.1007/s41315-025-00423-9)
- Sloped-terrain variant: "altered supporting polygons" that also include towed units. — [RIUMA (Univ. of Málaga)](https://riuma.uma.es/entities/publication/35cb472f-6c00-4b4b-9384-ef09034d5f7f/full)
- Text2Robot's built-in rules of the same kind: 2 cm motor ground clearance, 4 cm limb offsets to avoid self-collision, and a uniform-density CoM. — [arXiv 2406.19963](https://arxiv.org/html/2406.19963v1)

### Inferences (standard derivations, written as agent-callable checks)
- **Joint-sweep self-collision:** for each joint j, step q_j from min to max (e.g. 2–5° steps, plus combined extremes of adjacent joints), apply forward kinematics to child meshes, and test every link pair that isn't parent-child and isn't intentionally fastened with BVH triangle intersection (three-mesh-bvh `intersectsGeometry`, or the existing `interference.ts` depth check). Report it the SolidWorks way: joint, angle, the two parts, penetration depth or volume, and the usable range ("Left knee hits thigh shell at −62°; usable range −58…+90°"). Also add a clearance threshold (e.g. ≥ 1 mm for printed parts) like SolidWorks Clearance Verification.
- **Static joint torque:** for joint j, τ_j = Σ over every body i downstream of j of m_i · g · r⊥_i, where r⊥_i is the horizontal lever arm from the joint axis to body i's CoM (more precisely τ = (r × m g) · axis). Include the payload at the end effector. The worst case for an arm is usually fully outstretched horizontally. Example: a 0.5 kg payload plus a 0.2 kg forearm at 15 cm needs about 0.5·9.81·0.30 + 0.2·9.81·0.15 ≈ 1.77 N·m ≈ 18 kg·cm at the shoulder for a 30 cm reach. An MG996R (datasheet stall ~9–11 kg·cm) would fail. The same quantity is MuJoCo's `qfrc_bias` at zero velocity.
- **For legged robots:** per-leg static load is roughly body weight ÷ legs in stance (use the 2-leg stance for trot gaits, 1 for biped single support). Knee torque ≈ F_foot × horizontal distance from the knee to the foot contact.
- **Servo pass/fail rule (suggested):** τ_required × SF ≤ τ_stall, with SF = 2 for static holding (≈ the "rated ≈ stall/3" rule leaves ~1.5× margin over rated) and SF = 3 for dynamic or legged joints. Also report the expected speed at load, ≈ no-load speed × (1 − τ/τ_stall) (linear DC-motor model). Use datasheet values at the actual supply voltage.
- **Mass estimate:** m_printed ≈ ρ · [V_shell + f_infill · (V − V_shell)], where V_shell ≈ surface area × wall thickness (perimeters × line width) plus top/bottom skins. Typical densities: PLA ~1.24 g/cm³, PETG ~1.27, ABS ~1.04 (unsourced in this pass, see Gaps). Add catalog masses for servos, boards, batteries and fasteners. Flag any link with mass < 1 g as a modeling error (the onshape-to-robot near-zero-mass issue).
- **CoM / support polygon:** project the whole-robot CoM onto the ground. Support polygon = convex hull of ground contacts (wheels, feet, casters). Margin = minimum distance from CoM to a hull edge. Static tipping angle about edge e: θ_e = atan(d_e / h), where d_e is the horizontal distance from the CoM to the edge and h is the CoM height. Report the smallest θ and the edge it belongs to ("Tips backward at 14° slope; arm extended forward reduces to 9°"). Sweep arm poses or a lift height, since the CoM moves. For acceleration a, the CoM tips when a/g > d/h, which gives a maximum safe deceleration of g·d/h.
- **Reachable workspace:** Monte-Carlo-sample the joint ranges, run forward kinematics, and keep collision-free samples. Report the reach envelope and whether specified targets (a table top, the floor, a shelf height) are reachable.

## 4. Lightweight structural checks (FEA in JS/WASM, beam formulas, print anisotropy)

### Takeaway
There's no mature general-purpose 3D FEA solver for the browser. NGSolve runs in WASM through Pyodide/JupyterLite, and smaller Rust→WASM tools cover frames (Stabileo) or 2D plane stress (Feasium). For printed brackets around hobby servos, closed-form beam or plate checks with an anisotropy knock-down are enough. Layer-adhesion strength is about 30–55% of in-plane strength in CNC Kitchen's hook tests, so a part loaded across its layers is the main risk. FEA is worth running only for heavily loaded, oddly shaped parts, and a native subprocess (CalculiX, gmsh) beats WASM there.

### Cited Findings
- CNC Kitchen hook tests (Prusa MK3S, stock profiles; identical wall and infill settings, values not stated). Failure loads, flat versus vertical (load across layers): PLA 73 / 40 kg (55%), PETG 55 / 25 kg (46%), ASA 57 / 17 kg (29%; 20 kg in a ~30 °C enclosure). Bending modulus: PLA 3300 MPa, ASA 2300, PETG 1900. Notched Izod impact: PLA 5 kJ/m², PETG 8.6, ASA 18. PETG bent rather than snapping. — [CNC Kitchen: Comparing PLA, PETG & ASA](https://cnckitchen.com/blog/comparing-pla-petg-amp-asa-feat-prusament?format=amp)
- CNC Kitchen also studied extrusion temperature versus layer adhesion (PLA 190–270 °C, PETG 200–260 °C, standing specimens). I did not get numeric results. — [CNC Kitchen: extrusion temperature and layer adhesion](https://www.cnckitchen.com/blog/the-influence-of-extrusion-temperature-on-layer-adhesion)
- Community reports (anecdotal) say too much cooling or printing too fast or cold "really destroys layer adhesion for PETG". — [Bambu Lab forum: PETG brands compared](https://forum.bambulab.com/t/various-petg-brands-compared/72387)
- Browser/WASM FEA: Stabileo (Rust→WASM frame analysis that re-solves on every edit; not continuum FEA); Feasium (2D plane-stress FEA in Rust→WASM with React/PixiJS); NGSolve compiled to WASM and run through Pyodide in JupyterLite (nonsymmetric direct solvers umfpack/pardiso unavailable there). A 2024 paper reports WASM serial FEM speed "close to that of native C++" and big WebGPU speedups at million-DOF scale. — [Stabileo wiki](https://github.com/lambdaclass/stabileo/wiki); [NGSolve in JupyterLite](https://docu.ngsolve.org/ngs24/myaddons/lite.html); [J. CAD & CG 2024](https://jcad.cn/en/article/doi/10.3724/SP.J.1089.2024-00596)

### Inferences (standard formulas for agent checks)
- **Cantilever bracket** (servo or arm load F at length L, rectangular section b × h): σ_max = 6FL/(b h²) and tip deflection δ = FL³/(3EI) with I = b h³/12. Allow σ_max ≤ σ_allow / SF, with SF ≈ 2–3 for printed parts. Use E from the bending modulus above (PLA ~3.3 GPa, PETG ~1.9 GPa). When the bending stress pulls layers apart (the bracket's long axis is along Z of the print), multiply allowable strength by ~0.5 for PLA, ~0.45 for PETG and ~0.3 for ASA (CNC Kitchen ratios). A good check output is the print orientation that puts the layers parallel to the bending axis.
- **Deflection matters as much as strength for servo robots:** a 1° droop at a 20 cm reach is 3.5 mm. Add a stiffness check (δ/L or end-slope θ = FL²/(2EI)) alongside the strength check.
- **Bolted joints into plastic:** check bearing and pull-out at screw bosses (heat-set inserts versus self-tapping). Consider this a heuristic rule set, not a computed check.
- **When FEA is worth it:** thin ribs, large topology changes or loads near the allowable after the beam check (e.g. SF < 3). In Electron, the practical path is a sandboxed native subprocess (gmsh mesh → CalculiX static solve, both GPL). That keeps GPL code out of the app bundle (licensing to verify) and avoids building a WASM FEA. NGSolve-in-Pyodide is the only full WASM FEM I found.

- I did not verify CalculiX/gmsh licenses (believed GPL) or whether any CalculiX WASM build exists. I found none.

## 5. How professional tools present these checks, and how an agent should report them

### Takeaway
Professional CAD reports each problem as a located, clickable fact: the pose or frame, the parts involved, the size (interference volume, clearance below the threshold), and a jump to that state. An agent should report a pass/fail table per check, with numbers, the worst case, the margin and one fix per failure.

### Cited Findings
- SolidWorks interference results list frame, time, parts and interference volume, and selecting one moves the assembly to that frame. Every selected component pair is checked unless they belong to the same mechanism part. — [SolidWorks: Detecting Interference](https://help.solidworks.com/2019/english/SolidWorks/motionstudies/t_detecting_interference_motion.htm)
- Clearance Verification flags gaps below a user-set minimum. Dynamic Clearance shows the minimum distance live. Collision Detection can stop a drag at contact with an audible warning, and there are also checks for hole/fastener thread mismatch. — [SolidWorks Clearance Verification](https://help.solidworks.com/2020/English/SolidWorks/sldworks/c_Detecting_Problems_SWassy.htm); [Solid Solutions: collision detection](https://solidsolutions.co.uk/SOLIDWORKS/3d-cad/features/collision-detection.aspx)
- The Artifex community tool runs a render → find errors (joint axes, scale, orientation) → fix loop on AI-generated URDFs. — [Artifex thread](https://discourse.openrobotics.org/t/artifex-ai-generated-urdfs-with-visual-error-checking-seeking-feedback/51511)

### Inferences
- Suggested `verify_design` tool output for the agent, one row per check with a status, a worst case and a fix:
  - Kinematics: every joint has a servo, an axis, a range and a parent/child.
  - Self-collision sweep: usable range per joint, and clashing pairs with angle and depth.
  - Clearance: minimum gap to cables and moving parts.
  - Joint torque: required at worst pose vs. servo stall, SF, and speed at load.
  - Mass: total, per subassembly, and links under 1 g.
  - Stability: CoM margin, minimum tipping angle and edge, maximum acceleration.
  - Structure: highest-stressed bracket, SF, deflection, and whether it's loaded across layers.
  - Optional dynamic test: MuJoCo settle/drop and scripted joint motion.
- Match the studio's copy rules: state what happened, then the fix ("Shoulder needs 18 kg·cm; MG996R stalls at 11. Use an STS3215 or shorten the arm to 18 cm.").
- Make each failure selectable in the canvas (pose the robot at the failing angle and highlight both parts), as SolidWorks does, so the user and the agent's `look` render see the same state.
- Mark checks as "estimated" when their inputs are assumptions (infill, density, unknown servo specs), and as "exact" when they come from manufacturer meshes and datasheets.
