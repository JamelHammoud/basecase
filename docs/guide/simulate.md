# Simulate and train

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8d. Simulate & Train (MuJoCo)

Stages 3 and 4 of the robotics loop (§1); milestones in [docs/Robotics loop.md](../../docs/Robotics%20loop.md). The **Simulate** tab (right panel, shown while the scene has joints) runs the scene's robots under MuJoCo physics and trains policies for them.

- **One formulation, one model, one oracle.** MuJoCo's formulation runs everywhere: the live sim (`@mujoco/mujoco`, DeepMind's official WebAssembly build), Forge's own batched physics for training (§8g), and C MuJoCo as the unforked oracle, all from the same generated MJCF at the **same pinned version**. Forge may train on a cheaper profile of the model, but a result counts only after replay on the reference model in C. Never add a physics engine with a different formulation.
  - **Pinned at 4.0.0.** The trainer takes `mujoco-core` (4.0 split the Python package into `mujoco-core`, the bindings and C library with only `numpy`; `mujoco-studio`; and `mujoco`, which installs both): `train.py` and `verify/` need nothing from Studio, and `rollout` is in core. 4.0 needs Python 3.11 or newer.
  - **Updating MuJoCo:** `node tools/sim/update-mujoco.mjs [version]` (latest when omitted) bumps `package.json`, `electron/trainer/pyproject.toml` + `uv.lock` and Forge's `VERSION` (`forge-mujoco/build/fetch.rs`, which `tools/forge/stage.mjs` reads too) together, then runs `node tools/sim/smoke.mjs`, which fails if the three pins differ or the WASM and Python engines differ in version or in result. Never bump one side alone. Then read the release notes against what `mjcf.ts` generates and what `forge-ir` accepts (a new enable flag or model feature must be refused until Forge implements it), rebuild Forge (it fetches the new C library), and rerun every gate that touches physics: `s0-foundation`, `s1-f1-native-trainer`, `s1-f1b-sysid-rewardlang`, `s1-f2-learner`, `s1-f3-simd-engine`, `s1-f4-metal`, `s2-m1-first-case`, `s3-servo-models`, `s3a-motor-kit`, `s4-routines-core`, `s4b-routines-flow` and `s5b-daemon-app`. The `s3a-motor-kit` run retrains the Kit on the new version; refresh `src/routines/kit/` from it (`node tools/routines/kitLibrary.mjs quad-servo:velocity-tracking quad-servo:settle-to-neutral`), so the committed policies record the version they were trained on. We consume upstream releases; we don't fork MuJoCo's C code.
  - **What 4.0 changed for us:** nothing in the generated models. Its breaking changes are in tendons (sidesite), flexes, the removed cable plugin and `composite`, RK4 with ball or free joints, height fields, cameras and skins; we generate none of those. The fixes that touch our features don't apply either: implicit actuator derivatives are now skipped under a saturated joint or tendon `actuatorfrcrange`, and we clamp with the actuator's `forcerange` (already skipped before 4.0); accelerometers on static bodies (we have no sensors); pair `solref` mixing (no explicit pairs); `boundinertia` now also bounds non-positive-definite inertias that used to fail to compile (we set it, so a degenerate hull now loads instead of erroring). Native CCD's numerics changed, which can move hull-to-hull contacts (robot against scenery or SimReady objects) at rounding level; plane contacts don't use it.
- **The scene is the source of truth.** `src/sim/mjcf.ts` (`buildMjcf`) writes the MJCF from the scene; never hand-edit or store a model file as truth. Fix the design, and the model follows.
  - Bodies: one per joint (`buildRig`), holding the parts that joint moves, under a root body with the robot's base. `src/sim/morphology.ts` classifies each robot as fixed, legged, wheeled or wheel-legged from its joint tree, names and catalog parts; anything but fixed floats (free joint), and `MjcfInput.fixedBase` overrides it. Continuous wheel joints get `velocity` actuators, and `SimJoint.actuator` maps joints to actuators, so never assume the two share an index. Parts with `physics.dynamic` (SimReady objects, §8e) get a free body per group, with their own mass and friction (`priority="1"`, because MuJoCo otherwise takes the higher of two friction values and the 0.9 default would hide anything lower), and collide with robots, scenery and each other. Every other solid part is fixed scenery, except one whose mesh starts sunk at least 2 mm into a robot part's mesh on every axis (bounds of the placed meshes, not the listed size, since a catalog part keeps its own mesh) and is smaller than that robot (a speaker or sensor placed on it but not grouped with it): it rides on that part's body and adds its mass (`mjcfEmbedded.ts`). A part that only rests on the robot, or encloses it, stays scenery.
  - Body frames keep the world's orientation at rest (origin = the joint's pivot), so sim poses map back to parts without rotations (`simDeltas` in `useSimulation.ts`).
  - Frames: scene mm Y-up → MuJoCo m Z-up as `(x, −z, y) / 1000` (the agent frame). The robot faces −Y.
  - Geoms: the convex hull of each part's mesh (hull vertices only, `maxhullvert` 96, `inertia="convex"`), mass from `partMasses` (§8b), inertia from the hull. Robot geoms collide with the floor and scenery, not with each other (rest-pose hulls overlap); exact self-collision stays with the mesh sweeps in `three/interference.ts`.
  - **Measured servos** (every servo on a revolute joint has an `ActuatorSpec.fit`, §8a; `src/sim/servoModel.ts`, `mjcfServo.ts`): BAM's voltage P law, at the variant's `atVolts`. `kp` = kt / R × firmware P × error gain × V; `kv="0"` set explicitly (the firmware runs D 0, and `dampratio` resolves only at compile time, so randomized armature or mass would leave a stale `kv`); joint damping = viscous + kt²/R (back-EMF); armature from the fit; force range ±kt × max duty × V / R. Damping sits on the joint, outside the force clamp, so a saturated servo still loses torque with speed, as a voltage-limited motor does. `frictionloss` = M6 base friction + `load_friction_external` × the weight moment beyond the joint (`holdingLoad`), a static stand-in for BAM's load-dependent friction. The servo's command delay uses MuJoCo's native actuator delay (`delay`, `nsample` = ⌈delay / timestep⌉ + 2, linear interpolation). These joints read `dynamics: 'measured'`. A joint with a calibration (`MjcfInput.servoFits`, set by `calibratedInput`, §8k) uses its fitted `ServoFit` and volts in place of the catalog's.
  - **Estimated servos** (no fit, or no servo): range from `RobotJoint`, force limit from the servos' stall torque (`actuatorOf`), else the published `effortNm`, else an estimate from the weight the joint holds. `kp` reaches full torque about 10° off target, `dampratio` 1, armature from the torque. The Model section and the agent's sim report count these (`dynamics: 'estimated'`).
  - **Not modelled:** the STS3215 firmware's target rate limit (BAM's `max_velocity`, 5.1 rad/s), current limits, Stribeck and motor-side load friction, supply sag and backlash. The gate shows the rate limit is the largest remaining gap on steps (a light-load step is 21 mrad RMS off BAM, against 22 for a fitted first-order-plus-delay); adding it means a per-substep target ramp in the engine, `train.py` and Forge alike.
  - **Delay history:** a delayed actuator reads past controls, and MuJoCo starts that history at zero, which would yank every joint toward 0 at reset. `SimEngine.reset` and `respawn` fill it with each joint's current position (`primeCtrlHistory` → `mj_initCtrlHistory`), and `train.py` does the same with `ctrlDefault` before saving its start state (`mjSTATE_FULLPHYSICS` includes the history, so every episode reset restores it). Anything else that resets a model with delays must do the same.
  - **Proof:** gate `s3-servo-models` (§0k) runs plant-bam's nominal STS3215 at 7.4 V and XL330 at 5 V on four pendulum loads through a step, a 0.2–5 Hz chirp, a multisine and a hold against gravity (`verify/servo/bam-reference/`), and requires the sim's RMS error to beat half the teleport baseline and a first-order-plus-delay filter fitted to the same BAM trajectory, on every run. It also checks no fixture robot is kicked at reset and that WASM matches C MuJoCo with delays.
  - The start state is the pose on the canvas, lifted to just above the floor.
- **Simulating never edits parts.** Like posing (§8c), the sim only moves what the canvas shows (`Viewport3D.setPose`). Ending it, or editing parts or joints while it runs, returns the canvas to the posed model.
- **World items** (§8h) come in through `MjcfInput.world` (`src/sim/mjcfWorld.ts`): bodies with no parts, posed by `worldDeltas`; markers don't collide.
- **Off the main thread.** `src/sim/sim.worker.ts` runs `SimEngine` (`src/sim/engine.ts`, no DOM, so it also runs in Node) in real time × speed and posts body poses per frame, with each joint's target (`jointTargets`: the actuator's control for position joints, the joint position otherwise), which a connected emulated robot follows from Test up (§8k). `Simulation.run()` steps a fresh model headless in its own worker (for agent checks) without touching the live one. `Simulation.runRoutine()` loads the scene and sends a `routine` message: the live worker then steps a Routine's L1 run (§8j) in place of free stepping and posts its new trace events with each frame.
- **Controllers:** Hold pose, an animation's keyframes (does the walk cycle really walk?), a trained policy, a skill (Try in the Train section), Drive (live commands by robot class or through a ready Walk, §8h), or Limp (zero force range, so only passive joint damping and friction remain). Push shoves the robot sideways with half its weight for 0.15 s.
- **Grab and fling:** while a simulation is loaded, the Move and Rotate gizmos grab instead of edit (`Viewport3D` `onGrab`; parts never change). The dragged part's body is pulled toward the gizmo on a critically damped spring scaled by its robot's mass, with gravity compensated (`SimEngine.grab`, like MuJoCo's viewer perturbation), so a slow drag lifts or turns the robot and a quick release flings it. A multi-selection grabs its first part, and its gizmo follows the robot.
- **Result:** per robot "Standing" or "Fell at 2.4 s" (tilt over 60° or the root below 45% of its start height), tilt and distance moved; Peak torque lists the hardest-working joints (peak / limit, time at the limit), and a click selects the joint's link.
- **Training** (`useTraining.ts`, `electron/trainer.mjs`, `electron/trainer/train.py`):
  - One job runs at a time across the whole app (`electron/trainer.mjs`), because each job uses every core. Others queue, user training ahead of background work; user training pauses a running Motor Kit job, and the Kit waits while the Gatekeeper lease exists (§8i). A crash reads as a crash rather than a stop. Each run keeps its folder in `library/training/<id>` so a later Kit stage can warm-start from it by id (anything else in `warmStart` is refused, never read as a path); the newest 8 finished runs stay. The time budget counts active time, so a sleeping laptop doesn't spend it.
  - Runs as a child process through **uv**, which installs the pinned Python, MuJoCo and PyTorch on first use into `library/trainer-env` (`--frozen` against `uv.lock`, and `--exact`: `uv run` otherwise leaves packages the lock dropped, and an env made for 3.17 kept the old `mujoco` package beside `mujoco-core`, whose stale cable plugin then failed every import). Without uv the Train section says how to install it.
  - **The Train section** has no task menu. **Teach it to** takes any goal (the placeholder is an example for this robot's body, `teachExamples.ts`) and sends `/train <goal>` to the agent, which drafts a contract, shows it and races solvers on it (§8i). Under it, the robot's **skills**: the Motor Kit for legged robots (Stand, Walk, Get up, Settle) and every skill the user taught, each with its state: training (the trainer's message, a share and a progress bar, and Stop for user jobs), ready (its Arena line and Try, which runs it in the sim; Walk has Drive instead), Recheck after a mass or size edit (Arena only), or Train. Train on a taught skill sends its words to the agent again. Hidden in the web demo.
  - PPO (rsl_rl-style: ELU MLP 256-128-64, adaptive KL step, GAE) over 64 robots stepped together by MuJoCo's threaded `rollout`; about 20K steps/s on an M-series Mac.
  - **Sim-to-real by default:** every robot gets its own friction (0.6–1.3×), link masses (±15%) and servo stiffness (±15%), a random heading and start noise, and is shoved every 2–5 s.
  - Progress streams as `train-progress` events (one JSON line per batch). Stop saves what it learned. The policy is checkpointed every minute, then evaluated in a clean 8 s run.
  - Results go to `library/policies/<id>/`: `policy.json` (the app runs it), `policy.onnx` (anything else runs it) and the `model.xml` it trained on. The scene keeps a `PolicyRecord` in `project.policies`, stamped with the job's `minutes`, sim version and robot fingerprint (below). The **Policies** section (`PoliciesSection.tsx`) lists them with their steps, like Poses (§8c): a click runs one as the controller. A stale policy's row shows an amber `Badge`, Out of date. Right-click offers **Retrain** (disabled while a job runs) and Delete, which asks first. Retrain (`Training.retrain`) starts the same job for the record's robot, task, command and minutes (20 when the record predates `minutes`) under the same name; while it runs the row shows the trainer's message, its share of the time budget with a progress bar and Stop (or the trainer's error if it fails), and when it finishes the new record takes the old one's place and the old policy's files are deleted. Until then the old policy stays and runs. There's no Delete button on the row.
- **Stale models** (`src/sim/policyFreshness.ts`, `isStalePolicy`): a policy is stale when it was trained on an older sim or on a different model of its robot.
  - `SIM_MODEL_VERSION` (`src/sim/mjcfTypes.ts`) goes on every job and `PolicyRecord`, and a missing version counts as 0. Bump it when actuator or contact behaviour changes for existing robots.
  - **Fingerprint:** `buildMjcf` gives each `SimRobot` a `fingerprint` (`mjcfFingerprint.ts`), a hash of the MJCF it writes for that robot: its mesh assets (vertices sorted, since hull order follows where the robot stands), its body tree without the root body's position, its actuators and the timestep. Scene-wide numbering (`j3_`, `m5_`, `root_1`) is dropped, so scenery, world items, other robots, the canvas pose and moving the robot don't change it; a resized link, a mass, a servo or a new active calibration (`calibratedInput`, §8k) do, and rolling a calibration back restores the old one. `trainingJob` stamps it on the job, and the trainer copies it to the record.
  - The current fingerprints come from the scene model `useSkills` rebuilds after edits (1.5 s after the last one, while the robot is legged or the scene has skills or policies, and on any calibration change). `Training.isStale` compares against them; a record with no fingerprint, or before the model is built, falls back to the version check.
  - Readers: the Policies row, the agent's `simulate` (refuses a stale policy), `training_status` (marks it) and Peak torque (reports Not run with "Train it again" instead of failing), all through `Training.isStale`, so they always agree. `isPolicySpec` refuses another `POLICY_VERSION`. Version 1: measured servo models.
- **The policy contract** (`src/sim/policy.ts`, mirrored in `train.py` and Forge's `forge-train`, §8g): observation = gravity, angular and linear velocity in the root frame, command, joint positions − default, joint velocities, last action, then each depth eye's rays when `eyes` is set (§8l); action = default + 0.25 × clip(a, −1, 1), every 20 ms. Change all three together and bump `POLICY_VERSION`. `eyes` is the one optional extension: a v1 policy without it means what it always meant, and `isPolicySpec` checks the normalizer's width (`policyObsSize`). The sim engine casts the eyes in `stepPolicy` (`policyStep.ts`).
- **Camera views** (§8l): while a simulation is loaded, the camera strip shows the robot's camera parts and the stationary camera views live; `Simulation.subscribePoses` feeds it the same poses the canvas gets.
- **Robot package** (Export ▸ Robot Package, ⌘K Export Robot Package; on once the scene has a movable joint): one zip, `<scene>-robot.zip`, for MuJoCo, ROS and LeRobot, with an “Exporting robot package…” progress toast while it builds, then “Exported ⟨name⟩”. Help: `site/content/help/export-a-robot-package.md`. `src/workspace/robotPackageExport.ts` gathers the model, measures, robot part triangles and the scene's policies (`loadPolicy`; missing ones are left out); `src/sim/robotPackage/` builds the files and zip in `robotPackage.worker.ts` (local fallback through `workerRpc`).
  - `robot.xml`: the sim's model, byte for byte (`sim.model`, else `buildModel()`, the same call Simulate loads). Hulls are inline, so it needs no other file. It holds what the sim holds: every robot, scenery and world items.
  - `robot.urdf` (`src/utils/robotImport/urdfWriter.ts`, beside the reader): one link per robot body (`SimBody.robot`, `parent`, `joint`, set by `buildMjcf`), named as the MJCF bodies, and one joint per body named as the MJCF joint (`j3_knee`), so the MJCF, URDF, joint map, policies and LeRobot datasets share joint names. Same frame as the MJCF: metres, Z up, the robot facing −Y, link frames at the joint pivot with the world's orientation (`rpy` always 0). Revolute with a range, continuous without, prismatic, fixed; limits in rad or m, `effort` from the actuator, `velocity` from the joint's `velocity` or 0 when unknown. Inertials from `partMasses` (`urdfLinks.ts`): mass is the parts' sum, so the total matches the Weight check; centre of mass from the parts' centroids; inertia from each part's placed bounding box about the link's centre of mass. A link with no weighed part gets 0.5 g, like MJCF's `boundmass`. Visual and collision share one mesh per part, `meshes/<part>.stl` (binary, `src/utils/stlBytes.ts`), already placed in its link frame; paths are relative to the URDF. With more than one robot, a `world` link holds each root on a fixed joint.
  - `joint_map.json` (`jointMap.ts`, Robotics loop T4): `{ robot, class, joints }`, one entry per movable joint in `project.joints` order, with servo `id` 1…n and `class` from `servoLayout`, the helper Operate's `sceneRobot` uses (§8k), the MJCF `name`, the scene `joint` label, `type`, the servo `family` (`sts3215`, `xl330` or null, `servoFamilyOf`), `zero_counts` 2048 and `direction` 1 (Operate's defaults until calibration capture exists), `min_rad`/`max_rad` (or `min_m`/`max_m`) and the active `calibration` (§8k) or null. Those keys are the daemon's `calibration.json`, which ignores the rest, so for a robot of ranged revolute joints the file loads there as is.
  - `policies/<id>/policy.json` (the spec the app runs, weights included) and `spec.json`: the observation terms and sizes in contract order (below), the action joints by MJCF name, default pose, scale, `control_dt`, the command and how inputs are normalized. `policy.onnx` stays in `library/policies/` for now: no bridge route reads it.
  - Proof: `robotPackage.test.ts` packages every fixture robot, loads `robot.xml` in the WASM build, reads `robot.urdf` back with `parseUrdf` (same joint names, axes, limits; mass within 1% of the Weight check) and round-trips an imported URDF; `e2e/robotPackage.e2e.test.ts` exports an arm from the menu and checks the zip through `__studio.robotPackage()`.
- **Agent tools** (`src/agent/agentSim.ts`, `cad-mcp-server.mjs`): `simulate` (seconds, controller `hold` / `limp` / `animation:<name>` / `policy:<name>`, shoves by direction and share of body weight, rendered frames) reports falls, tilt, travel and each joint's peak effort against its limit; `draft_skill`, `train_skill` and `list_skills` teach skills (§8i, §9); `training_status` reports progress and the older policies with their clean-run results. The prompt has the agent simulate every legged design (hold, then shoves) and fix the design, not the test. `__studio.simTool(kind, payload)` runs the same tools in dev.
