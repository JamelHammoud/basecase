# Robot runtime

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8k. Robot runtime

The daemon that owns motor writes, the servo emulators, the emulated Unitree G1, the emulated ros2_control robot and the fault tests, in `hw/` (a Cargo workspace). Nothing here has moved a real motor. Everything is proven against emulated servos, an emulated G1 and an emulated ros2_control robot, which are models, not hardware.

- **One write handle.** Only the safety layer can write to a motor.
- **Motors stay locked.** Real serial transport and the motor network are compiled out of default builds until the Stage 8 session (§0k), because this code has never moved a motor. The optional authenticated control listener can reach emulators in a default build.
- **`hw/emu/ledger.yaml` records where each emulated behaviour came from:** datasheet, client-derived, community or assumed.

### Motor lock

- Default builds can't open a serial port. `robot-daemon --port <path>` exits with "Real motors are locked in this build" unless it was built with the `unlock-real-motors` feature, which is the only path to `transport-real`.
- The daemon never opens a device path itself. Its only default transport is the in-process emulator (`--emulated`).
- Default builds cannot open a motor network interface. `robot-daemon --family unitree-g1 --interface <name>` and `robot-daemon --family ros2 … --interface <name>` exit with the same words; only `--emulated` works, and it binds a pair of UDP sockets to 127.0.0.1 and nothing else.
- The gate fails if `serialport` or `rustdds` appears in `cargo tree -e normal`, or if the hardware source guard finds a motor transport outside `transport-real`. The emulator sockets must bind `LOOPBACK`. The control listener has one permitted bind in `network/server.rs`, behind its private-address check, with wildcard and public addresses covered by rejection tests. `verify/hw/motorLock.mjs` asks the built binary for a port, a G1 on an interface and a ROS 2 robot on an interface, and checks it carries neither `serialport` nor `rustdds`. Real motors remain locked until the Stage 8 hardware session (§0k).

### Control interface

The app spawns `robot-daemon --family feetech|dynamixel --ids 1,2,3 --emulated [--factory] [--units <file>] [--latency-ms 16] [--class arm|legged] [--artefacts <dir>] [--seed N]`, or `robot-daemon --family unitree-g1 --emulated [--latency-ms 16] [--artefacts <dir>] [--seed N]` (no ids or class: the G1 has its own 29 motors), or `robot-daemon --family ros2 --controller forward_position|joint_trajectory|diff_drive --topic <topic> --joints a,b,c --emulated [--latency-ms 16] [--artefacts <dir>] [--seed N]` (ROS 2, below), and talks JSON lines over stdin and stdout. Without `--listen`, there is no control network port or discovery advertisement. The artefacts folder holds `calibration.json` and `policy.onnx`; the app writes both (The daemon in the app, below). Every `enter` and `recheck` reads them again, so a policy written after the daemon started counts. Only builds with the `onnx` feature run the policy, loaded once at start; the app's build doesn't, so on Rehearse and up the robot follows the app's intents. Its observation is each joint's position and velocity, not the 12 + 3n terms a trained policy reads (§8d), so the two must meet before an `onnx` build can run one.

In, one object per line:

| `cmd` | Fields | Effect |
|---|---|---|
| `enter` | `mode`: `look`, `set_up`, `test`, `rehearse`, `first_run`, `policy`, `longer_runs` | Climb one rung, or drop to Look. The daemon checks the artefacts itself; the UI can't skip a rung |
| `intent` | `joints`: radians, one per calibrated joint; `null` becomes not-a-number and stops the robot | Latest wins. Also counts as a heartbeat |
| `heartbeat` | | Must arrive at least every 100 ms while motors run |
| `stop` | | Arm: hold. Legged: walk to the stand pose, then hold |
| `fall` | | Lower torque to 10% and hold |
| `release` | | Switch every motor off and return to Look. The only write a stopped robot accepts |
| `clear_fault` | | Only in Look |
| `recheck` | | Re-read the artefacts now |
| `assign_id` | `id`: a servo id in `--ids`; `model`: the model it must report | Number the one new servo on the bus (Servo IDs, below). Only in Set up, motors off |
| `plug_in` | | `--factory` only: put the next new servo on the emulated bus |

Out: `{"event":"hello",...}` first (below), then `{"event":"status",...}` every 100 ms (mode, run state, sealed, fault latched, and per joint id, position, temperature, volts, torque, reply, plus `velocity` in rad/s and `effort` in N·m when the robot reports them: a ROS 2 robot's `/joint_states` when its arrays are full, and the G1's `dq` and `tau_est`; a missing or non-finite value leaves its key out, and Feetech and Dynamixel lines never carry either), plus `fault` (with `code`, a plain `message`, and `id` when the fault is about one motor: overheat, servo protection, stall and wrong direction, `Fault::motor_id`), `mode`, `stopped`, `completed`, `refused` and `assigned` (`id`) events. When stdin closes, the robot stops within 100 ms and the daemon exits once nothing moves. If the daemon itself dies, show `daemon_lost_message`: Dynamixel servos stop on their bus watchdog within 100 ms; Feetech servos have none and hold their last goal.

### Network control

`--listen <private-IP>:7447 --name <robot name>` runs the same daemon persistently on the robot computer. Port 0 chooses a free port for tests. Binding and accepting peers both require a private, link-local or loopback address. Wildcard, public and IPv4-mapped public addresses are refused. The listener advertises `_basecase-robot._tcp.local.` with the robot's name, protocol family and stable `id` in TXT records, restricted to the bound interface. The ID is the lowercase SHA256 hash of the decoded permanent 32-byte pairing key, so saved credentials follow the same robot across hostname, IP and DHCP changes. The motor transport still comes from `--emulated`, `--port` or `--interface`, with the same feature lock as local operation.

Installed services use `--listen-interface <name> --listen-port 7447` instead of pinning an address. `--interface-for <private-IP>` identifies the interface used for installation without opening a motor transport or listener. Each service start selects a private address on that same active interface, preferring a non-link-local address. `--listen-ipv6` keeps an IPv6 installation on IPv6. A missing interface or private address fails closed rather than selecting a VPN or another interface. This follows DHCP changes across service restarts, not during a running session. Numeric `--listen` remains available and cannot be combined with the interface option. With neither option, the daemon starts no listener.

The first start creates `pairing.json` in the artefacts directory with a random 32-byte shared key and a six-digit code. The code appears on the robot computer's stderr. Terminal use can supply `--pairing-code <six digits>` when creating that file. Existing credentials survive restart and ignore a replacement code. On Unix the file has mode 0600. The first authenticated connection using the shared key consumes the code through a synced replacement file, so the code cannot enroll another computer after a restart. Waiting for that proof of key receipt lets a dropped pairing response be retried. Five pairing attempts within one minute are refused after the fifth.

The SSH installer supplies the initial code through a private `pairing-code.seed` file and `--pairing-code-file <path>`, keeping its value out of the service's arguments and environment. The daemon removes the seed after successfully loading or creating `pairing.json`. A missing seed generates a fresh random code when the pairing file is absent, so resetting pairing does not reuse the installation's code. Direct `--pairing-code` remains available for terminal use and tests, but cannot be combined with the file option.

Pairing uses the `spake2` crate's Ed25519 group, HKDF-SHA256 and AES-256-GCM. A challenge carries a fresh 32-byte nonce and the server's SPAKE2 message. The client and server exchange password-authenticated messages and confirm the derived key over the nonce and both messages. The encrypted response carries the permanent key. The code and permanent key are never sent as plaintext on the network. The desktop worker invokes its shipped daemon as `--pair-client <private-IP>:<port>`, writes one JSON line `{ "code": "123456" }` to stdin, and reads the key from that local helper's stdout. The helper does not open a motor transport.

Every connection authenticates again with `HMAC-SHA256(key, "basecase-robot-v1:" + nonce)`. Client commands use `{seq,body,mac}` envelopes, starting at sequence 1. The MAC covers `nonce + ":" + seq + ":" + body`, with `body` the exact JSON string. Server events, including hello, also start at sequence 1 and cover `nonce + ":server:" + seq + ":" + body`. Each direction advances independently. A copied proof, command, event or sequence cannot authenticate in a later session. The shared key is decoded from hex to 32 bytes before HMAC.

Authenticated hello adds `name`, the same stable `id` advertised by discovery, the robot's connection `spec`, and its parsed calibration. The app verifies the ID against the shared key before associating another endpoint with saved credentials. `put_artefact` takes only `calibration.json` (64 KiB) or `policy.onnx` (16 MiB), with base64 `data`. A null policy removes the policy. Calibration is parsed before replacing the file. Writes finish before the next command is accepted, then an `artefact` event names the file. No network command chooses a filesystem path.

Unauthenticated lines are capped at 4 KiB, authenticated lines at 23 MiB to carry a base64 policy. Each line has a five-second total deadline and an authenticated connection closes after one second without input. Malformed or unauthenticated input closes the connection before commands reach the control loop. A separate writer thread uses bounded queues for telemetry and local stdout diagnostics, so a slow or closed socket or log pipe cannot delay a safety tick.

The 100 ms heartbeat and intent watchdogs keep the existing stop plans when the app disappears. Arms hold, legged servo robots execute their stand plan, ROS 2 publishes its hold, and the G1 hands its arms back to its own controller. The daemon stays up. A new authenticated connection waits until the old stop finishes, returns to Look and clears the old fault before accepting commands. It never resumes the previous rung. Local diagnostics include daemon-clock `client_disconnected`, fault and status events for timing that path.

`tests/network_security.rs` covers address classification, a synthetic 1 GB input, HMAC's RFC 4231 vector, SPAKE2 code agreement and encrypted transcript binding, and persistent consumed credentials. `tests/binary_network.rs` drives six-servo Feetech and Dynamixel arms, an 18-servo Feetech legged robot, the G1 and ROS 2 over TCP. It checks the watchdog fault within 150 ms of socket loss, the completed safe stop, a reconnect in Look, unpaired commands, replayed proofs and sequences, a silent connection, the pairing helper, hostile artefact paths, artefact limits and a 1 GB unauthenticated stream. CI runs these with the existing motor fault matrix and unsafe-write tests.

### Installing a robot computer

Operate's Add a Robot Computer and its command in ⌘K collect the host, SSH user and optional absolute private-key path. The current scene supplies the joint map through the existing Robot Package worker, with active calibration, zeros and directions. The form installs the daemon, shows the initial pairing code and connects automatically. Reinstallation preserves an existing key and connects with the saved credential when its one-time code is already consumed.

The terminal entry is `basecase robot install <user@host> --package <folder> [--key <file>]`. `--scene <scene.basecase>` generates the map instead, and with neither option the package folder is the working directory. `--family unitree-g1` and `--family ros2` choose those connections explicitly. Feetech and Dynamixel use the map's servo family. Installation requires bounded rotary ranges that the daemon's calibration accepts. The range, zero and direction must map into encoder counts 0 through 4095 using the daemon's float32 arithmetic and rounding. G1 installation remaps its 29 named scene joints to its 17 writable ids. ROS 2 installation uses the explicit controller's joint names. No physical limits are invented for a sliding or unlimited wheel joint.

`electron/robot/robotInstall*.mjs` validates the SSH target, key and map, resolves the target to a private RFC 1918 or ULA address and pins that address in SSH. The architecture probe chooses the release's `robot-daemon-linux-arm64` or `robot-daemon-linux-x64`, verifies its SHA-256 checksum and ELF architecture, and copies it with `joint_map.json` and `calibration.json` under `~/.local/share/basecase-robot`. The uploaded binary must refuse a real motor port before replacing the existing service. Configured per-servo models travel as `units.json` too.

The service is `~/.config/systemd/user/basecase-robot.service`. It uses systemd's user manager and requires `loginctl enable-linger` for the SSH user, so closing SSH or the laptop does not end the service. The installer checks `systemctl --user` and `journalctl --user`, then waits for the current systemd invocation's listener event and confirms the service remains active. An old pairing file or a briefly started process cannot report a completed installation. SSH uses batch mode, host-key checking, no config file, proxy or local command, and no local shell. The first code is returned from the installed pairing file only after the listener is ready.

Before replacing the service, the staged daemon identifies the interface owning the pinned SSH address. Its checked name is saved in private `network.env`, which the user service reads through `EnvironmentFile`. Every later start resolves that interface's current private address, so restarting after a DHCP change keeps the pairing and discovery identity.

### Runtime tiers and intent slots

- The loop runs every 20 ms. It reads each slot once a tick and never waits on a client. A slot is a seqlock of atomics (`intent.rs`): a writer that stalls mid-write only makes the reader skip that tick.
- A coordinator gets an `IntentWriter`, which can only publish intents and heartbeats. Policy actions use their own slot from `First run` up; Test and Rehearse read the coordinator slot.
- No new intent for 100 ms stops the robot (`intent_stale` or `policy_stale`), and so does no heartbeat for 100 ms (`client_lost`).
- The policy runs on its own thread. A hung or slow policy can't stretch a tick, and a policy that outputs a value that isn't a number stops the robot.

### Safety layer

- `safety::ReadBus` can only ping and read. Write encoding (`safety/encode.rs`) and `ReadBus::send` are private to the safety module. A `SafetyLayer` needs an `ArmGrant`, which only the ladder issues. `compile_fail.md` holds doctests that fail to compile if any of this leaks.
- Every write is a broadcast sync write, so it never gets a reply that could be mistaken for telemetry.
- Goals are integer counts. `guard::next_goal` clamps to the calibrated range, moves at most one step per tick (`min(0.02 rad, speed cap × 20 ms)`), and won't lead the measured position by more than 0.25 rad. Not-a-number never reaches a goal.
- **Soft start:** read positions, write the torque limit at 5%, the goal at the present position, the speed cap, and the Dynamixel bus watchdog (100 ms); then enable torque and ramp it over 1 s. A joint outside its calibrated range refuses to start.
- **Stale replies:** each tick's telemetry read asks for a length that cycles through four values, so a late reply to an earlier request is rejected and counted as late, never used as present. Without this, 40 ms of latency fed 40 ms-old positions to the controller.
- **Seal:** after a stop finishes, the layer is sealed and every write returns `Sealed`. Leaving a sealed layer means dropping it (`release` or Look), and climbing again builds a new one.
- **Hold only what's powered.** Some Feetech firmware switches torque on when a goal is written (the emulator models this), so a hold never writes a goal to a motor that reports torque off.

### Caps (hard-coded in `caps.rs`)

| | Test, Rehearse, First run | Policy | Longer runs |
|---|---|---|---|
| Torque | 30% | 60% | 60% |
| Speed | 0.5 rad/s | 2 rad/s | 2 rad/s |
| Step per tick | 0.02 rad | 0.05 rad | 0.05 rad |
| Run length | 30 s | 5 min | none |

All tiers stop a motor at 50 °C, keep the supply inside 6.0 to 8.4 V (Feetech) or 3.7 to 6.0 V (Dynamixel), and stop on a 100 ms watchdog.

### Mode ladder

Look (read-only bus), Set up (servos checked: each that answers has the right model and no ID is shared, and servos still missing are allowed so they can be numbered; motors off), Test (needs calibration and known firmware, which is read only once every servo answers, so from Set up the daemon recounts the bus and refuses Test until each id answers; earns `tested` after 5 s with every joint moved), Rehearse (needs a policy; motors off, intents run through the guard without writing; earns `rehearsed` after 10 s), First run, Policy, Longer runs.

- Each `enter` re-reads the calibration and policy files, hashes them with the servos' firmware versions, and checks the target's requirements. Evidence is earned only by finishing a stage; it can't be set.
- A calibration, policy or firmware change clears the evidence it invalidates, drops anything above First run back to First run, and holds.
- A fault latches. Nothing climbs until the robot is back in Look and `clear_fault` is sent.
- `hw/spec/ladder.tla` is the TLA+ spec. TLC isn't installed here, so `tests/ladder_model.rs` reads the spec's `Requires`, `Clears`, `Earns`, `Observed` and `Earned` tables, checks the Rust table matches, and walks every reachable state (about 1,300 states and 46,000 transitions) checking the spec's invariants. That search found a real bug: evidence could once be set directly.

### Faults and stops

| Fault | Stop |
|---|---|
| No reply, garbled replies, wrong ID, late replies, duplicate ID, adapter unplugged | Seal at once: no more writes on an unreliable bus |
| Overheat, stall, wrong direction, servo overload flag | Switch that motor off (confirmed by reading it back, up to 5 tries), hold the rest |
| Supply voltage, servo restarted, bus watchdog tripped, joint out of range | Switch every motor off |
| Lost app, stale or not-a-number intents or policy | Arm holds; legged robot stands still |
| Reported fall | Torque down to 10%, hold |
| ROS 2: any of the above that applies, `/joint_states` lost or damaged for 60 ms | Publish a hold at the last measured positions (a base: zero twist) at once, then seal (ROS 2, below) |
| G1: any of the above that applies, lost or damaged lowstate, a motor error | Ramp the arm_sdk weight to 0 (at most 80 ms), then seal (Unitree G1, below) |

Each fault has a beginner-readable message in `fault.rs`. The fourteen gate tests (`fault_*` in `crates/robot-daemon/tests/faults_*.rs`) check the safe state, its time limit, no writes after it, and the message. Comm faults seal in 58 ms (three ticks), and a lost app or policy in about 100 ms.

Known limits: a calibration with the wrong sign moves the joint the wrong way while its encoder agrees, so only a person or a camera can catch it. Calibrate Servos catches it from a camera on the emulated robot (Zero and direction from a camera, below); a real robot waits for Stage 8 step 4. Two servos sharing an ID and sitting at exactly the same position answer identically and go unnoticed until they differ. Gravity-loaded joints that sag during the 5% soft start trip `wrong_direction`.

### Unitree G1

The G1 talks DDS over Ethernet through unitree_sdk2. The daemon drives its arms and waist through `rt/arm_sdk`, which the G1 blends with its own locomotion controller by a weight from 0 to 1, so the robot keeps balancing. Handing the weight back to 0 is the G1's stop.

- **Messages** (`servo-wire/src/unitree/`): `LowState` from `rt/lowstate` and `LowCmd` on `rt/arm_sdk`, in unitree_hg's layout as CDR (little endian, 4-byte encapsulation header). There are 35 motor slots with the 29 joints first in unitree_sdk2's order (legs 0–11, waist 12–14, left arm 15–21, right arm 22–28); slot 29's `q` is the arm_sdk weight. Each message carries unitree's `crc32_core` over the C struct image (padding as zeros, every word but the last), and a test pins it to that function compiled from C (1004 and 2092 bytes). A `LowState` whose CRC doesn't match is refused and counted.
- **Ids:** a daemon joint id is the motor index + 1, so 1–29, and only ids 13–29 (waist and arms) can be written. Status lists all 29 with positions in the servo counts convention (`2048 + rad × 4096 / 2π`), plus `weight`.
- **Transport:** `TopicTransport` (`servo-wire/src/topics.rs`) publishes and receives whole CDR samples. Default builds have one kind: the emulated G1 on a thread in the daemon's process, reached through two UDP sockets on 127.0.0.1 (`LoopbackLink`, one datagram per sample, a topic byte first). That isn't RTPS. The real network is `transport_real::DdsTransport` on rustdds, built only with `unlock-real-motors` (`--interface en0`). rustdds is pure Rust, so it builds on Mac and Windows with no C toolchain, and it speaks RTPS, which CycloneDDS matches by topic and type name (rustdds sends XCDR1 and no XTypes type information). It binds its unicast sockets to the wildcard address even when told which interface to use, which is why it can't be in a default build. Its writers are reliable, keep last 1; its readers are best-effort, so they match either kind of writer. Nothing in it has met a real G1 or CycloneDDS.
- **Safety layer:** `safety::ArmSdkLayer` is the G1's one write handle. Like `SafetyLayer` it needs an `ArmGrant` from the ladder, and `G1Bus` (the read side: lowstate, and the loco service's GetFsmId) can't publish (`compile_fail.md`). Every arm command goes through the same guard (`next_goal`): the calibrated range intersected with the G1's URDF limits (`g1.rs`), one step per tick at the caps' speed, and no more than 0.25 rad ahead of the measured joint. Gains are kp 60 and kd 1.5 with no feed-forward, as in unitree_sdk2's arm example. The encoder only fills writable motors, so leg slots and slots past 29 are never written. The weight rises 0.02 per tick (the 1 s soft start) and falls 0.25 per tick, so it reaches 0 at most 80 ms after a stop begins; then the layer seals. Dropping a layer (`release`) publishes weight 0 only when that is one tick's fall or less, and `enter` is refused (“Go back to Look first.”) while the arms are held (soft start, running or handing back), so a new layer never replaces a weighted one in a single message.
- **Stops:** Stop, Fall, a stale intent, a lost app, an intent that isn't a number, a joint out of range, a motor error, and lowstate that's lost or damaged for 60 ms all hand the arms back: the weight ramps to 0, the layer seals and the daemon says so, in words that say the arms went back to the G1's own controller (`Fault::g1_message`). The torque cap and voltage window don't apply; the G1's own PD and limits set its torque.
- **Ladder:** Look reads lowstate and publishes nothing. Set up waits up to 60 ms for fresh lowstate, that all 29 motors answer (mode 1, no motorstate error), and that the loco service's GetFsmId (api 7001 on `rt/api/loco/request`) answers 200, its locomotion mode; no answer within 50 ms is `loco_silent`, a wrong mode `not_balancing`. It records the robot type and version as the firmware. Test needs `calibration.json` listing ids 13–29 exactly, streams arm intents, earns `tested` after 5 s with every joint moved, and runs until stopped. Rehearse and the policy rungs above it are refused for the G1.
- **Emulator** (`servo-emu/src/g1/`): publishes lowstate every 2 ms. Each joint is a PD-driven inertia with friction and torque limits, stepped at 1 kHz, following the weighted blend of arm_sdk and its own standing pose; hidden per-unit inertia, friction and gain come from the seed. `InProcessG1` (virtual clock, latency each way, a sample filter) carries the tests and `serve_loopback` the binary. Faults: `BadCrc`, `Silent`, `MotorDown`, `NotBalancing`. Every behaviour has a `unitree-g1` entry in the ledger.
- **Tests:** `tests/g1.rs` (the round trip, the weight ramp both ways, `enter` refused while the arms are held, a stale intent released within 100 ms, a bad CRC refused, legs never written, policy rungs refused, Set up's checks including a silent loco service, Look and Set up never publishing), `tests/faults_g1.rs` (`fault_g1_lowstate_lost` and `fault_g1_app_lost` in the gate's fault matrix, and a motor error), `tests/binary_g1.rs` (the release binary over JSON lines and the loopback sockets, and `--interface` refused), and `tests/no_unsafe_write_g1.rs`, a 128-case proptest whose checker decodes every `LowCmd` and fails on a leg or spare slot written, a goal outside calibration and the URDF limits, a jump larger than one step other than a hold at the measured position, a weight rising or falling faster than the ramp, changed gains, or anything published after the layer sealed. Its canaries check that it sees real motion and catches a planted jump and a planted weight drop.

### ROS 2

Most robots people already own run ROS 2 through `ros2_control`: UR and Franka arms, TurtleBot bases, SO-101 drivers. The `ros2` family drives any of them the same way: it reads `sensor_msgs/JointState` from `/joint_states` and writes one controller's topic. Only an emulated one connects in this build.

- **Messages** (`servo-wire/src/ros2/`): `JointState`, `std_msgs/Float64MultiArray`, `trajectory_msgs/JointTrajectory` and `geometry_msgs/Twist` in CDR (XCDR1, little endian), as rmw lays them out; golden byte arrays pin each. A ROS topic `/a/b` is DDS topic `rt/a/b`. Decoding checks every length against the bytes left before allocating: at most 64 names or values, 256 bytes a string, 64 trajectory points. A `JointState` with mismatched counts, a duplicate name or a position that isn't a number doesn't decode.
- **Spec:** a controller kind and its topic, and the joints in the scene's order (ids 1…n). The topic follows ROS 2 name rules (absolute, one to four segments of `[A-Za-z_][A-Za-z0-9_]*`, no `__`, at most 128 characters) and must end in its kind's fixed segment: `commands` (`forward_position`), `joint_trajectory` (`joint_trajectory`), `cmd_vel` or `cmd_vel_unstamped` (`diff_drive`). Joint names are 1 to 64 of `[A-Za-z0-9_]`, not starting with a digit, 1 to 32 distinct, exactly two (left wheel, right wheel) for `diff_drive`. `checked_topic` and `checked_joints` (`names.rs`) refuse anything else before a socket opens, and the app checks the same rules first (`electron/robot/ros2.mjs`).
- **Joint map:** `map_joints` (`ros2/joint_map.rs`, pure) matches the spec's names to `JointState.name`, so a robot that publishes in another order works. Status reads each joint by name; one missing from the newest fresh state replies `missing`.
- **Transport:** the G1's seam. `Endpoints::ros2` reads `rt/joint_states` and writes the controller topic; the emulated robot runs behind the shared loopback sockets (`serve_ros2_loopback`), and `DdsTransport` takes the same endpoints in an unlocked build. Nothing in it has met a real ros2_control robot or a ROS 2 DDS.
- **Safety layer:** `safety::Ros2Layer` is the one write handle and needs an `ArmGrant`; `Ros2Bus` reads and can't publish (`compile_fail.md`). Arm goals go through `next_goal` like every servo: the calibrated range, one step per tick at the caps' speed, at most 0.25 rad ahead of the measured joint. `forward_position` publishes the goals as a `Float64MultiArray` in the spec's order, so the controller's `joints` must list them in that order; `joint_trajectory` publishes one point at the goals, 20 ms from start, with `joint_names`. `diff_drive` intents are `[m/s, rad/s]`, capped at 0.2 m/s and 1.0 rad/s in Test (0.5 and 2.0 from Policy), changing at most 0.01 m/s and 0.04 rad/s a tick.
- **Stops:** ros2_control controllers hold their last command, so the daemon's stop is a hold: Stop, Fall, a stale intent, a lost app, an intent that isn't a number, a joint out of range, and `/joint_states` lost or damaged for 60 ms publish the last measured positions (each within its range, else its last goal) or a zero twist at once, then the layer seals and the daemon says the robot is holding still (`Fault::ros2_message`). Torque and voltage caps don't apply; the robot's own controller sets its torque.
- **Ladder:** Look reads `/joint_states` and publishes nothing. Set up waits up to 100 ms for a fresh `JointState` and refuses (`joints_unmatched`) if the robot leaves out a scene joint or publishes one the scene lacks, naming up to three of each in one sentence; it records the published names as the firmware. Test needs `calibration.json` listing ids 1…n, soft-starts with one hold at the measured pose, streams intents, earns `tested` after 5 s with every joint (or both wheels) moved, and runs until stopped. Rehearse and the policy rungs are refused until the app can send a policy (issue #286).
- **Emulator** (`servo-emu/src/ros2/`): `Ros2Emulator` takes `Ros2Options` (joints in controller order, a `ControllerKind`, the controller's topic, a seed, a fault) and refuses joints and topics the name rules refuse. It publishes `sensor_msgs/JointState` (name, position, velocity, effort) every 10 ms, its joints in a seeded permutation of the controller order. `forward_position` and `joint_trajectory` drive an arm: one PD-driven joint each (kp 50, kd 3, 10 Nm), stepped at 1 kHz, starting within ±0.2 rad, with hidden per-unit inertia, friction and gain from the seed. `forward_position` holds the last `Float64MultiArray` of the right length; `joint_trajectory` matches `joint_names` to its joints, refuses a message naming an unknown joint or leaving one out, interpolates linearly from the current setpoint over each point's `time_from_start` and holds the last point. `diff_drive` takes `Twist` (linear x, angular z) with acceleration limits of 1 m/s² and 4 rad/s², turns its two wheels (left, then right) at `(v ∓ ω·0.160/2)/0.033` rad/s times a hidden per-wheel gain within 10%, and zeroes the command 0.5 s after the last one. Messages it can't decode are ignored and counted (`Ros2Counters`). Faults: `Silent`, `MissingJoint`, `ExtraJoint`, `Malformed` (a NaN position). `in_process_ros2` (virtual clock) carries the tests and `serve_ros2_loopback` runs it behind the loopback sockets. Every behaviour has a `ros2-control` entry in the ledger.
- **Tests:** `tests/ros2.rs` (a 6-joint arm on a forward position controller and on a joint trajectory controller, a diff-drive base inside its caps, a robot publishing in another order, Set up naming a missing and an extra joint, a stale app held within 100 ms then nothing more, hostile `JointState`s with a NaN or 10,000 entries dropped and counted, Look and Set up never publishing, Stop holding at the measured position, policy rungs refused), `tests/faults_ros2.rs` (`fault_ros2_joint_states_lost` and `fault_ros2_app_lost` in the gate's fault matrix), `tests/binary_ros2.rs` (the release binary over JSON lines and loopback, `--interface` refused, crafted topics and joint names refused before hello) and `tests/no_unsafe_write_ros2.rs`, a 128-case proptest over both arm controllers and the base whose checker decodes every command and fails on a goal outside calibration, a jump larger than one step other than a hold at the measured position, a twist over the cap or ramp, a wrong-length or unnamed command, or anything after the seal; its canaries check it sees real motion and catches a planted jump and an over-cap twist.

### Emulator

- `servo-emu --family feetech|dynamixel --ids 1,2,3 --pty [--seed N] [--fault bad-checksum|wrong-model|silent|wrong-id|truncated]` prints `{"pty":"/dev/ttysNNN"}` and serves until killed or its parent exits. The PTY is put in raw mode before the path is printed.
- Windows has no PTY: the PTY module is behind `cfg(unix)` and the binary says so. The Windows path is the in-process transport with 16 ms of injected latency (`InProcessBus`, `WINDOWS_LATENCY_US`), which the fault and end-to-end tests cover.
- **macOS PTYs reject 1 Mbaud.** macOS has no `B1000000`, so pyserial sets custom rates with the `IOSSIOSPEED` ioctl, which only real serial drivers accept, so `setBaudRate(1000000)` fails on a PTY. On macOS the gate runs `verify/hw/conformance.py` through `verify/hw/pty_baud.py`, which turns only that ioctl into a no-op on PTYs and leaves the SDKs untouched. On Linux, PTYs accept it and the gate runs the script directly; `sh hw/emu/linux-gate.sh` runs Gatekeeper's `s5-emu-daemon` in a Linux container (Docker), with Linux build output kept in a volume so it never mixes with `hw/target`.
- **Build output and `npm run check`:** Prettier reads only the root `.gitignore`, so `hw/target/` (which the gate builds) needs `hw/target` in the root `.prettierignore`, or `npm run check` fails on cargo's fingerprint JSON.
- **Seed:** `robot-daemon --seed N` (with `--emulated`, any family) seeds the emulated robot's hidden per-unit parameters as `servo-emu --seed` does: it reaches `BusOptions`, `G1Options` and `Ros2Options` through `Target::Emulated`, and on a servo bus each servo's `UnitParams::from_seed`. Without it the seed is 1. A seed that isn't a whole number stops the daemon (“Bad seed”), and so does `--seed` without `--emulated`.
- **Factory bus:** `--factory` (with `--emulated`) starts the bus empty, the bag of new servos a first robot arrives as. Each `plug_in` adds one new servo at the factory ID 1 (`ServoBus::plug_in_new_servo`, through `add_servo`), up to one per id in `--ids`; another answers “Every new servo is already plugged in.” as a `refused` line.
- **Part models:** `--units <file>` (with `--emulated`, Feetech or Dynamixel only) makes each servo stand in for the catalog part on its joint. The file is a JSON array with one entry per `--ids` entry: `null` keeps the protocol's own unit (STS3215 C001 on Feetech, XL330 on Dynamixel), and an object gives the part's BAM M6 fit (`ServoUnit` in `robot-daemon/src/units.rs`: `volts`, `kt`, `resistance`, `armature`, `friction` with its eleven terms, `firmwareKp`, `errorGain`, `errorGainRatio`, `maxDuty`, `maxVelocity`, `delayS`). A wrong count, an unknown or missing key, friction below 0, any other number not above 0, volts over 60 or anything over 10⁴ stops the daemon before its hello (“The servo models file must give one entry per servo ID.”, “The model for servo 3 has a number out of range.”). The hidden per-unit spread (`UnitParams::from_seed`) is drawn around the part's fit with the same seed rule, so a seed repeats exactly; with no `--units`, or all `null`, every unit is what it was without it.
  - **P gain:** the firmware's P-gain register keeps the protocol's factory value (32 on Feetech, 400 on Dynamixel), so a part's error gain becomes `firmwareKp × errorGain ÷ that value`, which matches the part's model at factory settings.
  - **Supply:** the bus keeps one supply at the protocol's volts (7.4 or 5.0) and its sag; a part's motor is driven at the sagged supply times `volts ÷ the protocol's volts` (`UnitParams::supply_scale`), so an XL430 rated at 11.1 V runs at 11.1 V. Present voltage, the firmware's voltage limits and the daemon's voltage window all read the bus's own supply.
  - **Factory bus:** a servo takes the part of the id it holds (`ServoBus::with_parts`, `factory_with_parts`). A new servo starts as ID 1's part and becomes the part of the id it's given (`refit_renumbered`, after every instruction), so the order of the Set Up walk doesn't matter.
- **Broadcast ping** replies from servos that share an ID collide like addressed replies (bytes AND together), so identical replies read as one servo, as on a real half-duplex bus.
- **Ledger:** `datasheet` is the maker's manual, `client-derived` is read from client library source (scservo_sdk, DynamixelSDK, rustypot, LeRobot), `community` is published third-party measurement (BAM), and `assumed` was chosen here and is unchecked. Stage 8 step 2 dumps real registers and resolves every `assumed` entry. A new emulated behaviour gets a ledger entry in the same change.

### Proof

- `cargo test --release --manifest-path hw/Cargo.toml` runs unit tests, the emulator firmware tests, the fault matrix, the binary end-to-end tests, the ladder model, `no_unsafe_write`, the G1's tests (Unitree G1, above) and the ROS 2 robot's (ROS 2, above). The gate runs this full command. On pull requests touching `hw/`, Check runs only `cargo test --locked --manifest-path hw/Cargo.toml -p robot-daemon --bin robot-daemon` to compile the daemon and check its argument parser. That last one is a 256-case proptest whose checker decodes every frame on the wire and fails on a goal outside calibration, a jump larger than one step (other than a hold at the measured position), a torque or speed limit above the cap, torque switched on without a soft start, an ID written to a powered servo or outside the robot, or any write after a seal. Its steps include `assign_id`, and a separate case numbers three factory servos and then drives them. It carries two canaries: the checker must see real motion and must catch a planted jump.
- Loom: `RUSTFLAGS="--cfg loom" cargo test --release --manifest-path hw/Cargo.toml -p robot-daemon --test loom_intent --target-dir hw/target/loom`.
- Kani (`cargo install --locked kani-verifier && cargo kani setup`): `cargo kani --manifest-path hw/Cargo.toml -p servo-wire` proves both frame scanners never panic and never consume past their input, and that a single flipped byte never passes the Feetech checksum. `-p robot-daemon` proves the goal guard stays in bounds and moves at most one step, malformed rules never move a goal, torque requests never exceed their cap, and holds stay in bounds.
- Mutation testing: `cargo mutants --dir hw -p robot-daemon -f crates/robot-daemon/src/safety/guard.rs` (repeat `-f` for `layer.rs`, `encode.rs` and `bus.rs`). Every viable mutant in the safety module must be caught; `hw/.cargo/mutants.toml` skips the `cfg(kani)` proofs, which `cargo test` never compiles.
- Tests that mix the virtual clock with real threads (the policy worker) wait for the worker to act, within limits that hold under heavy load, and never assert a tight wall-clock bound. The end-to-end binary test accepts `intent_stale` as well as `client_lost`: a test thread starved past 100 ms stops the robot before the app closes, which is the same safe stop.
- The daemon's write encoder is checked against bytes captured from scservo_sdk and DynamixelSDK. The Python DynamixelSDK 4.1.0 never byte-stuffs what it sends (see the ledger).

### Servo IDs

A first robot's servos all answer at the factory ID 1. `assign_id` (`control/assign.rs`) writes one layout id onto the one new servo on the bus:

- Only in Set up with run Idle, and only for an id in `--ids`. The write goes through the safety layer (`SafetyLayer::renumber`), which refuses once that layer has switched torque on: Feetech clears Lock (55), writes ID (5) and sets Lock again on the new id; Dynamixel writes ID (7), which its firmware accepts only with torque off. Each is a broadcast sync write, like every other write.
- A broadcast ping (`ReadBus::census`, a 780 ms window, since the emulator spaces replies 3 ms per id) lists who answers. A servo is new when it's at ID 1 or at an id outside the robot. Then: the target id held by another servo refuses (“Another servo already has ID 2…”); none new or more than one refuse; the new servo must report `model`, pass the duplicate probe (two new servos at ID 1 answer a ping as one, but not a position read) and have torque off. The id is read back before `assigned` goes out; a servo that didn't keep it refuses.
- The census blocks the loop for under a second. That's safe because Set up never powers a motor and no watchdog runs below Test.
- Because new servos come at ID 1, which is also the first joint's id, the walk numbers from the highest id down and ID 1 last: every numbered servo stays plugged in, never collides with the next new one, and the finished bus holds every id, so Set up → Test climbs at once (LeRobot's motor setup walks in reverse for the same reason).
- Tests: `tests/assign_id.rs` (writes and reads back on one factory servo and survives a power cycle; refuses two new servos, none, outside Set up, a powered servo, a taken id; Test waits for every id) and `fault_numbering_interrupted` (adapter unplugged, or a second new servo appearing mid-walk: refused, nothing written).

### The daemon in the app (interface)

Stage 5b is judged by `s5b-daemon-app` (§0k); its tests in `verify/hw/` are the contract. The main-process side is `electron/robot/`, the page side `src/robot/` and `src/components/operate/`.

- **Bundling:** `npm run build:daemon` builds the release `robot-daemon` (`robot-daemon.exe` on Windows) and `tools/hw/stage.mjs` copies it into `hw/dist/` (build output, not committed), ad-hoc signed on macOS like Forge. electron-builder's `extraResources` copies `hw/dist` to `<resources>/hw` on Mac and Windows, and `npm run dist` / `dist:win` stage it first; any other electron-builder run stages it in `beforePack` when it's missing (§0i). If the binary is still missing, Connect answers “This copy of Basecase can’t run robots. Download Basecase again from basecase.so.”, never the word daemon. The packaged app spawns only that file; from source it uses `hw/dist`. `BASECASE_ROBOT_DAEMON=<path>` overrides the binary, for tests (`daemonBinary` in `robotLink.mjs`).
- **Hello:** the daemon's first stdout line, printed once the transport opens (`hello_line` in `protocol.rs`), is `{"event":"hello","version","family","emulated":true,"real_transport":false,"lost_message"}`. `real_transport` is `real_motors_unlocked()`, so an unlocked build says so; `lost_message` is `daemon_lost_message(family)` (the G1's is `g1_lost_message`: an emulated G1 runs in the daemon's process and stops with it; a real one keeps its last arm command), so the app has the words before it needs them. A refused `--port` exits before any hello.
- **Network connection:** `robot:discover` (`robotDiscover()`) browses `_basecase-robot._tcp.local` through a shared UDP port 5353 socket, joins the multicast group and sends queries on each private IPv4 interface, and returns `{ name, host, port, family?, id? }` with private IPv4 addresses only. Discovery decodes at most 256 records per packet, limits names to 253 bytes and compression to 16 jumps, and collects at most 512 records per scan (`networkDiscovery.mjs`, `networkDns.mjs`). Query sends share one callback-driven queue, keeping the selected interface until the UDP send completes. `robot:network-connect` (`robotNetworkConnect({ host, port?, code?, id? }, unit?)`) accepts a local hostname or private IP, a port (7447 by default) and an optional six-digit code. Every DNS answer must be private or loopback, and the selected address is pinned before connecting. The code goes only to the bundled daemon's `--pair-client` helper through stdin, never argv or the environment. That helper performs the daemon's password-authenticated pairing exchange. Its key is kept in `robot-pairings/` in the app's user data, with private file permissions, and never enters a scene, exported package or renderer event. Each private key record is indexed by SHA256 of its decoded 32-byte key, which is the robot's stable ID in discovery and its signed hello. Hostname and resolved IP endpoint aliases contain only that ID. Reconnects from discovery use the stable ID across DHCP changes and daemon restarts, and the signed hello ID must match the saved key and requested ID. Key and alias writes complete before the key enters the memory cache or authenticates a connection. Omitting the code reconnects with the saved key. The authenticated hello supplies the checked robot specification and saved calibration. Before associating scene joints, the renderer checks its family mapping, robot class and ordered servo IDs against the scene connection choice. ROS 2 connections also match joint names and controller kind. An incompatible connection is disconnected. Discovery cannot establish these facts. Real motor greetings are refused by this build.
- **Network runtime:** `NetworkRobotLink` extends `RobotLink`, so network robots use the same command validation, intent pacing, mode ladder, fleet policy assignment and run recorder. Its socket and 30 ms intent pacer run in a worker. A new challenge nonce authenticates each connection. Commands and telemetry carry increasing sequence numbers and HMAC-SHA256 signatures with separate directional transcripts. The app closes on a forged, replayed or oversized event, accepts at most 64 KiB per incoming line, and closes after one second without an authenticated event even while outgoing heartbeats continue. Calibration and policy updates use the authenticated `put_artefact` command, followed by `recheck`, with fixed artifact names. Pairing and connection attempts can be canceled before DNS or authentication finishes. A failed local session setup closes its authenticated socket before returning failure. Disconnect closes the socket, allowing the daemon's existing watchdog to stop its robot. `networkRobotLink.test.mjs`, `networkSocket.test.mjs`, `networkDiscovery.test.mjs` and `networkPairClient.test.mjs` cover the network path and hostile input.
- **IPC** (all `handle` channels through `trustedIpc`, `electron/robot/robotRoutes.mjs`; preload names in brackets): every channel goes to the `RobotFleet` (Fleet, below), and each unit-addressed channel takes the unit it addresses as its trailing argument: a name matching `[a-z0-9][a-z0-9-]{0,31}` (`isUnitName` in `electron/robot/units.mjs`), or none for `robot` (`DEFAULT_UNIT`), the scene's own robot, so existing single-robot calls address that default unit. Any other unit is refused as “The robot only takes the documented commands.” `robot:connect` (`robotConnect(spec, unit?)`) takes exactly `{ family: 'feetech' | 'dynamixel', ids: number[] (1–253, distinct, at most 32), class: 'arm' | 'legged', emulated: true }`, optionally with `factory: true` (spawns with `--factory`) and `units` (one servo model or null per id, `electron/robot/servoUnits.mjs`: exactly the numeric fields of a `ServoFit` plus `volts`, finite and bounded; written to `units.json` and passed as `--units`), or exactly `{ family: 'unitree-g1', emulated: true }`, or exactly `{ family: 'ros2', emulated: true, controller: { kind, topic }, joints }` (ROS 2, above; `electron/robot/ros2.mjs`) as plain objects (`checkedRobotSpec`) → `{ ok: true }` or `{ ok: false, message }`. The G1 form becomes `{ family: 'unitree-g1', ids: [13…29], class: 'legged', emulated: true }` for everything after it, so intents carry its 17 writable joints, and the ROS 2 form becomes `{ family: 'ros2', ids: [1…n], class: 'arm', emulated: true, controller, joints }`; anything else (a `port`, `emulated` not exactly `true`, extra or inherited keys, bad ids, a second robot under a unit that's connected) is refused in plain words and starts nothing. A 33rd unit is refused as “Disconnect a robot first: a fleet runs at most 32.” `robot:command` (`robotCommand(cmd, unit?)`) forwards only the documented commands, rebuilt from their known fields (`checkedCommand`); an `intent` must carry one finite number or `null` per servo, and `assign_id` an integer id 1–253 and model 0–65535. `robot:policy` (`robotPolicy(refs, unit?)`) takes an array of at most 16 references, each exactly `{ kind: 'policy', id }` or exactly `{ kind: 'skill', hash }` as a plain object (`checkedPolicyRefs`, Policy below). `robot:calibration` (`robotCalibrate(joints, unit?)`, Feetech and Dynamixel only) takes an array of plain objects, each exactly `{ id, zero_counts, direction }`: ids from the connected robot, each at most once, `zero_counts` an integer 0–4095 and `direction` 1 or -1 (`checkedMounts`). It replaces those joints' zero and direction in the session's calibration, keeping names and ranges, writes `calibration.json` (a `.part` file renamed into place), emits `{event:'calibration', joints}` and sends `recheck`; the daemon re-reads it, and a robot running in Test stops, so the page enters Test again. Before Connect it answers “Connect an emulated robot first.”; any other ask, or a G1 or ROS 2 robot, gets “The robot only takes the documented commands.” `robot:disconnect` (`robotDisconnect(unit?)`) closes that unit's stdin; the daemon stops the robot and exits, and is killed if it hasn't after 3 s. `robot:state` (`robotState(unit?)`) returns the unit's connection, hello, latest status, mode and `calibration` (each id's `{ id, zero_counts, direction }`, or `null` when nothing is connected or the robot isn't Feetech or Dynamixel), plus `unit`, `version` (the resolved policy's skill hash or policy id, or null), `previous` (the version Roll Back returns to, or null) and `hasPrevious` (whether a rollback exists, including a return to no policy), so a reloaded page picks up where the main process is. `robot:units` (`robotUnits()`) returns that state for every connected unit, sorted by name. `robot:rollback` (`robotRollBack(unit)`) returns the unit to its previous policy (Policy, below). `robot:record` (`robotRecord(sample, unit?)`) takes exactly `{ scene }` (a safe scene id, a robot name up to 512 characters, a 64-hex model hash and one joint name up to 128 characters per connected id) or a plain object with only `input` (`{ id }` of up to 32 lowercase word characters and at most 512 finite numbers or nulls) and `twin` (one number or null per connected id), and feeds the open recording (Recording every session, below). Events reach the page on `robot:event` (`onRobotEvent`), each carrying its `unit`: every daemon line, plus `{event:'link', state:'connected'|'closed'|'lost'}`, for a Feetech or Dynamixel robot `{event:'calibration', joints}` right after `connected` and after every `robot:calibration`, `{event:'recorded', id, reason, manifest}` when a session closes, and `{event:'policy', unit, version, previous}` when a unit is pinned or rolled back.
- **Spawn:** `spawn` from the pipe's worker thread, with no shell, argv `--family <f> --ids <ids> --class <c> --emulated --artefacts <dir>`, then `--factory` for a factory bus and `--units <dir>/units.json` when the spec carries `units` (for the G1, `--family unitree-g1 --emulated --artefacts <dir>`; for ROS 2, `--family ros2 --controller <kind> --topic <topic> --joints <names> --emulated --artefacts <dir>`), never `--port` or `--interface`. Every unit but `robot` ends with `--seed <n>`, where n is the 32-bit FNV-1a hash of the unit's name (at least 2, `unitSeed` in `electron/robot/robotFleet.mjs`), so each emulated unit has its own hidden parameters and the same name gets the same ones every time. `robot` passes no seed and keeps the daemon's seed 1. The fleet chooses the seed and passes it to `daemonArgs` beside the checked spec, so the page never chooses one. The artefacts folder is a fresh temp folder per connection, removed when the daemon exits. For an emulated robot the app writes `calibration.json` itself, and keeps it for the session (`emulatedCalibration`: every id zeroed at 2048 counts, direction 1, ±2.8 rad, until `robot:calibration` rewrites it; the G1's joints named by their URDF names, a ROS 2 robot's by its joint names), so Set up → Test climbs with no hardware steps. A Feetech or Dynamixel spec, with or without `factory`, may also carry `units`, one entry per id: `null` (the protocol's own unit) or exactly the part's fit numbers (Part models, above; checked in `electron/robot/servoUnits.mjs` with the daemon's bounds and refused as “Give one servo model, or null, per servo ID.”, “A servo model takes only the numbers of its fit, nothing else.” or “A servo model has a number out of range.”). The checked spec keeps its own copy, and the app writes it to `units.json` beside `calibration.json` for that connection.
- **Policy** (`src/robot/robotPolicy.ts`, `electron/robot/robotPolicy.mjs`): the scene in front sends the robot its candidates, and sends again when they change: its policies that aren't stale (`Training.isStale`, §8d) and its ready skills (`skillRows`, §8i), newest first, at most 16 (`readyRobotPolicies`). The renderer sends only references; the main process takes the first that yields ONNX, so a ready skill that replays an animation or follows IK doesn't hide an older policy. A policy is `library/policies/<id>/policy.onnx`, the trainer's own copy (`Trainer.policyOnnx`, ids matching `policy-[a-z0-9-]+`). A skill whose controller is a policy is encoded from its `skill.json` (`getSkill`) by `policyOnnx` (`electron/robot/policyOnnx.mjs`), which builds the graph Forge's `onnx.rs` builds: input `obs`, the normalizer, MatMul and Add per layer with Elu (or Tanh) between, an optional Tanh squash, output `action` clipped to ±1. It refuses layers that don't line up or numbers that aren't finite. When no candidate yields ONNX (none trained, a policy trained before ONNX export, only skills that aren't policies), it writes none and the daemon keeps refusing with “Load a policy first.” With no unit, `robot:policy` sets the scene's candidates for every unit that isn't pinned and for every unit that connects later. With a unit it pins that connected unit to exactly one reference: the actual previously resolved reference goes on the unit's history, at most 32 deep, and the fleet emits `{ event: 'policy', unit, version, previous, hasPrevious }`. `robot:rollback` takes the newest entry off the history, places that exact reference (or removes the policy when it's null) and emits the same event. A unit with no history is refused as undocumented. Pins and rollbacks require available policy bytes and a successful atomic write before changing history or version. Failed reads or writes preserve the previous file and history. A restored reference stays pinned, so later scene candidates never replace it. `RobotLink` keeps the references, writes `policy.onnx` before the daemon starts, and while connected rewrites it (a `.part` file renamed into place, or removed) and sends `recheck`, so `PolicyPresent` turns on with no click and a new policy clears the evidence it voids (§8k, Mode ladder). Tests: `policyOnnx.test.mjs` decodes the graph and runs the Motor Kit's Walk through it against `act()`; the same file in ONNX Runtime matched `act()` within 3e-6. `robotLink.test.mjs` checks the bytes for a stored skill and a trained policy, skipping candidates with none, the swap and `recheck`, and ids that try to leave the library. `robotFleet.test.mjs` pins two skills on one unit, rolls back twice to the exact earlier references and checks the placed file's hash each time, while another unit keeps the scene's. `tests/policy_folder.rs` writes the file after connect and climbs.
- **Fleet** (`electron/robot/robotFleet.mjs`): `RobotFleet` runs several robots at once. It takes the options `RobotLink` takes and keeps a `Map` of named units, each its own `RobotLink` with its own daemon, pipe, pacer, artefacts folder, recorder, mode and seed, so a fault, exit or disconnect of one unit never touches another. A unit joins the map at Connect and leaves it when its link reports `closed` or `lost`. It holds at most 32 units (`MAX_UNITS`). Each unit keeps its policy pin and history (Policy, above), and the fleet tags every event with its unit. `robotFleet.test.mjs` drives fake daemons (`fleetWithFake` in `robotLinkFake.mjs`): three arms connect at once with distinct folders and seeds, a stall on one leaves the other two in Test with their intents arriving, intents never cross units, twelve units connect, Roll Back restores a unit's previous policy, the same names get the same seeds, and a 33rd unit, a bad name and a connected name are refused.

### Calibration (Stage 6)

The least-squares linear solver uses `utils/matrixScans.ts` to select pivots and accumulate back-substitution terms without copying matrix tails. It preserves the first row on equal pivot magnitudes, the arithmetic order and the `1e-300` singular threshold. `leastSquares.test.ts` checks a row-swapped dense system, unchanged inputs and singular refusal with no tail copies.

`src/reality/` fits a servo's model from logs and feeds it to the sim. It's judged by `s6-hidden-twin` against a hidden twin (§0k). No real servo has been logged with it.

- **Bench and logs:** a servo turning a pendulum (`benchInput`: the catalog servo and a 20 mm bob of the payload's mass at its arm), logged at 100 Hz with the servo's part id and variant, goal, position, load, volts, temperature and payload (`ServoLog` in `types.ts`).
- **Which servo:** each joint is fitted against its own catalog servo and variant (`jointServo` in `servoPart.ts`: the first actuator part with a catalog actuator spec), never a family. Its starting model is `presetServo` (`servoEstimate.ts`): the variant's `fit` when the catalog has one (STS3215 C001, XL330), else `estimatedFit`, the measured fit of the same bus's servo (XL330 for Dynamixel, STS3215 C001 for the rest) scaled to the part's stall torque, rpm and volts, so its force limit, stiffness and no-load speed match the catalog (an STS3215 C046 gets 1.412/1.912 of the C001's force). The preset the verdict and the grey replay compare against is the sim's own model of the joint, the MJCF built with no `servoFits`, the path `mjcfServo.ts` takes: the catalog fit where there is one, else the MJCF writer's estimated actuator. Old records name a `family` (`sts3215`, `xl330`) instead of a `servo`; `servoPartOf` reads them as that family's servo (`FAMILY_SERVOS`), so they still apply and roll back, and `calibrateServo` takes a request named by family the same way (the hidden twin sends one).
- **Forward model:** the MJCF and `SimEngine` the sim runs. `replayLog` holds the log's first position, then plays its goals. `MjcfInput.servoFits` gives a joint a fitted `ServoFit` and volts in place of the catalog's (`mjcfServo.ts`).
- **What it fits:** multipliers on the BAM M6 terms the MuJoCo model carries (`servoParams.ts`): position gain (`errorGain`), delay, damping (back-EMF and viscous together), armature, base friction, load friction (`loadExternal`, times the bench's holding torque) and torque limit (kt / R). Each stays within 0.25x to 4x, delay up to 8x. `scaledFit` writes them back into a `ServoFit`, so a calibration has the catalog's shape. Backlash, series compliance, stick-slip, supply sag, thermal drift and encoder bias aren't in the model; the fit absorbs what it can of them into these terms.
- **How it fits:** Levenberg–Marquardt with forward-difference Jacobians on MuJoCo replays (`leastSquares.ts`), a weak prior toward the preset, and a coarse delay grid first, because the cost has local minima in delay. It's TypeScript rather than `forge-id`: forge-id has no delay or torque-limit parameter, and the gate calls the calibrator in-process.
- **Held-out honesty:** the first 0.3 s of each log is skipped, because the servo may still be moving from the log before and the log doesn't record its speed. The rest is split in time: the first half fits, the second half checks.
- **Update ladder** (`ladder.ts`): `response` (gain, delay, damping, armature), then `friction-force` (adds base friction, load friction and torque limit). Each rung is fit on the first halves and scored on the second. Climbing stops at the first rung that predicts the second halves at least 25% better than the preset with no log worse; if none does, the best rung that's at least 5% better is kept. The chosen rung is then refit on whole logs.
- **Verdicts** (`calibrateServo`). Only `measured` changes the model; the other two return the preset fit.
  - `cant-tell`: fewer than two logs, a log from another servo or with missing samples, logs where the preset explains under half the motion (positions that don't follow the goals, as in shuffled logs), or an update that still leaves over 20% of the checked motion unexplained.
  - `consistent`: the preset predicts every log within one encoder count, or no rung is 5% better while the preset explains at least 80% of the motion.
  - `measured`: a rung passed or helped.
- **Versions and rollback** (`history.ts`): `project.servoCalibrations` keeps a `CalibrationHistory` per joint. Every calibration is recorded with the next version number, only a `measured` one becomes active, so a failed update keeps the last good one, and `rollBack` steps back to the previous measured version, then to the preset. A version may carry a `mount` (`{ zeroCounts, direction }`, the joint's zero and direction): `recordMount` records one found by the camera on top of the active version's fit (or the preset's, with rung `preset`), and `recordCalibration` carries the active mount into every later fit, so rolling back steps through both and past the first one returns the defaults (`activeMount`, `activeMounts`). Those belong to the scene's default unit (`DEFAULT_UNIT`). Every other unit of a fleet keeps its own histories in `project.unitCalibrations[unit]`, read with `unitHistories(project, unit)`, and `withCalibration`, `withRollBack` and `withMount` (`projectCalibrations.ts`) take the unit last, so recording or rolling back one unit leaves the others alone.
- **Into the sim:** `calibratedInput` applies each joint's active calibration when its servo and variant are the joint's own and its rung isn't `preset` (a version that only carries a mount changes no fit; `calibrationApplies` in `measuredJoints.ts`, kept apart from `bench.ts` so Checks don't load the bench fixtures). `useSimulation`'s `buildModel` uses it, so the Simulate tab, Cases, Skills and training run on calibrated servos. A new active calibration changes the robot's model fingerprint, so every policy trained before it shows Out of date in its row in the Simulate tab's Train section until it's retrained (right-click ▸ Retrain), and rolling back to the calibration it trained on makes it fresh again (§8d, Stale models).
- **Calibrate in Operate** (`RobotCalibration`, Calibrate Servos, also in ⌘K): offered only for Feetech and Dynamixel servos (`servoFamily`), only in Test with motors running, because Test is the one rung where the app's intents move motors (Rehearse writes nothing, First run and up follow the policy slot), and only in the scene the robot was connected from (`connectedFrom`: its movable joint ids match the ones recorded at Connect), so fits never land in another scene's project. `playBench` (`src/robot/benchRun.ts`) streams intents every 25 ms through the normal path (pacer, guard, motor lock, fault matrix all apply) and owns them while it runs, so `offerSimTargets` stays out. Every joint moves at once, offset from where it stood (a row's Calibrate, or Checks' Servo models Fix, passes `playBench` those joints' indexes, so only they move, the rest hold their start, and only their samples are logged): `benchOffset` (`benchSequence.ts`) is 9 s of ramps at 0.12 rad/s to ±0.25 rad with 0.6 s holds, then 9 s of a 0.15 rad, 0.12 Hz sine. It's that slow because the guard and the servo's speed cap clip anything faster, and a log whose goals aren't what the servo was given reads Can't tell. Status events (every 100 ms) are timed by `at_us`, put on the page's clock through the one heard soonest after its stamp, so a status that arrives late (a stalled page, a busy relay) keeps its place; the bench records until a status passes its 18 s (or 1 s after, if none does). They become two logs per joint (`benchLogs`), positions relative to the start so the bench's gravity doesn't bend them, with `EMULATED_LOAD` (0.2 kg at 0.1 m, the emulator's 0.002 kg·m²) as the payload and each joint's servo from the scene (`benchServo`: its catalog servo, or for a joint with none the protocol's stand-in, STS3215 C001 on Feetech and XL330 on Dynamixel). A joint whose catalog servo is on a bus the daemon can't speak (a PWM servo like the DS3218, a Hiwonder bus servo, a DC gearmotor, a CAN or RS485 actuator) is skipped: it holds its start, records nothing, and its row reads No reply in place of the emulator's reading (`offTheBus`, applied in `jointRows`). Fits run in `calibrate.worker.ts` one joint at a time and each is recorded through `history.ts` (`withCalibration`) as it lands. If the robot leaves Test or faults, nothing is recorded and the daemon's message says why. Before the bench, the zero and direction capture below runs on the joints that still have the defaults.
- **Zero and direction from a camera** (`src/robot/mountCapture.ts`, `src/reality/mountSearch.ts`): the first phase of Calibrate Servos (`data-calibrating="capturing"`). It first sends the connection any zero the project holds that `calibration.json` doesn't (a reconnected robot), then takes the joints being calibrated whose project zero and direction are still the defaults (2048, +1).
  - **Capture:** each in turn steps +0.1 rad at 0.5 s, −0.1 rad at 1.75 s and back at 3.5 s (`WIGGLE`, a 4 s `BenchPlan` through `playBench` with that joint as its subset, so the pacer, guard and fault matrix apply). The first status heard in each of three windows just before a step (0.3–0.5 s, 1.45–1.75 s, 3.2–3.5 s, on the daemon's clock) gives one frame: every joint's counts and a silhouette from the camera source (Cameras, §8l). A window with no status, or a source with no frame, ends Calibrate Servos with nothing recorded.
  - **Search** (`findMounts`, in `calibrate.worker.ts`): joints in depth order, root first. For each, every candidate (direction ±1, zero offsets −20° to +20° in 0.5° steps around the current zero, then 0.1° steps within 0.5° of each direction's best) poses the robot at each frame's counts, with the joints above at what they've just been given, and draws only the joint's own link (`rig.ownerOf`). Its score is the share of those pixels inside the frame's silhouette, summed over all frames. Scoring only the joint's own link keeps a wrong joint below from pulling it off; scoring the whole silhouette joint by joint stalled in local optima on the six-joint fixture. The best candidate must beat the best one with the other direction or a zero more than 3° away by 0.02 (`MOUNT_SEARCH.margin`), or the joint reads `cant-tell` and keeps its zero. A winner within 1° of the current zero with the same direction reads `consistent`; anything else is `measured`. Same frames, same answer. The six-joint fixture (18 frames, 184 candidates per joint) takes about 0.35 s in Node on a MacBook Pro under load.
  - **Write:** `measured` and `cant-tell` joints are recorded (`withMount`); `consistent` ones record nothing, so a robot with nothing planted changes nothing. When a zero changes, `remount` sends every connected id's zero and direction through `robot:calibration` (`setRobotMounts`), waits for the daemon to stop on the `recheck` (a calibration change clears Tested, Mode ladder), enters Test again and waits for the motors to run, so the bench runs on the new zero. Each row shows the newest verdict, so the bench's verdict replaces the capture's in the row; the menu keeps both versions.
  - **Readings:** the main process sends a `calibration` event with every id's zero and direction at Connect and after each rewrite (`robotState.calibration`, kept by `robotStore` and returned by `robotState()` for a reloaded page). The page converts every status count to radians through it (`radiansFromCounts(counts, mount)`, `statusRadians`, `measuredRadians`): the rows, gaps, ghost, run buffer, intent mirror and bench. `useRobotMounts` (`src/robot/robotMounts.ts`, through `useRobotSync`) sends the project's active zeros whenever they differ from the connection's and no calibration runs, so Connect and Roll Back reach `calibration.json` too.
  - **Unit tests** (`mountSearch.test.ts`, fixtures built in code in `mountSearch.fixtures.ts`): a reversed elbow on a two-joint arm, a 12° horn offset within 2°, both on one joint, three planted of six with the rest unchanged and the search under 10 s, a biped's reversed right knee beside its left, a joint behind a shield and a cylinder wrist roll reading Can't tell, the camera rolled 30°, a canary with nothing planted, and the same result twice. `history.test.ts` checks a mount version under later fits and rollback to the defaults; `jointMap.test.ts` checks `joint_map.json` carries the found zero and drops it on rollback.
- **Rows:** calibration lives in the joint's row under Emulated servos (`JointRow`; `[data-calibration-joint]` beside `[data-robot-joint]` on the same element, `data-verdict` from the newest version, `data-version` the active one or 0): under the name, the newest verdict when it isn't Measured (Consistent with preset, Can’t tell) and the active version (`v2`), or Preset when none is active and the newest isn't Consistent. Calibrate Servos sits above the rows. A right-click on the row (`useJointRowMenu`) opens a menu that lists the measured versions (`v1`, `v2`…, the drawn one ticked) and Roll Back, after a confirmation (`rollBack`).
- **Which joints the sim measures** (`measuredJoints`, `src/reality/measuredJoints.ts`): a joint is Measured when its active calibration is `measured` and `calibrationApplies` to its servo, the same rule `calibratedInput` follows, so it says exactly which joints the sim runs on a fit. A preset servo with a catalog fit (STS3215 C001, XL330) isn't Measured: its model came from another unit. It's never read from the model's `dynamics`, which marks every catalog fit as measured. One state, shown wherever joints appear: a `Badge` reading Measured (the verdict word, accent; `MeasuredBadge` in `components/verdicts.tsx`, which Pose and Operate share) beside the joint's name in the Pose tab's rows (`pose/JointRow.tsx`) and in Operate's rows (`data-measured` on the row; the row drops its Measured verdict word only where the badge shows, so a measured fit for another servo still reads Measured beside its version), and the Servo models row in Checks (§8b). Every reader derives it from `project.servoCalibrations` in render, so a calibration or a rollback flips all three at once; the readiness fingerprint carries each joint's active version (`activeVersions`), so Checks run again.
- **Replay** (`JointReplayPlot`, `src/reality/jointReplay.ts`): clicking a joint's row opens its replay under it, one `TracePlot` (§14) on one time axis: the logged position (`trace-logged`, light), the preset's replay (`trace-preset`, grey) and the calibration's replay (`trace-calibration`, the accent), then the median absolute error of the two replays in degrees, grey and accent, with no other text. Choosing a version from the menu redraws the accent trace against it, so a person sees what a rollback would change before doing it; with no measured version there are two traces and one figure. Replays go through `predictLog`, the path the fitter scores, over the newest bench run's logs, skipping the settle window. They run in `calibrate.worker.ts` (`replay`) and are cached by log and version (`replayClient.ts`; version 0 is the preset). The logs live in memory only (`benchLogStore.ts`, `logId` on each recorded calibration): after a reload the rows stay, and replays come back with the next Calibrate Servos. The agent's `operate` reply ends with the same errors per joint (`calibrationErrorsText`), and `__studio.calibrationReplay(jointId)` returns them for tests.
- **Measured through the daemon** (3 emulated STS3215 on the release daemon, 90 samples per log at 97.6 ms): all three Measured at the `friction-force` rung, 7 to 10% better than the preset on the check halves, about 2 s of fitting each. ### Body calibration

Fit Body (`BodyCalibration`, `src/components/operate/BodyCalibration.tsx`, and ⌘K) fits the body from the selected unit's recorded intents and measured joint positions. It sends no motor commands. The fit button shows the shared spinner while the worker runs. Real motors stay locked under the same runtime gate as every other Operate action.

- **Recording:** `robot:read-run` (`robotReadRun(unit?)` in preload and `platformBridge`) flushes the selected unit's recorder and reads the same `session.jsonl`. It uses the active session, or the latest kept ended session after disconnect, with at most the latest 20 s, 1,024 statuses and 1,024 intents. The last accepted intent at or before the first included status anchors replay. The disk read is capped at 1 MiB and drops partial boundary lines. It retains no second sample buffer. Unit metadata remains available after disconnect for up to 32 unit names. The HTTP bridge and web demo return null because neither owns the desktop robot fleet.
- **Fit:** `fitBodyFor` (`src/workspace/bodyActions.ts`) builds without an existing body fit and uses the selected unit's active servo calibrations. `bodyClient.ts` sends that model and the run to `body.worker.ts`, where `fitBody.ts` and `bodyReplay.ts` replay the run on top of the active servo fits. The body rung fits per-link mass scales, terminal payload in kilograms and floor friction for a floating robot. A fixed arm's base mass is left alone. Payload is placed at the terminal link's farthest transformed bounding corner from its pivot, through the same body transform the MJCF writer uses. The run window drops statuses before the first accepted intent, so a session may start in Look before any command. Only the selected robot's moving joints contribute residuals, using a range over one encoder count for a revolute joint or 10 µm for a sliding joint. Stationary joints never lower the reported error. The first half supplies the fit, and the second half checks its median absolute joint-position error against the unfitted body. The fit must lower that error by at least 25% (`BODY_RUNG.passGain` in `src/reality/ladder.ts`) and pass the motion plausibility check. Invalid, still or shuffled recordings read Can't tell. Completion compares the captured parts, joints, selected unit's servo history, body history and model fingerprint with a fresh build. A change while the worker runs rejects the result before recording it.
- **Evidence units:** `BodyCalibration.evidence.units` (`bodyTypes.ts`) records `rad` for angular-only scoring, `m` for linear-only scoring and `mixed` when both contribute. The legacy `presetErrorRad` and `fittedErrorRad` field names hold the recorded SI values. Missing units in existing records mean radians. Operate and the tool reply show degrees for angular errors, millimetres for linear errors and only the dimensionless replay improvement for mixed scoring.
- **History:** `BodyHistory` (`bodyTypes.ts`) stores every attempt under `project.bodyCalibrations[robot]`. `recordBodyCalibration`, `activeBodyCalibration` and `rollBackBody` (`history.ts`) share the version rules. A measured body fit becomes the active version for its robot. An attempt that reads Can't tell keeps the active model. Roll Back asks for confirmation, then restores the previous measured version or the unfitted body. Versions stay in the scene project. Operate shows completed fit evidence inline without a duplicate toast. A result completed out of view still toasts, using current scene-tab and sidebar visibility. Refusals and worker errors still toast. `recordedAt` orders active floor estimates across robots, and optional `bodyKeys` maps generated body names back to the raw joint or root id when an unrelated robot changes body numbering.
- **Readers:** simulation and training apply the active body fit after the active servo fits. Its body-model fingerprint makes a policy trained on the previous model Out of date. Rollback restores the prior fingerprint. Weight and Servo torque use the adjusted mass and center of mass. Stored walk and fall results are invalidated so Peak torque is measured again. The newest active body version supplies the world floor friction once, and every robot's fingerprint includes that effective floor.

- **Tests:** `bodyFit.test.ts` recovers a planted 150 g wrist payload within 20% and a 1.3× forearm mass within 15%, with identical results on repeated input and at least the 25% held-out gain. Shuffled, still and mistimed logs read Can't tell. A supported three-legged fixture records over 20 frames of sliding contact while holding level, then recovers a planted 0.55 floor-friction scale within 20% with the same gain requirement.

### Servo populations

One model per servo from many measured units (`src/reality/population.ts`), so a joint nobody calibrated can run on what units of its servo are like, and training can randomize each servo by how units differ. Judged by `s6-servo-population` (§0k), which fits its populations from fresh hidden-twin units each run.

- **Fit:** `fitPopulation` takes the `measured` calibrations of one servo part, variant and voltage (`populationKey`, the names `servoPart.ts` uses; fewer than 8 give none). Each unit is its log multipliers on the seven `SERVO_PARAMS` (a term its rung didn't fit is 0). The population is the median per term, and a covariance about it: units more than 3.5 MAD-sigmas off on any term are dropped (when 8 or more remain), then the sample covariance is widened by (n+1)/n × (n−1)/(n−p−2), p the terms any unit fitted, the spread a new unit is drawn from rather than the spread of these few, plus 0.01² on the diagonal so an unfitted term stays a little open. Correlations are kept: units with more delay keep their gain. `inBand` is the 90% band, Mahalanobis distance within χ²₀.₉ of 7 terms.
- **None ships yet.** The app passes no populations, so every uncalibrated joint stays on the catalog preset and no environment carries servo spreads. A population ships only once it is fitted from real measured units. Never derive one from `verify/twin`: the hidden twin is gate-side (§0k), and its units sit outside the model class on purpose, so their median delay reads about 2.5× the catalog's.
- **Into the sim:** `calibratedInput(input, calibrations, populations)` runs each revolute joint whose servo has a population, and no Measured calibration of its own, on the population's median (`populationFit`), and gives it the servo's spread (`MjcfInput.servoSpreads`, carried to `SimModel.servoSpreads`). A joint's own Measured calibration always wins, and a joint whose latest bench read Consistent with preset for the same servo (`presetConfirmed`, `measuredJoints.ts`) stays on the catalog preset with no spread: the bench just matched that model. Callers pass `simCalibrations(histories)` (`history.ts`): each joint's active version, or its latest when none is active and that one read Consistent, so a rolled-back Measured version never comes back. `useSimulation` and the robot package pass no populations yet; `s6-servo-population` and its canaries pass the population they fit, and `s6-hidden-twin` passes none, so its preset stays the catalog's. The actuator's `nsample` covers the slowest delay the spread can draw (`historyS`). Policies trained on the preset read Out of date once the median runs, as for a new calibration.
- **Next:** sharing measured calibrations, opt in, through the Hub so populations come from real units, and each unit's percentile in its population shown in Calibrate.
