# Skills

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 8i. Skills

Train any robot to do anything you ask. The pipeline is Intent Compiler, TaskContract, Feasibility Gate, Method Router, Solver Race, Arena, SkillCard. The core lives in `src/skills/` and `forge/crates/contract`; the gate is `s3-contract` (§0k).

- **The contract judges, the reward only teaches.** Reward authors can't edit a contract, so a hacked reward can't fake success.
- **A Skill is bound to what it was proved on:** contract hash, compiled-physics hash, actuator hash, observation and action schema, and Arena evidence.
- **Moving a Skill to another design warm-starts training and never carries "verified".**

### Task contract (`forge/crates/contract`, `src/skills/contract.ts`)

One Rust crate, built native (Forge) and to WASM (the app), so both judge with the same code. `evaluateContract(contract, trace)` resolves to `{ passed, margin, worstAt, failed }` and rejects (throws) on anything it refuses; `contractSignals(contract)` checks a contract without a trace and lists the signals it reads.

- **Shape:** `{ version: 1, success: Formula, failures: [{ label, formula }] }`. Formula: `all`, `any`, `always { window, state }`, `eventually { window, state }`, `hold_for { seconds, state, within }`, `sequence`. State: `all`, `any`, `not`, `atom { expr, cmp, value, scale }`. Expr: `signal`, `abs`, `delta`, `dist [[a,b,c],[d,e,f]]`, `angle [[a,b,c],[d,e,f]]` (each name is a signal). Window: `'whole'`, `{ from, to }` or `{ last }`, in seconds. Every object has exactly its fields; unknown or extra keys are refused.
- **Trace:** `{ dt, signals: { name: number[] } }`, every signal the same length, at least two samples. Sample `i` is at `i × dt`. `null` (what `JSON.stringify` writes for NaN and ±Infinity) reads as NaN.
- **Margins:** an atom is `(x − value) / scale`, negated for `<` and `<=` (strict and non-strict give the same number). `all` and `always` take the minimum, `any` and `eventually` the maximum, `hold_for` the best placement's minimum over the dwell (`ceil(seconds / dt)` samples, sliding minimum), and `sequence` the minimum over its steps. A step of a sequence starts at the tick where the previous step first held: `eventually` at its first positive tick, `always` at its window end, `hold_for` at the end of its first full dwell, `all` at the latest of its parts, `any` at the earliest. A step that never holds ends the sequence there.
- **`delta` is the change since the first sample** (`x[t] − x[0]`), not per tick, so it means the same at any timestep (Arena runs half the timestep). `angle` is in radians, from a deterministic atan, so native and WASM agree to the bit; a zero vector has no angle (NaN).
- **Pass:** `passed` is a success margin above 0 and no failure fired; a failure fires when its own margin is above 0. `margin` and `worstAt` are the success formula's (the tick that set it). Exactly 0 never passes.
- **Fails closed.** `not` is pushed down to the atoms (De Morgan), so a NaN or overflowed value is always the adverse value: −∞ in the success formula, +∞ in a failure formula (a NaN can never pass a success, and always fires a failure). An empty window, or one shorter than a dwell, is adverse the same way.
- **Refused, never passed:** unknown signals; more than 64 levels of nesting or 4096 nodes (formula, state and expression nodes together); JSON nested over 256; any parameter that isn't a finite number (scale above 0, `hold_for` seconds above 0, windows that start at or after 0 and end after they start, `last` at or above 0); empty `all`, `any` or `sequence`; another version; a success that looks only at the final state (`{ last: 0 }`, statically, and on each trace any window that covers only the last sample, through `all` and `sequence` when every part does, and `any` when one does). Failures may look only at the end.
- **Cost is linear** in trace length per node: each temporal node evaluates its state series once, and `hold_for` uses a monotonic deque.
- **The WASM:** plain `extern "C"` exports (`contract_alloc`, `contract_free`, `contract_evaluate`, `contract_check`), JSON in and out over linear memory, no wasm-bindgen; the reply's pointer and length come back packed in one `u64`. `contract.ts` reads the file with `fs` in Node and `fetch` in the browser, and drops the instance after a trap. About 105 KB, no dependencies.
- **`src/skills/contract.wasm` is a committed output** (§0g). `npm run build:contract` (`tools/build-contract.mjs`) runs `rustc` directly on `src/lib.rs` from the crate's `src/` folder (relative paths only, `--remap-path-prefix`, `opt-level=s`, fat LTO, one codegen unit, `panic=abort`, stripped), so the bytes match on any checkout path. Rebuild and commit it with every change to the crate; the gate rebuilds it and compares hashes, so a different `rustc` than the one that built it (1.99.1 today) fails the gate until it's rebuilt.
- **Fuzz parity:** `cargo run --release -p contract --bin contract-fuzz -- <n> [seed]` prints n accepted random contracts and traces with the native result; the gate checks WASM against them. Non-finite margins print as `±1e999`, which `JSON.parse` reads as ±Infinity.
- **The canary** `canary_planted_false_pass_fails` (`tests/canary.rs`) runs the false-pass check against an evaluator that passes everything. Run by its exact name, it asserts the check let that through, so it fails while the check works and the gate sees the canary fire. In a plain `cargo test` it asserts the opposite and passes. Rust in the crate keeps §0's spirit: no comments, small functions, `cargo clippy -- -D warnings` (also with `--target wasm32-unknown-unknown`), `cargo fmt`.

### Artifacts (`artifacts.ts`, `bundle.ts`)

- **Hashes over `SimModel`** (`modelHashes`): visual elements and attributes (`light`, `camera`, `visual`, `rgba`, `material`, `texture`, `group`) are stripped first. **Topology** is the body tree, joint names, types and axes, actuator kinds and robots. **Physics** is the rest of the MJCF (masses, sizes, hulls, ranges, contact, timestep) plus the start pose. **Actuators** is the `<actuator>` block plus each joint's effort and drive. All carry `SIM_MODEL_VERSION`.
- **`skillFreshness(skill, current)`:** another design, topology, observation or action schema → `needs-training`; no evidence, or a contract, physics or actuator hash that moved → `rerun-arena`; evidence that failed → `needs-training`; otherwise `fresh`. A colour or name change leaves every hash alone.
- **Moving a skill:** `warmStart(skill, target)` gives a training seed (the skill's hash and controller, bound to the target). A skill trained from it has `warmStartFrom` set and no evidence until Arena runs on the new design; the source's evidence never moves.
- **Storage:** content-addressed, `library/skills/<sha256 of the canonical skill JSON>/skill.json` (`skillFolder` refuses anything but a hash). Rerunning Arena makes a new skill, so a folder never changes.
- **`.basecase` files** carry skills as an optional `scene.skills` list, with the file `VERSION` unchanged: older builds ignore the field, and `readSkillBundle` drops entries that don't parse.

### Environment interface (`environment.ts`)

One task description that lowers to WASM now and to native, SIMD and GPU later, so it holds only data: observation terms (`policyObservation(joints)` is exactly today's policy contract), action spec, reset distribution, randomization ranges, a reward reference (contract robustness or a RewardLang hash) and the contract, plus named signal sources the contract reads (time, joint position, velocity and effort, part position, base height, tilt and forward travel, contact). `validateEnvironment(env, model)` returns plain problems; an empty list means valid.

### Arena (`arena.ts`)

The independent verifier, on the WASM `SimEngine`. `runArena({ mj, model, contract, controller, environment })` refuses a contract that differs from the environment's, then runs three variants of 32 tries each: held-out randomized starts and physics, half the timestep, and random servo delays. Evidence gives passes per variant, a one-sided 95% Clopper-Pearson lower bound, the conditions in plain words. It passes when every variant's lower bound is at least 0.75 (29 of 32).

- **Agents can't change it.** `ARENA` is frozen; `runArena` takes no counts, bars or ranges. Randomization is the environment's ranges widened to Arena's floor (friction ×0.8–1.2, mass ×0.9–1.1, strength ×0.9–1, start joints ±1°, delays to 40 ms in the delay runs), so an environment can't make Arena easier.
- **Sealed instances:** each try's seed is the SHA-256 of a fresh random 32-byte salt, the variant, the try and the environment hash. Evidence holds counts and the salt's hash only, never seeds or drawn values, so feedback can't be fitted to the instances.
- **Delay** wraps `mj_step` (the engine is unchanged), **divergence** turns off MuJoCo's auto-reset and fails the try on a bad-state warning, and a NaN trace fails the contract.

### Method Router (`router.ts`)

`routeTask(analysis)` is pure and walks the plan's rungs in order: unverifiable, IK or motion plan, tracking, Routine, LQR or MPC (12 state values or fewer, no rich contact), tracking RL with a reset curriculum, reward search (6 candidates at 5M steps, 2 at 25M, 1 at 100M, up to 3 rounds, warm-started after the first), ask for a demo, then not found with design relaxations. It returns the method, the rung and the reason.

### Feasibility, Tier 1 (`feasibility.ts`)

`checkFeasibility(mj, model, task)` runs only checks that a model can settle, each marked `exact`, `estimate` or `sampled`, with plain messages:

- **Holding torque** from `mj_inverse` (constraints off, zero velocity and acceleration) plus foot and payload loads by virtual work. Stand checks the start pose and a crouch 15% lower (feet held by IK), with the weight shared over the feet by a minimum-norm force and moment balance. A joint fails above 0.60 of its torque, the Stance limit in the Build checks (§8b).
- **Support polygon:** the center of mass over the hull of the feet's soles, margin in mm.
- **Workspace:** fails exactly past the summed link lengths, else samples 2048 poses and refines the best six with damped least squares.
- **Gripper opening:** prismatic travel, or `2 × finger × sin(span / 2)` for hinged fingers, against the object plus 2 mm.
- **Relaxation ladder:** servos ×2, ranges +20° at each end, links +20%, in that order; the first that makes every check pass is reported, otherwise it says none does. `must-fail-weak-quad` comes back as too weak to stand, with servos ×2 as the fix.

### Motor Kit (`motorKit.ts`, `kit*.ts`)

Every legged robot gets Stand, Velocity tracking, Get up and Settle to neutral, trained through Forge and proved in Arena. Gate `s3a-motor-kit` (§0k) judges them again on its own contracts. Nothing here judges itself: the gate reruns `runArena` and `evaluateContract` on what comes back.

- **Training goes through the runner it's given.** `ForgeJob`, `ForgeOutcome`, `ForgeRunner` and `SkillSave` (`forgeRunner.ts`, re-exported from `motorKit.ts`): in the app the runner is `electron/trainer.mjs`, in the gate one that spawns `forge-train --job <dir>`. A skill's policy is the `policy.json` a runner returned, weights unchanged, and `cost.steps` adds up every run's `done.steps`.
- **`kitEnvironment(model, entry)` is pure:** the environment and contract the Kit trains and Arena judges for `model.robots[0]`, from the model alone (`kitModel.ts` reads the start height from the root body's `pos` in the MJCF, as the engine places it). A colour edit changes nothing; a mass edit moves the physics hash (Rerun Arena); a joint edit moves topology (Needs Training). Its bars are the gate's, published below, and its reward is the entry's RewardLang program (`kitRewards.ts`), referenced by hash.
- **Entries** (`kitEntries`): floating robots whose morphology is legged. Pose tracking is in the type but not trained yet; `trainKitEntry` says so. The top speed is 0.2 m/s on four or more feet and 0.15 m/s on two (`kitTopSpeed`, counted from leaf bodies).
- **`trainKitEntry({ mj, design, model, entry, forge, save, signal? })`:** Tier 1 feasibility first (the stand checks; the weak quad is refused with servos ×2 and spends nothing), then the tries in `kitSchedule`, run by `firstPassingTry` (`kitTries.ts`). A try is one or more Forge stages, each with its minutes and servo delays; a later stage warm-starts from the one before it (`warmStart`, §8g, the folder `runFolder` reads from the run's `done` event), and only a try's last policy goes to Arena on the Kit environment. A failed try's Arena passes, summed over every acceptance run, rank it, and the next try continues from the best so far instead of starting over (a new seed each). On four or more feet every try is one stage at 0 to 20 ms: Velocity tracking 12 then 12 minutes, Stand 2 then 4, Get up 2, 6 and 8, Settle 2 then 4. Bipeds get a delay curriculum, below. A Velocity tracking policy must first pass Arena at half its top speed and standing still (`kitAcceptance.ts`, the same bars), because one seed walked at the top speed and drifted 0.1 m standing still under 40 ms delays. The first policy that passes is saved with its evidence and `origin = { method: 'motor-kit', cost }`; when none does, it comes back refused with no relaxation. `kitStatus({ design, model, skills })` gives one row per entry with the best freshness among skills named `kitSkillName(entry)`, or `missing`.
- **Jobs** (`kitJob.ts`): the scene's MJCF and the usual `job.json` fields, plus the entry's reward and Forge's training conditions (§8g): action delays of 0 or 1 control step, encoder offsets ±0.015 rad, an IMU mount bias up to 0.03 rad, and an actor blind to linear velocity (the critic keeps it). Kit policies act at `KIT_ACTION_SCALE` 0.5 rad around the neutral pose, recorded in the policy and the environment's action spec. Measured on quad-servo: at 0.25 rad, with resampled commands, it never left the spot in 8.6M steps; at 0.5 it walked all three judged speeds after 14.6M. Delays up to 2 steps with offsets stopped it learning to walk in the same time, so the Kit trains 0 to 20 ms and relies on Arena's 40 ms runs to show it holds. Bipeds sit on the edge of that trade: trained on 0 to 20 ms, biped Stand and Velocity tracking have fallen in 4 of 32 of Arena's delay runs (28 against a bar of 29); trained on 0 to 40 ms from the start, two of two 22-minute runs held every delay run but neither steered (one circled, one ignored the turn command). So bipeds train in two stages: Velocity tracking learns to steer on 0 to 20 ms for 20 minutes, then warm-starts onto 0 to 40 ms for 12 with command resampling still on, and a second try continues from the best for 8 more (40 minutes of training, as before); Stand trains 3 minutes on 0 to 20 ms, then 5 on 0 to 60 ms, and a second try 5 more (13 minutes, 2 more than before, inside its 15-minute budget, because Arena's noise between two 32-run samples is about 3 runs: one Stand policy passed 30 of 32 delay runs in the Kit's Arena and 28 in the gate's, and the 0 to 60 ms stage scored 30 and 32 where 0 to 40 ms scored 29 and 27). Every warm-started stage sends `logStdMin: -2.5`: without it, both 12-minute continuations onto 0 to 40 ms collapsed after about 8,000 iterations (§8g). In the `s3a-motor-kit` run of 8 November both biped entries passed on their first try, the gate's own contracts and the steering timeline included: Stand in 486 s (6.5M steps at 0 to 20 ms, then 10.7M at 0 to 60 ms; Kit Arena 31, 32 and 31 of 32), Velocity tracking in 1,941 s of its 45 minutes (42.3M steps, then 25.4M; 31, 31 and 32 of 32). The quad's Velocity tracking needed its second try, which continued from the first (24.7M + 24.7M steps, 1,497 s of 30 minutes). In the rerun that recorded the pass, biped Velocity tracking needed its second try too: 42.4M and 25.5M steps, then 17.0M more from the best of them at 0 to 40 ms, 2,443 s of its 2,700 (Arena 30, 31 and 29 of 32), so the 45-minute budget has about 4 minutes to spare when every try runs. Stand and Settle start ±0.3 rad off neutral (Settle's reward pulls every joint home with wide and narrow kernels plus a quadratic, because a narrow kernel alone is flat 17° out and the policy settled into a crouch); Velocity tracking (rewarded on speed error scaled to the top speed, a linear penalty on speed error, and on four or more feet a linear penalty on turn-rate error, so a robot that veers loses reward as it loses travel; and, with a still command, harder penalties on joint motion, action changes and drift, drift clipped so a fall can't swamp the return. Bipeds keep the plain reward with a stronger turn-rate kernel (weight 2 against 0.8, width 0.05 against 0.1): they sway in yaw as they step, and with the turn-rate penalty or the stillness terms four biped runs stood still or circled one way. With the 0.8 kernel, four of four 41M-step first stages failed the steering test (two circled, one turned the wrong way, one turned only left), with the input mask (§8g) and with the old weight projection alike on the same seed; at weight 2 and width 0.05 the same seed walked 0.50 m in the steering test's forward segment and turned +1.98 and −2.01 rad, where weight 2 at width 0.1 turned but walked 0.29 m) resamples `[forward, left, turn]` every 2 to 4 s from `[0, 1.25 × top]`, `±0.25 × top` and ±0.6 rad/s, with a fifth of the commands still; Get up starts from the pose limp collapses to out of a 40° crouch (`kitStart.ts`, the gate's own procedure), with no reset on a fall and the standing height as `standHeight`.
- **Velocity tracking is commandable:** the policy reads `PolicySpec.command` as `[forward m/s, left m/s, counter-clockwise rad/s]`, and `SimEngine.command({ v })` on a policy controller replaces it from the next control tick (`setController` and `reset` start from the spec's). Drive goes through this for any legged robot with a ready Walk, bipeds included (`policyCommand` scales the keys to the trained ranges: forward 0 to the top speed, strafe ±a quarter of it, turn ±0.6 rad/s). No external force moves the robot.

### Solver race (`race.ts`, `race*.ts`)

- **Goals** are `reach` (a part through waypoints), `velocity` (a command) or `open` (anything else: IK says it has no point to reach; reward search runs on a floating robot with the agent's RewardLang candidates plus the contract-robustness one, and says so when it has neither).
- **`runSolverRace({ mj, task, forge, save, rewardCandidates?, robustnessCandidate?, budgetSteps?, signal? })`** routes with `routeTask(task.analysis)` and tries that rung, then each later built rung, cheapest first. A skill comes back only with passing Arena evidence on `task.environment`, so a candidate with a high reward and a failing contract never wins. `solveWith({ ...input, method })` runs one method alone; a method that isn't built (tracking, Routine, LQR or MPC, tracking RL) returns `not-found` at once.
- **IK or motion plan** (`raceIk.ts`): for `reach` goals. Damped least squares on MuJoCo's own kinematics finds joint targets for the part's body, with restarts; then each target is settled 2 s under the hold controller and the aim moves by the sag, up to six rounds, until the settled point is within 0.5 mm. One waypoint becomes a hold controller; several become a linear keyframe animation that holds each pose for its share of the horizon and moves in 0.4 s. Steps cost 0.
- **Reward search** (`raceRewardSearch.ts`): for `velocity` goals on floating robots. Candidates are the agent's RewardLang programs (`rewardCandidates`, otherwise the Kit's velocity reward), then the contract-robustness candidate (`raceRobustness.ts`: each success atom over base height, tilt or forward travel lowered to a per-tick margin, clipped to ±1 and summed; a contract over other signals has none). Stages follow the router (6 at 5M steps, 2 at 25M, 1 at 100M), each run capped by what's left of `budgetSteps`, re-ranked by Arena's lower bound between stages. Every trained candidate goes through Arena; the first that passes wins.
- **`Skill.origin = { method, cost: { wallS, steps } }`** records where a skill came from (optional, so older skill files read; `motor-kit` for Kit skills).

### Kit retraining (`electron/kitScheduler.mjs`, `kitPlan.ts`)

`new KitScheduler({ trainer, debounceMs })` with `request({ workspaceId, xml, job })`, `cancel(workspaceId)` and `dispose()`. Requests for one scene within `debounceMs` collapse to the latest. Before it starts, `trainer.release('kit:<scene>')` drops a queued Kit job for that scene or stops a running one and waits for it to close, so only the latest design trains; it then starts at `PRIORITY.kit`, behind every user job in the trainer's one global queue. `request` resolves `{ jobId }` once it starts, or `{ jobId: null }` when a newer request, `cancel` or a refusal replaced it, so the caller can follow its own job's events. Scenes are independent, and a Kit job never blocks the user's own training of the same scene (it runs under its own `kit:` key).

Compute priority is viewport, Gatekeeper lease, user training, Motor Kit (`electron/trainer.mjs`):

- **User training pauses the Kit:** starting a user job stops a running Kit job (the trainer's stop file), re-queues it unchanged behind the user job (“Paused for other training. Starts again after it.”) and starts it again from scratch after.
- **The gate lease holds the Kit:** with `useGateLease()` (the app's trainer; tests construct their own), no Kit job starts while `$TMPDIR/basecase-gatekeeper.lease` exists, and a running one is paused when the lease appears (polled every 30 s). User training isn't held.
- **The viewport comes first:** a Kit child process runs at OS priority 10 (`os.setPriority`).

In the app (`src/workspace/useSkills.ts`) a legged robot's model is rebuilt 1.5 s after the last edit to parts or joints. When its topology, physics or actuator hash moved (`designMoved`; a colour or name edit moves none), `backgroundTasks` lists every Kit entry that was trained before and isn't fresh now: Arena again for `rerun-arena` (`recheckSkill`, no training), the Kit pipeline for `needs-training`. Entries nobody trained never start on their own. A newer design aborts the running one (latest wins); a user job aborts it too and the queue resumes after.

### In the app

- **Teaching anything** (`teach.ts`, `teachEnvironment.ts`): `draftSkill({ mj, model, design, request })` checks the agent's goal, contract, signals and RewardLang candidates (`draftProblems`, then `validateEnvironment`), builds the environment (the Kit's observation and 0.5 rad action scale on floating robots, 0.25 on fixed ones; free signals `time`, `q_<joint>` and, on floating robots, `height`, `tilt` and `forward`), routes it and runs nominal rollouts (`rollout.ts`, no randomization): holding still, which must fail (a pass comes back as a warning), and for reach goals the planned poses. A floating robot also gets the stand check, with its relaxation. `contractWords` says the contract in plain words. `raceDraft` runs the race on the draft and `raceSummary` lists what each method tried.
- **Where it runs:** `skills.worker.ts` runs `runSkillsJob` (`skillsJob.ts`: draft, race, Kit or Arena recheck) off the main thread; its Forge and save calls come back to the page (`skillsClient.ts`), which trains through the app's trainer (`trainerForge.ts`: user jobs under `skill:<scene>` at user priority, background Kit jobs through the Kit scheduler; each follows its own job id's `train-progress` events, reads the policy and deletes the trainer's copy) and saves skills through `saveSkill` (`electron/backend/skillStore.mjs`, `library/skills/<hash>/skill.json`, hash-checked).
- **`SkillsRuntime`** (`skillsRuntime.ts`, framework-free) holds drafts, jobs with progress and the last race, one user job at a time, and the background queue. A skill that passes Arena becomes a `SkillRecord` in `project.skills` (`skillRecords.ts`: the skill without its controller, plus the Kit entry or the user's words and, for taught skills, the environment); `.basecase` files drop them, like policies.
- **The skills list** (`skillRows.ts`): one row per Kit entry (Stand, Walk, Get up, Settle) and per taught skill, each training (with the job's message and share), ready (its worst Arena variant: “31 of 32 tries, at least 86%”), recheck or untrained.

### Cases on the one contract

`src/cases` keeps no evaluator. `parseCase` accepts any contract shape as plain JSON (version 1, depth 64, 4096 nodes, finite numbers, at most 16 failures) and leaves the rest to the crate; `runCase` and `scoreTry` judge with `evaluateContract`, and `CaseResult` carries the `trace` and the `failed` labels. A contract the crate refuses makes `runCase` reject. Scaling a Case to another arm scales every atom's value and scale except those that read an `angle`.

### Gate s3a-motor-kit: bars and why

The gate judges Kit skills twice with the unchanged `runArena` (its files are hashed in the gate): once on the Kit's own environment, and once on the gate's own contracts in `verify/skills/judge.ts`, so an easy Kit contract can't pass. Every bar was checked against stand-ins before the gate was approved: a hold controller passes Stand, Get-up and Settle; limp fails Stand on all three robots and Get-up and Settle on quad-servo; a zero policy fails Velocity tracking. Where limp fails the gate's contract, the Kit's own contract must fail it too.

- **Stand**, 6 s from starts up to 15° off neutral: tilt under 0.35 rad, base above 75% of its start height, drift under 0.15 m. The 15° matters: these fixtures stand passively on straight legs, so limp passes from the neutral pose.
- **Velocity tracking**, 8 s: tilt under 0.6 rad, base above 60%, and after a 1 s ramp the distance covered sits between 0.5× and 1.5× the command (0.2 m/s for quad-servo and hexapod, 0.15 for biped-servo), judged at the top speed, half of it (the four- and six-legged robots) and standing still (under 0.1 m drift). Three speeds catch a policy that only knows one. 0.2 m/s is the time-to-skill bar (§0k).
- **Get-up**, 6 s, from the pose limp collapses to out of a 40° crouch: hold base above 80% and tilt under 0.35 rad for 1 s.
- **Settle to neutral**, 4 s, from 12° off neutral on every joint: every joint within 8° of neutral for 1 s, upright. The servo law is `kp = effort / 0.17 rad`, so a joint under stance load sits several degrees off its target; 8° leaves room for that and still fails a robot that stays where it started.
- **Biped steering**, a 13 s timeline in the WASM sim through the app's policy path: 1 s still, 4 s forward at 0.15 m/s, 4 s left and 4 s right at 0.1 m/s and ±0.5 rad/s. It must cover 0.3 m along its heading in the forward segment (half the command), turn at least 0.35 rad (20°) of the commanded sign in each turn segment, never tilt past 45° or drop under 60% of its start height, and no external force may act. 0.15 m/s on a 0.15 m leg is a Froude number (v²/gL, Alexander's dynamic similarity) of about 0.015, a slow, nearly quasi-static walk: people walk near 0.25 and change to running near 0.5. The run is one clean rollout, because Arena already covers randomized physics and servo delay for the same skill. The turn bar is a fifth of the command because biped-servo has no hip yaw joint, so it turns only by uneven strides and foot pivots; a robot that drifts one way can't pass both turns.
- **Wall-clock budgets** on the M5 Pro, Arena included, against Forge F1 at 40K steps/s or more: quad-servo Stand 10 min, Velocity 30, Get-up 20, Settle 10; hexapod Stand 10, Velocity 30; biped-servo Stand 15, Velocity 45. The race: 5 min per arm task, 45 min for the walk. These checks are `timed`.
- **The race suite:** arm-3dof reach (IK expected, a 20 mm box held 0.5 s), arm-6dof touch then hold (IK expected, 0.1 s at one point, then 1 s at another), quad-servo walk at 0.2 m/s (reward search expected, judged by the Velocity tracking contract). The 2× rule is checked by running every other method with a cap of half the router's wall time (10 min at most); any that passes Arena inside it fails the gate.
- **Canaries** fire only on their own assertion; a canary that crashes or doesn't load counts as not fired (`verify/lib/canary.mjs`). Limp on Stand and a zero policy on Velocity tracking are planted against the gate's own contracts; a reward-hacked RewardLang candidate (rewards staying upright) alone in the race with a 10M-step budget; the weak quad's Stand; a quad-servo Stand skill on the hexapod; and the biped driven on the same timeline with every turn command zeroed.
