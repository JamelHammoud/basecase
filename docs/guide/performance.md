# Performance

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the index of these files; section numbers (§) are shared across them.

## 0f. Performance (mandatory)

The app must feel instant. These rules came out of profiling real scenes (60+ CAD parts, 50+ MB saved files); don't regress them.

- **The viewport never rebuilds everything.** `src/three/viewport/` is a plain TypeScript engine behind the thin `Viewport3D` component. `PartLayer.sync` diffs parts by object identity: unchanged parts are kept, a transform-only change moves the group, and only changed or re-selected parts are rebuilt. Parts are immutable; always replace a part object to change it, never mutate one. Builds are time-sliced (about 10 ms per frame), so opening a big scene never freezes; queries that need the whole scene (captures, measurements, picking, framing) finish pending builds and spawn animations first (`NEEDS_WHOLE_SCENE` in `engine.ts`): a part caught mid pop-in is scaled down, and the print report caches what it measures.
- **Parts draw in batches, not one draw call each.** `PartBatches` (`three/viewport/partBatches.ts`) draws every plain part mesh in a three.js `BatchedMesh` per material (`MeshBatch`, one geometry slot shared by every copy of a shape, colour per instance) and every part's edge lines in one `LineBatch` per line material (one buffer, instance index per vertex, matrices in a float texture). `my-robotics-design` (488 parts) went from 1,273 GL calls per orbit frame to 9, main-thread work from 3.2 to 0.9 ms and GPU-process time from 1.5 to 0.9 ms.
  - Part groups stay exactly as before for picking, snapshots, bounds, the gizmo and the outline; their batched meshes and lines just move to `BATCHED_LAYER` (off layer 0, so the main and shadow passes skip them). Every part raycaster comes from `partRaycaster()`, which enables that layer. Code that hides a part uses `visible`, never layers.
  - `scene.onBeforeRender` syncs matrices, visibility, colours and in-place geometry edits (attribute versions) after three updates world matrices. Materials are replaced, never edited in place: a new material or geometry object re-tracks the mesh.
  - Batchable: an opaque, untextured, non-glowing `MeshStandardMaterial` mesh with position and normal and at most 32k vertices (`batchKey.ts`); selected parts glow, so they draw alone. Bigger meshes draw alone: a draw call is nothing next to their vertices, and copying them would cost more. Lines: plain `LineBasicMaterial` segments.
  - Freed geometry slots are reused best-fit (`setGeometryAt` re-uploads only that range); a batch compacts only when half of it is waste and grows by doubling. Deleting a geometry in `BatchedMesh` never frees its space, and growing or compacting re-uploads the whole buffer: an edit to one part once stalled `look` for 284 ms.
  - Captures that isolate parts, swap materials or draw silhouettes run inside `batches.unbatched(...)`, which puts the originals back on layer 0 for the call; plain captures and screenshots stay batched. Edges that arrive late from the worker announce themselves with `noteLateChildren(group)`.
  - `warmShaders` also compiles the batched program.
- **Derived geometry is shared and released.** `buildPartGroup(part, selected, { shareGeometry: true })` takes creased normals, edge lines and hardware booleans from a reference-counted cache keyed by the source data (`partMesh/sharedGeometry.ts`). Every group built that way is freed with `releasePartGroup`, which also disposes the materials and owned geometry. Anything you remove from a scene must be disposed.
- **Heavy geometry runs in workers, never on the main thread.** The geometry worker (`three/geometry.worker.ts`, ops in `geometryOps.ts`, client `geometryWorker`) parses robot meshes, welds and simplifies links, assembles link soups, computes creased normals, edge lines and component GLBs. Before a big `mesh` / `cad_part` is built, `PartLayer` waits for `preparePart` (`partMesh/prepare.ts`) to seed the shared cache from the worker, so the main-thread build only wraps ready arrays; edge lines over 500 triangles arrive later (`partMesh/lateEdges.ts`, `lateEdges: true` in the viewport only) and redraw through `requestRedraw`. Builds are also capped by vertices uploaded per frame, so a robot's GPU uploads spread over frames. Send mesh arrays to workers as typed arrays (`packedMesh`): structured-cloning a JS number array costs several times more. `workerRpc` falls back to running in-thread where there are no workers (tests, Node). Never pause builds while the camera moves: make the build cheap instead.
- **Booleans cut in the geometry worker** (§7a). The main thread only hashes the operands, hands their mesh arrays over with a matrix each, and turns the reply into the result's mesh. For two 50,000-triangle meshes (`booleans.perf.test.ts`) that is about 2 ms to hand off and 3 ms to take the reply, while the cut (welding, Manifold) takes about 180 ms in the worker; it used to run on the main thread in three-bvh-csg. The test fails if any main-thread step reaches 16 ms.
- **Agent checks never run on the main thread.** Interference (`check_scene`, pose checks), the posed floor height (`posedFloor`, exact vertex heights, never a rotated bounding box), range-of-motion sweeps (`verify_design`), printability and part measurements run in a pool of analysis workers (`three/analysis/`: `analysis.worker.ts`, client `analysisPool`). The viewport only snapshots plain data (`snapshotShapes`: per part a shape key, its geometry and a rigid frame matrix) synchronously, so a snapshot always matches the pose at call time; the work is awaited. Workers keep each shape's geometry, BVH (built lazily) and samples by shape key, so identical parts share one shape and later calls reuse them; geometry is copied to a worker once, in 8 ms slices. Checks use matrices on cached shapes, never a mutated live scene. Sweeps fan out one joint per worker and skip pairs that move together. Strength solves fan out one part per worker and are cached by shape, frame and load; the stiffness matrix is assembled once into 3×3 blocks, which halves the work per iteration against multiplying element by element. A 3 mm bracket (about 1,900 cells) solves in 0.2 s, a 124 mm hollow arm (8,900 cells, the cap) in 0.9 s on an M-series Mac; `engineeringStrength.test.ts` holds the bracket under 2 s of CPU time, which a busy test run doesn't inflate the way it does wall time. The engineering report runs twice: once to collect the sweeps, strength jobs and payload maps it needs, then with their results (`engineeringNow.ts`). Every `Viewport3DHandle` query that does real work is async (`interference`, `posedInterference`, `sweepClashes`, `measureParts`, `printShapes`, `captureViews`).
- **Wrap Robot runs in its own worker** (`src/wrap/wrap.worker.ts`, §8c), with Manifold loaded only there. The main thread takes a rest-pose snapshot of the mesh and the robot (`restShapes`) and copies its geometry in 8 ms slices (`copyGeometries`, shared with the analysis pool); the worker returns the shells as transferred typed arrays, and `prepareParts` seeds their geometry before they're committed.
- **Captures encode off the main thread.** `captureViews` renders each view with the live renderer (so the agent's renders look exactly like before), copies it at the requested size into an `OffscreenCanvas` right after rendering (`transferToImageBitmap`, synchronous: a WebGL canvas has no preserved drawing buffer, and `createImageBitmap` on it reads blank), and encodes it in the image worker (`utils/image.worker.ts`, `encodeBitmap`). `downscaleDataUrl` goes through the same worker. Never `toDataURL` a capture on the main thread.
- **Printing never blocks the UI** (§8f): orientation candidates are found in the analysis workers (cached per shape), each scene's 3MF is welded, written and zipped in an analysis worker (`threeMf` task), and slicing runs as a child process in the main process. Plate layout and packing are plain data on the main thread (microseconds per part).
- **Thumbnails render in a worker** (`thumbnail.worker.ts`, OffscreenCanvas, encoded with `convertToBlob`): Library, Parts, scene previews and robot previews all go through `renderPartGroups`, which is async. A try's filmstrip draws and encodes in `filmstrip.worker.ts` (§8h), and the agent's camera shots encode in the image worker (`encodeBitmap`). Never `toDataURL` or `convertToBlob` a thumbnail, filmstrip or camera shot on the main thread: reading a canvas back there is a synchronous GPU round trip, which waits behind every frame the GPU process has queued.
- **Shaders are compiled before they're needed.** `warmShaders` compiles the scene (gizmo included) and the part materials with `compileAsync` at startup, finishes one program per idle callback, then renders one hidden shadow pass, so the first part, selection or shadow never stalls.
- **Render on demand.** `RenderLoop` draws only when something changed (`invalidate()`), the camera moved, an animation runs, or a texture finished loading, plus a 1 s idle refresh. Code that changes the scene outside the engine's own paths calls `invalidate()`. Never add an always-on `requestAnimationFrame` render. Camera moves call `noteInteraction`, not `invalidate`: the shadow map (`autoUpdate = false`) re-renders only when the scene changed, and the key light refits once the camera settles. Anything that renders a changed scene itself (captures) sets `shadowMap.needsUpdate`. Nothing redraws for a change no one can see:
  - `setPose` returns early when every delta is within 0.01 mm and 1e-5 of the one shown (`samePose.ts`), so a live sim's resting robot doesn't re-render the scene and its shadows at 60 Hz.
  - `update` returns early when no prop changed but callbacks (`shownPropsChanged`), and agent frames rebuilt with the same parts keep their identity (`steadyProps`). A Case try re-renders the workspace ten times a second for its stats; each one used to redraw the canvas.
  - A new LiDAR scan redraws through `redraw()`, which leaves the shadow map alone, and only when a hit moved more than 0.01 mm: `LiveScans` (`src/dataLayers/liveScans.ts`) keeps the layer's last track when no hit moved.
  - In a Linux container like CI's (software GL), these redraws ran during a LiDAR Case's dataset export and slowed it from about 40 s to over 200 s. The viewport has no `preserveDrawingBuffer`: read the canvas only right after rendering it, in the same task.
- **Sensor data costs only what changed** (§12). A data layer redraws when its track is replaced or its message, color field or playhead span changes, never per frame: an unchanged layer costs a string compare. A `PointCloud2` with float `x`, `y`, `z` takes a typed-array path: positions in one pass, colors in a second through a 256-entry turbo table, both into the layer's own buffer. A million points rewrite in about 6 ms solid and 11 ms colored by intensity on an M-series Mac, and an unchanged update takes under 0.1 ms (`dataLayers.perf.test.ts`, best of 8, run with `npm run perf:booleans`, which takes every `*.perf.test.ts`); a first version with a function call per point took about 170 ms. The test fails past one 16 ms frame solid and 24 ms colored, and when an unchanged update takes 1 ms.
- **Map tiles stream by distance and draw on demand** (§12). The Earth layer updates the tiles renderer only inside `RenderLoop.beforeRender`, so tiles load and refine only when a frame draws; a tile arriving asks for one redraw (`needs-update`, `needs-render`), and nothing renders once the view and the loads settle. Screen-space error picks each tile's detail from the canvas camera, so a tile near the camera loads finer and the rest stay coarse. Draco decoding runs in `DRACOLoader`'s workers, and `3d-tiles-renderer` loads as its own chunk the first time a scene has a place.
- **Autosave never re-serializes unchanged parts.** `sceneJson` caches each part's JSON by object identity, slices the work across frames and sends one string (`saveSceneJson`).
- **No canvas reallocation during panel animations.** `CanvasSizer` keeps the canvas centred in its card, grows the drawing buffer once and shrinks it only after the size settles, and redraws synchronously after a resize so there's never a blank frame.
- **Heavy work never blocks a click.** Cache by input identity (a `WeakMap` on immutable parts, or shape keys) and spread uncached work across frames with `await` between small chunks (`components/build/useBuildReport.ts`). Profile anything over 16 ms.
- **Keep views alive.** Panels that switch (sidebar views, inspector tabs) mount on first use and then stay in React's `<Activity>`, so switching back is instant and hidden views run no effects.
- **A Case's code panels cost only what they draw** (§8h). The studio adds no render loop for them: a frame runs its own, out of the studio's renderer process. The bridge sends a frame only the signals it subscribed to, at most 20 times a second (a trailing timer, so the last value always arrives), never the whole bus, and the heartbeat is one small message every 500 ms.
- **Small payloads across IPC and HTTP.** Lists are summaries (`SavedSceneSummary`: counts, size, a small WebP preview); full records load on demand (`platformBridge.getScene`). Library JSON is written compact. Never send a whole library over IPC. Saving, renaming, duplicating or deleting a Library model, a scene in the Scenes menu or a chat changes the list on screen at once, then writes that one record (`withModel`, `sceneStore`); the list is read again only when the write fails. A scene's writes run in order, and opening it waits for them (`queueSceneWrite`). The desktop models-folder watcher sends only the record that changed, and skips the app's own writes (`ModelChanges`).
- **React Compiler friendliness** (§0c) is a performance rule: one rule break makes the compiler skip the whole component, and everything under it re-renders on every change. One that isn't a Rules of React break: the compiler can't lower `try` without `catch`, so a handler in a component that resets a flag after an awaited call chains `.finally(...)` instead (`agent/ConnectionBanner.tsx`).
- **Boot never waits on anything it doesn't need to draw.** The window opens before the agent connects (`connectAcpAgent` runs in parallel; it used to delay the window 0.7–2 s, and status reads `connecting` meanwhile, so nothing says “disconnected”). Anything that needs a session awaits that first connect (`AcpAgent.pending`) instead of starting a second. Only the active tab mounts at first; background tabs mount one per idle callback after its first frame (`useMountedTabs`), since each builds its own WebGL context, environment map and shaders (about 60–250 ms apiece). Events for a tab that hasn't mounted are dropped, not refused: on mount it adopts its runs from the journal and the bridge replays unanswered requests. Measure boot with real scenes reopened (`open-scenes` in `localStorage`), not an empty one.
- **The CAD kernel never touches the renderer or boot.** Its sandbox windows open in the main process on the first compile (or 2 s after an MCP server starts), never during boot, and paint nothing (`show: false`, `paintWhenInitiallyHidden: false`, no WebGL); results pass through the main process as bytes it doesn't parse. A first compile costs about 0.15 s more than the old forked process (opening the window); later ones match it (guide examples: OpenSCAD 0.06–2.1 s, replicad 0.06–0.25 s, either host).
- **Measure in production:** `npm run build && npm run preview`, then time interactions with a `PerformanceObserver` for `longtask` entries. Dev mode adds 30–130 ms per interaction and misleads.
