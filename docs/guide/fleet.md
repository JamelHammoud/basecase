# Basecase Fleet

Part of the Basecase guide. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and the guide index.

## 8n. Shared identity and inventory

Fleet is a self-hosted browser workspace and PostgreSQL service, separate from Operate's live `FleetRows`. `src/fleet/service/` owns persistence, accounts and the version 1 API. `src/fleet/browser/` owns the browser workspace. `electron/fleet/` publishes studio status. Existing rollout and twin modules under `src/fleet/` still belong to [Robot runtime](robot-runtime.md).

An organization owns regions, nested sites, robot identities, roles, groups, accounts and text assets. UUIDs identify everything. Display names and vendor names need not be unique. A robot belongs to a site and needs no scene, joints, mesh or editable CAD model. Inventory survives studio disconnects and service restarts. Parentage is fixed on creation. Names and attributes can change. Delete a site's children before deleting the site.

### Run the service

Use Node from `.nvmrc` and PostgreSQL 18, or the PostgreSQL installation supplied by Windows CI. Install the repository dependencies. Build the browser bundle with `npm run build:web -- --outDir dist-web`. The default static directory is `dist-web`, overridden by `FLEET_WEB_DIRECTORY`.

Set `FLEET_DATABASE_URL` to a PostgreSQL connection URL. Set `FLEET_ORGANIZATION`, `FLEET_EMAIL` and `FLEET_BOOTSTRAP_PASSWORD` and run `npm run fleet -- bootstrap`. This local database operation creates a separate organization and administrator and prints their IDs. Passwords require at least 14 characters. Bootstrap is never an HTTP endpoint. Remove the bootstrap password from the environment after use.

`npm run fleet` runs migrations and serves `http://127.0.0.1:7440/fleet`. Outside loopback, configure `FLEET_ORIGIN=https://fleet.example.test`, `FLEET_TLS_CERT` and `FLEET_TLS_KEY`. Origins without an explicit port listen on 443 for HTTPS or 80 for HTTP. `FLEET_BIND` chooses the listening interface. HTTP refuses nonloopback binds and peers, including a remote peer forging a loopback Host. HTTPS terminates in the service. Forwarded headers cannot substitute for TLS. Each request must match the configured Host. API requests require same-origin browser headers. Public app navigation can originate in the studio. Keep PostgreSQL and its credentials outside scenes and exports.

Operate's Fleet address field saves only the service origin on this computer. Open Fleet and the Operate command of the same name open its browser entry. The `/fleet` web entry loads before the small-screen landing decision. Fleet needs the self-hosted service, including when using the static web bundle. It is not a hosted service on the web demo.

### Local organization recovery

`node src/fleet/service/main.mjs recovery-setup <organization UUID>` installs one dedicated local administrator into an existing organization, even after ordinary administrators lose access. `recover <organization UUID>` rotates that account's password. Both take bounded JSON through noninteractive stdin, at most 8 KiB. Setup takes `email` and `password`, recovery takes `password`. Passwords use the existing salted scrypt implementation and 14-character minimum. Never put passwords in arguments, logs, project files or browser storage. [Recover a Fleet organization](../../site/content/help/recover-a-fleet-organization.md) shows hidden terminal input through a pipe. No active session or identity provider is required. Local recovery and bootstrap commands load only their database and identity dependencies. The HTTP server and SAML verifier load only when starting the service.

The operator explicitly selects the organization. Setup creates new account and role UUIDs, never promotes an email match, never creates a replacement organization and refuses a second setup. An unused email is required within that organization. Recovery preserves resources, assets, role definitions, robot identities, observations and generations. It deletes every credential in the selected organization, including sessions, service tokens and enrollment tokens. Existing PostgreSQL notifications invalidate subscriptions. Reissue publisher tokens after recovery. No revoked token is restored. Other organizations are untouched.

The bounded model is one permanent protected local account and role per organization. Local database access is the recovery authority. There is no extra recovery bearer material, email ownership proof, expiry or one-use recovery code. The password remains usable until the next local rotation. Rotation refuses the current password and does not keep a password history. `fleet_recovery` binds both identities to the organization with restrictive foreign keys. The recovery role grants the existing actions through the existing evaluator. It is frozen, and ordinary accounts cannot reference it. Recovery accounts cannot join groups. Ordinary roles remain customizable and explicit denies remain authoritative for every evaluated rule.

`recoveryProtection.mjs` is the protected local identity contract. All account, group, role and invitation mutations lock the organization row through `lockIdentity`, then call `protectRecovery` before writing. Protected account and role replacements and deletions are refused. Membership and role references are refused too. Enrollment checks the same protection before consuming its token. Login derives the password hash before locking, then rechecks the unchanged stored hash under the same lock through credential issuance. HTTP identity mutations reacquire current credentials and roles after obtaining the lock, so a waiting stale administrator cannot act after recovery commits. Local setup and rotation share this transaction lock. Ordinary token revocation and sign-out remain available.

Federation enforcement must exempt identities listed in `fleet_recovery` from external-only login requirements. Provisioning must use `lockIdentity` and `protectRecovery` in the same transaction for deprovisioning, password, role and group mutations. It must refuse changes to those local identities, including indirect group membership. These rules describe the local identity contract, not a second identity evaluator or a remote recovery API. SAML and SCIM use this contract through the adapters described below.

`fleet_recovery_audit` stores organization, stable actor identity, action, affected UUID, database timestamp and outcome, without secrets. Successful setup and recovery commit their authority changes and audit row atomically. Protected mutation refusals roll back the original transaction before recording the refused attempt, without changing authority. Local input and setup refusals against an existing organization are recorded when the command can validate the organization and database connection. Malformed organization IDs, unavailable databases and interrupted processes cannot guarantee refusal records. Success never commits without its record.

`recovery-audit <organization UUID> [after sequence]` reads at most 100 records with an increasing sequence cursor. Local actors combine database login, hostname and OS username. HTTP actors use `account:<UUID>`, and enrollment identifies its token-bound account. Shared database and OS accounts share attribution. The database operator can alter recovery authority and audit records. This is not tamper resistance against a database administrator. Audit export and retention can consume this existing table without duplicating recovery records.

### Version 1 API

All organization paths start with `/v1/<organization UUID>/`. JSON bodies are capped at 128 KiB. Errors disclose no database text or credentials. Browser sessions use an HttpOnly, SameSite=Strict cookie, with Secure on HTTPS. Automation uses `Authorization: Bearer <token>`. Neither browser sessions nor publisher tokens enter project data, scene storage or inventory exports.

| Path | Methods | Contract |
| --- | --- | --- |
| `/v1/sessions` | POST | Organization ID, email and password exchange for a 12-hour session |
| `/v1/enroll` | POST | A one-use enrollment token and new password exchange for a session |
| `/v1/me` | GET | Authenticated account, organization and credential IDs |
| `/v1/sessions/current` | DELETE | Revoke this session |
| `region`, `site`, `robot`, `role`, `group`, `account`, `asset` | GET, POST | Paginated enumeration or creation |
| `<kind>/<id>` | GET, PUT, DELETE | Read, replace name and attributes, or delete |
| `asset/<id>/content` | GET | Authorized text content, at most 32 KiB per asset |
| `invitations` | POST | Account ID and email produce a one-use, 24-hour enrollment token |
| `credentials` | POST, GET | Issue a scoped 30-day service token or enumerate credential metadata |
| `credentials/<id>` | DELETE | Revoke a session, service token or unused invitation |
| `generations/<robot>` | POST | Allocate the next persistent connection generation |
| `status` | POST | At most 100 identity-addressed status events |
| `subscribe` | GET | Authenticated SSE snapshots of at most 100 visible robots |
| `export` | GET | Paginated robot inventory with separate export authorization |
| `contracts` | GET | Version, action names and page and update limits |

Creation takes `name`, optional `attributes` and a parent ID where applicable. Accounts have `roles`. Groups have `members` and `roles`, each containing local UUIDs. Roles have `rules`. Each rule has `effect: allow|deny`, `actions`, `scope` and optional `conditions`. Scope is an organization-local resource UUID, including all descendants, or `*` for the organization. Conditions are `robot` and `site` maps from an attribute name to an array of allowed string values. Every condition must match. Site attributes inherit down nested sites, with the nearest site's value taking precedence. Robot conditions on a text asset use its ancestor robot.

The single evaluator is `authorization.mjs:allowed`. There are separate actions for inventory view, inventory management, export, incident response, work scheduling, software deployment, robot control, status publishing and identity management. A matching explicit deny beats every grant, including grants from another group. No grant means no access. Service scopes intersect the issuing account's current effective roles. Accounts may belong to at most 100 groups with at most 256 distinct effective roles. Exceeding these limits refuses authentication instead of dropping rules or denies. Identity administration requires organization-level `iam.manage`, including direct account, group and role reads, group membership, role edits and credential issuance. The API does not execute robot control, incidents, schedules or deployments.

For example, a site viewer's role can contain:

```json
{
  "name": "Ward viewer",
  "rules": [
    {
      "effect": "allow",
      "scope": "<site UUID>",
      "actions": ["inventory.view"],
      "conditions": { "site": { "country": ["US"] } }
    }
  ]
}
```

Send this to `POST /v1/<org>/role` using an administrator session. Create an account referencing the returned role UUID, then issue its invitation. The enrollment page is `/fleet/enroll#token=<enrollment token>`. Its fragment stays out of HTTP requests and is removed after the page opens. An invitation opens enrollment even when the browser already has a session. Completing it replaces that browser session with the invited account. Access provides account, group, role and credential administration alongside provider configuration. The browser workspace also provides sign-in, enrollment, site selection, robot pages and sign-out.

### Browser access administration

Access keeps providers in its existing entry and uses the Resource selector for Accounts, Groups, Roles and Credentials. Organization-level `iam.manage` remains the server authority for every identity read and write. Names are displayed with UUIDs, including federation role choices, so duplicates are distinguishable. Access is keyed by organization and the current credential UUID, never its bearer token. Account, group, role, credential, grant and scope lists retain only the current page, at most 100 records. IAM enumeration accepts optional `summary=1` and returns only `id`, `kind` and `name` after the same authorization filtering. Existing enumeration defaults remain unchanged. Access uses summaries for lists and reads the complete selected resource on demand, so large rule and membership arrays are not sent with every page. First Page and Next Page use the service's existing keyset cursors. Provider definitions retain the existing 32-connection limit.

Accounts edit direct role grants. Groups edit local account membership and role grants, including empty groups. Federated mappings remain in Providers and combine through the existing evaluator with ordinary grants. Roles edit up to 64 allow or deny rules, multiple contract-provided actions, organization or resource scope and robot and site attribute conditions. The scope picker pages through sites, regions, robots and assets. The Scope field also accepts an existing resource UUID or `*`. Each condition retains its exact attribute key and individual string values, including unfamiliar attributes and embedded newlines. Editing a resource preserves its attributes and every unchanged role, member, scope, action and condition, including references outside the displayed page. Server validation remains authoritative.

Save retains the editor after an ordinary validation or network failure. Selecting another resource, directory page, credential page, organization or administration surface discards the departed editor and its transient invitation or token. Credential issuance is keyed by the list cursor, so paging also aborts pending issuance presentation. Grant, scope and provider-role pickers retain the enclosing draft while paging their choices. Administrative requests use component-owned abort scopes nested under the current Access session. Departed reads cannot repopulate the current page, and departed issuance responses cannot display bearer material. Access uses the existing subscription endpoint with `access=1`, an IAM-authorized mode that emits empty snapshots while current authority remains valid. Identity notifications reauthenticate through the existing bounded refresh flag, and revoked sessions or lost organization-level IAM authority receive reset and closure. Robot status and facility events do no administration refresh work. It shares the existing 64-stream limit and opens no retry or polling loop. A reset, stream error, 401 or 403 aborts every pending Access request, clears forms, lists and confirmations, and prevents subsequent writes until Access is opened again. Cancellation cannot roll back a write already accepted by the service. Protected local recovery identities and roles remain read-only under the service's existing refusal contract. Access provides no recovery operation.

Invite uses the existing account invitation operation. The returned enrollment fragment is displayed only in the current editor, never saved or reconstructed from credential metadata. Credentials lists only UUID, account UUID, kind and expiry. Revoke uses the shared delete confirmation before deleting an existing session, invitation or service credential. Issuing a service credential uses the same rule editor and existing account-current-role intersection. SSO sessions remain unable to issue service credentials. Provider SCIM issuance also clears its preceding token before rotation. No bearer value enters browser storage, logs, query strings or scene data. Enrollment consumes its fragment through the existing page and removes it from browser history.

### Enumeration and subscriptions

Lists, including credential metadata, use `after=<last UUID>` keyset cursors and return `{ items, next }`, at most 100 records per page. Candidate queries restrict organization, resource kind and grant scopes before applying the same evaluator to each result. Denied records and counts never appear. `robot?site=<UUID>` checks access to that site and includes its descendants. Exports use the same filtering with `inventory.export`. Passwords, token hashes, tokens and asset content are absent from those summaries.

The browser workspace scrolls inside its viewport-sized main element, with the shared overlay scrollbars. The studio stylesheet keeps document scrolling locked, so the Fleet entry supplies its own scroll container for long inventory pages and narrow windows.

PostgreSQL notifications drive status subscriptions. Each connection retains one pending refresh flag, never a growing event queue. A snapshot is capped at 100 robots and 256 KiB. Slow connections close when buffered output exceeds 256 KiB. The service permits 64 subscriptions and 128 HTTP connections. Every status refresh reauthenticates and reloads current roles and groups. Registry mutations reset organization subscriptions, including role and group changes. Credential revocation resets only streams using that credential. A reset contains no resource data and closes the stream. Issuing another session does not reset existing streams. The browser clears its inventory immediately and offers Reload Fleet. It closes EventSource on reset or error and does not schedule reconnection. Failed inventory requests also clear the rows. Late replies and subsequent refreshes cannot restore them before a reload.

### Studio adapter

Set `BASECASE_FLEET_CONFIG` to an operator-owned JSON file outside the library. It contains `origin`, `org`, `token` and `units`, a map from studio unit names to registry robot UUIDs. Issue the token with only `status.publish` on the intended site or robots. Keep this file private to the account running the studio. Renderer messages cannot change it.

`RobotFleet.onEvent` publishes only events from the current link. A connection allocates a persistent generation before publishing. Each update has a random event ID, source timestamp and generation. PostgreSQL ignores duplicate event IDs, older generations and older timestamps within one generation. A new generation can use a new source clock while retaining the previous observation until an update arrives. Timestamps more than 30 seconds in the future are refused. Disconnect writes offline status without deleting inventory.

The adapter keeps at most one active request and one newest pending observation per mapped robot, with at most 32 mappings. Unchanged status is sampled at most once a second. Connection and fault transitions publish immediately. Requests have a 5-second deadline, refuse redirects and cap replies at 4 KiB. Failures never affect robot control and are not retried. A failed observation does not strand a newer pending observation. Reconnecting discards the previous generation before allocation, so a later observation cannot reuse it after an allocation failure. Status becomes stale after 60 seconds without an observation. The browser advances this age locally every 10 seconds without polling the service. No Fleet token crosses IPC or the desktop HTTP bridge. The daemon connection cap stays at 32.

### Sites and facility twins

The Site selector opens a facility and supplies its visible name without a repeated facility heading. All sites opens the globe. Registered site pins and the current robot page share the globe. Selecting a robot opens its timestamped position, status, current work and declared next work. Open Facility follows its site. The globe is a local WGS84 graticule without external tile imagery. Tile subpaths return 404. It never sends site data to a map provider.

`sites/facility.ts` reuses the Case GLB, glTF and OBJ readers, without `normalizeMesh`. Geometry becomes meters with Z up. Source units, axis, SHA-256 hashes and floor identities remain metadata. The upload accepts up to 256 local files totaling 32 MiB. The complete JSON request, including prepared geometry, must fit 64 MiB. Linked resources must accompany the upload. Nested file names and local dependencies are accepted by the API. Browser file selection supplies flat file names, so packages with nested dependencies should use USDZ or a self-contained GLB.

DXF supports ASCII LINE and straight LWPOLYLINE entities, including closed polylines and elevations. `$INSUNITS` must agree with the declared units when present. Unsupported unit codes are refused, while unitless files use the selected units. Curves, nondefault entity axes, block references and other geometric entities require flattening in the exporter. DXF layers supply default floor identities. The Floor identities field can declare comma-separated identities for any import. It replaces those defaults. A floor identity labels a reported robot position and filters robot markers. It does not slice a mesh or infer a floor from its height.

PLY imports point clouds with up to one million vertices. Recorded LiDAR maps exported as PLY use this path. PLY faces and list properties are refused. Meshes retain the Case reader's 200,000-triangle and 600,000-vertex limits. Scene coordinates must stay within 100 km of the source origin. The browser renders plain facility geometry without source textures, splats or articulated physics.

Local USD, USDA, USDC and USDZ uploads use the production [SimReady converter](simready.md). Source-stage units and axes override the upload selectors. Packages with multiple USD layers require an explicit Root file. A package without that declaration must contain one USD or USDZ file. OpenUSD's unauthored unit is centimeters. Meshes are transformed into world coordinates before applying the stage metric. The facility converter does not group geometry into moving bodies or level a floor. Source frames remain recorded alongside the original uploaded files and their hashes. This is local export import, without Nucleus connectivity.

### Explicit registration and positions

A facility starts unregistered. It remains viewable locally and supplies no inferred geolocation. Register Site takes two known control points in normalized facility meters, with local east, north and up coordinates and WGS84 latitude, longitude and altitude. Points must be at least one meter apart horizontally. The horizontal distances must agree within 0.1% or 5 cm, whichever is larger. Their vertical residual must stay below 10 cm. Registration solves a rigid yaw and translation into the WGS84 ECEF frame. It does not fit scale, pitch, roll or a different geodetic datum. The declared source up axis handles axis conversion before registration.

Choose WGS84 ellipsoid, orthometric height or a named local vertical datum. The last two require a named reference and a signed offset to ellipsoid height in meters. Ellipsoid height equals the declared altitude plus that offset. This is an operator-supplied local offset, not a geoid lookup. Other geodetic datums require conversion before registration. The service recomputes the matrix from canonical control points and ignores any supplied matrix. Source elevations, floor identity and site registration survive service restarts. Replacing a facility clears its registration. A pose tied to an old facility hash cannot use a replacement's frame. Replacing the source also clears the browser control-point fields. The map and registration form use distinct load-version keys so every replacement, including identical source bytes, remounts both without retaining an old map. Registration changes remount the form independently of geometry. Each robot retains its own source registration when projected into a different facility view. A registered site pin never supplies a position for an unreported robot. Robot navigation uses its nearest visible ancestor facility.

Status events retain the foundation's robot identity, event ID, generation and observation timestamp. Optional `pose` and `work` fields add location and declared work without a new transport or schedule format. Omitted pose means absent. `work` has optional `current` and `next` strings, at most 200 characters each. These are source declarations, never inferred intentions or executable schedules.

A pose has `quality: reported|estimated` and either:

- `frame: WGS84`, `datum: WGS84`, latitude and longitude in degrees, altitude in meters and a declared `vertical` frame.
- `frame: facility`, `site` UUID, the current `facility` SHA-256, `pointM: [east,north,up]` and an optional declared `floor` identity. The site must be an ancestor of the robot and must have a registered facility. A floor must belong to that facility.

The event timestamp is copied to the pose, independently of receipt time. Position becomes stale after 60 seconds. Reported positions draw blue, estimated positions gray and stale positions amber. Missing or incompatible positions draw no marker and read Absent. Altitude is never clamped to a floor or water surface. ECEF placement crosses the antimeridian without a longitude discontinuity. Drone heights, multilevel positions and submerged vessel offsets use the same frame.

### Facility API and authorization

`/v1/<org>/site/<site>/facility` supports GET metadata and PUT `{ files: [{name,base64}], geometry, sourceFrame? }`. Geometry contains normalized `positions`, triangle `indices`, line endpoints, point-cloud coordinates and `floors`. The browser worker creates it using the shared readers. The service worker validates its bounds and indices and computes source hashes from uploaded bytes, rather than trusting browser hashes. Hashes identify retained source bytes and prepared geometry. They do not certify an arbitrary authorized client's geometry against its original CAD.

`facility/geometry` returns `{ facility, registration, geometry }` from one database row, so a concurrent replacement cannot pair old metadata with new geometry. An empty site returns null for all three fields. `facility/registration` accepts PUT control points, a vertical frame and the current `facility` SHA-256. The write matches that hash atomically, so a replaced source cannot receive an older registration request. A source mismatch returns 409. `facility/convert` accepts POST local USD files and an optional root filename and returns the converter's GLB and source frame. All reads require `inventory.view` on the site. All writes and conversions require `inventory.manage` on the site. Organization checks, explicit denies and credential ceilings use the existing evaluator. Authorization happens before reading a large body and again after preparation. Robot-only grants reveal no site geometry or registration. Inventory site summaries contain only the facility name, content hash, import revision and registration. Each import gets a new revision, including identical source bytes, without changing the content hash. Full source records load on demand.

### Preparation, rendering and coverage

File reading, source hashing, parsing, coordinate conversion, bounds and typed-buffer preparation run in a short-lived browser worker. Geometry buffers transfer to the renderer. Each upload or load owns one worker and terminates it on completion, failure or navigation. Upload cancellation cannot retract a service mutation already accepted. The service admits two facility preparations at once, with no pending queue, and performs large JSON parsing, hashing and validation in workers with a 512 MiB JavaScript heap limit. Nonconversion jobs stop after 15 seconds. USD conversion uses the existing five-minute total deadline. Its Python process is launched directly after pinned environment preparation, so timeout targets the converter process itself. Runtime installation can require internet access. ### Federation and provisioning

Fleet Access configures at most 32 independent SAML connections per organization. Each connection fixes its issuer and owns an HTTP-Redirect sign-in endpoint, up to three pinned PEM signing certificates or RSA public keys and at most 32 group mappings with eight local role IDs each. The browser form starts with one role per mapping row, displays every role in existing mappings and pages through role definitions, 100 at a time. Existing roles outside that page appear by UUID. Editing one role preserves the other roles in its mapping. Delete controls use the shared danger tone and confirmation. API configurations can reference additional existing roles. Provider discovery requires an explicit organization UUID and returns only its enabled provider names and IDs. Configuration refuses XML metadata and metadata URLs and performs no server fetch.

[Node-SAML](https://github.com/node-saml/node-saml) implements the [OASIS browser SSO flow](https://docs.oasis-open.org/security/saml/Post2.0/sstc-saml-tech-overview-2.0-cd-02.html). `@node-saml/node-saml` validates both signed Response and signed Assertion, audience, issuer, assertion age and request correlation. `saml.mjs` additionally requires exact destination and verified bearer recipient, persistent NameID, bounded validity, unique XML IDs and RSA-SHA256 signatures. Requests expire after five minutes with zero clock skew. The browser binds RelayState and the exact AuthnRequest ID to an HttpOnly transaction cookie. A response for another outstanding request cannot complete that browser flow. Initiation reserves both cache rows within the organization limit. HTTPS callbacks use SameSite=None with Secure. Local loopback HTTP uses SameSite=Lax. PostgreSQL caches consume requests atomically and retain replay records through assertion validity. Cleanup removes expired records at initiation, with at most 10,000 live entries per organization. Only SP-initiated Redirect requests and POST responses are supported. Encrypted assertions, unsolicited responses and logout bindings are refused. XML entities, document types, comments and CDATA are refused before parsing.

Accounts are keyed by organization, connection's immutable issuer and persistent subject. Email never links accounts. New SAML identities get new foundation account UUIDs without local passwords or direct roles. The existing evaluator combines current mapped roles with ordinary grants and deny rules. Mapping updates revoke connection sessions and pending requests. Disabled providers cannot authenticate, and their credentials are deleted. Provider deletion is unavailable, preserving issuer identity. Unprovisioned identities use their latest asserted group snapshot. Repeated sign-in with the same distinct group set leaves existing subscriptions open. A changed snapshot still resets subscriptions. Provisioned sign-in does not write unused assertion groups. SCIM-provisioned identities use current SCIM membership instead. SSO sessions cannot mint service credentials, and no federation token reaches robot pairing or the publisher.

SCIM lives at `/scim/v2/<org>/<connection>`. Hashed 30-day tokens scope provisioning to that connection. Rotation replaces the old token. Users use externalId as persistent SAML subject, userName as display name and active as status. Groups use externalId as mapping key, displayName and at most 100 local member account IDs. POST adopts an existing JIT identity only by subject. PUT keeps external IDs fixed. PATCH supports replace of active/userName or displayName/members, at most 32 operations. Lists use SCIM startIndex/count pagination, at most 100 rows, and exact equality filters on externalId, userName or displayName. User DELETE hides the user, removes its group memberships and retains an inactive identity tombstone. Group DELETE removes the group. No password provisioning, arbitrary role grants, extensions, bulk, sorting or add/remove PATCH operations are supported. Each connection supports 10,000 visible provisioned users and 10,000 groups. The protocol reference lists exact fields and routes.

Provisioning, SSO completion, enforcement and all authenticated API writes serialize through the foundation's organization identity lock. Queued writes and new subscription handshakes reload credentials under that lock. Initial subscription snapshots use the same transaction client, avoiding a second pool checkout while holding the lock. Facility workers prepare outside it, then reacquire it before authorization and commit. Deactivation deletes every credential belonging to the account. Existing notifications reset subscriptions. Enrollment checks the current local-login policy under the identity lock before writing a password or issuing a session. Federated accounts cannot enroll local passwords, including when SSO enforcement is off. Enforcement refuses ordinary password login and enrollment only in its organization, requires installed local recovery and revokes ordinary local credentials. Recovery identities and roles are protected from direct provisioning and indirect membership or mapping. Local recovery also deletes SCIM tokens and pending SAML exchanges atomically with its durable audit.
